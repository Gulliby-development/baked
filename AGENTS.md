# Working on BAKED

These instructions apply to every coding agent and every model provider that works in this repository, and to human contributors.

## Project

BAKED is a TypeScript coding agent with an OpenTUI/React terminal UI and a headless CLI. It runs on Bun and uses SQLite for persistent data. Read `README.md` for setup and `CONTRIBUTING.md` for architecture and extension points.

## How BAKED works

- `src/boot.tsx` parses the command line and starts either the terminal UI or the headless CLI.
- The main agent (`src/core/agents/bake.ts`) assembles the system prompt, context, tools, approval callbacks and execution mode for a session, then runs the model loop through a provider from `src/core/llm/providers/`.
- Context comes from `src/core/context/` and the repository graph in `src/core/intelligence/` (language servers and tree-sitter), so the agent can reason about code structure rather than only raw files.
- Tools in `src/core/tools/` (files, shell, Git, code analysis) execute through the registry. Writes and commands pass access checks and user approval before they run.
- Sessions, memory and workflow state persist in SQLite (`src/core/sessions/`, `src/core/memory/`, `src/core/workflows/`). Durable workflow events are authoritative; the UI only renders them.
- The terminal UI (`src/components/`, `src/hooks/`, `src/stores/`) and the headless CLI (`src/headless/`) are front ends over the same core.

## Task workflow

- Planned work is tracked as GitHub Issues in this repository (shown on the project board), not in markdown files. Before starting, find the issue for the task or open one; record a new idea, follow-up or deferred item as an issue instead of a document or a TODO list.
  - Labels: `verification` (a check that needs a real model, device or account), `idea` (not yet decided), `needs-gulliby` (only the owner can do or decide it), `deferred` (agreed for later), and `area:workflow|tui|desktop|api|ci|release`. Use the issue type Task, Bug or Feature.
  - Every new issue goes on the BAKED project board with Status `Backlog` (or `Ready`) and a Priority: `P0` (blocks current work or a release), `P1` (next up), `P2` (later or an idea). With the GitHub CLI: `gh project item-add` then `gh project item-edit` (the token needs the `project` scope). If your tools cannot reach GitHub Projects, put `Priority: P0|P1|P2` on the first line of the issue body so it can be set on the board.
  - Before you open or extend a Bug issue, follow the [file-issue skill](.agents/skills/file-issue/SKILL.md), whoever files it (a person, the bench loop, a smoke run or a review). It finds the root cause and sweeps the code for every place with the same or a neighbouring defect: other copies of the computation, parallel stages, toolchains, providers and surfaces. The issue then lists all of them. A pull request that fixes such an issue fixes every place the issue lists, runs the sweep again before it opens, and reports both in a `## Sweep` section of its description; CI fails a pull request that closes a Bug issue without one, or whose Sweep section has no `Languages:` line. Before it merges, run `bun run review:adversarial --pr N --post` when the Claude Code or Codex CLI of the other model family than yours is logged in on your machine: it has that model look for places the sweep missed, with the [adversarial review prompt](.agents/skills/file-issue/adversarial-review.md) and the skill's own sweep checklist, and posts one advisory comment (no CI job and no API key; the bench loop reviews the fix pull requests other machines merged). Add a new sweep dimension to the skill's Sweep sections, so the reviewer checks it too. The review reads its inputs from the pull request's base commit (`REVIEW_INPUTS` in `scripts/adversarial-review.ts`); a new file the reviewer or its verifier reads joins that list, so a pull request cannot edit it to pass its own review (#1845). Its call-graph context takes each language's call and import spellings from `CALL_SYNTAX` (`src/core/intelligence/call-context.ts`), a `LanguageRecord` registered in `tests/language-parity.test.ts`; function definitions come from the tree-sitter backend's queries, so a language whose functions tree-sitter misses gets its query fixed there. Answer a real finding in the same pull request or with a new issue.
  - When a bug is bound to a language (it branches on a language, extension, manifest, toolchain or test convention, or appeared only in one language's project), check whether it reproduces in every other language BAKED supports, taking the list from the code rather than memory. Every language where it reproduces, or where the code shows it would, is covered by the same issue when one shared fix serves them all, or gets its own linked Bug issue when it needs its own fix. The issue and the fixing pull request record the result in a `Languages:` line of their Sweep section.
  - A change that adds or changes a host decision (anything that stops, parks, declines, refuses, retries, times out or grows a limit on its own) records the decision's inputs in the run's database and adds its replay hook, a corpus case and an `accepted.json` entry for any recorded run it means to decide differently, in the same pull request. Follow the [replay-corpus skill](.agents/skills/replay-corpus/SKILL.md); `tests/forecast-replay-corpus.test.ts` replays every bench-round trace in `tests/fixtures/bench-traces/` in CI.
  - The nightly mini-suite in `bench/suite/` runs small tasks in every supported language; follow the [bench-suite skill](.agents/skills/bench-suite/SKILL.md) for its task format and graduation rules. Adding a supported language or toolchain adds at least two suite tasks for it in the same branch, and a bench round or smoke stop that a small task can reproduce adds that task.
  - A pull request that finishes an issue says `Closes #N` in its description so the merge closes the issue; reference it with `Refs #N` when the PR is only part of it.
- Start every task on its own branch, created from an up-to-date `main`:
  - new feature: `feature/<name>`;
  - bug fix: `bugfix/<name>`.

  These are the only two prefixes, for every change and every author: documentation, specs (including `bench/loop/`), CI, refactors and chores use `feature/` unless they fix a bug. `<name>` is a few lowercase words joined by hyphens that say what the task is. Never use another prefix (`docs/`, `fix/`, `chore/`, `claude/`, `codex/`, `copilot/`) or a generic name such as `project-thread`, `patch` or `update`; if your tool proposes a default branch, rename it before the first push. A random suffix your platform appends after the name (`feature/desktop-checkpoints-sgmb4g`) is fine. CI fails a pull request whose head branch breaks this rule; only Dependabot's `dependabot/` branches are exempt.
- Commit intermediate working states on the task branch. Before each intermediate commit, run at least `bun run typecheck` (or `bun run build` for startup and bundling changes) so every commit is a state you can return to.
- Ship major features on every surface of the app: the terminal app (TUI and headless CLI), the desktop app (`apps/desktop`, through the `baked serve` local API), and every supported operating system (Windows, macOS, Linux). Core logic stays in `src/core/` so each front end only renders it. If a surface cannot be done in the same branch, open a follow-up issue for it on the project board and reference it from the pull request. Every user-facing feature has an entry in the feature registry (`src/core/features/registry.ts`) naming how each surface reaches it, or the issue or reason a surface lacks it; `tests/feature-parity.test.ts` fails when a slash command, a `/v1` route or a desktop screen is missing there. See [docs/parity.md](docs/parity.md).
- Keep extension points maintainable. When a task adds a mechanism that later features must extend to stay complete (a registry, a per-language table, a replay or fault-injection hook, a stop reason, a test matrix, a bench-suite task list), its issue says so in a `## Maintainability` section, and the pull request that implements it adds the rule to this file in the same branch: what a later change must add, where, and which test fails when it is skipped. When the rule needs more than a few sentences, write it as a skill under `.agents/skills/<name>/SKILL.md` and link it from here, as the file-issue skill is. Every Feature and Task issue has the section; it says `None` when nothing will need extending. A pull request that extends such a mechanism follows its rule or skill.
- Any new or changed logic that can stop a run, park it or decline an approval registers its reason in `src/core/workflows/stop-reasons.ts` and ships in `shadow` mode, recording `decision.would_stop` events instead of stopping. A stopping fault is made with `stopFault`; `tests/stop-reasons.test.ts` fails on one made another way. Promoting a reason to `enforce` is a pull request of its own that cites two bench rounds with no false would-stop. Hard limits the person set (money, tokens, time, storage) are registered as enforce-only. A reason that compares a measured quantity with the plan's estimate waits for the first measurement (as `initiative-dollar-share` waits for `measuredFeatures` above 0, #1714), and its replay case in `tests/forecast-replay-corpus.test.ts` shows the round whose false would-stops it removes. A rule that can decline a start keeps its shadow data in the corpus with the final spend of the run (`shareWouldStop` on each replayed start of `replayInitiativeStarts`, next to `finalUsd`; a would-stop for dollars the initiative never ran short of is false, and an accepted one is listed in `tests/fixtures/bench-traces/accepted.json` with that spend in its reason), and its promotion to `enforce` cites two rounds with none false; a dollar rule that prices with a measured rate waits, as the forecast's ratio does, for `MIN_CALIBRATION_FEATURES` measured features before the cap bounds it (`initiative-dollar-share` counts the remaining dollars to the tolerance ceiling until then, #2099). See [Stop reasons and shadow mode](docs/workflows/runtime.md#stop-reasons-and-shadow-mode). A corrective chain's failing required checks are compared, not only counted: each failing corrective records `repeats/tasks/<task>.json` (kind `repeated-failure`, kept in traces, replayed by `replayRepeatedFailures` with the `newRepeatStops` counter) and the `repeated_failure` reason records a would-stop when its hash equals the previous corrective's (`src/core/workflows/repeated-failure.ts`, #1996). A new check runner whose failing output carries a value that changes between runs of the same failure (a timestamp, a duration, a temporary path, an address) adds its normalization to `normalizeVolatile` (`src/core/verification/volatile.ts`), the one table that `normalizeCheckOutput`, the check baseline's `shapedFailureSignature` (`output-counts.ts`) and the check finding's `failureSignature` (`convergence.ts`) all read, never to one of them (#2295), and its pair of outputs to `tests/repeated-failure.test.ts`, which fails when two runs of one toolchain's failing check hash, or get a baseline signature or finding text, differently and when a runner of `TEST_RUNNERS` (`src/core/verification/output-counts.ts`) has no pair (the pair's name starts with the runner); a value is normalized by its shape (a number with a unit word, a compound `1m 3s`, `mm:ss.fff`, a rate `N runs/s`, a seed, an address with or without `0x`), not by one runner's spelling, and a whole number with a unit only after a word that introduces a time (`in`, `after`, `Time:`, `Duration:`), so positions and asserted values still differ (#2281); a new path that opens a task-level correction for check failures goes through `repair(..., "task")` or calls `recordRepeatedFailures` itself, with a case in `tests/workflow-scenario-repeated-failure.test.ts`.
- Whether a dollar-capped initiative would pause instead of starting a feature is decided only by `dollarCapPark` in `src/core/workflows/initiatives/service.ts` (the `initiative-dollar-cap` reason, shadow-only, #2218), from the share gate's recorded view: the dollars left under the cap after each open run's dollar plan charge (`planCharge.usd`, both ways, whatever the `initiative-plan-charge` mode), compared with the starting feature's own low. A new reserve or open-run need on the dollar side changes that function, never a second check beside it, with a case in `tests/workflow-scenario-initiative-dollar-cap.test.ts` and its invariant under "dollar cap park invariants" in `tests/workflow-accounting-invariants.test.ts`; its remedy names one `extend --budget-usd` amount (the larger of the low's shortfall and the forecast). Its promotion to `enforce` pauses the initiative with the `dollar_cap` reason and cites two bench rounds whose replayed starts (`capWouldStop` in `replayInitiativeStarts`) hold no would-stop for dollars the initiative never ran short of, citing R70 evalpin's report-cli as the true one. A split approval that warns on dollars states the expected total beside the lows (`expectedSplitUsd`), never the lows alone.
- A test writes its scratch repositories, databases and files under `os.tmpdir()`, never in the checkout or a fixed path, so CI decides which disk they use: Windows `OS tests` shards point `TEMP` and `TMP` at a directory in `RUNNER_TEMP` on D: that grants the runner user its own ACE, because the runner's C: temp directory stalled file and git work for tens of seconds (#1910). A test passes its own time limit only above the suite's 30 s; passing 30 s itself overrides the 90 s Windows shards allow, and `tests/os-tests-workflow.test.ts` refuses it.
- `OS tests` shards are balanced by each file's measured time in `scripts/test-shard-weights.json`, never by name. A change that adds a test file taking more than a minute on Windows or macOS, or moves time between files (a split, a merge), refreshes that table with `bun scripts/test-shard-weights.ts <windows|macos> <shard logs>...` in the same branch (see CONTRIBUTING.md); `tests/test-shard.test.ts` fails when a file would run in no shard or in two.
- A time bound inside a test never decides its outcome on a slow runner. A wait for things to happen at once (a rendezvous of parallel calls) waits for the number the code under test should reach, never more, and its bound only ends a run that never gets there (#1915). A bound inside a fixture (a child process's `timeout`, a worker call, a CLI call) stays a few seconds under the test's own limit, so the test's limit and its slow-test report, not a kill, decide a slow run (#1917, #1919).
- Subscription usage limits come from `LIMIT_READERS` in `src/core/llm/usage-limits.ts`, which `GET /v1/providers/limits`, `baked limits`, `/limits` and the desktop's Subscription limits panel render as they are. A provider that gains a subscription limit adds a reader there and its parse case to `tests/usage-limits.test.ts` (whose first test lists the readers), and reads it the way the provider offers without reading a CLI's own tokens; a report a provider only sends during a turn is recorded from its provider through `usage-limits-record.ts`, which imports no provider (#2300).
- The chat's preview panel (#2298) takes its document kinds from `PREVIEW_KINDS` in `src/core/files/preview-kinds.ts` only, which `GET /v1/files/preview` uses too, and finds the documents of a session only in `previewTargets` (`apps/desktop/src/renderer/screens/chat/preview-model.ts`). A new previewable kind is added to `PREVIEW_KINDS` with a case in `tests/file-preview.test.ts`; a new tool that writes files joins `WRITE_PATHS` there, and a new artifact tool output joins `previewOf`, each with a case in `apps/desktop/tests/chat-preview.test.ts`. The panel draws HTML only in a sandboxed frame without `allow-same-origin` or scripts; running a page goes through Open.
- A desktop client module (`apps/desktop/src/renderer/`) loads in any order and without a `window`: it reads browser globals through a `typeof` guard or inside a function, and a mock route module imports `response` and the route types from `client/mock-response.ts`, never from `client/mock-routes.ts`, which imports every route module. The desktop tests share one module registry, so a module that needs one load order fails every later test once the run picks another order; `apps/desktop/tests/module-load-order.test.ts` loads each route module first and the bridge without a `window`.
- A host check whose timeout decides a task's outcome (`onTimeout: "failed"`, the `<check>-written` checks) allows for the toolchain's cold first build: its first timeout without a result in a run reruns it once, so a cold Go, cargo or Gradle cache on a Windows runner is not the task's defect (#2162). A test that runs a compiler cold (`go test`, `cargo test`) gives itself a limit for the cold build, not the warm one.
- A check timeout is never a dead end: a required check that timed out after passing earlier in the run, or whose formatter does not finish on one written file run alone (`fileScopedFormat` in `src/core/workflows/format-written.ts`, bisected by `hangingFile` in `src/core/verification/check-runner.ts`), is failed with the reason `timeout_slow` and a note naming the file; its fixer is not run (the same tool hangs again), and an inconclusive check that timed out twice on one snapshot blocks with that said and the `revise` remedy (`inconclusiveFault` in `scheduler.ts`), never an automatic skip. A new formatter gate gets a file-scoped form (a `FILE_FORMATTERS` row, or a case in `fileScopedFormat`) and its stack's row in `FORMAT_FILE` for the gate-matrix cell "formatter timeout is a finding"; a new place that runs a check's fixer skips `timeout_slow` results; a new check reason that blocks gets its case in `tests/workflow-scenario-formatter-timeout.test.ts` (#2240).
- A test cleanup that removes a directory a stopped process ran in or held files in (a fake Codex app-server, a language server, a fixture CLI, a disposed `ContextManager`) uses `removeTempDir` from `tests/helpers/temp-dir.ts`, never a bare `rmSync`: a killed process keeps its working directory locked on Windows until it exits (#2161; `tests/app-server-test-cleanup.test.ts` guards the app-server tests).
- A test that expects a path the code built with `path.join` builds the expected path with `path.join` too, never from a literal folder with `/` or `\`: on Windows a POSIX folder joins as `\home\...` (#2188).
- A flaky test is fixed, never skipped, disabled or retried into green. When the `OS tests` flaky ledger (the `flaky-ledger-*` artifact and its annotations, see CONTRIBUTING.md) marks a failure likely flaky, open or extend a Bug issue for that test and record the cause there. The daily `Flaky test ledger` workflow (`scripts/flaky-issues.ts`) files that issue itself, labelled `flaky-test`, once a test has two likely flaky failures in 14 days, adds later failures to it, and reopens it when the test flakes again after it was closed.
- When a task adds or changes a user-visible feature, a command, a setting, the local API or a workflow, update the matching page in `docs/` in the same branch. Long-lived documentation (guides, references, architecture, the design of shipped features) goes only in `docs/` and describes current behavior; plans and one-off reports do not go in the repository.
- The security scanners' allowlists (`.github/zizmor.yml`, `.gitleaks.toml`, `.github/security/osv-scanner.toml` with an `ignoreUntil` date) are an extension point: every suppression carries a one-line reason and a link to the issue or pull request that accepted it, a new workflow or composite action passes zizmor instead of being excluded from the scan, and a tool the `Security` workflow downloads is pinned by version and hash, with a failed download failing the job (#1844).
- When the task is complete and the checks in [Verification](#verification) pass, open a pull request to `main` and add it to the merge queue: `gh pr merge <number> --merge --auto`. `main` takes changes only through the queue, which runs CI on the pull request merged with the current `main` and every pull request ahead of it, then merges it. A pull request whose checks fail in the queue leaves it; fix it and add it again. Do not push to `main` directly.

## Working conventions

- Use Bun for installation, scripts, and tests. Runtime APIs include `bun:sqlite`; Node.js is not a substitute for running the application.
- Follow strict TypeScript and the existing Biome configuration. Avoid `any`, unused variables, and unrelated formatting changes.
- Prefer small changes to existing modules. Keep agent logic independent of the terminal UI.
- Preserve access controls, approval callbacks, secret handling, and coordination when changing tools.
- Every config file that decides what a linter, formatter or type checker enforces is a row of `CHECK_CONFIGS` (`src/core/workflows/quality/check-configs.ts`), one table for every supported language; auto-approval (`alwaysNeedsPerson`, `CONFIG_KINDS`, the scope check, the planner's advice) and the manifest field check read it and never name a tool config of their own (#2221). A new linter or type checker, or a new supported language, adds its config files there with the fields that tighten it (`on`, `off`, `added`, `removed`, `raised`, `lowered`) or reads it as text, or gives the language `none(reason)`; check settings a manifest holds go into `EMBEDDED` in the same file. `tests/language-parity.test.ts` fails on a language without its `checkConfigs` golden, and `tests/check-configs.test.ts` runs every row's example through the approval (unnamed, named, opted in, deleted, created). Approving more than before stays opt-in (`autoApproval.requestedCheckTightening`), and a newly protected config declines only through the `check-config-approval` stop reason (shadow until promoted).
- A host tool that writes a file on an agent's behalf (`apply_fix`, `restore_file`) writes it through the attempt's tool guard (`guard.execute("edit_file", { path }, ...)`), so the edit is journaled with its pre-image, stays inside the task's write scope and counts as an edit for the progress watcher (`EDIT_TOOLS` in `src/core/workflows/progress-watch.ts`). A new watcher hint about the files themselves comes from state the executor keeps as it edits (the `broken` map of unparsable files) and is passed to `steeringNotice`, never re-read inside the synchronous step controller (#1835).
- A workflow step opened in `src/core/workflows/` goes under its stage step (`beginStep(runId, id, stepId)`), so the drive's catch, recovery and the run's end close it with the stage; a top-level step outside a stage closes itself on every exit path (try/catch or finally). No step stays `running` or `waiting` after its work ended (#1745, #1746); a task step's work runs inside `closingStep` in `scheduler.ts`, and an exit that blocks the task ends its step before the corrective is opened (#1805).
- A field of a task attempt's input that carries earlier work into a repeated, restarted or corrective attempt (`earlierEdits`, `earlierReads`, `previousAttempt`, `recurringFindings`, `correctionFocus`, `battery`, `misquoteContinue`) is added to the `attempt-context` keys in `src/core/workflows/scheduler.ts`, so `attempts/ID/context.json` records it, and to the attempt-context paragraph of `docs/workflows/runtime.md`; its scenario test asserts the saved context equals what was sent, as `tests/workflow-scenario-recurring-symbol.test.ts` does (#1774).
- A resume after an `invalid_output` stop is refused as a repeat only when the diagnostic and every run input are unchanged (`noteInvalidOutput` in `src/core/workflows/service.ts`). The prompt is one input; the others are the revisions `invalidOutputInputs` returns (today the `routing.json` revision a reroute writes). A new way to change a run's input after an invalid output without touching the prompt (a policy revision, a profile edit) adds its revision there and its case to `tests/workflow-scenario-reroute-repeat-guard.test.ts`, which fails when `reroute --resume` is refused or a plain resume with nothing changed passes (#2191).
- The cross-run defect class list (`defectClasses`, `src/core/workflows/defect-classes.ts`) is shared host state under the rule above; a stage input reads it only through `defectClassesFor`, called in one place (`call` in `src/core/workflows/scheduler.ts`), and a new consumer adds its case to `tests/workflow-scenario-defect-classes.test.ts`. A new domain goes into `DOMAINS` with a unit case there (#1970). A finding is filed under one domain only (`defectDomain`, scored over its claim, family, symbol, file and repro command, else `GENERAL_DOMAIN`), never under every domain the run names, and a stored case keeps its command whole up to `CASE_TEXT_MAX` or a one-line `summarized` summary, never a program cut mid-way; what a planned implementer was shown is the `defectClasses` attempt-context key (#2140).
- A criterion the host knows how to settle (manual, post-release in `deferredCriteria`) is settled by the host when the convergence report omits it (`hostSettledOmission` and `OMITTED_DEFERRED` in `src/core/verification/review.ts`), never left to the reviewer; a new criterion method adds its rule there and a case to `tests/workflow-scenario-converge-omitted-criterion.test.ts`, which fails when a method's omission yields `changes_requested` without a finding (#2190).
- A finding chain (a `repeatOf` chain on one file and symbol, `src/core/workflows/finding-chain.ts`) escalates at one threshold, `CHAIN_REWRITE_AT`; never compare a chain's length with a number written elsewhere. The rewrite corrective's battery travels as the `battery` attempt-context key and the host's battery check before a review reads the same chain (`batteryOf`), so the worker and the host hold the same cases. Both decisions, and the rewrite's sibling probe (`chainFamily`, `familyDecision`, #1969), record their inputs under `chains/` (kind `finding-chain`, kept in bench traces) and replay in `replayFindingChains`. A new corrective origin, or a new path that opens a corrective for a review or convergence finding, adds its case to `tests/workflow-scenario-finding-chain.test.ts`, which fails when the second link of a chain is not a rewrite with its battery or when a broken battery case reaches a review call (#1959). A chain's key is its file and the symbol or the reviewer's `family` (`sameSpot` and `familyLink`, #2048); a new field on a finding that a chain or another host decision reads is added to the finding schema (`ReviewSchema` in `schemas.ts`), kept readable by the bench trace export (`scrubTrace`, which keeps `family` folded), read by `chainFindings` and covered in `tests/workflow-scenario-finding-chain.test.ts`, and the chain replays (`replayChainEscalation`, the R62 and R65 md-site cases of `tests/forecast-replay-corpus.test.ts`) gain its column. A reviewer's own `repeatOf` link also joins on one file when either finding names no symbol (`explicitLink`, #2098), and a chain on a test file is routed to the test sweep (`corrective: "test-sweep"`; code that runs or shows a battery asks `rewritesSymbol`, never `decision === "rewrite"` alone). A new join rule adds a case to `tests/finding-chain.test.ts` with a pair of findings that the older rule failed to join. A reviewer's link also joins a class and its member on one file (`containsSymbol` over `symbolPath`, #2137): a language's qualified-name spelling (a separator, a receiver or arity form) joins `symbolPath`, which `symbolKey` reads, and its row joins `CONTAINER_MEMBER` in `tests/workflow-scenario-finding-chain.test.ts`, which fails when a supported language lacks a container/member row. Every finding kind that can repeat carries `family` (`missing` and `partial` as well as `correctness`, `FAMILY_REVIEW_RULE`), so a family join never depends on the kind. A finding that repeats one whose corrective changed no file records the `repeat_without_change` would-stop (`recordUnchangedRepeats`, called from `appendCorrections`, which every review and convergence corrective path goes through); a new path that opens such correctives without `appendCorrections` calls it too, with a case in `tests/workflow-scenario-finding-chain.test.ts`.
- The edge-input probe of a planned source task (`edgeProbe` in `src/core/workflows/scheduler.ts`, `src/core/verification/edge-inputs.ts`) decides a case only through `edgeDecision`, records its inputs under `probes/edge/` (kind `edge-probe`, kept in bench traces) and replays in `replayEdgeProbes`. A runtime limit worth probing goes into the language's `NUMERIC_LIMITS` row (a language-bound record: its golden in `tests/fixtures/languages/*.json` changes with it), never into the profile's instructions. A new path that settles a planned task calls the probe as the serial and parallel implement paths do, and `tests/workflow-scenario-edge-probe.test.ts` covers it (#1808). A probed case that crashes (the edge probe's, a chain battery's, a sibling probe's, and a reviewer finding's inconclusive repro through `reproCrash`, #2152) is decided only through `edgeCrashDecision`, on the output tail its record keeps (`caseCrash`, `outputTail`), and records its would-be finding through the `edge_crash_finding` stop reason (shadow until promoted). A new runtime's frame spelling joins the frame table (`CRASH_FRAMES` in `edge-inputs.ts`) with a case in `tests/workflow-scenario-edge-crash.test.ts`, whose table test fails on a row without one (#2136). The review and convergence gates decide the crash rule only through `gateAllows` (`reviewGateCrashKeeps`, `convergenceGateCrashKeeps`), with a case in `tests/workflow-scenario-repro-crash.test.ts`. Output is read through `outputLines`, which reads a CI annotation (`::error …::`, line breaks escaped as `%0A`) as the lines it carries; macOS and Windows tests run only in the merge queue, so a decision on CI output gets a unit case with the long temp path and annotation of those runners (#2153).
- A corrective attempt stopped by its cap or by the progress watcher, with edits whose repro no longer reproduces (or whose finding's named check passes) and whose required task-end checks pass, is finished by the host (`hostFinishAfterStop` in `src/core/workflows/scheduler.ts`), never by another model session. A new path that restarts, widens or continues a stopped task goes through it first, and a cap stop that would stop the run waits for it. ## Language

- Write everything in English: code, comments, identifiers, test names, documentation, design documents, audit records and commit messages.
- Workflow artifacts are English too: research, specifications, plans, task titles and descriptions, reviews, findings and summaries. Write them in English even when the request, project files or answers use another language; translate the meaning and keep identifiers, paths, commands and quoted source text unchanged.
- Tests that need non-ASCII text use Unicode escapes or non-Cyrillic scripts.

## Verification

CI runs these on every pull request to `main`; run them before merging:

```sh
bun run lint
bun run typecheck
bun run test
bun run build
```

`bun run typecheck` runs `bun check`, which needs Bun 1.4.3 or newer; on an older Bun use `bun run typecheck:tsc`. While iterating, `bun test tests/<feature>.test.ts` runs one feature's tests. The suite is hermetic: tests must not depend on the developer's home directory, global hooks or configuration, or provider environment variables such as `ANTHROPIC_BASE_URL`. Point home-dependent code at a temporary profile instead of skipping the test. Documentation-only changes need link, path, and configuration checks rather than new unit tests; `bun test tests/docs.test.ts` checks the links in `docs/` and the slash command list in `docs/commands.md`. Report what was checked and any failures that remain.
