# Working on BAKED

These instructions apply to every coding agent and every model provider that works in this repository, and to human contributors.

## Project

BAKED is a TypeScript coding agent with an OpenTUI/React terminal UI and a headless CLI. It runs on Bun and uses SQLite for persistent data. Read `README.md` for setup and `CONTRIBUTING.md` for architecture and extension points.

## How BAKED works

- `src/boot.tsx` parses the command line and starts either the terminal UI or the headless CLI.
- The main agent (`src/core/agents/bake.ts`) assembles the system prompt, context, tools, approval callbacks and execution mode for a session, then runs the model loop through a provider from `src/core/llm/providers/`.
- Context comes from `src/core/context/` and the repository graph in `src/core/intelligence/` (language servers and tree-sitter), so the agent can reason about code structure rather than only raw files.
- Tools in `src/core/tools/` (files, shell, Git, code analysis) execute through the registry. Writes and commands pass access checks and user approval before they run.
- Sessions, memory and workflow state persist in SQLite (`src/core/sessions/`, `src/core/memory/`, `src/core/workflows/`). Durable workflow events are authoritative; the UI only renders them.
- The terminal UI (`src/components/`, `src/hooks/`, `src/stores/`) and the headless CLI (`src/headless/`) are front ends over the same core.

## Task workflow

- Planned work is tracked as GitHub Issues in this repository (shown on the project board), not in markdown files. Before starting, find the issue for the task or open one; record a new idea, follow-up or deferred item as an issue instead of a document or a TODO list.
  - Labels: `verification` (a check that needs a real model, device or account), `idea` (not yet decided), `needs-gulliby` (only the owner can do or decide it), `deferred` (agreed for later), and `area:workflow|tui|desktop|api|ci|release`. Use the issue type Task, Bug or Feature.
  - Every new issue goes on the BAKED project board with Status `Backlog` (or `Ready`) and a Priority: `P0` (blocks current work or a release), `P1` (next up), `P2` (later or an idea). With the GitHub CLI: `gh project item-add` then `gh project item-edit` (the token needs the `project` scope). If your tools cannot reach GitHub Projects, put `Priority: P0|P1|P2` on the first line of the issue body so it can be set on the board.
  - Before you open or extend a Bug issue, follow the [file-issue skill](.agents/skills/file-issue/SKILL.md), whoever files it (a person, the bench loop, a smoke run or a review). It finds the root cause and sweeps the code for every place with the same or a neighbouring defect: other copies of the computation, parallel stages, toolchains, providers and surfaces. The issue then lists all of them. A pull request that fixes such an issue fixes every place the issue lists, runs the sweep again before it opens, and reports both in a `## Sweep` section of its description; CI fails a pull request that closes a Bug issue without one, or whose Sweep section has no `Languages:` line. Before it merges, run `bun run review:adversarial --pr N --post` when the Claude Code or Codex CLI of the other model family than yours is logged in on your machine: it has that model look for places the sweep missed, with the [adversarial review prompt](.agents/skills/file-issue/adversarial-review.md) and the skill's own sweep checklist, and posts one advisory comment (no CI job and no API key; the bench loop reviews the fix pull requests other machines merged). Add a new sweep dimension to the skill's Sweep sections, so the reviewer checks it too. The review reads its inputs from the pull request's base commit (`REVIEW_INPUTS` in `scripts/adversarial-review.ts`); a new file the reviewer or its verifier reads joins that list, so a pull request cannot edit it to pass its own review (#1845). Its call-graph context takes each language's call and import spellings from `CALL_SYNTAX` (`src/core/intelligence/call-context.ts`), a `LanguageRecord` registered in `tests/language-parity.test.ts`; function definitions come from the tree-sitter backend's queries, so a language whose functions tree-sitter misses gets its query fixed there. Answer a real finding in the same pull request or with a new issue.
  - When a bug is bound to a language (it branches on a language, extension, manifest, toolchain or test convention, or appeared only in one language's project), check whether it reproduces in every other language BAKED supports, taking the list from the code rather than memory. Every language where it reproduces, or where the code shows it would, is covered by the same issue when one shared fix serves them all, or gets its own linked Bug issue when it needs its own fix. The issue and the fixing pull request record the result in a `Languages:` line of their Sweep section.
  - A change that adds or changes a host decision (anything that stops, parks, declines, refuses, retries, times out or grows a limit on its own) records the decision's inputs in the run's database and adds its replay hook, a corpus case and an `accepted.json` entry for any recorded run it means to decide differently, in the same pull request. Follow the [replay-corpus skill](.agents/skills/replay-corpus/SKILL.md); `tests/forecast-replay-corpus.test.ts` replays every bench-round trace in `tests/fixtures/bench-traces/` in CI.
  - The nightly mini-suite in `bench/suite/` runs small tasks in every supported language; follow the [bench-suite skill](.agents/skills/bench-suite/SKILL.md) for its task format and graduation rules. Adding a supported language or toolchain adds at least two suite tasks for it in the same branch, and a bench round or smoke stop that a small task can reproduce adds that task.
  - A pull request that finishes an issue says `Closes #N` in its description so the merge closes the issue; reference it with `Refs #N` when the PR is only part of it.
- Start every task on its own branch, created from an up-to-date `main`:
  - new feature: `feature/<name>`;
  - bug fix: `bugfix/<name>`.

  These are the only two prefixes, for every change and every author: documentation, specs (including `bench/loop/`), CI, refactors and chores use `feature/` unless they fix a bug. `<name>` is a few lowercase words joined by hyphens that say what the task is. Never use another prefix (`docs/`, `fix/`, `chore/`, `claude/`, `codex/`, `copilot/`) or a generic name such as `project-thread`, `patch` or `update`; if your tool proposes a default branch, rename it before the first push. A random suffix your platform appends after the name (`feature/desktop-checkpoints-sgmb4g`) is fine. CI fails a pull request whose head branch breaks this rule; only Dependabot's `dependabot/` branches are exempt.
- Commit intermediate working states on the task branch. Before each intermediate commit, run at least `bun run typecheck` (or `bun run build` for startup and bundling changes) so every commit is a state you can return to.
- Ship major features on every surface of the app: the terminal app (TUI and headless CLI), the desktop app (`apps/desktop`, through the `baked serve` local API), and every supported operating system (Windows, macOS, Linux). Core logic stays in `src/core/` so each front end only renders it. If a surface cannot be done in the same branch, open a follow-up issue for it on the project board and reference it from the pull request. Every user-facing feature has an entry in the feature registry (`src/core/features/registry.ts`) naming how each surface reaches it, or the issue or reason a surface lacks it; `tests/feature-parity.test.ts` fails when a slash command, a `/v1` route or a desktop screen is missing there. See [docs/parity.md](docs/parity.md).
- Keep extension points maintainable. When a task adds a mechanism that later features must extend to stay complete (a registry, a per-language table, a replay or fault-injection hook, a stop reason, a test matrix, a bench-suite task list), its issue says so in a `## Maintainability` section, and the pull request that implements it adds the rule to this file in the same branch: what a later change must add, where, and which test fails when it is skipped. When the rule needs more than a few sentences, write it as a skill under `.agents/skills/<name>/SKILL.md` and link it from here, as the file-issue skill is. Every Feature and Task issue has the section; it says `None` when nothing will need extending. A pull request that extends such a mechanism follows its rule or skill.
- Any new or changed logic that can stop a run, park it or decline an approval registers its reason in `src/core/workflows/stop-reasons.ts` and ships in `shadow` mode, recording `decision.would_stop` events instead of stopping. A stopping fault is made with `stopFault`; `tests/stop-reasons.test.ts` fails on one made another way. Promoting a reason to `enforce` is a pull request of its own that cites two bench rounds with no false would-stop. Hard limits the person set (money, tokens, time, storage) are registered as enforce-only. See [Stop reasons and shadow mode](docs/workflows/runtime.md#stop-reasons-and-shadow-mode).
- A test writes its scratch repositories, databases and files under `os.tmpdir()`, never in the checkout or a fixed path, so CI decides which disk they use: Windows `OS tests` shards point `TEMP` and `TMP` at a directory in `RUNNER_TEMP` on D: that grants the runner user its own ACE, because the runner's C: temp directory stalled file and git work for tens of seconds (#1910). A test passes its own time limit only above the suite's 30 s; passing 30 s itself overrides the 90 s Windows shards allow, and `tests/os-tests-workflow.test.ts` refuses it.
- A desktop client module (`apps/desktop/src/renderer/`) loads in any order and without a `window`: it reads browser globals through a `typeof` guard or inside a function, and a mock route module imports `response` and the route types from `client/mock-response.ts`, never from `client/mock-routes.ts`, which imports every route module. The desktop tests share one module registry, so a module that needs one load order fails every later test once the run picks another order; `apps/desktop/tests/module-load-order.test.ts` loads each route module first and the bridge without a `window`.
- A flaky test is fixed, never skipped, disabled or retried into green. When the `OS tests` flaky ledger (the `flaky-ledger-*` artifact and its annotations, see CONTRIBUTING.md) marks a failure likely flaky, open or extend a Bug issue for that test and record the cause there. The daily `Flaky test ledger` workflow (`scripts/flaky-issues.ts`) files that issue itself, labelled `flaky-test`, once a test has two likely flaky failures in 14 days, adds later failures to it, and reopens it when the test flakes again after it was closed.
- When a task adds or changes a user-visible feature, a command, a setting, the local API or a workflow, update the matching page in `docs/` in the same branch. Long-lived documentation (guides, references, architecture, the design of shipped features) goes only in `docs/` and describes current behavior; plans and one-off reports do not go in the repository.
- The security scanners' allowlists (`.github/zizmor.yml`, `.gitleaks.toml`, `.github/security/osv-scanner.toml` with an `ignoreUntil` date) are an extension point: every suppression carries a one-line reason and a link to the issue or pull request that accepted it, a new workflow or composite action passes zizmor instead of being excluded from the scan, and a tool the `Security` workflow downloads is pinned by version and hash, with a failed download failing the job (#1844).
- When the task is complete and the checks in [Verification](#verification) pass, open a pull request to `main` and add it to the merge queue: `gh pr merge <number> --merge --auto`. `main` takes changes only through the queue, which runs CI on the pull request merged with the current `main` and every pull request ahead of it, then merges it. A pull request whose checks fail in the queue leaves it; fix it and add it again. Do not push to `main` directly.

## Working conventions

- Use Bun for installation, scripts, and tests. Runtime APIs include `bun:sqlite`; Node.js is not a substitute for running the application.
- Follow strict TypeScript and the existing Biome configuration. Avoid `any`, unused variables, and unrelated formatting changes.
- Prefer small changes to existing modules. Keep agent logic independent of the terminal UI.
- Preserve access controls, approval callbacks, secret handling, and coordination when changing tools.
- A host tool that writes a file on an agent's behalf (`apply_fix`, `restore_file`) writes it through the attempt's tool guard (`guard.execute("edit_file", { path }, ...)`), so the edit is journaled with its pre-image, stays inside the task's write scope and counts as an edit for the progress watcher (`EDIT_TOOLS` in `src/core/workflows/progress-watch.ts`). A new watcher hint about the files themselves comes from state the executor keeps as it edits (the `broken` map of unparsable files) and is passed to `steeringNotice`, never re-read inside the synchronous step controller (#1835).
- A workflow step opened in `src/core/workflows/` goes under its stage step (`beginStep(runId, id, stepId)`), so the drive's catch, recovery and the run's end close it with the stage; a top-level step outside a stage closes itself on every exit path (try/catch or finally). No step stays `running` or `waiting` after its work ended (#1745, #1746); a task step's work runs inside `closingStep` in `scheduler.ts`, and an exit that blocks the task ends its step before the corrective is opened (#1805).
- A field of a task attempt's input that carries earlier work into a repeated, restarted or corrective attempt (`earlierEdits`, `earlierReads`, `previousAttempt`, `recurringFindings`, `correctionFocus`) is added to the `attempt-context` keys in `src/core/workflows/scheduler.ts`, so `attempts/ID/context.json` records it, and to the attempt-context paragraph of `docs/workflows/runtime.md`; its scenario test asserts the saved context equals what was sent, as `tests/workflow-scenario-recurring-symbol.test.ts` does (#1774).
- The test-task split rule is one rule in three places: the oversize decision (`exceedsTestCapacity` and `sizePlan` in `src/core/workflows/sizing.ts`), what the planner is told (`plannerSizing`, `splitNote`, `ROWS_TASK_NOTE`) and what the host can split (`splitTestTasks`, which skips rows tasks, and the rows rule in `rowPlanProblems`). A change to one updates the other two, so sizing never asks for a plan the host cannot make and the planner may not write, and adds a case to `tests/workflow-scenario-rows-task-sizing.test.ts`; a new rows framework adds its row there (#1930).
- Every caller of the case walk (`criterionCases`, `caseCheck`, `contestedRows` in `src/core/verification/criteria-cases.ts` and `src/core/workflows/conflict-rows.ts`) passes the run's policy checks in its `CaseContext`; `checks` is required, so `bun run typecheck` fails when a new caller leaves them out and would count host commands as test cases (#1762).
- An optional task field that only a policy setting enables (`rows`, `rowTest` with `rowsAsData`) is dropped by the host in `planGraph` when the setting is off, as a recorded host edit, never rejected: a model cannot change the policy, and a rejection naming it comes back unchanged until the run blocks. Any plan rejection a model reads names the change the model can make. `tests/workflow-scenario-rows-off-plan.test.ts` fails when a new gated field is rejected instead (#1816). A field that only some spec content can fill (`rows` on a criterion with a table the host reads) comes with that list in the model's input (`plannerRows`, `rowsEligible` in `acceptance-rows.ts`), the rejection names it, and with an empty list the field is treated as off; `tests/workflow-scenario-rows-eligible.test.ts` covers it (#1833).
- Test code the host writes into a project (the acceptance rows of `src/core/workflows/acceptance-rows.ts` and `acceptance-rows-inline.ts`) passes that language's lint and format gates as written, and every check that a host-written file or block is unchanged compares through `layoutFree`, so a formatter's fixer never counts as an edit. A new row template, or a new check of host-written content, gets a case in `tests/workflow-scenario-rows-lint-clean.test.ts` (#1927).
- A block the host writes into a file an agent owns (the inline acceptance rows of `src/core/workflows/acceptance-rows-inline.ts`) keeps the layout a brief sets for that language: in Java and C#, where briefs ask for one top-level type per file, the block is a class nested in the file's own type (`nest` on the template). A new inline template for a language with one type per file nests the same way and gets a case in `tests/workflow-scenario-rows-one-type.test.ts`, which also fails when a framework that adds no type starts to (#1804).
- A host step that runs project commands before approval (a baseline check, a quality or mutation measurement) runs inside `takeBaseline` in `src/core/workflows/scheduler.ts`, before its second snapshot, so the files a first run creates are in the base. A toolchain whose first build writes files outside its usual ignores gets a row in `FIRST_RUN_OUTPUTS` (`tests/helpers/baseline-created-files-scenario.ts`), which the gate-matrix cells "files a first check run creates" run; a directory only a toolchain writes goes in `TOOL_CACHES` (`src/core/verification/snapshot.ts`); a step that runs commands after the snapshot fails them with `input_changed` (#1815).
- A host decision that takes a model's verdict as authority over a run's own evidence (an audit's `matches`, a reviewer's claim) stores that verdict with the evidence the host can re-check, and a verdict against what the code did is re-checked once before it settles anything, as the derivation re-audit of a spec conflict does (`reaudit` in `src/core/workflows/scheduler.ts`). Every conflict decision that overrules criteria records them as `criterionIds` through `recordConflictDecision`, so the case walk stops demanding their literals; `tests/workflow-scenario-reaudit-row-conflict.test.ts` and `tests/workflow-scenario-misquoted-row-conflict.test.ts` fail when either is skipped (#1788). A model's claim that the request states something is evidence the host can re-check: it carries the request's words (`quote` on a derivation) and the host checks them against the request before the claim settles a row (`checkedDerivations` in `src/core/workflows/derivation-audit.ts`, #1823); a new place where a model cites the request adds the same check. See [Spec conflicts](docs/workflows/runtime.md).
- A reroute of analysis findings under `clarification: assume` is budgeted so that a finding first raised after the run's budget is spent still gets a return before a person is asked (`lateDefect` in `src/core/workflows/scheduler.ts`, `newFacet` in `analysis-notes.ts`), with a cap on the passes; a new budget or settle rule there adds a case to `tests/workflow-scenario-analysis-late-inconsistency.test.ts`, which also asserts the cap still asks (#1830).
- A forecast floor ("forecast at no less than N times a measured rate") takes the lowest measured rate for its low end, never a quantile of the rates: a quantile is a typical value, and a whole project cheaper than it falls below every range (R54 lanewalk, #1806). A new floor in `src/core/workflows/initiatives/estimate.ts` or `src/core/workflows/sizing.ts` adds a scenario test with a sample cheaper than the rest. A pool of finished features or runs that prices a feature takes those of the feature's own workflow before mixing in other workflows' (#1813).
- Host state that outlives a workspace (a file in the BAKED data directory, such as `first-byte-history.json` of the adaptive first-response deadline) is written only by a run whose policy turns it on, read back before each write so other processes' entries are kept, written through a temporary file and a rename, and bounded per key. The workspace's own record comes first, and the shared state only fills in where the workspace has too little (#1880).
- Host code that combines features of an initiative split (`mergeFeatures` in `src/core/workflows/initiatives/plan.ts`, behind the skeleton fold, the small-sibling merge and the `merge` edit) never joins words written for a different feature run where they could contradict the merged run: a skeleton-only part's scope and contract are restated (`skeletonTexts`), and which stubs the merged feature implements is recorded as data (`implements`), never as text in a scope. Facts about host-written files reach every stage from the plan the run starts on (`stubFates` and `skeletonLines` in `src/core/workflows/initiatives/service.ts`: content, own stubs, fillers), and a spec that quotes other content goes back (`hostFileSpecProblems`). A new combining path, or new generated text about stubs, gets a case in `tests/workflow-scenario-skeleton-fold-scope.test.ts` or `tests/workflow-scenario-skeleton-content-spec.test.ts` (#1829, #1847).
- A criterion the host's own rules require (`HOST_REQUIRED_CRITERIA` in `src/core/workflows/host-required-criteria.ts`) states its condition once, as its `required` predicate; the scheduler's host-required filter, the `extra.crossPlatform` notes for the spec author and the spec reviewer, and the condition text the prompts read all derive from it, so analysis never demands a criterion the author is told not to write, nor objects to one it is told to write (#1765, #1831). `tests/workflow-scenario-analysis-cross-platform.test.ts` checks that the readers agree.
- A formatter gate a toolchain detector offers (`src/core/workflows/gates.ts`) gets its file-scoped form in `FILE_FORMATTERS` (`src/core/workflows/format-written.ts`, a `LanguageRecord` registered in `tests/language-parity.test.ts`) in the same pull request: check mode and write mode on named files, or `none(reason)` where a file-scoped run cannot be told from the whole unit's, plus its `range` form when the formatter can format a range of lines (or a comment saying it cannot); a range flag that older releases lack names its first release and sets `probe`, so a formatter without it gets no range check (#1907). The format-written check holds the files a task creates whole and the files it edits only on the lines the run changed (#1582) to the project's formatter when no formatter check in the run's checks covers the file (its paths and `cwd`, not only its program), and a host check that holds only some of a task's files sets `fixPaths` so its fixer touches no other file (#1837). A formatter whose program may lack the formatter altogether (a Bun before 1.4.4 has no `bun fmt`) sets `available`, so no check is built that would fail every attempt (#1920). A formatter the edit tools detect (`detectJsFormatter` and the other branches of `detectToolchain` in `src/core/tools/project.ts`) also gets its stdin form in `formatProbeCommand` (`src/core/tools/auto-format.ts`), or nothing is formatted after an edit, with a case in `tests/edit-format-toolchains.test.ts`; detection the edit tools and the gates share lives in one helper both import (`ruffSource`, `bunFmtConfigured`).
- A host decision about a file that already exists in the workspace and is called a test by its name (read-only for implementers, run by the written-tests check) asks `isTestFileAt(root, path)` or `isTestContent` in `src/core/intelligence/language-traits.ts`, never the name rule alone: a plain-word suffix (`Test`, `Spec`, `Suite`, `_test`) also names domain code, and `TEST_MARKERS` (a row per supported language, golden `testMarkers` in `tests/fixtures/languages/`) holds what a real test of the language contains (#1848).
- A pull request that adds an accounting quantity (a token, cost, reservation or forecast figure of a run) or a scheduler command adds its invariant to `tests/workflow-accounting-invariants.test.ts` or its command to the model in `tests/workflow-scheduler-model.test.ts` in the same pull request.
- An id format a result schema checks with a pattern (requirement, criterion and task ids) comes only from `HOST_ID_FORMATS` in `src/core/workflows/host-ids.ts`: the schemas in `schemas.ts`, the instructions that state the formats (`SPEC_ID_RULE` and the planner's task-id sentence in `builtin.ts`) and the normaliser `fillHostConstants` runs before validation all read it. A new id kind gets its row there, its spelling, and a case in `tests/workflow-spec-ids.test.ts`; never write the pattern into a schema or an instruction by hand (#1871).
- The number of runs a workspace executes at once comes from `parallelRunCap` (`src/core/workflows/schemas.ts`), and an initiative's slot count from `InitiativeService.parallelRuns`, which applies the plan's width (`planWidth` in `src/core/workflows/initiatives/critical-path.ts`) under `parallelRunsFromPlan`; never read `workflows.maxParallelRuns` or `DEFAULT_MAX_PARALLEL_RUNS` anywhere else (the scheduler's field is set from `parallelRunCap` before each drive), or the lease cap and the slot count disagree and a third feature is refused with `WORKSPACE_BUSY` (#1822).
- A per-run limit derived from an initiative's shared budget (a feature run's dollar and token growth bounds, its calls and active time) is refreshed for open runs in `refreshedGrowth` (`src/core/workflows/initiatives/service.ts`), which the drive calls before each run is driven, and never only at the feature's start; the run's drive adopts the stored limits (`adoptStoredLimits`). A new limit of that kind joins `refreshedGrowth` with a case in `tests/workflow-scenario-initiative-growth-refresh.test.ts` (#1931).
- Which feature may own another feature's tests is decided only in `testOwnershipProblems` (`src/core/workflows/initiatives/plan.ts`), which the scheduler and the initiative service both call; a new rule about `testedBy` goes there with a case per supported language layout in `tests/initiative-plan-testedby.test.ts`, never as a second check elsewhere (#1873).
- A planned-ahead initiative feature (`workflows.planAhead`, #1834) is held only by its run's `planAhead` state and the `hostRelease` requests the scheduler's task-graph stage creates; it is released only through `NativeWorkflowService.releaseBase`, called from `InitiativeService.releasePlanned` once every upstream feature is accepted, and its provisional base comes only from `featureBase` with the unfinished upstream features (`provisionalBase` in `src/core/workflows/worktree.ts`). Never start a feature's tasks on a provisional base or decide a `hostRelease` request anywhere else; `tests/workflow-initiatives.test.ts` "plan ahead (#1834)" covers the overlap, the release and a contract that changes under a planned-ahead feature. A fork of a worktree run publishes its documents again into its new worktree (`forkRun` clears `published`). A check of a plan against the workspace (a path that must exist) takes a planned-ahead run's upstream files into account only through `pathsExistLater` (`src/core/workflows/dependencies.ts`), readable but never writable, with a case in "plan ahead (#1834)" (#1932).
- A command a project installs is run through its entry point, never by adding the command's name to the executables: a new manifest kind or language gets a reader in `ENTRY_POINTS` (`src/core/verification/entry-points.ts`), whose launcher is a program the checks already start, an `entryPoints` golden in its `tests/fixtures/languages/` fixture, and a stack row in `WITH_ENTRY_POINT` for the "doc examples entry points" cell of `tests/gate-matrix.test.ts`. The documented-example runner, `run_repro` and `run_probe` resolve it the same way through `entryPointCommand`, so a fix to one of them is a fix to all three (#1821).
- The documented-example runner (`src/core/verification/doc-examples.ts`) runs an example only on what a reader would have: the workspace plus the files the document tells them to save (`extractFixtures`), and reports a difference that comes from an input nobody supplies as `not_run`, never as a mismatch. A new README shape (an example form, a way to introduce a file) is read in `extractExamples` or `extractFixtures` and gets a case in `tests/workflow-scenario-doc-example-fixtures.test.ts`, whose per-toolchain rows keep it language-agnostic (#1849).
- A host step that runs a command a spec or document quotes (documented examples, `run_repro`, the case walk's source probe) runs it through `entryPointCommand` in a copy of the workspace (`copyWorkspace` in `src/core/verification/doc-examples.ts`), never in the run root, and treats a command that cannot say (not the project's program, not built, an input nobody supplies, a timeout) as no evidence. A probe that finds source code disagreeing with a criterion routes the difference to the task that wrote the source, never to the test task's own correction (#1836). The copy is removed with `removeScratch` (`src/core/verification/repro.ts`), never a bare `rmSync`: on Windows a program stopped at the timeout holds the directory for a moment, and the removal error must not replace the result.
- A dependency manifest reader in `DEPENDENCY_MANIFESTS` (`src/core/workflows/quality/manifests.ts`) states its executable fields (`fields`, extractors in `quality/manifest-fields.ts`): what runs code or chooses where code comes from, which the manifest field check holds to the request (#1793). The type requires the entry; add a cell for the manifest to "manifest executable fields" in `tests/gate-matrix.test.ts` with one executable and one plain change.
- A diagnostics summary parser in `diagnosticCount` (`src/core/verification/output-counts.ts`) counts errors and warnings only, never infos or hints, sets `errors` where the summary splits them, and adds a cell for the tool to "diagnostics ratchet severity" in `tests/gate-matrix.test.ts`; a parser that counts infos turns a passing check into a correction (#1791).
- A new provider adapter joins the provider fault matrix (`FAULT_PROVIDERS` in `tests/helpers/faulty-provider.ts`, run by `tests/provider-fault-matrix.test.ts`) in the same pull request, and a new timer, retry or limit on model calls adds the fault profile that exercises it, with the class it expects: an answer, an outage, a retry, a model mistake or a host fault. Fault profiles take their latencies and `retry-after` waits from the replay corpus (`CORPUS` in the same helper, from `corpusCallProfile`), not from numbers written by hand; a value a profile needs that the corpus lacks is recorded in each call's `calls` timing first (#1729).
- A provider adapter with more than one transport (Codex app-server and `codex exec`) names the one serving each call with `providerCallDetail` (`src/core/llm/provider-health.ts`), so the attempt's usage `calls` say which transport stalled, and moves a call shape that stalled on one transport to the other rather than repeating it. Code that decides whether a provider answered an attempt (the provider circuit in `src/core/workflows/retry.ts`) reads the attempt's `calls`, never its recorded tokens alone: a transport may report usage only after a later call (#1875, #1876).
- A provider adapter names the words its provider uses to refuse a request under its usage policy in `POLICY_REFUSALS` (`src/core/llm/policy-refusal.ts`), or `{ none: "why" }`, in the same pull request; `tests/policy-refusal.test.ts` requires an entry for every adapter. The scheduler recognises refusals only through `policyRefusal`, so a refused request is never filed as a lost worker or an outage (#1895).
- A check that runs test files a task wrote, or tests chosen by changed files, sets `requireTests: true`, so it fails when it exits 0 without running a test (`testsRan` in `src/core/verification/output-counts.ts`: a new test runner's `TEST_COUNTERS` entry adds `ran`, the executed tests without skipped or ignored ones). A language whose test files declare a build gate the test command turns on with a flag reads it in the `TEST_GATES` record of `src/core/workflows/test-gates.ts`, and the command that runs the file passes it; a language without one keeps its `none(reason)` row. Add the runner's zero-run output to `ZERO_RUN_OUTPUT` in `tests/gate-matrix.test.ts` (#1832).
- A failed required check that the run's own plan cannot repair (static debt from before the run, a test check that collected no test in a plan that writes none) is exempted in one scheduler helper (`staticDebt`, `noOwnedTests` in `src/core/workflows/scheduler.ts`) that both check stages call (`runChecks` for v1, `runCheckStage` for v2), and records a `checks/<kind>/` artifact with the evidence id. Acceptance and every view of a run's checks (report, view, compare, delivery) read that decision only through `hostPassedChecks` and `decidedChecks` (`src/core/verification/host-passed.ts`); a new exemption kind is added there, and a new reader of check results goes through `decidedChecks`. A test runner's "no test collected" output is added to `noTestsCollected` (`src/core/verification/convergence.ts`) with a cell in the gate matrix's "no tests collected (#1864)" block, for every supported language whose runner prints it.
- The property-test mode of a run is decided by `propertyTestsOf` (`src/core/workflows/quality/properties.ts`), reached in the scheduler only through `propertyMode`, which gives it the request, the policy and the repository's own tests (`quality/property-repository.json`). A host default that adds a test construct (property loops, generated inputs) gives way to an existing repository that has none, unless the request asks for it. A language that gains a property library joins `PROPERTY_LIBRARIES` with a case in `tests/property-tests-brownfield.test.ts`.
- A spec-author answer that breaks a host rule the host can mend without changing the criterion's meaning (a `property` flag in a feature that owns no test path, `clearBoundaryProperties` in `src/core/verification/initiative-ownership.ts`) is mended after acceptance and recorded under `spec-repairs/`, next to `repairHostBoundCriteria` and `repairDeliverables`, instead of rejecting the written spec; the validator rejects only what the host cannot mend.
- An acceptance-rows test framework (`rowTest.framework`) ships both modes in the same pull request: a file template (`TEMPLATES` in `src/core/workflows/acceptance-rows.ts`) and an inline block (`src/core/workflows/acceptance-rows-inline.ts`) that uses only the language's standard library and test framework, so a brief that fixes its test files or forbids new dependencies can still use the rows. `tests/language-parity.test.ts` fails when a framework lacks the inline block (#1763). The row replay of source tasks (#1617) reuses that inline block in a one-shot file named by `REPLAY_FILE` in `src/core/workflows/acceptance-rows-replay.ts`, so a new framework also adds its replay file there and a row in `tests/acceptance-rows-replay.test.ts` showing the project's written-tests command runs that file alone; change how rows are run or read in those two modules, not in the scheduler or the executor.
- Keep comments focused on non-obvious intent. Keep documentation technical: setup, behavior, architecture, troubleshooting, and development.
- Preserve user changes already present in the working directory.
- A stalled model call (no first response, or a stream that ended without a finish) recovers through the rungs of the recovery ladder in `src/core/workflows/stall-ladder.ts` (`LADDER_RUNGS`, `nextRung`), not through another retry branch in `scheduler.call` (#1877). A new rung says when it changes something for the call, keeps what earlier rungs changed, gets its `rungText` and a case in `tests/workflow-stall-ladder.test.ts`; a knob a provider adapter reads per call travels in provider options (`withCodexRecovery`), and the replay hook `replayStallLadder` decides it again on the corpus.
- Hot harness modules ([`.github/hot-modules.json`](.github/hot-modules.json): cost forecast, sizing, cap growth, auto-approval, provider timers, scheduler retry) follow an error budget ([docs/bench-loop.md](docs/bench-loop.md#hot-modules)): at most one behavior change per hot module per bench round, and after a round with two or more stops caused by fresh fixes only reverts and regression fixes in those modules until a round passes without one. A pull request that changes one is labelled `hot-module` and runs the module's tests and the forecast replay on their own. A module that shows two escapes in a month (`bun scripts/hot-modules.ts escape`) is added to the list in the same pull request as its fix; a new file of a listed module's computation joins that module's `paths`.
- A toolchain gate detector joins `TOOLCHAIN_GATES` in `src/core/workflows/gates.ts` and its languages' `GATE_TOOLCHAINS` rows, with the fixture's `gates` golden, a row in the gate table of `docs/workflows/runtime.md` and a cell in `tests/gate-matrix.test.ts`. Check the gates it suggests against the rest of the check routing in the same branch: a linter or analyzer that resolves imports is whole-unit (`WHOLE_UNIT_COMMAND` in `check-policy.ts`), a formatter's fixer takes the task's file in `fixerCommand`, and the test runner's "no tests" message is read by `noTestsCollected` (#1753). A lint or test gate that takes path arguments adds its "path does not exist" output to `MISSING_PATH_LINES` in `src/core/verification/convergence.ts`, with a case in `tests/missing-path-owner.test.ts`, so a failure on a folder a later task creates goes to that task (#1913).
- Code that branches on a language, file extension, manifest or toolchain takes its data from an exhaustive per-language record (`LanguageRecord` in `src/core/intelligence/language-records.ts`): a row for every supported language, or `none(reason)` where the language has no such thing. Register each record in `tests/language-parity.test.ts`, with a golden in every language's fixture under `tests/fixtures/languages/`. Adding a language to `SUPPORTED_LANGUAGES` means filling every record and adding its fixture; the compiler and the parity test list what is missing.
- Code that reads a test or source file as code, and not its comments or strings, goes through `maskNonCode` or `stripComments` in `src/core/workflows/quality/code-mask.ts`, whose per-language syntax is the `MASK_SYNTAX` record; a matcher of the case walk never searches raw file text for evidence (#1846). A new literal shape the walk holds gets a case for each of C#, Go, Java, Python and TypeScript in its scenario test.
- A JSON schema BAKED sends as a provider's structured output in strict mode (the `codex exec` `--output-schema`) builds its objects with `strictObject` (`src/core/llm/providers/codex/runner.ts`): `additionalProperties: false` and `required` listing every property, `required: []` for an object with none. `tests/codex-strict-schema.test.ts` walks every such schema, with and without tools, and fails on an object strict mode refuses; a new schema joins that walk (#1889).
- Provider names in runtime code (Claude, OpenAI, Codex, GitHub Copilot, GitHub Models) describe supported integrations. Do not rename them when editing these instructions or other contributor documentation.

## Language

- Write everything in English: code, comments, identifiers, test names, documentation, design documents, audit records and commit messages.
- Workflow artifacts are English too: research, specifications, plans, task titles and descriptions, reviews, findings and summaries. Write them in English even when the request, project files or answers use another language; translate the meaning and keep identifiers, paths, commands and quoted source text unchanged.
- Tests that need non-ASCII text use Unicode escapes or non-Cyrillic scripts.

## Verification

CI runs these on every pull request to `main`; run them before merging:

```sh
bun run lint
bun run typecheck
bun run test
bun run build
```

`bun run typecheck` runs `bun check`, which needs Bun 1.4.3 or newer; on an older Bun use `bun run typecheck:tsc`. While iterating, `bun test tests/<feature>.test.ts` runs one feature's tests. The suite is hermetic: tests must not depend on the developer's home directory, global hooks or configuration, or provider environment variables such as `ANTHROPIC_BASE_URL`. Point home-dependent code at a temporary profile instead of skipping the test. Documentation-only changes need link, path, and configuration checks rather than new unit tests; `bun test tests/docs.test.ts` checks the links in `docs/` and the slash command list in `docs/commands.md`. Report what was checked and any failures that remain.
