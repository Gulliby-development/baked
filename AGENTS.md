# Working on BAKED

These instructions apply to every coding agent and every model provider that works in this repository, and to human contributors.

## Project

BAKED is a TypeScript coding agent with an OpenTUI/React terminal UI and a headless CLI. It runs on Bun and uses SQLite for persistent data. Read `README.md` for setup and `CONTRIBUTING.md` for architecture and extension points.

## How BAKED works

- `src/boot.tsx` parses the command line and starts either the terminal UI or the headless CLI.
- The main agent (`src/core/agents/bake.ts`) assembles the system prompt, context, tools, approval callbacks and execution mode for a session, then runs the model loop through a provider from `src/core/llm/providers/`.
- Context comes from `src/core/context/` and the repository graph in `src/core/intelligence/` (language servers and tree-sitter), so the agent can reason about code structure rather than only raw files.
- Tools in `src/core/tools/` (files, shell, Git, code analysis) execute through the registry. Writes and commands pass access checks and user approval before they run.
- Sessions, memory and workflow state persist in SQLite (`src/core/sessions/`, `src/core/memory/`, `src/core/workflows/`). Durable workflow events are authoritative; the UI only renders them.
- The terminal UI (`src/components/`, `src/hooks/`, `src/stores/`) and the headless CLI (`src/headless/`) are front ends over the same core.

## Task workflow

- Planned work is tracked as GitHub Issues in this repository (shown on the project board), not in markdown files. Before starting, find the issue for the task or open one; record a new idea, follow-up or deferred item as an issue instead of a document or a TODO list.
  - Labels: `verification` (a check that needs a real model, device or account), `idea` (not yet decided), `needs-gulliby` (only the owner can do or decide it), `deferred` (agreed for later), and `area:workflow|tui|desktop|api|ci|release`. Use the issue type Task, Bug or Feature.
  - Every new issue goes on the BAKED project board with Status `Backlog` (or `Ready`) and a Priority: `P0` (blocks current work or a release), `P1` (next up), `P2` (later or an idea). With the GitHub CLI: `gh project item-add` then `gh project item-edit` (the token needs the `project` scope). If your tools cannot reach GitHub Projects, put `Priority: P0|P1|P2` on the first line of the issue body so it can be set on the board.
  - Before you open or extend a Bug issue, follow the [file-issue skill](.agents/skills/file-issue/SKILL.md), whoever files it (a person, the bench loop, a smoke run or a review). It finds the root cause and sweeps the code for every place with the same or a neighbouring defect: other copies of the computation, parallel stages, toolchains, providers and surfaces. The issue then lists all of them. A pull request that fixes such an issue fixes every place the issue lists, runs the sweep again before it opens, and reports both in a `## Sweep` section of its description; CI fails a pull request that closes a Bug issue without one, or whose Sweep section has no `Languages:` line. Before it merges, run `bun run review:adversarial --pr N --post` when the Claude Code or Codex CLI of the other model family than yours is logged in on your machine: it has that model look for places the sweep missed, with the [adversarial review prompt](.agents/skills/file-issue/adversarial-review.md) and the skill's own sweep checklist, and posts one advisory comment (no CI job and no API key; the bench loop reviews the fix pull requests other machines merged). Add a new sweep dimension to the skill's Sweep sections, so the reviewer checks it too. The review reads its inputs from the pull request's base commit (`REVIEW_INPUTS` in `scripts/adversarial-review.ts`); a new file the reviewer or its verifier reads joins that list, so a pull request cannot edit it to pass its own review (#1845). Its call-graph context takes each language's call and import spellings from `CALL_SYNTAX` (`src/core/intelligence/call-context.ts`), a `LanguageRecord` registered in `tests/language-parity.test.ts`; function definitions come from the tree-sitter backend's queries, so a language whose functions tree-sitter misses gets its query fixed there. Answer a real finding in the same pull request or with a new issue.
  - When a bug is bound to a language (it branches on a language, extension, manifest, toolchain or test convention, or appeared only in one language's project), check whether it reproduces in every other language BAKED supports, taking the list from the code rather than memory. Every language where it reproduces, or where the code shows it would, is covered by the same issue when one shared fix serves them all, or gets its own linked Bug issue when it needs its own fix. The issue and the fixing pull request record the result in a `Languages:` line of their Sweep section.
  - A change that adds or changes a host decision (anything that stops, parks, declines, refuses, retries, times out or grows a limit on its own) records the decision's inputs in the run's database and adds its replay hook, a corpus case and an `accepted.json` entry for any recorded run it means to decide differently, in the same pull request. Follow the [replay-corpus skill](.agents/skills/replay-corpus/SKILL.md); `tests/forecast-replay-corpus.test.ts` replays every bench-round trace in `tests/fixtures/bench-traces/` in CI.
  - The nightly mini-suite in `bench/suite/` runs small tasks in every supported language; follow the [bench-suite skill](.agents/skills/bench-suite/SKILL.md) for its task format and graduation rules. Adding a supported language or toolchain adds at least two suite tasks for it in the same branch, and a bench round or smoke stop that a small task can reproduce adds that task.
  - A pull request that finishes an issue says `Closes #N` in its description so the merge closes the issue; reference it with `Refs #N` when the PR is only part of it.
- Start every task on its own branch, created from an up-to-date `main`:
  - new feature: `feature/<name>`;
  - bug fix: `bugfix/<name>`.

  These are the only two prefixes, for every change and every author: documentation, specs (including `bench/loop/`), CI, refactors and chores use `feature/` unless they fix a bug. `<name>` is a few lowercase words joined by hyphens that say what the task is. Never use another prefix (`docs/`, `fix/`, `chore/`, `claude/`, `codex/`, `copilot/`) or a generic name such as `project-thread`, `patch` or `update`; if your tool proposes a default branch, rename it before the first push. A random suffix your platform appends after the name (`feature/desktop-checkpoints-sgmb4g`) is fine. CI fails a pull request whose head branch breaks this rule; only Dependabot's `dependabot/` branches are exempt.
- Commit intermediate working states on the task branch. Before each intermediate commit, run at least `bun run typecheck` (or `bun run build` for startup and bundling changes) so every commit is a state you can return to.
- Ship major features on every surface of the app: the terminal app (TUI and headless CLI), the desktop app (`apps/desktop`, through the `baked serve` local API), and every supported operating system (Windows, macOS, Linux). Core logic stays in `src/core/` so each front end only renders it. If a surface cannot be done in the same branch, open a follow-up issue for it on the project board and reference it from the pull request. Every user-facing feature has an entry in the feature registry (`src/core/features/registry.ts`) naming how each surface reaches it, or the issue or reason a surface lacks it; `tests/feature-parity.test.ts` fails when a slash command, a `/v1` route or a desktop screen is missing there. See [docs/parity.md](docs/parity.md).
- Keep extension points maintainable. When a task adds a mechanism that later features must extend to stay complete (a registry, a per-language table, a replay or fault-injection hook, a stop reason, a test matrix, a bench-suite task list), its issue says so in a `## Maintainability` section, and the pull request that implements it adds the rule to this file in the same branch: what a later change must add, where, and which test fails when it is skipped. When the rule needs more than a few sentences, write it as a skill under `.agents/skills/<name>/SKILL.md` and link it from here, as the file-issue skill is. Every Feature and Task issue has the section; it says `None` when nothing will need extending. A pull request that extends such a mechanism follows its rule or skill.
- Any new or changed logic that can stop a run, park it or decline an approval registers its reason in `src/core/workflows/stop-reasons.ts` and ships in `shadow` mode, recording `decision.would_stop` events instead of stopping. A stopping fault is made with `stopFault`; `tests/stop-reasons.test.ts` fails on one made another way. Promoting a reason to `enforce` is a pull request of its own that cites two bench rounds with no false would-stop. Hard limits the person set (money, tokens, time, storage) are registered as enforce-only. See [Stop reasons and shadow mode](docs/workflows/runtime.md#stop-reasons-and-shadow-mode). A corrective chain's failing required checks are compared, not only counted: each failing corrective records `repeats/tasks/<task>.json` (kind `repeated-failure`, kept in traces, replayed by `replayRepeatedFailures` with the `newRepeatStops` counter) and the `repeated_failure` reason records a would-stop when its hash equals the previous corrective's (`src/core/workflows/repeated-failure.ts`, #1996). A new check runner whose failing output carries a value that changes between runs of the same failure (a timestamp, a duration, a temporary path, an address) adds its normalization to `normalizeCheckOutput` and its pair of outputs to `tests/repeated-failure.test.ts`, which fails when two runs of one toolchain's failing check hash differently; a new path that opens a task-level correction for check failures goes through `repair(..., "task")` or calls `recordRepeatedFailures` itself, with a case in `tests/workflow-scenario-repeated-failure.test.ts`.
- A test writes its scratch repositories, databases and files under `os.tmpdir()`, never in the checkout or a fixed path, so CI decides which disk they use: Windows `OS tests` shards point `TEMP` and `TMP` at a directory in `RUNNER_TEMP` on D: that grants the runner user its own ACE, because the runner's C: temp directory stalled file and git work for tens of seconds (#1910). A test passes its own time limit only above the suite's 30 s; passing 30 s itself overrides the 90 s Windows shards allow, and `tests/os-tests-workflow.test.ts` refuses it.
- A desktop client module (`apps/desktop/src/renderer/`) loads in any order and without a `window`: it reads browser globals through a `typeof` guard or inside a function, and a mock route module imports `response` and the route types from `client/mock-response.ts`, never from `client/mock-routes.ts`, which imports every route module. The desktop tests share one module registry, so a module that needs one load order fails every later test once the run picks another order; `apps/desktop/tests/module-load-order.test.ts` loads each route module first and the bridge without a `window`.
- A flaky test is fixed, never skipped, disabled or retried into green. When the `OS tests` flaky ledger (the `flaky-ledger-*` artifact and its annotations, see CONTRIBUTING.md) marks a failure likely flaky, open or extend a Bug issue for that test and record the cause there. The daily `Flaky test ledger` workflow (`scripts/flaky-issues.ts`) files that issue itself, labelled `flaky-test`, once a test has two likely flaky failures in 14 days, adds later failures to it, and reopens it when the test flakes again after it was closed.
- When a task adds or changes a user-visible feature, a command, a setting, the local API or a workflow, update the matching page in `docs/` in the same branch. Long-lived documentation (guides, references, architecture, the design of shipped features) goes only in `docs/` and describes current behavior; plans and one-off reports do not go in the repository.
- The security scanners' allowlists (`.github/zizmor.yml`, `.gitleaks.toml`, `.github/security/osv-scanner.toml` with an `ignoreUntil` date) are an extension point: every suppression carries a one-line reason and a link to the issue or pull request that accepted it, a new workflow or composite action passes zizmor instead of being excluded from the scan, and a tool the `Security` workflow downloads is pinned by version and hash, with a failed download failing the job (#1844).
- When the task is complete and the checks in [Verification](#verification) pass, open a pull request to `main` and add it to the merge queue: `gh pr merge <number> --merge --auto`. `main` takes changes only through the queue, which runs CI on the pull request merged with the current `main` and every pull request ahead of it, then merges it. A pull request whose checks fail in the queue leaves it; fix it and add it again. Do not push to `main` directly.

## Working conventions

- Use Bun for installation, scripts, and tests. Runtime APIs include `bun:sqlite`; Node.js is not a substitute for running the application.
- Follow strict TypeScript and the existing Biome configuration. Avoid `any`, unused variables, and unrelated formatting changes.
- Prefer small changes to existing modules. Keep agent logic independent of the terminal UI.
- Preserve access controls, approval callbacks, secret handling, and coordination when changing tools.
- A host tool that writes a file on an agent's behalf (`apply_fix`, `restore_file`) writes it through the attempt's tool guard (`guard.execute("edit_file", { path }, ...)`), so the edit is journaled with its pre-image, stays inside the task's write scope and counts as an edit for the progress watcher (`EDIT_TOOLS` in `src/core/workflows/progress-watch.ts`). A new watcher hint about the files themselves comes from state the executor keeps as it edits (the `broken` map of unparsable files) and is passed to `steeringNotice`, never re-read inside the synchronous step controller (#1835).
- A workflow step opened in `src/core/workflows/` goes under its stage step (`beginStep(runId, id, stepId)`), so the drive's catch, recovery and the run's end close it with the stage; a top-level step outside a stage closes itself on every exit path (try/catch or finally). No step stays `running` or `waiting` after its work ended (#1745, #1746); a task step's work runs inside `closingStep` in `scheduler.ts`, and an exit that blocks the task ends its step before the corrective is opened (#1805).
- A field of a task attempt's input that carries earlier work into a repeated, restarted or corrective attempt (`earlierEdits`, `earlierReads`, `previousAttempt`, `recurringFindings`, `correctionFocus`, `battery`) is added to the `attempt-context` keys in `src/core/workflows/scheduler.ts`, so `attempts/ID/context.json` records it, and to the attempt-context paragraph of `docs/workflows/runtime.md`; its scenario test asserts the saved context equals what was sent, as `tests/workflow-scenario-recurring-symbol.test.ts` does (#1774).
- A finding chain (a `repeatOf` chain on one file and symbol, `src/core/workflows/finding-chain.ts`) escalates at one threshold, `CHAIN_REWRITE_AT`; never compare a chain's length with a number written elsewhere. The rewrite corrective's battery travels as the `battery` attempt-context key and the host's battery check before a review reads the same chain (`batteryOf`), so the worker and the host hold the same cases. Both decisions record their inputs under `chains/` (kind `finding-chain`, kept in bench traces) and replay in `replayFindingChains`. A new corrective origin, or a new path that opens a corrective for a review or convergence finding, adds its case to `tests/workflow-scenario-finding-chain.test.ts`, which fails when the second link of a chain is not a rewrite with its battery or when a broken battery case reaches a review call (#1959). A chain's key is its file and the symbol or the reviewer's `family` (`sameSpot` and `familyLink`, #2048); a new field on a finding that a chain or another host decision reads is added to the finding schema (`ReviewSchema` in `schemas.ts`), kept readable by the bench trace export (`scrubTrace`, which keeps `family` folded), read by `chainFindings` and covered in `tests/workflow-scenario-finding-chain.test.ts`, and the chain replays (`replayChainEscalation`, the R62 and R65 md-site cases of `tests/forecast-replay-corpus.test.ts`) gain its column.
- The edge-input probe of a planned source task (`edgeProbe` in `src/core/workflows/scheduler.ts`, `src/core/verification/edge-inputs.ts`) decides a case only through `edgeDecision`, records its inputs under `probes/edge/` (kind `edge-probe`, kept in bench traces) and replays in `replayEdgeProbes`. A runtime limit worth probing goes into the language's `NUMERIC_LIMITS` row (a language-bound record: its golden in `tests/fixtures/languages/*.json` changes with it), never into the profile's instructions. A new path that settles a planned task calls the probe as the serial and parallel implement paths do, and `tests/workflow-scenario-edge-probe.test.ts` covers it (#1808).
- A corrective attempt stopped by its cap or by the progress watcher, with edits whose repro no longer reproduces (or whose finding's named check passes) and whose required task-end checks pass, is finished by the host (`hostFinishAfterStop` in `src/core/workflows/scheduler.ts`), never by another model session. A new path that restarts, widens or continues a stopped task goes through it first, and a cap stop that would stop the run waits for it. The watcher's stop comes at the earliest one full step after its steering (`STEER_GRACE_STEPS` in `progress-watch.ts`). See the host finish in [Progress watcher](docs/workflows/runtime.md#progress-watcher) (#1978).
- The test-task split rule is one rule in three places: the oversize decision (`exceedsTestCapacity` and `sizePlan` in `src/core/workflows/sizing.ts`), what the planner is told (`plannerSizing`, `splitNote`, `ROWS_TASK_NOTE`) and what the host can split (`splitTestTasks`, which skips rows tasks, and the rows rule in `rowPlanProblems`). A change to one updates the other two, so sizing never asks for a plan the host cannot make and the planner may not write, and adds a case to `tests/workflow-scenario-rows-task-sizing.test.ts`; a new rows framework adds its row there (#1930).
- The subject of a commit or pull request BAKED makes of a run (the run branch in `commitAccepted`, the delivery commit and pull request title in `prepareDelivery`) comes from `runSubject` in `src/core/workflows/run-title.ts`, never from `spec.title` sliced: a host-made spec's title is the request's first characters, so a quick run takes its first planned task's title, cut at a word by `wordCut` (#2001). `tests/workflow-scenario-quick-commit-title.test.ts` checks quick and sdd runs.
- A commit BAKED makes of a run's result (the run branch in `commitRunBranch`, the delivery plan in `prepareDelivery`) decides whether `specs/<feature>/` ships through `shipsSpecs` (or `treeShipsSpecs` on a listed tree) and `runSpecPath` in `src/core/workflows/delivery-git.ts`, never with its own check: only a base that already tracks a `specs/` folder of its own gets it, so a new top-level folder never breaks a project's packaging (#1998, flat-layout Python). An initiative's spec folders (`initiativeSpecPrefix`) never count as the project's own and leave every commit of its features, also when inherited from the base (unless the project's HEAD already tracks them); a dependent feature reads its upstream specs (`upstreamSpecs`, from `specPublication`) as untracked files of its worktree (`baseFiles`, written by `placeBaseFiles` in `src/core/workflows/worktree.ts`), never from a commit of its base (#2046): any file the host places in a worktree base for the run only to read goes through that untracked path, and `provisionalBase` holds only files the run's tasks modify (the skeleton stubs). A copy of the run the host builds or tests in (`inRunCopy`) leaves them out too (#2017). `tests/workflow-worktree.test.ts` holds the flat-layout scenario and checks both commits agree; `tests/workflow-initiatives.test.ts` holds the initiative scenario (uritpl R65), which fails when a new commit path ships them, and the history scenario (nodepluck R66, `addedSpecs`), which fails when any commit of a run branch's history adds a spec file.
- Every caller of the case walk (`criterionCases`, `caseCheck`, `contestedRows` in `src/core/verification/criteria-cases.ts` and `src/core/workflows/conflict-rows.ts`) passes the run's policy checks in its `CaseContext`; `checks` is required, so `bun run typecheck` fails when a new caller leaves them out and would count host commands as test cases (#1762).
- Every reader of a Markdown table row in a spec (the case walk's `tableRows` in `src/core/verification/criteria-cases.ts`, `cellsOf` in `src/core/workflows/acceptance-rows.ts`, and any new one) takes its cells from `tableCells` in `src/core/specs/table-cells.ts`, which splits only at a `|` outside a backtick code span and a double-quoted string and not escaped as `\|`; a row that does not split to its header's width is skipped, never demanded. `tests/table-cells.test.ts` fails when a file in `src/core` calls `.split("|")` outside that module and its explicit list of non-table uses (a new non-table use joins the list with its reason), and a new table literal shape gets a case per language in `tests/workflow-scenario-casewalk-pipe.test.ts` (#2044).
- The case walk (`src/core/verification/criteria-cases.ts`) trims and splits a criterion literal only on ASCII spaces and tabs (`asciiTrim`, `[ \t]+`), never with `trim()` or `\s`, which also take a BOM, NBSP, U+2028, U+2029, U+3000 and a bare CR that belong to the literal; its quote scans (`QUOTED`, `DOUBLE_QUOTED`) match an empty span (`""`) so it never pairs with the next span's quote, and `literalCase` keeps an empty literal from becoming a case. `tests/workflow-scenario-case-walk-invisible-literals.test.ts` holds a cell per character and language spelling (#1979, #1980). Criteria whose rows the host wrote are not demanded from the test text: while the task's inline rows block is intact (`hostRows` in `CaseContext`, checked with `hasInlineRows`), the walk skips those criteria's table cells, and for every other case it decodes the test text to a canonical form (`canonicalText`) as it does the literal; a new inline framework or a new text shape adds a cell to the gate-matrix block "inline rows block holds its own cells" (#1997, #1846 family).
- Whether a test holds a multi-line criterion literal is decided by one function, `linesHeld` in `src/core/verification/criteria-cases.ts`: it keeps every line between the first and the last non-blank one, blank lines included, and demands them in order as consecutive line breaks; no other path drops, merges or reorders a literal's lines. A new multi-line literal shape (a blank line, CRLF, a list of lines, doubled escapes) gets a case for each of C#, Go, Java, Python, Rust and TypeScript in `tests/workflow-scenario-case-walk-blank-lines.test.ts`, including one that refuses a missing line (#2021).
- An optional task field that only a policy setting enables (`rows`, `rowTest` with `rowsAsData`) is dropped by the host in `planGraph` when the setting is off, as a recorded host edit, never rejected: a model cannot change the policy, and a rejection naming it comes back unchanged until the run blocks. Any plan rejection a model reads names the change the model can make. `tests/workflow-scenario-rows-off-plan.test.ts` fails when a new gated field is rejected instead (#1816). A field that only some spec content can fill (`rows` on a criterion with a table the host reads) comes with that list in the model's input (`plannerRows`, `rowsEligible` in `acceptance-rows.ts`), the rejection names it, and with an empty list the field is treated as off; `tests/workflow-scenario-rows-eligible.test.ts` covers it (#1833). A field that only some spec content can fill is repaired or refused with the change the author can make: the spec's `property` flag is cleared by the host as a recorded edit when nothing the author writes can make it valid (`clearBoundaryProperties` for a feature without a test path, `clearBannedProperties` for a request that bans generated inputs, both in `src/core/verification/initiative-ownership.ts`), and refused on a literal `Input | Expected` table with "remove property or the table" (`literalPropertyProblems` in `acceptance-rows.ts`). A new reader of `property` reads the spec after those steps; the scenario test covers both cases (#2045).
- Test code the host writes into a project (the acceptance rows of `src/core/workflows/acceptance-rows.ts` and `acceptance-rows-inline.ts`) passes that language's lint and format gates as written, and every check that a host-written file or block is unchanged compares through `layoutFree`, so a formatter's fixer never counts as an edit. A new row template, or a new check of host-written content, gets a case in `tests/workflow-scenario-rows-lint-clean.test.ts` (#1927); a file-mode template also gets a fixed-point case there that runs its language's default formatter, linter and typechecker when installed and expects no change and no diagnostic (#1942). Each rows template, inline and file, also gets a fixed-point case there for every formatter option that rewrites tokens rather than whitespace (Prettier `arrowParens` and `semi`, Biome `arrowParentheses`, google-java-format's string reflow), with a recorded layout so it runs without the tool; a template leaves the option nothing to choose where it can, and `layoutFree` absorbs the rewrite where it cannot. A new framework adds its formatters' options to that list (#1961).
- A block the host writes into a file an agent owns (the inline acceptance rows of `src/core/workflows/acceptance-rows-inline.ts`) keeps the layout a brief sets for that language: in Java and C#, where briefs ask for one top-level type per file, the block is a class nested in the file's own type (`nest` on the template). A new inline template for a language with one type per file nests the same way and gets a case in `tests/workflow-scenario-rows-one-type.test.ts`, which also fails when a framework that adds no type starts to (#1804).
- A host step that runs project commands before approval (a baseline check, a quality or mutation measurement) runs inside `takeBaseline` in `src/core/workflows/scheduler.ts`, before its second snapshot, so the files a first run creates are in the base. A toolchain whose first build writes files outside its usual ignores gets a row in `FIRST_RUN_OUTPUTS` (`tests/helpers/baseline-created-files-scenario.ts`), which the gate-matrix cells "files a first check run creates" run; a directory only a toolchain writes goes in `TOOL_CACHES` (`src/core/verification/snapshot.ts`); a step that runs commands after the snapshot fails them with `input_changed` (#1815).
- A host decision that takes a model's verdict as authority over a run's own evidence (an audit's `matches`, a reviewer's claim) stores that verdict with the evidence the host can re-check, and a verdict against what the code did is re-checked once before it settles anything, as the derivation re-audit of a spec conflict does (`reaudit` in `src/core/workflows/scheduler.ts`). Every conflict decision that overrules criteria records them as `criterionIds` through `recordConflictDecision`, so the case walk stops demanding their literals; `tests/workflow-scenario-reaudit-row-conflict.test.ts` and `tests/workflow-scenario-misquoted-row-conflict.test.ts` fail when either is skipped (#1788). A model's claim that the request states something is evidence the host can re-check: it carries the request's words (`quote` on a derivation) and the host checks them against the request before the claim settles a row (`checkedDerivations` in `src/core/workflows/derivation-audit.ts`, #1823); a new place where a model cites the request adds the same check. A conflict decision uses verified quotes, not report wording (#2016): whether the request settles a `spec_conflict` is decided by `requestConflictDecision` in `src/core/workflows/request-conflict.ts` on the sides the host checked against the spec and the request (`checkedSides`) and on the request re-audit's checked quotes, on every report of a task, and records its inputs under `conflicts/request/` for `replayRequestConflicts`. A new rule of `specConflict` that reads the report goes through checked sides or a checked quote, never a phrasing regex like `namesRequestSide` (kept only as the first-report fallback), and adds its case to `tests/workflow-scenario-spec-conflict-request.test.ts`, whose first-report phrasings (request, brief, contract, task text) fail when the decision hangs on one word. Whether the host corrects a misquoted test itself instead of opening a session (`misquoteFix`, #2047) is decided only by `misquoteFixDecision` in `src/core/workflows/misquote-fix.ts` on the sites `misquoteFixPlan` reads, recorded under `conflicts/misquote/` for `replayMisquoteFixes`; the edit is journaled and kept only when the task's required checks pass on it. A new spelling the plan rewrites (an escape layer, a raw or interpolated string) adds its case per language to `tests/workflow-scenario-misquote-host-fix.test.ts`, which fails when a second session opens after a fix whose checks pass. See [Spec conflicts](docs/workflows/runtime.md).
- A reroute of analysis findings under `clarification: assume` is budgeted so that a finding first raised after the run's budget is spent still gets a return before a person is asked (`lateDefect` in `src/core/workflows/scheduler.ts`, `newFacet` in `analysis-notes.ts`), with a cap on the passes; a new budget or settle rule there adds a case to `tests/workflow-scenario-analysis-late-inconsistency.test.ts`, which also asserts the cap still asks (#1830).
- A forecast floor ("forecast at no less than N times a measured rate") takes the lowest measured rate for its low end, never a quantile of the rates: a quantile is a typical value, and a whole project cheaper than it falls below every range (R54 lanewalk, #1806). The left side of a before/after pair in a Then (`"0.1.0" -> "0.2.0"`, `from A to B`, `A becomes B`) is the state before the change, not a case; its phrasings are data (`BEFORE_AFTER_PHRASINGS` in `src/core/verification/criteria-cases.ts`), and a new phrasing gets a case per language in `tests/workflow-scenario-case-walk-before-after.test.ts`, which fails when one lacks it (#2000).
- A JSON schema BAKED sends as a provider's structured output in strict mode (the `codex exec` `--output-schema`) builds its objects with `strictObject` (`src/core/llm/providers/codex/runner.ts`): `additionalProperties: false` and `required` listing every property, `required: []` for an object with none. `tests/codex-strict-schema.test.ts` walks every such schema, with and without tools, and fails on an object strict mode refuses; a new schema joins that walk (#1889).
- Provider names in runtime code (Claude, OpenAI, Codex, GitHub Copilot, GitHub Models) describe supported integrations. Do not rename them when editing these instructions or other contributor documentation.

## Language

- Write everything in English: code, comments, identifiers, test names, documentation, design documents, audit records and commit messages.
- Workflow artifacts are English too: research, specifications, plans, task titles and descriptions, reviews, findings and summaries. Write them in English even when the request, project files or answers use another language; translate the meaning and keep identifiers, paths, commands and quoted source text unchanged.
- Tests that need non-ASCII text use Unicode escapes or non-Cyrillic scripts.

## Verification

CI runs these on every pull request to `main`; run them before merging:

```sh
bun run lint
bun run typecheck
bun run test
bun run build
```

`bun run typecheck` runs `bun check`, which needs Bun 1.4.3 or newer; on an older Bun use `bun run typecheck:tsc`. While iterating, `bun test tests/<feature>.test.ts` runs one feature's tests. The suite is hermetic: tests must not depend on the developer's home directory, global hooks or configuration, or provider environment variables such as `ANTHROPIC_BASE_URL`. Point home-dependent code at a temporary profile instead of skipping the test. Documentation-only changes need link, path, and configuration checks rather than new unit tests; `bun test tests/docs.test.ts` checks the links in `docs/` and the slash command list in `docs/commands.md`. Report what was checked and any failures that remain.
