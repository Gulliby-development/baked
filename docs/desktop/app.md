# Desktop app

Date: 2026-10-10. Technical design. Status: proposed; implementation starts with the scaffold while this document is open for review.

Sources: the desktop mockups in Claude Design (15 screens), the multi-project analysis of 2026-10-10 (one `baked serve` per project), the local API in `src/core/api/server.ts`, projects-lite ([projects](../projects.md)) and the known-projects list (`src/core/projects/known.ts`).

## Goal

A desktop app for BAKED, like the desktop apps of Claude and Codex, over the same core as the terminal UI and the headless CLI:

- Several projects open side by side. Each project is a folder with its own sessions, workflow runs, memory and settings; runs in background projects keep going.
- Chat with the agent is the main screen of a project.
- Everything that waits for a person (approvals, clarifications, delivery plans, tool approvals in chat) is collected in one "Needs you" list and raised as a system notification.
- Workflow runs, initiatives, acceptance and usage are readable and actionable without a terminal.
- Project setup (gates, instructions, working set) is visible inside the project, separate from app settings and from settings shared by all projects.

## Non-goals

- Several projects inside one backend process. `getCwd()` and the intelligence singletons make that a large refactor (see the multi-project analysis); the desktop runs one backend per project instead.
- A second agent implementation. The app never runs models, tools or workflows itself; it renders the core's durable state and sends the person's decisions back.
- Remote or multi-user access. The backend stays on 127.0.0.1 with a per-start token.
- Publishing to npm or an app store. Builds ship as GitHub release assets like the CLI.

## Shell: Electron

The default is **Electron** with a React renderer built by Vite.

| | Electron | Tauri | Electrobun |
| --- | --- | --- | --- |
| Renderer | Chromium, identical on every OS | system WebView (WebView2, WKWebView, WebKitGTK) | system WebView or bundled CEF |
| Main process | Node.js | Rust | Bun |
| Toolchain in CI | Node/Bun only | Rust plus per-OS WebView dependencies | Bun, young project |
| Installer size | about 100 MB plus the `baked` binary | about 10 MB plus the binary | small |
| UI testing | Playwright drives Electron (`_electron.launch`) | WebDriver only | none established |
| Used by | Claude desktop, Codex desktop, VS Code | | |

Reasons for Electron:

1. One rendering engine on Windows, macOS and Linux. The mockups rely on CSS that differs between WebKitGTK and Chromium, and Linux WebKitGTK is the most common source of Tauri bugs.
2. Playwright, already the browser driver of the AI acceptance gate, launches and drives Electron apps. BAKED can run acceptance checks against its own desktop app.
3. The main process only supervises child processes and proxies HTTP, which Node does well; no Rust toolchain enters CI.
4. The size cost is accepted: the app bundles the `baked` binary either way.

The main process runs on Electron's Node.js; everything else (install, scripts, tests, builds) uses Bun, as the rest of the repository does.

## Architecture

```
┌──────────────────── Electron app ────────────────────┐
│ renderer (React, sandboxed, no Node)                  │
│   window.baked.request / subscribe  (preload bridge)  │
│                      │ IPC                            │
│ main process                                          │
│   ProjectSupervisor ── one backend per open project   │
│   ApiProxy (token stays here)                         │
│   AttentionHub ── notifications, tray badge           │
│   AppSettings (userData/settings.json)                │
└──────┬───────────────────┬───────────────────────────┘
       │ spawn, HTTP       │ spawn, HTTP
  baked serve --cwd A   baked serve --cwd B   …
```

### Main process

- **ProjectSupervisor.** Reads the project list with `baked projects list --json` (no backend needed). Opening a project spawns `baked serve --cwd <folder> --port 0 --token-file <userData>/tokens/<hash>.token`, waits for the one JSON line `{"url","port","tokenFile"}` on stdout, reads the token and checks `GET /v1/health`. A backend that exits unexpectedly is restarted with backoff (1 s, 2 s, 4 s … up to 30 s, five tries, then the project shows "backend stopped" with a Restart button and the last stderr lines). Closing a project or quitting sends SIGTERM (on Windows, `taskkill /T` after a grace period); the backend pauses its active drives and resumes them on the next start, as the CLI does today.
- **Backend binary.** Packaged builds bundle the `baked` binary for their platform under `resources/bin/`. In development the app runs `bun <repo>/src/boot.tsx serve`. App settings can point to another `baked` (for example one on PATH).
- **VoiceEngine.** Local speech-to-text for voice input (#419), in `src/main/voice.ts`. It runs the Whistle model of [cactus-needle](https://github.com/afshinm/cactus-needle) (WebAssembly, English, German, French, Spanish, Italian, Dutch, Polish) in the package's own worker thread and never uses the network. The bridge's `voiceStatus()` says whether it can run and why not; `transcribe(samples, language?)` takes up to 30 seconds of 16 kHz mono samples and loads the model on first use. Packaged builds carry the package and the model under `resources/voice/`; a source run reads `apps/desktop/dist/.stage/voice/`, filled by `bun run stage:voice` (`bun run dev` runs it on start when nothing is staged yet; without network access the app still starts with voice input off), and `BAKED_VOICE_DIR` points either at another copy. When the engine or the model is missing, the microphone button is disabled and its tooltip says why and what fixes it: staging it in a source run, reinstalling a packaged app.
- **ApiProxy.** The renderer never sees a URL or a token. It calls `request(projectPath, method, path, body)` and `subscribe(projectPath, path, lastEventId)`; main checks that the path starts with `/v1/` and the method is GET or POST, adds the bearer token and forwards the call. Server-Sent Events are parsed in main and forwarded as IPC messages; main reconnects with `Last-Event-ID` after a backend restart, so a renderer subscription survives one. Because main's `fetch` sends no `Origin`, `baked serve` needs no `--allow-origin` and no CORS change.
- **AttentionHub.** Subscribes to `GET /v1/attention` of every running backend, merges the lists into "Needs you", raises a system notification for each new blocking item (advisory items only when the user opted in; on Windows under the app's own user model ID `dev.baked.desktop`, the installer's `appId`), and sets the dock or taskbar badge: the count of blocking items on macOS and on Linux desktops with Unity launcher badges (`app.setBadgeCount`), and on Windows an overlay icon on the taskbar button (an orange disc with the count, `9+` above nine) that clears when nothing blocks.
- **AppSettings.** Settings of this app only (theme, density, language, notifications, tray, which `baked` to run, open projects and window state, voice input and its language) in `<userData>/settings.json`. Agents and runs never read it.
- **Tray.** When "Keep runs going in the tray" is on, closing the window keeps backends with active runs alive; quitting from the tray stops them.

### Renderer

- React 19, Vite, TypeScript strict. Colours come from design tokens in `src/renderer/styles/tokens.css` (the dark TUI palette: `#191410` ground, `#ff9d52` accent; IBM Plex Sans and Plex Mono, bundled as files so the app works offline). A light theme follows the TUI's light tokens.
- Visual style: neobrutalism. Controls and panels have a 2px ink outline (`--ink`) and a hard offset shadow (`--shadow`, `--shadow-sm`); a button moves into its shadow on hover. Native checkboxes and selects get the same outline (`base.css`): a ticked box fills with the accent, and a select draws its own chevron (`--chevron` per theme) centred on the line of its text, and the select, its options and its picker use the app font (IBM Plex Sans) rather than the system one. Where Chromium supports a customizable select (`appearance: base-select`), its option list is drawn in the same style and the hovered or focused option takes the accent fill instead of the platform blue. Scrollbars are an ink-outlined block thumb without arrow buttons that fills with the accent on hover. The window itself never scrolls: screens scroll inside `<main>`, which is the positioning context for visually hidden labels so they cannot stretch the page. Status colours appear as colour blocks (`--fill-accent`, `--fill-ok`, `--fill-warn`, `--fill-err`, `--fill-info`) that always carry `--on-fill` text, so they read in both themes.
- Components: [shadcn/ui](https://ui.shadcn.com) on [Base UI](https://base-ui.com) primitives, styled after [neobrutalism.dev](https://www.neobrutalism.dev) (MIT). They live in `src/renderer/components/ui/` and are styled with Tailwind CSS v4; `components.json` lets the shadcn CLI add more. `src/renderer/styles/index.css` is the stylesheet entry: it maps the kit's token names (`main`, `background`, `border`, `shadow`, …) onto BAKED's tokens and loads Tailwind without its preflight. Every screen is built from these components and Tailwind utilities; there are no per-screen stylesheets. Besides the kit, `components/ui/` holds the app's own building blocks (`Alert` for notices, `Empty` for placeholders, `SegmentGroup`/`Segment` for joined toggles, `Dot` for status dots, `Dialog` for editing in a popup, `Tooltip` and `Hint` (a small **?** that explains a term), `TitleTooltips`, mounted once in `App`, which shows every plain `title` attribute as the same styled tooltip instead of the system's native one (the attribute is set aside only while the element is hovered), and the compact `primary`/`secondary` button variants with size `md`), and `src/renderer/lib/styles.ts` holds shared class strings for layout and text patterns (`PAGE`, `LABEL`, `PANEL`, `TABLE`, …); combine them with `cn` so a screen's own utilities win. `styles/base.css` keeps only element defaults (page font and colours, links, focus outline, native text inputs, selects, checkboxes and scrollbars) in a `base` layer below the utilities.
- Routing by URL hash: `#/projects`, `#/attention`, `#/p/<projectKey>/{overview,chat/<sessionId>,runs/<runId>,initiatives,usage,setup/{gates,instructions,working-set}}`, `#/settings/{app,providers,routing,commands,notifications,telemetry}` and `#/settings/chat/<page>` (the older `#/settings/global` opens Providers and keys). `projectKey` is a short hash of the folder path.
- Data access goes through one typed `BakedClient` interface. Two implementations: `IpcClient` (the real one) and `MockClient` (fixtures plus a scripted chat stream). The renderer runs in a plain browser against `MockClient` (`bun run dev:web`), so screens can be built and reviewed before the chat API lands.
- Screen data is cached in the renderer (`src/renderer/client/cache.ts`, read with `useQuery` from `src/renderer/lib/query.ts`), keyed by project and request, for as long as the window is open. A screen opened again shows its last answer at once and fetches again in the background when that answer is older than 30 seconds (the project home's run list and the Needs you details on every visit); placeholder bars (`Skeleton`) appear only when nothing is cached for the project. A refresh that fails keeps the cached data. Any write to a project (`POST`, `PUT`, `PATCH`, `DELETE` through the client) marks that project's cached answers stale: the screen that wrote shows the returned view, and every other screen refreshes when it is next shown or when the window regains focus. Screens that read the same request (the project summary on the home and Working set, the config on Gates and Settings, the model list) share one entry, so a change saved on one shows on the other. The model list (`GET /v1/models`) is fetched in the background as soon as a project's backend runs and counts as fresh for 5 minutes, so the chat composer's model and effort menus open on the cached list at once; setting or removing a key, signing a provider out, and a sign-in that finishes make the model list stale in every open project, because keys and sign-ins are the user's, not one project's, and a list a screen shows is fetched again at once. The Doctor card on the project home says when its report was made (**Updated 12s ago**) and has **Refresh** to run the checks again.
- Waits: a short read from the backend shows `Skeleton` bars. A real wait shows `Busy` (`components/ui/busy.tsx`): the terminal's pixel bun (`src/core/utils/bake-art.ts`, drawn as SVG by `components/ui/bun.tsx`) with what is happening, and a bar with the count when the backend counts it ([`GET /v1/progress`](api.md#progress)). Without a count the bun kneads; with one it proofs, rising and browning as the work advances. It appears while a project's backend starts or restarts, while the Code graph waits for the index ("Indexing files", "412 / 1,380 files"; a graph already drawn shows the count in its "Refreshing the index" chip), and while New run or Quick task starts a run. With reduced motion the bun stands still and only the bar moves.
- Security: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, a strict Content-Security-Policy (no remote scripts, no `eval`), navigation and new windows blocked, external links opened by main only for `https:` URLs.

The app uses the existing endpoints as they are:

`MockClient` follows that contract. Screens whose endpoints a backend does not have yet (an older `baked`) show "needs a newer BAKED" instead of failing.

## Repository layout and builds

```
apps/desktop/
  package.json, bun.lock, bunfig.toml, tsconfig.json, biome.json
  electron-builder.yml
  src/main/        supervisor, proxy, attention hub, settings, tray
  src/preload/     the contextBridge API
  src/renderer/    React app, screens, styles, MockClient
  src/shared/      types shared by main and renderer (BakedClient, IPC channels)
  tests/           bun:test for main-process logic and the client
  e2e/             Playwright UI tests of the renderer against the mock bridge
  e2e/electron/    Playwright tests of the built Electron app against a fake baked
```

- `apps/desktop` is its own package with its own lockfile, so `bun install` at the root does not download Electron. The root's lint, typecheck and tests keep their scope (`src/`, `tests/`); the desktop has the same checks under `apps/desktop`.
- CI: a `desktop` job in `ci.yml` runs `bun install --frozen-lockfile`, lint, typecheck, tests and the renderer and main builds in `apps/desktop` on Linux, then the UI tests (`bun run e2e`): the built renderer served statically and driven in Google Chrome by Playwright against the mock bridge, with a fixed clock. Then the Electron UI tests (`bun run e2e:electron` under `xvfb-run`): the built app launched by Playwright against a fake `baked` (`tests/fixtures/fake-serve.ts`) in a throwaway home, covering IPC, the bearer token, backend crash and restart, project open and close, and attention streams that reconnect with `Last-Event-ID`. One scenario runs the real `baked serve` from source with a scripted model and drives a chat turn with streaming text, tool cards and an outside-the-project write approved in the UI.
- Voice engine: `bun run stage:voice` copies cactus-needle into `dist/.stage/voice/` with the Whistle model, downloaded once from Hugging Face into `apps/desktop/.cache/voice/` (or taken from `--model <file>`) and checked against the size and SHA-256 pinned in the package. The `desktop` CI job stages it and transcribes silence with it (`scripts/voice-check.ts`); `bun run package` stages it before electron-builder. Unit and Electron UI tests use the real package with a placeholder model, so they need no download.
- Scripted model (test only): when the `BAKED_TEST_SCRIPT` environment variable names a JSON file, `baked serve` answers chat turns from that file instead of calling a model (`src/core/chat/scripted-host.ts`: text, reasoning, tool calls with optional outside-cwd or destructive approvals). Only the environment variable turns it on; no config file can. A failed run uploads the Playwright reports and traces as the `desktop-ui-report` artifact.
- Mock scenarios: the mock bridge reads `?mock=NAME` from the page URL: `default`, `empty` (no projects), `start-failure` (opening a project fails, Restart recovers), `older` (a backend without the optional capabilities) `uninitialized` (one open project without `baked/project.json`), `mic-denied` (the system refuses the microphone) and `no-voice` (the speech engine is not installed). `bun run dev:web` takes the same parameter, for example `http://localhost:5199/?mock=empty#/projects`.
- Packaging: `builds.yml` gets a desktop job per platform that takes the `baked` binary its bundle job built and runs electron-builder: NSIS installer for Windows x64 and arm64, DMG and ZIP for macOS arm64 and x64, AppImage and DEB for Linux x64. Like the CLI bundles, Windows and macOS run when packaging files change, nightly and for releases. After packaging, `scripts/smoke.ts` starts the unpacked app on linux-x64, windows-x64 and darwin-arm64 under a throwaway home and checks that All projects lists a folder registered with the bundled `baked` and that the bundled speech engine transcribes a second of silence. The release workflow uploads the installers as release assets.
- Code signing and notarization need certificates only gulliby can provide (an Apple Developer ID and a Windows code signing certificate). Until then builds are unsigned: macOS asks to allow the app in Privacy & Security, Windows SmartScreen warns.
- Updates: the repository is private, so the app checks GitHub releases only when a token is configured and otherwise shows its version with a link. Automatic updates come with signing.
