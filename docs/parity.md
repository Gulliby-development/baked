# Feature parity across surfaces

BAKED ships each major feature on every surface: the terminal UI, the headless CLI, the `baked serve` local API and the desktop app (see [AGENTS.md](../AGENTS.md)). The TUI and the desktop are the main surfaces and must match; a desktop gap is closed in the API and the desktop together; the headless CLI gets what scripts and CI need.

## The feature registry

`src/core/features/registry.ts` lists every user-facing feature and how each surface reaches it:

- **TUI**: a slash command from `src/core/commands/registry.ts`, or `key <keys>` for a key binding.
- **Headless CLI**: `baked <command...>` or a `--flag`.
- **serve API**: a `/v1` path template with `:id` for parameters, without the method.
- **Desktop**: a screen from `apps/desktop/src/renderer/router.ts`: `projects`, `attention`, `project/<section>` or `settings/<section>`.

A reach can carry a note after `: ` (`project/chat: model picker`). A surface without the feature says why instead:

| Entry | Meaning |
| --- | --- |
| `gap(issue, note?)` | The surface should have it and does not yet; the issue tracks it |
| `partial(reach, issue, note)` | The surface has part of it; the issue tracks the rest |
| `notNeeded(reason)` | The surface does not need it, for example a setting scripts write to `config.json` |
| `terminalOnly(reason)` | A terminal workflow by design, such as tabs and file claims |
| `desktopOnly(reason)` | A desktop feature by decision, such as voice input in chat |

## The parity test

`tests/feature-parity.test.ts` reads each surface from the source and fails when:

- a TUI slash command, a `/v1` route served by `src/core/api` or a desktop screen is not in the registry;
- a registry entry names a command, route, screen or CLI word that does not exist;
- a surface has an empty reach, a gap without an issue or an exemption without a reason;
- a feature has a desktop screen while its API entry is a gap (the desktop reaches the core only through the API);
- the tables below no longer match the registry.

When you add a feature, add its entry with every surface filled in the same branch. When a surface cannot ship in that branch, open an issue and enter it as a `gap`; when a later branch closes the gap, replace the `gap` with the reach. Then regenerate the tables:

```sh
bun run parity:docs
bun test tests/feature-parity.test.ts
```
