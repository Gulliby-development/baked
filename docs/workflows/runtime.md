# SDD runtime: running and operations

The runtime is available through `baked workflow` and `/workflow` in the TUI. It is on by default in every project. Bun is required; SQLite and the existing BAKED providers are used. No separate server or daemon is needed; `baked serve` optionally exposes the same commands to local clients ([Local API](#local-api-baked-serve)).

## Enabling

Workflows need no setup: without a `workflows` block a run uses the default policy below with no checks, and `enabled` defaults to `true`. Select a configured BAKED model; `defaultModel: "none"` does not allow starting a workflow. To change the policy, add `workflows` to `.baked/config.json` (or the global config) and keep the other settings; to turn workflows off, set `"enabled": false`. The full example is below; `policy` is required in a `workflows` block and unknown fields are rejected.

Default checks are not written for you. A check is a command that runs as a trusted gate, so commands taken from a cloned repository's `package.json` become checks only after someone adds them in the gates window (G in `/workflow`), the desktop's Gates and checks screen, a chat ([below](#gates-from-chat)) or `.baked/config.json`. Gates in the repository's `baked/gates` still need the first-use confirmation.

```json
{
  "workflows": {
    "enabled": true,
    "importsEnabled": false,
    "defaultWorkflow": "sdd",
    "policy": {
      "maxConcurrentReadAgents": 3,
      "maxConcurrentWriters": 1,
      "maxAgentSteps": 24,
      "maxAgentCalls": 80,
      "maxTotalTokens": 800000,
      "maxActiveMs": 3600000,
      "maxCostUsd": null,
      "maxRepairRounds": 2,
      "maxConvergenceRounds": 2,
      "maxCorrectiveTasks": 20,
      "scopeApproval": "required",
      "reviewProfiles": { "correctness": "reviewer", "security": "security-reviewer", "language": null },
      "skepticProfileId": "skeptic",
      "forceSecurityReview": false,
      "allowedTools": ["read", "bake_find", "bake_impact", "navigate", "edit_file", "multi_edit", "delete_file", "request_check", "submit_result", "submit_artifact", "submit_review"],
      "network": "deny",
      "checks": [
        { "id": "typecheck", "executable": "bun", "args": ["run", "typecheck"], "cwd": ".", "timeoutMs": 120000, "required": true, "scope": "feature", "envNames": [], "writes": [] },
        { "id": "lint", "executable": "bun", "args": ["run", "lint"], "cwd": ".", "timeoutMs": 120000, "required": true, "scope": "feature", "envNames": [], "writes": [] },
        { "id": "tests", "executable": "bun", "args": ["test"], "cwd": ".", "timeoutMs": 600000, "required": true, "scope": "feature", "envNames": [], "writes": [] }
      ]
    }
  }
}
```

Check definitions contain an executable and argv. They run reviewed project code. With the policy's `sandbox` (or the `sandbox` setting, or `--sandbox`) they run in an OS sandbox: see [Sandbox](#sandbox) below and [OS sandbox](../sandbox.md); without it they run unsandboxed. `envNames` allows specific additional variables on top of `buildSafeEnv`; values are not stored in definitions. `writes` marks only generated outputs. An optional `fix` (`{"executable": "ruff", "args": ["check", "--fix"]}`) names the fixer for what the check reports; an implementer runs it with `apply_fix` on each file its task writes (the path is appended to the arguments; the whole-project formatters take it in their own form: `cargo fmt -- <file>`, `gofmt -w <file>` for a `go fmt` fixer, and `dotnet format ... --include <file>`), each run recorded like an edit, and gets the check's result back. A whole-project formatter (`cargo fmt` formats the whole crate) may rewrite files of other tasks too: the runtime keeps a copy of every file outside the fixer's scope before it runs and puts back those it changed (removing a file it created), and the result lists them as `reverted`, so a fixer never leaves another task's file edited in the worktree; the put-back also runs when a fixer run fails partway. A change it cannot put back fails the call. `cargo fmt`, which formats the whole package whatever file it is given, runs once per call for all of the task's code files (`cargo fmt -- <file> <file>`), each still recorded as an edit; documentation and data files the task writes are not passed to it. When a required check with a fixer fails at a check stage, the runtime first runs the fixer itself on every existing file the run's tasks write, before any repair task: each run is a journaled `file_patch` effect (`tool: apply_fix`, with the check ID, the task that writes the file last, and the pre-image), so `workflow undo` treats it like that task's own edits. If a file changed, the runtime takes a new snapshot and reruns the stage's checks once; only the failures that remain become repair tasks, so a run whose only failure is fully auto-fixable passes without a repair attempt. Files outside the run's tasks that a fixer changed are put back the same way; one it cannot put back stops the run. Static feature checks cover the code tasks too: when a plan is accepted, every task that writes a source file (any code extension, not documentation) gets the feature-scope checks that analyze source without running it, meaning a check with a `fix` or one that runs a linter, formatter or type checker, added to its `checkIds` beside the planner's own (a test suite is not added). Checks that analyze a whole compilation unit (`clippy`, `cargo check`, `cargo fmt`, `rustfmt`, `go vet`, `tsc`, a `typecheck` script, `mypy`, `pyright`) are not added either: in a task's own worktree they fail until the sibling tasks' files exist (`cargo fmt` follows every `mod x;` and fails on a module file a later task writes), so they run in the checks stage after integration (other formatters and file-local linters such as `gofmt`, `ruff` and `biome` stay per task; `apply_fix` still runs the `cargo fmt` fixer on a task's files). A task may still name such a check (planners list `cargo fmt` and clippy on every task of a Rust plan) and run it with `request_check`; when it fails, the result adds `taskErrors`, the errors located in the task's own files that neither the baseline nor a pending sibling task explains, and a note that the check runs in the checks stage, so the implementer does not chase errors about modules later tasks write. A task that writes a module index (`lib.rs`, `main.rs`, `mod.rs`, `__init__.py`, `index.ts` and its variants) gets a dependency on the tasks that create module files beside it (or a child directory's index), unless that would close a cycle, so a crate's `pub mod parse;` is checked after `parse.rs` exists. Likewise a task gets a dependency on every task that writes a file it names in `readHints` (not one it writes itself), unless that would close a cycle, so a component that imports a sibling task's module runs after it instead of in the same wave. A task that writes only documentation (a licence, notice or authors file beside it still counts) and whose title, description or read hints ask to run the program or show its output (run the CLI, capture output, a worked example, sample output), or one of whose criteria or requirements asks for an example block or for output copied, captured or shown from the program, gets a dependency on every task that writes an entry point (`main`, `cli`, `app`, `server`, `program`, a Python `__main__.py`, or a script under `bin/`), unless that would close a cycle, so a README with captured command output runs after the command exists. Such a documentation task is never a prerequisite of code or tests: a planner edge from a task that writes code or tests to it is dropped first, so a plan that put the package after its README (the code task depending on the documentation task) gets the edge the right way round instead of running the README first. A task that reads a file the documentation task writes (in its `readHints` or `reference`), such as a test of the README's examples that reads `README.md`, keeps its edge to it: it can only pass after the README exists. A task that creates an entry point (`main`, `cli`, `app`, `server` or `program` in any source language, such as `Cli.java` or `cli.ts`) while later tasks create code in the same language is a plan problem the planner fixes before submitting, unless a task that runs after that code writes the entry point or another file the entry task created (a registry or handler it imports): otherwise nothing wires the new code into the shipped command and the first review finds it. A task that writes code or tests may name a `reference`: an existing file of the project (or one an earlier task creates) whose structure, naming, error handling and test style the new code should follow. The planner picks it with `bake_find`; a reference that does not exist and that no earlier task creates is a plan problem the planner fixes before submitting. A task waits for the task that writes its reference, as for a read hint. The implementer reads the reference first and follows it unless the spec asks otherwise, and the correctness review receives `references` (each changed file mapped to its task's reference) and may report a file that departs from its reference as an `inferred` finding, which is a note and starts no correction. A task whose `profileId` is not an implementation profile (a planner that wrote its own role, or an unknown ID) gets the default implementer, `implementer` or else the first implementation profile, instead of the whole plan being rejected. The runtime runs them after the task like its task-scope checks, so a lint error blocks and is corrected in the task that wrote the file, and before they are evaluated it runs the fixers of those checks on the code files the task wrote, each run a journaled `file_patch` effect like the run-level pass, so what a tool fixes mechanically never fails the task. That pass covers code files only; when a required task check with a `fix` still fails after the task's checks ran (for example on a documentation or data file, or in a task that changed nothing the pass could see), the runtime runs that fixer once on every file the task writes, takes a new snapshot and reruns only that check before the failure becomes a finding and a repair task. The fixer runs are journaled `apply_fix` effects like the others, in the run worktree for several writers and in the run root otherwise. An optional `fixUnsafe` beside `fix` (for example `{"executable": "biome", "args": ["check", "--write", "--unsafe"]}`, limited to the rules the project allows in its own tool configuration) is a second tier: every fixer pass above and `apply_fix` run it after `fix` on the same files, each run journaled the same way, so only what neither tier fixes reaches the implementer or a repair task. Without `fix` it is ignored. A command gate carries the same optional `fix` and `fixUnsafe` in `command`; a policy check keeps it when a v2 definition binds it as a gate. The suggested `ruff` check comes with `ruff check --fix`. Task sources, the execution configuration and the internal database must not be excluded from a check. `network: deny` forbids network agent tools and, in a sandboxed run, the network of check, fixer, repro and probe processes (only `allow` grants it; `ask` cannot prompt from inside a process). Without the sandbox it does not isolate the executed project script, and it never forbids calls to the selected LLM provider.

A required check whose executable cannot be started stops the run at once. At start (with the native executor), before any model call, every declared check is started once: a bare command name must resolve on the PATH the check runs with, and then the command is spawned the way the run will spawn it (same executable, arguments, environment and Windows batch handling) in an empty scratch directory and stopped as soon as it started, so only whether it starts is judged and nothing it does reaches the workspace. A required check that is not on its PATH or cannot be spawned (`EINVAL`, `EACCES`, a refused `cmd.exe` line) refuses the start (`CAPABILITY_DENIED`, `reason: check_unavailable`, naming each check, executable and error); an advisory one becomes a routing warning. Checks named by a path that does not exist yet (`./gradlew`) may be generated by a task and are not probed, nor is `bun`, the running binary. For a run with checks the result is recorded as its `preflight/checks.json` artifact (`{checks: [{checkId, executable, required, status, detail?}]}`, `status` one of `started`, `not_found`, `cannot_start`, `not_probed`) and returned as `preflight` by `workflow status` and the run view; the desktop run screen lists the advisory checks that could not start. During the run, the first `spawn_error` result of a required check (the executable is missing or cannot be spawned, for example `spawn mvn.cmd EINVAL`) blocks the run with reason `check_unavailable`, the executable and the command in the message, instead of being treated as an inconclusive result the task works around; install the tool or fix the check, then resume.

A monetary cap is currently rejected: the current BAKED provider metadata has no verified shared source of exact prices. Use token/time/call limits; usage left unknown by a crash keeps its reservation. Arbitrary command hooks and compound effects are forbidden inside a workflow; MCP tools run only where a profile and the policy grant them (see [MCP tools](#mcp-tools)). Approved commands run as checks. The ECC import does not enable hooks.

### MCP tools

Workflow agents get no MCP tool by default: the built-in profiles and the default policy grant none. A tool is offered to an agent only when both its profile's `allowedTools` and the policy's `allowedTools` grant it, the same two lists that bound the built-in tools. A grant names one tool as the chat sees it, `mcp__SERVER__TOOL`, or every tool of a server, `mcp__SERVER__*`, with the server's name as in `mcpServers` ([MCP servers](../extensions.md#mcp-servers)), characters other than letters, digits, `_` and `-` replaced by `_`. For example, a project profile `baked/agents/docs-researcher.json` with `"allowedTools": ["read", "navigate", "mcp__docs__search", "submit_result"]` and a policy with `"mcp__docs__*"` in its `allowedTools` offer the researcher only `search` of the `docs` server.

- The policy is part of what a person approves, so its grants are approved with the plan. Auto approval treats an MCP grant like any other tool: a renewal refuses a policy that adds one, and `mcp__docs__*` counts as a new grant next to an approved `mcp__docs__search`.
- Any agent role may grant MCP tools in its profile; the acceptance roles (`acceptance-walker`, `acceptance-writer`) run on their host tools only, and their profiles refuse MCP grants. A grant that is not of the form above refuses the profile.
- An attempt connects only the servers that both lists name, when it starts, and reuses a server that the chat or another attempt already connected. A server that is disabled or fails to connect gives the agent none of its tools; `workflow doctor` warns about a profile grant that no enabled server provides.
- Every call passes the same guard as the built-in tools: the run must be executing and both lists must grant the exact tool. Its input and result are recorded as read evidence of the attempt, so a result can cite them. The runtime does not know what an MCP tool changes: it is not journaled as a file edit, `workflow undo` does not revert it, and its arguments are passed to the server as given. Grant only tools whose effects you accept for an unattended run. `network: deny` does not stop an MCP server from using the network.

## First run

From source, the command runs through `bun run src/boot.tsx workflow`; after a build, through `bun run dist/index.js workflow`. The installed launcher uses `baked workflow`.

```sh
baked workflow run --feature status-json --prompt "Add JSON status for a run" --events
baked workflow run sdd --feature status-json --prompt-file request.txt --events
baked workflow status RUN_ID --json
baked workflow list --status completed
baked workflow artifacts RUN_ID
baked workflow artifacts RUN_ID --file ARTIFACT_ID
```

### Proposing the workflow from the request

```sh
baked workflow propose "Fix the typo in the README install section"
baked workflow run --auto-preset --feature readme-typo --prompt "Fix the typo in the README install section"
baked workflow run sdd --auto-preset --feature readme-typo --prompt-file request.txt
```

`baked workflow propose TEXT` (or `--prompt`, `--prompt-file`; `--json` for the whole proposal) prints the workflow and budget a run would take for the request, with the reason. `run --auto-preset` runs that proposal when no workflow is named, and prints it on stderr. The rules read the request text only, with no model call (`src/core/workflows/preset-router.ts`), in this order:

| Request | Workflow | Budget |
| --- | --- | --- |
| A review or audit of existing changes (diff, pull request, branch, commits) and no change verb | `review-only` | standard |
| Research (investigate, explore, evaluate, compare, "how could we") and no change verb | `spike` | standard |
| A check, test, build or CI that fails, is red or broken | `fix-ci` | standard |
| Docs only (README, docs, changelog, typo, comments) that names no code (API, command, flag, screen) and is at most 80 words | `quick` | quick |
| A small change (rename, bump, tweak, label, message) of at most 30 words | `quick` | quick |
| A large change (redesign, rewrite, migration, new service or module, several or multiple parts) or 150 words and more | the project default | extended |
| Anything else | the project default | standard |

Only a workflow that can start in this project is proposed: a preset with validation problems (for example `quick` or `fix-ci` without a feature check) falls back to `workflows.defaultWorkflow` (default `sdd`) with medium confidence and says so. A workflow named on the command line wins over the proposal, and `--budget` wins over the proposed budget; the proposed budget applies only when the proposed workflow runs. The run records the proposal in its state (`presetChoice`: `proposed`, `chosen`, `overridden`, `budget`, `kind`, `confidence`, `reason`), and the [run report](#run-report) says what was proposed and whether the person chose another workflow. The TUI new-run form and the desktop New run screen preselect the proposal while you type the request and show the reason under the workflow; picking another workflow or budget keeps your choice, and the run records both. A request taken from a GitHub issue is not proposed in the forms; `run --issue --auto-preset` reads the issue's text.

### Starting from a GitHub issue

```sh
baked workflow run --issue https://github.com/OWNER/NAME/issues/12 --events
baked workflow run standard --issue OWNER/NAME#12 --prompt "Keep the text output as it is"
baked workflow run --issue '#12' --feature json-status
```

`--issue` takes the request from a GitHub issue: an issue URL, `OWNER/NAME#N`, or `#N` (or `N`) for the repository of the `origin` remote. The run's prompt is the issue title with its repository and number, the body without HTML comments (issue template hints; clipped after 20,000 characters with a link to the rest), the `--prompt` or `--prompt-file` text under "Additional instructions" when one is given, and the issue URL. Comments on the issue are not read. The feature ID is `issue-N-` followed by the slug of the title (at most 64 characters), so reruns of the same issue are listed under one feature; `--feature` names another. The run stores the issue (repository, number, URL, title) in its state, and the pull request its [delivery](#delivery) creates opens with `Closes #N`, or `Closes OWNER/NAME#N` when the pull request goes to another repository, so merging it closes the issue and moves it to Done on a project board that tracks closed issues. A delivery with `--no-pr` closes nothing.

The issue is read once, at start, through the GitHub REST API at `workflows.delivery.apiUrl` (an issue URL must be on that host). The token from `workflows.delivery.tokenEnv` (default `GITHUB_TOKEN`) is sent when it is set, so private repositories work; public issues are read without one. The start is refused with `details.reason` `invalid_issue` for a reference that is not an issue (another host, a pull request, `#N` without a GitHub `origin`) and `issue_unreachable` when GitHub cannot be reached or answers with an error; a 401, 403 or 404 names the token variable to set or check. The same start is available in the TUI new-run form (GitHub issue field), the desktop New run screen (GitHub issue field) and `issue` in `POST /v1/workflow/runs`.

`baked workflow list` accepts `--status STATUS` to show only runs in that status. Supported values are `created`, `running`, `waiting`, `paused`, `blocked`, `completed`, `failed`, and `cancelled`. Combine it with `--feature`, `--limit`, and `--cursor` to further filter or paginate the results.

The process runs research → specify → plan → analyze and stores an approval request. All artifacts (research, spec, plan, tasks, reviews, findings) are written in English even when the request is in another language. The spec author validates its spec when it submits it: a requirement without a criterion, an engineering requirement whose criteria are all post-release, a criterion naming an unknown requirement and duplicate IDs return to it in the same conversation (two corrections), because only the spec author can add or relink criteria. The spec also lists the request's deliverables (see [request coverage](#request-coverage)). Three criterion problems return the same way: a manual criterion about a file of the repository or a property of its code, such as "input is read line by line" when "a reviewer inspects it" (it becomes automated, a test or the reviewer reading the file or code), and an automated criterion that claims behavior on several operating systems, browsers or real devices ("confirmed on Windows, macOS and Linux", "cross-platform", "on a real device"). The third is an automated criterion that needs a build ("the production build succeeds", `cargo build`, `mvn package`) when no check of the run's `executionContract.checks` builds the project: convergence proves criteria only with those checks, so the spec author rewrites it as what the checks prove or a file the reviewer reads, or marks it post-release. A run checks on one host, so no check can prove such a claim and convergence could only answer `inconclusive`. The spec author rewrites it as what this host can check (platform-neutral APIs, the tests pass here) and, when the request asks for proof on other platforms, adds a criterion that a CI workflow file runs the checks on a matrix of them, which the reviewer verifies by reading the file. A criterion that names a CI matrix or a simulated platform (`path.win32`, a mock, an emulator) is not sent back. If the author keeps such a criterion after the two corrections, the spec is accepted, and convergence records the criterion as a known limitation (see below). Every later stage reads the whole spec, so its size is checked against the request ([spec-size](../../src/core/workflows/spec-size.ts)): the host passes the spec author `extra.specSize`, which asks for one criterion per behavior group (inputs that exercise the same behavior go into one criterion as a table in its `then`) and names the most criteria the request needs, the larger of 12 and twice the examples and items the request lists (list items, table rows below a header, fenced code blocks). A spec with more criteria goes back to the spec author once with that count, before the planner reads it; the author's next submission is accepted whatever its size. The planner validates the package when it submits a result: errors from `validatePackage`, unknown profiles and checks return to it in the same conversation, and it may send a corrected plan twice. Before that validation the host derives each task's `requirementIds` from its criteria (every requirement the task's criteria verify, plus the ids the planner listed that exist in the spec; an unknown id is dropped), so a planner is never sent back for a `criterion mapping mismatch`. If errors remain, the run blocks with these messages and R repeats the stage. Before source files are edited, review `specs/status-json/spec.json`, `spec.md`, `plan.md`, `tasks.json`, `tasks.md`, the policy and the pending request. Canonical JSON is also stored in immutable database artifacts; Markdown is a rendering.

```sh
baked workflow approve RUN_ID --request REQUEST_ID --digest SHA256 --expected-revision N
baked workflow resume RUN_ID --expected-revision NEW_N --events
```

In the terminal, `approve`, `answer` and `evidence` record the decision and then resume and drive the run in the same command, with the exit codes of `resume` (`--events` streams the events as for `resume`); when another request still waits for a person, the run is not resumed and the exit code is 3. `--no-resume` only stores the decision, and `resume` then owns the subsequent execution. The local API keeps recording only: its decision endpoints return after storing the decision and the client calls `resume`. Use the revision from the latest response: it changes after every command. `--command-id ID` allows repeating the same management mutation after a lost response; different content with the same ID is rejected. A start with a previous ID does not create a second run.

When stderr is a terminal, `run`, `quick` and `resume` also print the long waits of the run on it: opening the project, the repository map scan (`Indexing files 412/1,380`, at most one count every two seconds, then each later phase) and starting the run. With `--json` or `--events`, or when stderr is not a terminal, nothing extra is printed, so scripts that read the error JSON on stderr are unaffected.

Automatic execution walks the task graph, the required checks, independent correctness/security/language reviews and convergence for every criterion. High/critical findings go to the skeptic. Every severity starts a correction in the first round; once a repair or convergence round has run, only critical and high review and convergence findings start another, and medium and low ones stay in the review artifact, unless a convergence finding is why a criterion fails: acceptance needs every automated criterion to pass, so that finding is repaired whatever its severity. A policy with `lowFindings: "note"` (in `workflows.policy` of the configuration or a `--policy` file; absent means `repair`) keeps low findings as notes from the first round on: they are listed under "Review notes" in the run report with the reason that they are below the severities the run repairs, and start no correction. A low convergence finding that is why an automated criterion fails, and a low spec-based review finding whose repro the host reproduces, still repair. A low README wording finding cost one bench run 663k tokens and an attempt cap stop before this setting existed. A spec-based review finding with a `repro` also stays repairable after the first round: the runtime runs its repro, and when the repro prints `actual` the finding starts a correction whatever its severity; otherwise it stays a note. The exception is a `partial` convergence finding (test strength or documentation completeness, not a defect in behavior) of low severity, or of medium severity when it is on a test or documentation file, a `missing` finding of low severity, or of medium severity, on a test or documentation file (an absent test or README section), and a low `correctness` or `contradicts` finding (a detail such as a quoting style in an error message or a fixed timeout in a test helper), when every required check passes and each criterion it names has evidence in the review: it passes with notes. A medium finding never passes with notes when a criterion it names has the verdict `fail`: such a finding repairs, so a run does not complete with a failing criterion that the brief orders, such as a README example. It starts no repair, a criterion that fails only because of such findings counts as met, and the finding is listed under "Known limitations" in the [run report](#run-report) (and so in the delivery pull request) as accepted by the notes rule. An automated criterion that convergence reports `inconclusive` with no finding naming it (and no `fail` verdict among the criteria without a finding) is not an invalid output: the evidence it needs comes from an environment the run does not have, such as a claim about other operating systems on a single-host runner. The runtime records it as a known limitation (`unverified-<criterion>`, accepted by the notes rule, with the reviewer's explanation as the claim), counts the criterion as met for acceptance, and lists it in the run report and the run's `limitations` count; the run reaches acceptance instead of blocking with `Coverage is incomplete without an actionable finding`. A criterion that convergence marks `fail` with no finding naming it goes back to the walker inside its attempt, once: it adds a finding for the criterion, or changes the verdict to `pass` or `inconclusive`. A walker that keeps its answer gets a finding from its own explanation (kind `contradicts`, severity high, the explanation as the claim), so the criterion is repaired like any other failing one instead of the run ending `invalid_output` (mdtoc-update 20f81464 blocked there with every check green). The same holds when a stopped convergence is accepted (by a person, the assume rule or the critic): each automated criterion its last review left `inconclusive` that no accepted finding names becomes an `unverified-<criterion>` limitation as well, so acceptance does not fail with `Criterion <id> did not pass` on it. A finding with basis `inferred` (an edge case of a standard or convention the spec does not name, such as an ISO 8601 form when the spec only says ISO 8601) is a note from the first round on: it stays in the review artifact and starts no correction unless it is a security finding or critical, and the review gate passes without it. To make such cases count, the spec lists them: when a requirement names a broad standard or format, the spec author states the forms the feature must accept, with an example of each, and reviewers treat unlisted forms as out of scope. For a criterion that takes open-ended input (numbers, lengths, counts, dates) without naming a range, the spec author states its input domain in the criterion (for example amounts up to 1e9 with two decimals) and that larger inputs are out of scope. A review finding that claims how the code behaves on an input carries a reproducible example (`repro`): a program the run's checks already start, such as `bun`, `node` or `python`, its arguments, and the `expected` and `actual` values the program prints. Reviewers try a repro with the `run_repro` tool before they attach it, and the runtime runs it again before the finding starts a correction. The correctness reviewer also runs every empty, zero or single-element input that a criterion names through `run_repro` and compares the raw value with strict identity (`Object.is` in JavaScript), so a result that only prints like the expected one, such as `-0` for `0`, is caught in review. A finding whose repro does not print `actual` is a note: a refuted claim always, and a repro that cannot run, fails without the value, times out or changes files unless the finding is a security finding or critical. A correctness finding without a repro is a note unless it is critical. A reviewer that submits correctness findings with neither a `repro` nor `noRepro` (a short reason no command can show the claim) is told once, inside `submit_result`, to attach one or give the reason; a second submission without them is accepted. The review's context names `run_repro` and the programs it starts (`extra.reproTool`), and the same one-time advice turns back a `noRepro` that says no tool was available when `run_repro` is offered. The advice is given once per finding across review rounds too: a later round's finding that repeats (`repeatOf`) an earlier finding with a `noRepro` keeps that reason when it has neither a repro nor its own reason, and is not asked again. The run report's findings table has a **Repro** column: the outcome of the finding's repro (`reproduced`, `refuted`, `inconclusive`), `none:` with the reviewer's reason, or `unverified` for a correctness finding with neither. When none of the run's checks starts a program, there is nothing a repro may run and findings block as before. The outcomes are stored in a `repro` artifact of the run. The convergence walker gets `run_repro` and `extra.reproTool` as well, with the same one-time advice, and its findings of medium or low severity pass the same gate: a correctness claim the host does not reproduce (no repro, a `noRepro` reason, or a repro that cannot show the value) and any claim whose repro is refuted starts no correction. Such a finding that fails a criterion is a known limitation of that criterion, accepted by the repro gate in the run report; one that fails none is a review note. High and critical convergence findings, `missing` and other non-correctness findings without a refuted repro, and runs whose checks start no program repair as before. A static medium claim, such as an integer above Python's default 4300-digit conversion limit, cost about 1.1M tokens of corrective tasks before this gate. The convergence outcomes are stored in a `repro` artifact under `convergence/`. Fixes are added to the task graph through a bounded correction chain within the already approved scope. Findings of one round on the same file become one corrective task that carries all their finding IDs, so several failed checks of one task are fixed in one attempt rather than one attempt per check, each reading the same files again. This holds when the findings resolve to different planned tasks, such as a file one task creates and a later task extends with findings under each task's criteria: the task may write what both planned tasks write and carries both sets of criteria, so each finding still needs its own evidence (md-site 23c03a8e spent 239k, 347k and 910k tokens on three tasks for three findings in one file). A finding that names no file joins a task already correcting its planned task. Within a task the findings are listed most severe first. The findings of one failing check run (they cite the same evidence, claim `Required check X failed`) and one profile become one corrective task that may write every file they name, the union of the writes its tasks may use, with the checks of all of them: one run is one failure, and a task per file paid for the same reading again and left later tasks with nothing to change. A corrective task whose attempt changed no file is `implemented` with its checks as the judge: when the checks its findings name and its own task checks all pass on the current files, the task counts as satisfied and the run continues; otherwise it blocks as before. A corrective task whose findings are all failed required checks (`Required check X failed`, or a task's failed required check) runs those checks once before its first attempt, with one writer, when the files changed since the checks failed: when they already pass, because another correction fixed the cause, the task is `implemented` without a worker and the passing runs are kept as `tasks/<id>/already-passing.json`. During the implement stage a finding that already has a corrective task waiting or running (pending, running or interrupted) gets no second one: several test tasks that report one source defect record the same finding again, and each report used to open its own correction. The same holds for a planned task that runs again after a repair invalidated it (generation above 0) and finds nothing to change; a planned task's first run that changes no file still blocks. A rerun task with no such check (a README and licence task, whose project checks are for code) is satisfied when every file it writes still has the content its last implementation left, by the hashes in its `tasks/Tn/diff.json` artifacts; a file changed since still blocks. A check stage that finds a required check passing closes the open findings `Required check X failed` of that check, whatever the other checks report. A finding resolves to the planned task that writes its file and covers one of its criteria; when the plan gave the file to one task and the criterion to others of the same profile, it resolves to the task that writes the file, widened to that criterion, so the correction may also write the files of the tasks that cover it. A correction also gets a planned file its fix needs when another task of the same profile writes it: a file the finding's claim or suggested fix names, and the planned test of a file the correction writes, matched by name (`cli_test.go` for `cli.go`, `test_cli.py`, `cli.test.ts`, `CliTest.java`, or `tests/cli.rs`). A file no planned task writes never joins, so the approved scope still bounds every correction. A failed run-level check whose output names files of the plan (linters and compilers print the paths they reject) becomes one finding per task that writes such a file, on that file, so each is corrected from the task that owns it; output that names no planned file gives one finding for the first task with the check. A failed task check whose output also names planned files the failing task may not write gives its repair task those files when a task of the same profile owns them (the correction joins that task's scope, so one repair can format or fix what the check rejected), and a failure that names only files no task of the profile owns stops the run at once with `no_progress` and `out_of_scope_failure` naming the files, instead of repair attempts that cannot change them. Likewise a corrective task that reports `implemented` with no change while its check still fails only on planned files it may not write stops the run with `no_progress` and `out_of_scope_failure` naming them, with no second attempt; a resume tries it again only after those files or the plan changed. A check that exits nonzero while its output reports every test passing gets a note in its output that something the tests ran left a nonzero exit code, such as `process.exitCode` set by code called in-process. New requirements, checks or file scope require a revision and a new approval. `already_satisfied` requires host evidence and passes the same final checks: evidence of the run snapshot, or reads of the task's worktree as it is when the result is submitted, so a retry may cite reads of the edits an earlier attempt of the task left in place; a read taken before a later edit of the same attempt is stale.

Every review or convergence finding that starts no correction (an `inferred` edge case, a confidence below `reviewMinConfidence`, a severity below the ones the run repairs, an advisory review, or a claim its repro did not show) is also kept in the run state as a review note, listed under "Review notes" in the [run report](#run-report) with its review, why it was not repaired and **Repeats**: a note raised again in a later round on the same kind, file and symbol names the earlier note it repeats, because reviewers renumber and reword a re-raised claim.

Review and convergence results are submitted through a path in which the host fills what it knows. The host sets `snapshotHash` itself and ignores the model's value. Every current evidence entry of the review snapshot has a short handle (`E1`, `E2`, ... in the order the host recorded them) next to its id in the context; a result may cite a handle, an id, or an id whose first 8 characters name exactly one current entry, and the host replaces each with the evidence id before checking it. The same repair applies to the evidence of a task result; an `already_satisfied` task may cite reads of the run snapshot and of its worktree, and an entry that belongs to both (the attempt changed nothing) counts once, so a mistyped tail is still repaired. A review that omits criteria is not rejected: the host lists them as `inconclusive`, and the converge stage settles coverage. The host checks (unknown or stale evidence, a pass that contradicts a failed criterion, a request for changes without a finding, unknown IDs) run inside `submit_result`: the agent gets the exact message and the list of valid handles and ids and may resubmit twice in the same conversation, which costs a few thousand cached tokens instead of a new attempt. The one-step format correction of a review is told the hash and the valid ids too. A review that finished is kept in the run state before a sibling reviewer's failure is raised, and a resume reuses it when the snapshot has not changed. Before the review stage the host adds one review bundle to the review snapshot as `diff` evidence: a unified diff of every file the run edited against its content before the run (built from the edit journal and the kept pre-images, so it needs no Git repository and covers every task, not only the last one), the changed files with their hashes, a map from each criterion to the tasks that cover it, and each task's changed files (`taskFiles`). Check results are not copied into it: they are `command` evidence of the same snapshot and reach the reviewers next to the bundle. It is built once per snapshot, so a correction round gets a new one, and every reviewer, the security reviewer included, reads the change from it instead of reading files; a patch over 48,000 characters is cut and says so. Finding IDs are handles too: the host keeps the ID a reviewer wrote while it is free in the run and numbers it otherwise (`F1` becomes `F1-2`), so a later round that reuses `F1` for a new finding is recorded; a SQLite failure while storing blocks the run with reason `storage_failure`, not `invalid_output`. A fault of the host's own state (a stale snapshot, a missing artifact the host should have filled) blocks with reason `host_state`, not `invalid_output`, so a diagnostic separates a host fault from a model's invalid output; the run list, `workflow status` and the desktop show it. A required reviewer whose verdict is `inconclusive` is asked once more with the list of the criteria it left open (and their explanations) before anything else happens. Criteria it still cannot establish (manual ones are `deferred` as before) are routed to the converge stage as evidence gaps: the review is recorded as `pass` (or `changes_requested` when it has findings), the gaps are kept in the run state (`reviewGaps`) and the convergence agent receives them as `evidenceGaps`, so an automated criterion without evidence becomes a convergence task that adds a test or a declared check; acceptance still needs the converge stage to pass every criterion. In a workflow without a converge stage, such as `quick`, a review that still has no finding while every required check passes records each open criterion as a known limitation (`review-inconclusive-<dimension>-<criterion>`, accepted by the notes rule, with the reviewer's explanation as the claim) and counts as `pass`, so the run continues instead of stopping on a verdict with no defect to repair; the limitations appear in the run report and the run's `limitations` count. With a finding, or with a required check that does not pass, the run blocks with `invalid_output` (`<dimension> review inconclusive`) as before. Reviewer repros (`run_repro`) and the host's rerun of a finding's repro run with the project importable: a Python project with a `pyproject.toml`, `setup.py` or `setup.cfg` and a `src` directory gets `src` and the project root on `PYTHONPATH`, and the repro runs in the run's worktree when the run has one.

### Fresh-context restart

Repair rounds (`maxRepairRounds`) count checks-stage passes that start corrections. Review passes that start corrections count review rounds, which have their own budget of `maxRepairRounds`: a checks stage that needed both of its rounds still leaves the review two rounds for its reproduced findings, so a run whose required checks are green is not stopped as `no_progress` only because the checks stage spent the repair rounds. Each counter refuses its next round with `no_progress: N finding(s) remain after the policy's maxRepairRounds (N)`, a high finding the review keeps reproducing and a required check that keeps failing included. The exception is a review pass whose findings are all medium or low while every required check passed on the current snapshot: once the review rounds are used, those findings become known limitations (accepted by the review round limit in the [run report](#run-report)) and the run goes on to its next stage, the converge stage where the workflow has one, instead of stopping as `no_progress` (stmtsplit-update and cfgtrace ended blocked on one low or medium finding with every check green, each round having resolved the findings it was given); the definition's loop bounds, `maxCorrectiveTasks` and the token, call and time budgets still apply. The run's `repair_rounds` and `review_rounds` record both counters; the budget view of a run (`budget.reviewRounds`) and `workflow compare` show them. The review round correction artifact is `corrections/review-N.json`. A correction started by a task's own failed checks during the implement stage spends none: it is bounded by `maxTaskRepairs` (default 2) corrections in a row from one planned task, so early task-level corrections no longer use the rounds the checks stage needs. `maxCorrectiveTasks` counts corrective tasks, and the findings of one failed check run are one task. A defect a task finds in another task's file goes to that file's owner at once: when an implemented task's summary or unresolved items name a file an implemented task writes, the run's required feature checks run once, and a failing check's findings on the named files (or on the named file, when the output names no planned file) become a corrective task of the owner, as a task-level correction with the failing check as the repro. A failing check that declares a fixer (such as `cargo fmt` for `cargo fmt --check`) first runs it on the named files, journaled as `apply_fix` edits of their owners like the checks stage's fixer pass, and runs once more; only a check that still fails starts a corrective task, so mechanical formatting differences cost no model attempt. `tasks/defects/TASK_ID.json` records the files, the check results (`fixed: true` on a check whose fixer changed a file) and the findings; a passing check starts nothing. A failure that unresolved findings (open or in correction) already name, by its failing test lines or by an open `Required check X failed` finding on the same file, is not charged to the reporting task again; the artifact lists it under `covered` with those findings. A finding placed on a named file carries the requirements of that file's owner task, not the reporter's. Corrective tasks are titled by their first finding's claim and file, such as `Correct: Required check tests failed (render.go) and 1 more`. A path inside a package (`pkg/globs.py`) names that file, not the package's `pkg/__init__.py`. While none of the plan's test files exists yet, a test check that collects no test (pytest's exit 5 with "no tests ran", or only "No files were found in testpaths" when its `testpaths` directory does not exist yet; "No tests found"; Go's "no test files") is recorded as `no_tests` and starts nothing, so a plan that writes its tests last pays no corrective task for the gap. A repair round that leaves the same failures as the round before it (the same claims, criteria and failure signature; a failed task check is compared without the corrective task's ID) repeats. The first repeats get another round with a note to isolate the cause with `run_probe` before editing again. When the failure has repeated `freshRestartAfter` times (a policy setting from 1 to 5, default 2: two corrections in a row that changed nothing about it), the next correction starts from a clean context instead: its implementer gets the spec, the task, the current files and only the evidence its own findings cite, without the earlier attempts' diffs and check logs, plus a host-written account of what the earlier corrections changed and that the failure stayed (`freshStart` in its input, stored as `tasks/TASK/fresh-start.json`). This correction is not refused by `maxRepairRounds`, though `maxCorrectiveTasks` still applies. If it leaves the same failure again, the run stops as `no_progress` with a message that the clean-context correction did not change it, so a person fixes the cause or revises the plan.

## Decisions and revisions

```sh
baked workflow answer RUN_ID --request ID --answers-file answers.json --expected-revision N
baked workflow evidence RUN_ID --request ID --file observation.txt --accept --expected-revision N
baked workflow reject RUN_ID --request ID --reason "Needs clarification" --expected-revision N
baked workflow pause RUN_ID --expected-revision N
baked workflow cancel RUN_ID --expected-revision N
```

Rejecting an approval with a reason pauses the run. When it resumes, it does not request the same package again: it goes back to specify (or to plan when the workflow has no specify stage) with the reason as correction input, and specify, plan and analysis run again before a new approval request. Each rejection is used once, at most three times per run, and a v2 run stays within its `maxStageVisits`; past that, resuming asks for approval of the same package again. An answer does not restart the run. It is appended to the request, and `resume` continues from the stage the answer affects: research questions continue with specify and keep the research report, spec questions repeat specify, and analysis findings repeat specify when any finding of the request, blocking or not, refers to the spec (the person may answer any of them), and plan when they all refer only to `plan.md` or `tasks.json`. Before asking, a run sends blocking analysis findings the planner can fix alone back to the planner once: coverage gaps that refer to `plan.md` or `tasks.json` (they may name the criteria the tasks miss) and inconsistencies that refer only to `plan.md` or `tasks.json`, with the findings appended to the prompt; only findings that remain after that replan, or that involve the spec or other kinds, become a clarification.

Resuming a run that blocked with `invalid_output` repeats the stage, and the stage's agent gets the stored diagnostic (with the schema's message when the result failed validation) as a correction note, once per diagnostic. An answer does not restart the run. It is appended to the request, and `resume` continues from the stage the answer affects: research questions continue with specify and keep the research report, spec questions repeat specify, and analysis findings repeat specify when any finding of the request, blocking or not, refers to the spec (the person may answer any of them), and plan when they all refer only to `plan.md` or `tasks.json`. Before asking, a run sends blocking analysis findings the planner can fix alone back to the planner once: coverage gaps that refer to `plan.md` or `tasks.json` (they may name the criteria the tasks miss) and inconsistencies that refer only to `plan.md` or `tasks.json`, with the findings appended to the prompt; only findings that remain after that replan, or that involve the spec or other kinds, become a clarification.

The planner cannot change the spec, so a criterion it cannot cover would otherwise reject every plan (an `uncovered criterion` submission error) until the run blocks. When the planner submits a plan that leaves the same criterion uncovered a second time, and its plan names that criterion (its reason, such as "covering it needs a CI workflow the approval limits prohibit"), the criterion stops being a submission error. The run then goes back to specify once, with the criterion and the planner's reason as correction input: the spec author removes a criterion the request does not ask for, and the requirement only it verifies, or rewrites it so a task in scope can verify it. A criterion that comes back after that revision is asked as a blocking `scope` finding (`PLAN-SCOPE-N`, refs `spec.json` and the criterion); the answer resumes at specify. A criterion the plan leaves out while a task implements one of its requirements is not a submission error: the host lists it on that task (on a test task for an automated criterion when one implements the requirement, else on the task whose title, description and files share most words with it) and records it in `plan-repairs/uncovered.json`. A plan that does not name a criterion no task can take keeps getting the submission error.

The analysis passes when no finding is blocking, whatever the model's verdict (`pass` or `needs_revision`); non-blocking findings stay in the record as notes and an empty list is never routed anywhere. Only an `inconclusive` verdict without blocking findings still stops. The host computes the task and file counts of `tasks.json` and gives them to the analyzer as `extra.hostCounts`; a blocking finding that only compares such counts with the plan text ("plan says 8 tasks, graph has 9") is demoted to a note. When plan-time sizing split an oversized test task by file, the analyzer gets `extra.hostSplit` (planned task to its parts); plan.md names only the planned task, so a blocking finding whose task IDs all belong to one split and include an added part ("T009 is not in plan.md", "T005 and T009 check the same thing") is demoted to a note too. Only a finding about the split itself is demoted (a part plan.md does not list, parts that check the same thing); one that says implementing a part fails or contradicts a criterion or requirement ("T005 requires edits in tests/cli.test.ts, so the request fails AC-007") stays blocking. The host adds `dependsOn` edges after planning whatever the planner wrote (a module index after the module files, a reader after the writer of its read hint, a documentation task that runs the program after the tasks writing its entry points, a test task after the code tasks that share its criterion); the edges of `tasks.json` it would add are listed for the analyzer in `extra.verifiedByRuntime` as not defects, and a blocking `inconsistency` about dependencies whose task IDs are all joined by such edges ("T007 dependsOn T003, but plan.md says no dependency between tasks") is demoted to a note, because the planner cannot remove them. An answer to an analysis clarification also adds a fact to the research report that names the finding and the answer and declares conflicting earlier statements stale, so the analyzer does not raise the same fact again.

With the policy field `clarification: "assume"` (absent means `ask`, the behavior above) a blocking question reaches a person only when no default is safe. The researcher and the spec author are told so up front (`extra.assumeDefaults`) and settle such a question in their first submission; one that is still blocking is returned to its agent at submission: it chooses the most conventional default, records it in the spec's assumptions as "QUESTION Assumed: DEFAULT, because REASON." and makes the question non-blocking; it may keep the question blocking only when every reasonable default risks data loss, security, money or an irreversible public interface. Blocking analysis findings that remain after the plan-only replan go back once to the stage they refer to (specify for a spec reference, plan otherwise) with the same instruction. In a run of a v2 definition both loop-backs move the run's position to the definition's specify or plan stage outside its transitions; each counts as a stage visit, and when the visit would pass `limits.maxStageVisits` the findings go to a person instead. Whatever is still blocking after that is recorded as an assumption instead of being asked: the findings are written to the run artifact `assumptions/analysis.json`, shown as notes, and the analysis passes, so the approval is the point where a person sees them. A `scope` finding that names a clause the spec drops from the request is never settled this way and becomes one clarification request. A `scope` finding that names a restriction the request does not state (an input domain, a rejected form, an exclusion) or a requirement the request never asked for (such as CI on Windows, macOS and Linux; the host recognises both by their wording, and never for its own `COVERAGE-1` finding) is decided for the request: it gets one more return to the same stage with the instruction that the request is authoritative (delete the restriction or the addition with the criteria and tasks that only serve it; a domain may stay only as a non-narrowing assumption), and a restriction or addition that survives is recorded in `assumptions/analysis.json` like the other assumptions instead of being asked. A finding whose dropped cases are the effect of the spec's own exclusion or limit ("the assumptions exclude inputs outside the test domains, which drops required rejection cases") is such a restriction too: the fix is deleting the exclusion. The spec author's profile says the same: a domain is an assumption of its criterion, never an `outOfScope` entry, and never removes something the request names. An `inconsistency` finding whose one side is what the request states ("the request allows it", "the brief's explicit ban") is decided for the request the same way. Any other `inconsistency` finding (two statements that cannot both hold, such as two generated files that map to the same path) is a defect, not a decision: it gets one more return to the same stage with its text and an instruction to change the artifacts rather than assume it away, and when it still survives it also becomes a clarification request. A blocking `inconsistency` finding that names the same references as one an earlier pass raised, describes a different facet of it and offers alternatives ("either ... or ...") is recorded with its first alternative as an assumption instead of being asked, because the earlier pass already returned that defect once. The assumptions that are recorded reach the reviewers and the convergence agent as `knownRisks`, to check first. The assumptions are part of the spec, so the approval shows them and a person can reject the package. A run chooses the mode at start: `baked workflow run --clarification assume|ask`, the Questions field of the TUI new-run form, the "Open questions" checkbox of the desktop New run screen, or `clarification` in `POST /v1/workflow/runs`; each overrides the policy for that run and defaults to the configured policy. Only `assume` is stored in the run's policy, so a run that asks keeps the policy hash it had before the field existed. The approval request body carries `assumptions` (the spec's list), and the TUI approval, the desktop run decision and the desktop Needs you detail list them above the files in scope; `spec.md` has an Assumptions section when the list is not empty. Rejecting the approval with a note sends the run back to revise them when it resumes (see above).

**Revision by patch.** With the policy field `revision: "patch"` (absent means `regenerate`: the author writes the whole artifact again, as before; set it in `workflows.policy` of `.baked/config.json` or a policy file) analysis findings that send the run back answer with edit operations instead of a new spec or plan, when at most five findings block ([revision-patch](../../src/core/workflows/revision-patch.ts)). The author gets the findings and the instruction in `extra.revision` and submits `{"schemaVersion": 1, "operations": [...]}`: `set` replaces a field or a list element, `add` appends to a list, `remove` deletes a field or an element, and `replaceText` replaces text that occurs exactly once in a text field such as the plan's `markdown`. Paths name fields from the root of the spec (`criteria/AC-016/given`) or of the plan result (`taskGraph/tasks/T012/dependsOn`); a segment after a list is an element's `id` or its index. The host applies the operations to the current spec, or to the planner's last accepted plan (`revisions/base/plan.json`, before the host adds edges and splits tasks), and checks the result as it checks a submission; an operation that does not apply or a result that does not validate goes back to the author in the same attempt. A finding about the spec revises the spec and then the plan by patch; a finding about the plan only revises the plan. A sizing split (see [Plan-time sizing](#plan-time-sizing)) revises the plan the same way. Every patch is recorded as `revisions/spec-N.json` or `revisions/plan-N.json` with the findings, the operations and whether it was accepted. A patch that is still not accepted after the author's corrections falls back to the full re-author.

In either mode the researcher, the spec author and the spec reviewer are told to report every blocking question or finding in one submission, so a person answers them in one request instead of one per round.

Research, spec and analysis run before any code changes, so they cannot know check outcomes. A blocking research unknown or analysis finding that only says checks were not run (lint, typecheck, tests) is returned to the agent at submission to be made non-blocking; if the agent keeps it, the runtime records it as a non-blocking note. The planner and spec author take verification commands from the policy checks, and the spec reviewer treats a policy check that runs a superset of a named command (the whole test suite for one test file) as satisfying it and ignores project-instruction checks for files no task writes. The policy checks are the verification the operator chose for the run: a blocking finding that they are narrower than the project's usual verification (one test file instead of the whole suite, no build) is returned the same way and kept as a note. A requirement's verification and a criterion's method take only `automated`, `manual` or `post-release`, and `automated` includes the reviewer reading a file or the code; the spec reviewer is told so, and a blocking finding that asks for another method (inspection, review, demonstration) is kept as a note, because the spec author cannot satisfy it. Each analysis pass after a return sees the blocking findings earlier passes raised (`earlierFindings`) and is told to report every remaining one in that pass, so the findings do not arrive one per return. A criterion about how the implementer works (a command run before editing tests, an intermediate checkpoint) goes back to the spec author before planning: the implementer reads that instruction in the request, and nothing after the run can check the order of its steps. Two scope checks send the spec back the same way: an `outOfScope` line whose every word is in one `inScope` line ("CI workflows" against "Add a GitHub Actions CI workflow"), and, when the request calls limits non-narrowing, an `outOfScope` line with a numeric bound or a criterion that puts inputs beyond a numeric bound outside what the feature handles. Such a domain belongs in the assumptions. Whatever the request says about limits, a criterion whose Given, When or Then excludes inputs beyond its domain ("larger inputs are outside this criterion's checked domain", "more arguments are not covered") goes back too, unless every number in the criterion is in the request, so a bound the request sets may stay.

Research is scoped to the request. When the request names files that exist in the workspace, the researcher gets `4 + 2 × files` steps, at least 10 (the attempt step floor) and at most its profile limit of 12; a file the request asks to create is not counted or listed as a path to read and 14,000 tokens per step (at most the policy `maxAttemptTokens`); it is told to read the named files together, follow their direct dependencies with `bake_find`/`bake_impact` and submit once they are covered. A request that names no existing file keeps the profile step limit and the policy token cap. Every agent attempt is told to submit two steps before its step cap, so a submission that the schema or a validator rejects can still be corrected; the rejected payload is stored as a `diagnostic` artifact (`attempts/ID/rejected-N.json`). An attempt that ends at its step cap with no submission and no writes is repeated once with 1.5 times the steps and tokens.

Request coverage on a new project ([coverage](../../src/core/workflows/coverage.ts)). The host builds Workspace Facts ([workspace-facts](../../src/core/workflows/workspace-facts.ts)) before research and passes them as `extra.workspaceFacts` to the research, specify, plan and analyze stages: the files of the workspace at any depth, shallowest first (without `.git`, `node_modules`, `.baked`, `baked`, `.venv`, `dist`, `target`, `build`, `obj`, `.gradle`, `.idea` and `__pycache__`; the scan stops after 2000 entries and lists the first 80 files), with their sizes, so a Maven, Gradle or .NET project with its sources under `src/main/java/...` counts as `source`, the manifests among them, the scripts of the root `package.json`, and a `kind`: `empty` (no file), `scaffold` (files, but no source code: manifests, configs, a README) or `source` (at least one source file). The facts are stored as the run artifact `facts/workspace.json` (a new revision only when they change), so the run page of the terminal app, the headless CLI and the desktop API list them with the other artifacts. They are authoritative: the researcher states `scaffold: <files>` and reads the manifests the request touches instead of reporting that no project files exist, the planner modifies listed files and creates only unlisted ones, and an analysis finding of kind `inconsistency` that says a listed file does not exist is demoted by the host to a non-blocking note. When the kind is not `source` the program the request describes is the deliverable and is never out of scope because it does not exist yet. The planner then lays down the skeleton first (manifest, entry point, test setup) and plans no task that inspects code that does not exist yet; the quick planner skips its search. The reviewers get `extra.baseline.greenfield: true`, so a deliverable the request describes that the change lacks is a `missing` finding and no earlier behavior has to be kept compatible. The analysis compares the spec with the request, and the host adds a blocking `scope` finding `COVERAGE-1` (refs `spec.json`, `tasks.json`) when the workspace kind is not `source`, the request names something to build (a CLI, app, API, library, service, tool, tests and similar words) and the plan's tasks write no source or test file (only docs, licenses, manifests and configs). Like any finding that refers to the spec, it sends the run back to specify (once on its own with `clarification: "assume"`, otherwise to the person); it is judged on the request as the user wrote it, raised once per run, and not applied to a feature of an initiative (the person approved its boundary with the split), so an answer such as "documentation only" is not asked again. A request that asks for documentation only and names no deliverable is not affected. Not part of the gate yet: a deliverable-by-deliverable coverage table on the approval view and auto-approval declining on unmapped deliverables.

Answers is a JSON object of string answers. Manual evidence describes the user's actual observation. It is bound to a snapshot; a new source change makes it stale. Post-release criteria require explicit consent in the scope approval and keep the deferred status. A criterion with method `manual` has no evidence while the work is being reviewed, so the required reviewers do not judge it: the host lists it as `deferred` in their coverage and a review that is inconclusive only because of manual criteria counts as a pass over the rest. The converge stage then raises the `manual_evidence` request for each of them. The spec author may not mark a criterion manual when it is about a file of the repository (README text, documentation, configuration, source): the specify stage sends the spec back with that correction, because only a person can answer a manual request and a reviewer or a command check can read the file itself. Manual stays for behavior only a person can observe.

Editing the Markdown by hand does not change the accepted spec. Prepare an approved JSON revision, then:

```sh
baked workflow candidate RUN_ID --spec spec.json --plan plan.md --tasks tasks.json --policy policy.json
baked workflow revise RUN_ID --candidate CANDIDATE_HASH --expected-revision N
baked workflow resume RUN_ID --expected-revision NEW_N
```

`revise` leaves the run paused. `revise ... --resume [--events]` resumes and drives it in the same command, with the exit codes of `resume`.

Candidate fields are optional: missing ones are taken from the current package. The plan must contain Context, Decisions, Components, Data, Verification and Risks; DEC-001 and references to requirements. A candidate explicitly accepts the current instructions and configuration hashes. A changed skill requires a new profile/run. Profile versions inside an existing run stay frozen; a v2 definition changes only through a definition revision (see [Workflow definitions](#workflow-definitions-v2)). A repeated analyze and approval are mandatory; with `autoApproval.renewal` the host may give that approval (see below).

The terminal states completed/cancelled/failed are immutable; `fork RUN_ID --expected-revision N` creates a new run with the parent's artifacts, a new approval and no passing evidence. It does not start the model before resume. There is no automatic rollback of user changes.

`fork RUN_ID --expected-revision N --from-stage STAGE` starts the new run at a stage after the implementation (a `checks`, `review` or `converge` stage; the status JSON lists them as `forkStages`) instead of from the beginning. It is for trying a stage again, on another model for example, without repeating the plan and the implementation. The fork keeps the parent's spec, plan, task graph and approval, so it asks for no new approval, and it carries the parent's change. Its first drive puts each file the parent's journal changed back to its content before the parent's first edit, takes the fork's baseline there, and then writes the parent's content through the fork's own journal (step `fork-seed`), so the review bundle, undo and delivery of the fork see the change as the fork's own edits. Every task is marked implemented. When the result matches the parent's snapshot, the parent's passing command and manual evidence carry over, and a fork at a `converge` stage also carries the reviews of that snapshot; otherwise the checks run again. The parent must not be running and must have an approved package, its workspace (or worktree) must still exist, and the journal must have kept each file's earlier content; otherwise the fork is refused. The `fork/seed.json` and `fork/seeded.json` artifacts record what was carried.

### Project memory

A run starts with what earlier runs of the same workspace learned, so it does not ask the same question or rediscover the same facts again. At creation the run reads the 30 newest runs in `.baked/workflows.sqlite` ([project-memory](../../src/core/workflows/project-memory.ts)) and collects:

- the answers people gave to research and spec questions, from any run; the newest answer to a question wins (at most 12);
- the assumptions of the specifications that completed runs had approved, such as those recorded under `clarification: "assume"` (at most 12);
- the check commands that passed in completed runs, except the new run's own checks, which its execution contract already lists (at most 8);
- active [learned code rules](#learned-code-rules) (at most 12).

Answers to analysis findings are left out, since they are about one run's plan. The result is stored as the run's `project/run-memory.md` artifact, its hash joins the run's inputs, and a fork keeps it; a candidate revision keeps the memory the run captured. The researcher, the spec author and the planner receive it as `projectMemory` in their input, framed as background that the request, the answers in it and the run's policy override; implementers, reviewers and the auditor do not. When the project's memory settings turn on **Share with runs** (`shareWithRuns`, [memory](../guide.md#memory)), project memory also lists up to 10 of the project's chat memories that are pinned or are a decision, preference or gotcha, and chat sessions recall the run memory in return. A workspace with nothing to remember adds nothing. The policy field `projectMemory: false` turns it off (absent means on, so stored policies keep their hash), and runs removed by `baked workflow gc` drop out of it.

#### Learned code rules

Findings that keep coming back become rules for the agents that write and judge code (#643). A recorded review, convergence or task finding counts toward a rule by its kind and its directory: findings of the same kind on files in the same directory (or with no file) in at least two runs propose a rule. Refuted findings and `Required check X failed` findings do not count. The rule's text is the newest such finding's suggested fix, its scope the directory and everything below it (`src/api/**`, or `**` for files at the root or no file), and it lists the findings it came from. A proposed rule becomes active once its finding recurred in three runs, or when a person accepts or rewords it; forgetting it retires it, and restore makes it proposed again (unless three runs back it).

At creation a run captures the active rules as the artifact `project/learned-rules.json`, whose hash joins the run's inputs; a fork keeps it. Implementers receive the rules whose scope covers a file their task writes, reviewers, the critic and the auditor receive every rule with its scope (`learnedRules` in their input), and research, spec and planning read them as part of project memory. The policy field `learnedRules: false` turns them off (absent means on, so stored policies keep their hash); it works independently of `projectMemory`.

#### Viewing and editing project memory

People can review and correct the memory before the next run. Each entry has a stable ID (`a-` answer, `s-` assumption, `c-` check, `r-` rule, `n-` note) derived from its question, assumption or command, so an edit keeps applying when later runs record the same entry again. Changes are stored in the `project_memory_edits` table of `.baked/workflows.sqlite` and apply to runs created afterwards; started runs keep the memory they captured.

- **Add** a note of your own (at most 12, 600 characters each). Notes come first in what research, spec and planning read.
- **Accept** activates a proposed rule as recorded.
- **Edit** rewords a note, an answer, an assumption or a rule (a reworded rule is active). A reworded entry keeps your text even when a later run records a newer answer to the same question; the original stays visible as "runs recorded". Check commands cannot be reworded: forget them or change the workspace checks.
- **Forget** deletes a note, or hides a recorded entry from new runs. The desktop calls it Delete on a note and asks first, because a deleted note has no Forgotten entry to restore it from. A hidden entry frees its place, so the next entry of its kind moves in.
- **Restore** brings a forgotten or reworded entry back as runs recorded it.

```sh
baked workflow memory [list] [--json]          # what a run started now reads, then forgotten entries
baked workflow memory add --text "Public APIs keep their names"
baked workflow memory edit a-91d0c3e2aa --text "Yes, and mark them as failed"
baked workflow memory forget s-0b7e55d1c4
baked workflow memory accept r-5c1e0a9b27
baked workflow memory restore s-0b7e55d1c4
```

The listing marks a check the workspace policy already lists, and a proposed rule, as not sent; a rule shows its status, scope and how many runs had its finding, and `--json` returns `{enabled, entries, hidden, rendered}`, where `rendered` is the exact text the next run would receive (null when empty). In the TUI the **Runs** tab of `/memory` lists the same entries: Enter edits, Ctrl+N adds a note, Ctrl+A accepts a proposed rule, Ctrl+D forgets, Ctrl+R restores and typing filters. The desktop app shows them in the **Runs** part of the project's **Memory** screen, and the local API serves `GET|POST /v1/workflow/memory`.

### Diagnostics after edits

Implementers get the same [diagnostics after each edit](../tools.md#diagnostics-after-edits) as the chat: new errors in the edited file and in up to 8 files that import it, in the run's worktree when it has one. The policy field `editDiagnostics` sets what an edit that adds errors does during the run: `feedback` returns the errors with the tool result, `reject` also restores the file and fails the edit with the errors and the original lines. A run that starts without the field takes the project's `editDiagnostics` chat setting; only `reject` is stored in the run's policy, so the approval digest covers it and a run under `feedback` keeps the policy hash it had before the field existed. Set it for one run with `workflows.policy.editDiagnostics` in `.baked/config.json` or `--policy FILE`.

**Task-end type check.** Whole-unit checks (`tsc`, `typecheck`, `cargo check`, `clippy`, `mypy`, `pyright`, `go vet`) do not run as task checks, since a task's worktree lacks the files its sibling tasks write. When the policy has such a feature-scope check and the task writes code, the host runs it once when the implementer first submits the task as implemented, in the task's directory, and keeps only the errors that:

- are located in a code file the task writes;
- do not name a code file that a sibling task not yet done will write;
- are not an unresolved module or name while such a sibling is pending (`mod parse;` before `src/parse.rs` exists);
- were not reported by the same check on the code the run started from. The baseline stores these errors as `diagnostics` in `facts/check-baseline.json`.

Up to 20 remaining errors go back to the implementer with the rejected submission, and its next submission is accepted without running the check again. The check is advisory: the checks stage still runs it on the integrated change. Each run is journaled as `tasks/TASK/task-end-check-ID.json`.

**Task-end syntax check.** Every file an implementer's attempt wrote with `edit_file` or `multi_edit` is parsed with the tree-sitter grammars of the repository graph when the attempt submits the task as implemented, so a file that does not parse is caught in the attempt that broke it rather than by a whole-crate check after another task. It covers Rust (`.rs`), Go (`.go`), TypeScript (`.ts`, `.mts`, `.cts`, `.tsx`), JavaScript (`.js`, `.mjs`, `.cjs`, `.jsx`), Python (`.py`), C# (`.cs`) and Java (`.java`); a file of any other language, or one whose grammar does not load, passes unchecked. Only the parser's error and missing-token nodes count, and an edited file is blamed only when it has more of them than before the attempt's first edit of it, so syntax newer than a grammar in code the task did not write does not refuse it. While a written file does not parse, `submit_result` answers `accepted: false` with up to five errors per file as `Syntax error: path:line:column: message`, and the agent fixes them in the same conversation. A grammar can predate valid syntax (C# 12 primary constructors, Rust generic associated types), so the same errors submitted again are accepted, as is any submission after two refusals; each decision is journaled as `attempts/ATTEMPT/syntax-ID.json` with `accepted` and the errors. In a workflow attempt the `edit_file` and `multi_edit` results also end with the syntax errors the edit left in its file.

**Task-end repro check.** A corrective task whose findings carry a repro the run can start (a program its checks start) runs those repros on the attempt's files when the implementer submits the task as `implemented` or `already_satisfied`. A finding that still prints its `actual` output sends the submission back with the repro command and its output, at most twice per attempt. When an accepted result changed nothing or reports `already_satisfied` and a repro still reproduces, the host refuses it: the task restarts once in a fresh session that is told which finding still reproduces, and otherwise blocks the run with reason `invalid_output`. A correction no longer closes a reproduced finding as already satisfied and leaves it to the next review round. Each run is journaled as `tasks/TASK/repro-check-ID.json`.

**Large check output.** The output of a check that `request_check` or `apply_fix` returns to the model is bounded at 40,000 characters. Longer output comes back as its first 4,000 characters, the lines naming failed tests in the part left out (`FAILED`, `ERROR`, `(fail)`, `--- FAIL`, `not ok`, `... FAILED`; at most 40), and its last 32,000 characters, with `truncated: true`, the full length in `outputChars` and the evidence ID that holds the whole output. A failing property test that prints a diff of megabytes of generated data therefore no longer overflows the model's input. The check artifact stores the output once, in `output`, which already interleaves standard output and standard error.

**Whole-unit formatters.** `cargo fmt` and `rustfmt` also follow every module of the crate, so before integration they report the files of every other task. They are not part of the task-end check, and a planned task's `request_check` of one is not run: it answers `status: "deferred"` with a note that the formatter runs in the checks stage. There, when it fails, the host applies its fixer (`cargo fmt`) to the files the run's tasks write, journaled as edits of the task that last writes each file, and runs the check again. A corrective task, which runs after the checks stage, runs it as usual.

An implementer that submits `blocked` or `failed` after its attempt applied file edits gets the submission back once, naming the files it wrote and saying that only BAKED's edit tools change files and no sandbox setting refuses them. Its next submission is accepted. This catches an agent that hit a refusal from a tool outside BAKED, such as Codex's own read-only sandbox, and reported "no changes were made" over edits BAKED had applied.

### Library docs

When `libraryDocs` is configured (global or project config; a run freezes it into its policy, and a policy that names its own source keeps it), each implementer task gets docs for the versions of the libraries it uses. The versions come from the workspace's lockfiles:

- `package-lock.json` and `bun.lock` (npm);
- `Cargo.lock`;
- `uv.lock` and `poetry.lock` (PyPI);
- the `require` lines of `go.mod`.

A task uses a library when a file it writes or reads already imports it (`import`/`require` in JavaScript, `use` or `crate::` in Rust, `import`/`from` in Python, a quoted module path in Go), or when its title or description names it. Each task gets docs for at most 3 libraries. A `dir` source reads `<name>@<version>.md` or `<name>/<version>.md` below the directory (absolute, relative to the workspace, or under `~`). An `mcp` source calls the tool of a server in `mcpServers` with `args`, replacing `{name}`, `{version}` and `{ecosystem}` (`npm`, `cargo`, `pypi`, `go`); without `args` it sends `{library, version}`. The docs reach the implementer as `libraryDocs` in its input, each cut at `maxChars`. Each lookup, found or not, is journaled as `tasks/TASK/library-docs-ID.json`. A library the source has no docs for is left out. Without a source nothing changes. `workflow doctor` warns when the directory does not exist or the MCP server is not configured or is disabled. The source is also a setting: `/code-quality` in the terminal (dialogs for the directory, or the server, tool and `;`-separated `key=value` arguments, and the cap), the desktop **Code quality** page, and `libraryDocs` in `PATCH /v1/settings`, each in the project or global config; the terminal row, the desktop page and `GET /v1/settings` show the same warning.

### The run's own edits and undo

A run keeps the edits it executed. A revision, a failed or interrupted task attempt and a fork leave the files as they are, and the runtime recognises content the run itself wrote by the effect journal:

- Plan consistency and the implementer accept a `create` target that exists only because this run, or the run it was forked from, created it and nothing changed it since. Any other existing file is still a conflict ("already exists; use modify").
- A `modify` target that does not exist and that no earlier task (an ancestor in the dependency graph) creates is a plan problem the planner fixes before submitting ("does not exist and no earlier task creates it").
- A corrective task writes each file of the tasks it corrects once. The action follows the file, not the order of the plan: a path a planned task creates is `modify` when the integrated change already has it and `create` while it does not, even when a later task of the plan modifies it, so a correction that runs before the creating task can create the file.
- The workspace check before each stage accepts a file that differs from the last snapshot when it holds exactly what the run's last journaled write produced, and records it in the expected baseline. Pausing or interrupting a task no longer blocks the resume with "Sources changed outside the active task"; a change by anyone else still does.
- A package revision implements again only the tasks it changed. When the plan and project instructions are unchanged, the spec is unchanged apart from added acceptance criteria (and its revision number), no task's write scope changed and the revision is not a definition revision, an implemented task whose definition is unchanged apart from criteria added to its `criterionIds` keeps its implementation, unless it depends on a task that is implemented again or shares a file with one. A changed or removed criterion, or a criterion dropped from a task, keeps nothing of the affected tasks. The criteria a kept task gained are covered by the run's checks, review and convergence. Its evidence is invalidated like all other evidence: after the new approval the implementation stage runs its task checks again without calling the implementer, and the check stage reruns every check on the current snapshot. A policy-only revision, such as a changed check command, therefore reruns the checks and implements nothing.
- A repeated task receives the paths that still contain its earlier attempt's edits (`earlierEdits` in its input) and must read them before editing. Those edits count as the task's changes, so a repeated attempt that finds the work already done does not fail with "did not complete its implementation". Its edit tools accept those files as its own: a file whose content is the last journaled write of an earlier attempt of the same task, with no write after it, is not refused as "File changed outside this attempt". Nor is a file that is back to its content from before the task first wrote it (for example missing again, when a restarted task gets a rebuilt worktree without the file an earlier attempt created): the earlier write no longer counts, and the attempt creates or edits the file as if the task had not touched it. The same holds for a file that holds any other state the task's uncommitted writes passed through, such as the integrated file after the task was invalidated more than once, or the first attempt's content after a second lost worker. A plain resume after an attempt-cap stop takes this path in a run with several writers: the stopped task is invalidated and restarts in a fresh worktree from the run's content. An edit the hash check does refuse is not retried for ever: at the third refusal of the same path in one attempt the attempt stops with `input_changed` and names the path, instead of reading and retrying until its token cap.
- A `delete` write is done with `delete_file`. Its `expectedHash` is optional: the implementer passes the `hash:` footer that `read` printed for the file (the file's SHA-256, or a prefix of it of at least 16 characters, is accepted too), and a hash that no longer matches the file refuses the delete as `Delete target changed`. Without `expectedHash` the delete has the same guard as `edit_file`: it is refused when the file changed outside this attempt. The deleted content is kept as a `deleted-source` artifact for undo.

Undo is an explicit command:

```sh
baked workflow undo RUN_ID --expected-revision N [--path PATH]
```

It restores the files changed by the run's uncommitted task edits: edits of a task that has no snapshot because its attempt failed or was interrupted, a revision invalidated it or dropped it, or the run was cancelled. A task's edits are committed when the runtime snapshots them after the task; to undo implemented work, apply a revision that changes the task first (a task the revision keeps stays committed). Before each task edit the runtime stores the file's previous content as a `pre-image` artifact. Undo restores a file only while it still holds exactly what the run wrote last, and never overwrites a later change by a person or another tool. Before replacing a file, it keeps the run's version as a `rolled-back` artifact. Each restore is a journaled `file_patch` effect with the tool `rollback`, and the outcome is an immutable `workspace-rollback` artifact that lists restored files and the files left in place with the reason. The command prints that report. In the TUI the run screen does the same with U (see [TUI](#tui)). Files restored or left in place are settled and are not reported again; a file whose restore failed, or whose edit has an unknown outcome, is retried by the next undo. The expected baseline follows each restored path, so the next resume does not treat the restore as an outside change. The run must not be running: undo takes the run's execution and mutation leases.

When a repair task for a review or check finding passes its task checks, it restores the task it corrects, and the tasks that depend on that task are looked at again. A dependent is invalidated (its agent runs again) only when the repair changed a file it names: the file is among its writes or read hints. A dependent that writes only documentation files (`.md`, `.mdx`, `.rst`, `.txt`, `.adoc`) is reached only that way, so a documentation writer whose read hints do not list the changed file is not rerun. A dependent that merely imports a changed file (a relative import that resolves to it, or a dotted module name that ends in its path) is rerun by the host first when it has task checks: it keeps its implementation, the host runs its task checks, and a failure becomes a repair task of that dependent. A dependent that names a changed file but whose every written file the corrective tasks of the run rewrote (a deletion aside) is superseded: when it declares any check, of any scope (a test task whose only check is a feature-scope build such as Maven `verify` counts), it keeps its implementation and only runs its checks, because its agent would start from its original description and overwrite the correction (md-site round 6: one planned task ran three times, another four). A dependent that does not touch the changed files keeps its implementation and only runs its task checks again, with no agent call. Whenever a planned task that was implemented before is invalidated and ready to run again, the host runs its declared checks (any scope) first, in one-writer and parallel runs alike; when its earlier implementation passed its task checks under the same definition (a revision that changed the task always implements it again), they all pass and its written files exist, the task is implemented by supersession with an empty diff and no agent call (`tasks/Tn/host-first-G.json` records the outcome for generation G), and its gate check runs as for any implemented task. When a check fails, the agent runs as before. The changed files come from the `tasks/Tn/diff.json` artifacts of the repair tasks; when one is missing, or a written file is not a source file the scan understands, every dependent is invalidated as before. Dependents of an invalidated task are invalidated too. An invalidated planned task that writes only documentation (Markdown, a README, a licence, a changelog) waits while a corrective task is running or ready to run, and runs again once after them: a README cannot be right before the last source correction of the pass (cfgtrace round 26: one README and licence task ran four times for 902k tokens). A corrective that failed or is blocked is not waited for.

A task whose implementation did not complete (the implementer reported `blocked`, `failed` or an `unresolved` item, or its result was rejected) stops the run `blocked` with reason `invalid_output`; the diagnostic names the unresolved items, or, when the task reported `implemented` and changed none of its files, why that was not accepted (a planned task's first attempt that changed nothing, or the check that still fails with its evidence id and the files it names). A task that reported `implemented`, changed its files and lists as unresolved only failing tests or lint findings (up to five items, each naming a failing test, check or linter, or a rule code such as `ISC004`) is accepted instead: its task checks run as usual, and when no task check ran, each item that names no other planned task's file becomes a `partial` finding on the task's file, with `tasks/TASK_ID/unresolved.json` as evidence, and a corrective task fixes it. An item that names another task's file (a README assertion before the README task ran) is left to the checks stage and review. The task is not restarted for such a report, which a second attempt repeated before the run blocked. The implementer is told that a defect in a file outside its write scope is not unresolved: it finishes its own files and reports `implemented`, the failing task check becomes a corrective task, and that correction may write the files of the planned tasks that share its criteria. A required task check of a planned task that fails only on planned files that tasks still to run own (a file importing a module of a later task; none of the files named is the task's own, and no owner depends on the task), or that fails while a task still to run writes a file in its `readHints` (a type error names the importing file, which is the task's own), starts no corrective task: the task stays implemented without its check gate, the failing evidence stays in the run, and the check runs again once those tasks are done (`deferredChecks` in the run state). When no task can run any more, the wait ends and the check runs and is repaired as usual. A required task check of a planned task that fails only on existing test files that a planned task still to run rewrites (the plan changes a signature in T001 and updates the expectations in T003, which depends on T001) starts no corrective task either, and nothing waits: the task gets its check gate, the failure is recorded as `tasks/handoffs/T001.json` (`taskId`, `checkId`, `evidenceId`, `owners`), and the tests are the owner's to settle: its own task checks, and the checks stage, run them after it. This holds for any task check (type check, tests, affected tests): where the output locates failures in lines of their own (`tests/cli.test.ts(258,45): error TS2769`, a test file header, a `FAIL` line), only those files count, not the source files that indented related-information lines or stack frames name. Two test runners locate assertions differently and count too: `go test` prints an indented base name under `--- FAIL` (`    cli_test.go:42:`), which names the planned test file of that name, or, when several share it, the one in the directory of the `FAIL` package line; and a Rust test's `panicked at tests/cli.rs:12:5` names that file. A crate's `tests/*.rs` files are test files for this rule. When the failures are also located in another file, such as the task's own source, or the owner is already done, the failure is the task's own as before. The corrective task of a task that broke existing tests leaves alone the tests that planned tasks still to run update. `resume` sets such a task, which has no snapshot, back to `pending`, and the next attempt continues on the edits already in place. A typical recovery from a rejected implementation that needs a different plan: `candidate`, `revise`, optionally `undo` to start the tasks from the original files, then `resume`.

### Test integrity

Agents game tests: they delete or skip them, weaken assertions, special-case test inputs and add suppressions, and prompts against it barely help. The runtime guards the tests itself ([test-integrity](../../src/core/workflows/test-integrity.ts)). The guard is always on; the policy field `testIntegrity` only chooses what its findings do: `block` (the default; absent means `block`, so stored policies keep their hash) or `warn`. A run chooses it at start with `baked workflow run --test-integrity block|warn`, the Tests field of the TUI new-run form, the "Only warn about test gaming" checkbox of the desktop New run screen, or `testIntegrity` in `POST /v1/workflow/runs`; each overrides the policy for that run. Only `warn` is stored in the run's policy.

- **Existing tests are read-only.** A test file that existed before the run (a test path no task of the approved graph creates: `*.test.*`, `*.spec.*`, `*_test.go`, `test_*.py`, `*Test.java`, `*Tests.cs`, files under `tests/`, `test/` or `__tests__/` and similar) can be modified or deleted by an implementer only when the plan gives that write a `reason` (`{"path", "action", "reason"}` in `tasks.json`), which the approval covers. Otherwise the edit is refused with `CAPABILITY_DENIED` and the implementer is told to make the code pass the test. A plan that modifies or deletes an existing test without a reason is returned to the planner at submission. Corrections and integrators keep the reason of the write they repeat. Under `warn` neither applies.
- **Diff check.** After each task (and after each integration in a run with several writers) the host compares every changed file with its content before the task and records what it finds in `tasks/TASK_ID/integrity.json`: a deleted test file, fewer tests or fewer assertions in a test file (commented-out ones do not count; not reported for a write with a reason; fewer assertions are not reported either in a test file that a correction's own finding names when that finding is `contradicts` or names a lint rule, such as ruff `BLE001`, as long as every test case stays and the file still asserts), new `skip`, `only`, `todo`, `xit`, `@pytest.mark.skip`, `#[ignore]`, `t.Skip` and similar markers, new suppressions in any file (`@ts-ignore`, `@ts-expect-error`, `eslint-disable`, `biome-ignore`, `any` in TypeScript, `# type: ignore`, `# noqa`, `#[allow(...)]`, `@SuppressWarnings`, `nolint`), branches on running under a test runner (`NODE_ENV === "test"`, `process.env.VITEST`, `"pytest" in sys.modules` and similar), comparisons in source files with a literal that a test file of the task uses as input and that the spec and plan do not name, and new `--no-verify` or `--passWithNoTests`. Each rule counts occurrences before and after, so code that was already there is never reported, and documentation files are not checked for suppressions. Under `block` every finding becomes a task failure (`Test integrity (RULE): task T001 ... in PATH`) that a correction task must undo, like a failed task check; under `warn` the record is all. The checks stage repeats the scan at feature scope, over every file the run changed from its content before the run (the effect journal and the task diffs) to now, and records it in `integrity/run.json`; under `block` what it finds (`Test integrity (RULE): the run ... in PATH`) is repaired like a failed check, from the task that writes the file, so a problem a correction left in place or one spread over several tasks does not pass.
- **Spec conflicts.** An implementer that finds that the spec and a test (or a criterion) cannot both hold submits the outcome `spec_conflict` with the test, the requirement and why. The task stops without changing anything further and becomes ready again (`interrupted`), `tasks/conflicts/TASK_ID.json` records its account, and the run waits on a clarification request with the question `SPEC-CONFLICT-TASK_ID`, which the TUI decision view, `baked workflow answer`, the desktop run decision and Needs you show like any question. The answer is appended to the request, and the task runs again with it; it still may not weaken the tests. This also applies under `clarification: assume`, because every default would either fit the tests or drop a requirement, with one exception: when the report names what the request itself states as one side ("the request's explicit ban on property-based tests", "the request says this line is valid"), the request wins. The decision is recorded in `assumptions/conflicts/TASK_ID.json`, a note that the request is authoritative is appended to the request with the task's account, and the task runs again without a person; a second conflict of the same task asks. The other exception is a test the plan's own test task wrote: when the report names a test file that an implemented test task of the plan wrote and the reporting task cannot write (and the file is not one of the tests written first and approved by a person), the approved spec wins over that test. `assumptions/conflicts/TASK_ID.json` records it with the test files, a high finding against each file starts a task-level correction of the test task that may change only the assertions contradicting the spec, and the reporting task waits for that correction, then runs again. A second conflict of the same task asks. A test this run created (absent from the baseline snapshot) that the reporting task may write itself, such as a generated test a correction of a failed test check meets, is decided the same way without a correction task: two things the run wrote are never a question for a person. `assumptions/conflicts/TASK_ID.json` records that the approved spec and the request win over the test files, and the task runs again told to change only the assertions that contradict them and keep every other assertion. The report may name a test file the way models write paths, in a Markdown code span or emphasis and with a test name after it (`` `tests/test_cli.py::test_x` ``); the same matching maps review findings to the tasks that write the files they name. Tests that existed before the run and tests written first and approved by a person stay a question. A documentation task (every file it writes is documentation, a licence or a notice) whose report sets the rule for examples against the request's worked example ("FR-001 needs the worked example in the README, but the instruction forbids writing example output from the spec") is decided for the request too: `assumptions/conflicts/TASK_ID.json` records that the worked example is authoritative, and the task runs again told to copy every example output the request or the spec gives. A second conflict of the same task asks. An analysis finding of kind `inconsistency` whose one side is the request (a spec assumption excludes `tests/**`, the request allows it) is decided for the request the same way as a scope finding that adds a restriction, as described for `clarification: "assume"` above.
- **Spec amendments.** A review finding of kind `contradicts` that sets the approved spec against the request (its claim or fix names the request or brief) and whose fix says to change a criterion, a requirement, the spec, the plan or the task graph (for example "remove the generated-case count and seed from AC-003, the plan and T007") records a spec amendment in `amendments/FINDING_ID.json` ([spec-amendment](../../src/core/workflows/spec-amendment.ts)): the finding, the criteria and requirements it names, and the test file it names. The request is authoritative over them: the run's request gets one line saying so, which every later agent reads, so the correction makes code and tests follow the request and later reviews and convergence judge those criteria by what the request states. A correction cannot write `spec.json`, so it changes the tests that served the contradicting wording; the diff check accepts fewer tests or assertions in the test files of a correction of an amendment and in the test file the amendment names, as for a write with a reason. Skips, suppressions and the other rules still apply. The [run report](#run-report) lists the amendments under Decisions, so the delivered pull request names what the request overrode. Before this, a correction that replaced generated tests the request ruled out was flagged as a dropped test, and the guard's own correction restored them, until the run ended `no_progress` after 1.19M tokens of corrections (pngvet a2da6c24). Under `clarification: assume`, a blocking analysis finding that refers to the spec (`spec.json`, `inScope`, `outOfScope`, a criterion or requirement ID) and that the request settles (a restriction or addition the request lacks), and that survives the last return to the spec author, records an amendment too, in `amendments/analysis-FINDING_ID.json`. Implement then starts with the request authoritative over that point of the spec, and review does not raise it against `spec.json` again.
- **Findings on run documents.** A review or convergence finding whose file is one of the run's own documents (`spec.json`, `plan.md`, `tasks.json` or `research.json`, in any directory, unless a planned task writes a project file of that path) gets no corrective task, since no task can write it. It records a spec amendment in which the implementation wins: typically a correction deliberately departed from the approved wording (a collision policy the spec did not name) and the review reports the spec as the stale side. The run's request gets a line saying the implementation is authoritative over the criteria and requirements the finding names on that point, the run documents are not rewritten, and the finding is resolved. The other findings of the round are corrected as before; a round with only such findings adds no task, keeps the reviews and judges the convergence again, and it still counts as a round toward its limit. The run report lists these amendments separately ("the implementation wins over the spec"). Before this, such a finding stopped the run with `input_changed` ("Correction requires writes outside the approved task scope"), with every check green (md-site eed93dab at 5.30M tokens, colfit 0149cea7).
- Writers see the tests themselves, never the internals of acceptance gates or graders beyond them.

### Tests first

Tests written by the implementers share their wrong assumptions; failing tests written before the code are the stronger correctness filter. With tests first on, the planner plans a task that writes only test files for each criterion (a test task may cover several), and each test task names a task-scope check that runs its tests. A plan without a test task for a criterion, or with a test task that names no task check, is returned to the planner at submission. The policy field `testsFirst` chooses the criteria: `off` (the default; absent means `off`, so stored policies keep their hash), `criteria` (every criterion with the `automated` method) or `all` (every criterion except `post-release` ones). The `tdd` preset is `standard` with `testsFirst: "criteria"`, and `full` has it on too; start it with `baked workflow run tdd`, the workflow field of the TUI new-run form, the workflow picker of the desktop New run screen or `workflow: "tdd"` in `POST /v1/workflow/runs`. A workflow definition's `testsFirst` wins over the policy's.

- **Order.** Test tasks run first and depend on no code task; every code task waits for the test tasks that share one of its criteria. Until a person approves the tests, only test tasks run.
- **Red for the right reason.** After a test task the host runs its task checks on the code as it is and records `tests-first/TASK_ID.json`. The tests must fail, a failing output must name one of the task's test files, and no failing output may report a syntax error in them. Otherwise the reason (`Tests first: ...`) becomes a finding that a correction of the tests must fix, like a failed task check.
- **Approval.** When every test task is red, the run waits on an approval request whose body holds the criteria and the test files with their content; its digest is the hash of the files. The TUI decision view, the desktop run decision and Needs you show the tests next to the criteria; `baked workflow approve` and `reject` answer it like any approval. Rejecting appends `User rejected the tests written first: NOTE` to the request and writes the tests again. A run whose plan was approved automatically ([auto approval](#auto-approval)) approves the tests the same way.
- **Read-only after approval.** The approved test files are read-only for code tasks: an edit without a planned `reason` is refused with `CAPABILITY_DENIED` and the implementer is told to make the code pass. Implementation then runs until the tests pass, followed by the checks and review of the workflow.

### Auto approval

Auto approval is off by default. Enabling it is a human act: set `workflows.policy.autoApproval` in `.baked/config.json`, or pass it in a policy file or a revision candidate. The policy is part of the approval digest, so the setting is frozen with the run. A `workflows.policy` in a config file may name only the fields it changes: the rest come from the default policy, nested objects such as `reviewProfiles` merge field by field, and lists such as `checks` replace the default. An invalid field stops the command with one line naming the file and the field.

```json
"autoApproval": {
  "renewal": true,
  "limits": { "maxTasks": 3, "maxFiles": 5, "allowedPaths": ["src/**", "tests/**"],
              "allowDelete": false, "allowNewDependencies": false, "maxTotalTokens": 800000 }
}
```

At the approval stage the host compares the package with the setting. Either mode is enough to approve:

- `renewal` re-approves a revised package that stays within the latest human approval of the same run. Every write must be a path that approval covered: a delete only where a delete was approved. Every task must use a profile that approval covered. The workflow, profile and skill hashes must not change. Capabilities may stay or shrink but never grow, whoever changed them: no tool outside the approved `allowedTools`, no wider `network`, the same review profiles and skeptic, and `forceSecurityReview` stays on if it was on. The other policy settings (checks, budget limits, `maxAttemptTokens`, `maxCostUsd`, `checkpointTokens`, `autoApproval`) must either match the approval, with each budget limit (`maxTotalTokens`, `maxAgentCalls`, `maxAgentSteps`, `maxActiveMs`, `maxConcurrentReadAgents`, `maxRepairRounds`, `maxConvergenceRounds`, `maxCorrectiveTasks`) the same or lower, or be exactly the policy an operator command set later. `workflow extend` and a `workflow revise` that changes the policy each write a `policy-revisions/COMMAND_ID.json` artifact with `approvedBy: "user"` and the new policy hash; that command is the human decision on the policy, so a re-plan with the same writes after `extend --tokens N` or after a revised check command renews without a person. Only these host-written records count; nothing in a candidate's spec, plan or graph, or in any model output, is treated as consent. A fork starts without a human approval, so its first approval is always human. Approvals recorded before the policy, or before the task profiles, were stored in the request cannot be renewed; the next approval goes to a person once.
- `limits` approves a package with at most `maxTasks` tasks and `maxFiles` distinct files. Every write must match one of the `allowedPaths` globs, compared without case. Deletes are allowed only with `allowDelete`. The run's `maxTotalTokens` must not exceed `limits.maxTotalTokens`. `allowNewDependencies` can only be `false`. A setting with `renewal: false` and no `limits` is rejected.

Some packages always go to a person, whatever the setting. These are writes under `.git`, `.baked`, `baked/`, `specs/`, `.github`, `.gitlab`, `.circleci` or `.husky`, writes to package manifests (including `*.csproj`, `*.fsproj`, `pom.xml`, `build.gradle*`, `settings.gradle*` and `Directory.Packages.props`/`Directory.Build.props`) and lock files, `tsconfig*`, `biome*` (a task that creates a manifest or tool config that does not exist in the workspace yet, such as `package.json`, `pyproject.toml`, `tsconfig.json` or `biome.json`, is not held back: that is how a new app starts; lock files are never covered), `.env*`, `AGENTS.md`, `CLAUDE.md`, `constitution.md`, key and certificate files, and any spec that leaves a deliverable of the request unmapped (see [request coverage](#request-coverage)) or has post-release criteria (deferring them needs explicit consent), except under `clarification: "assume"`: there the automatic approval defers them, lists each deferred criterion in the approval request (`deferredCriteria`) and in its decision record, and acceptance reports them as deferred. The task limit counts the tasks the planner submitted: tasks the host adds by splitting an oversized test task during plan-time sizing do not count, because the person approves the plan and not the split.

A spec lists the deliverables of the request in `deliverables`: each has a `quote` copied from the request (a CLI, an API, a library, tests, documentation) and the `requirementIds` that cover it, or, for something the request itself leaves out or defers, no requirements and an `outOfScope` quote of the request's words that say so. The spec author's submission is checked against the request text, ignoring case, quotes and whitespace: a request that describes a program needs the list, a quote that is not a passage of the request, an unknown requirement, a deliverable with neither requirements nor an exclusion, and an exclusion the request does not state go back to the spec author like the other spec corrections. A deliverable with neither requirements nor an exclusion is mapped by the host first, and recorded in `spec-repairs/deliverables.json`: an entry of the spec's `outOfScope` that quotes the request and names it becomes its exclusion, else the requirements whose text holds its words cover it, else a request sentence that turns it down ("No CI workflow is wanted") becomes its exclusion; only a deliverable none of these fits goes back. A spec that still leaves a deliverable unmapped is accepted, but auto approval declines it (`Request deliverable not covered by the spec: ...`) and a person decides. The approval request carries the table as `requestCoverage`; the terminal approval prompt shows it under "Request coverage" and the desktop app under "What the request asks for and what covers it", with uncovered rows marked. A feature of an initiative is not checked: its boundary is approved with the split. Specs without `deliverables` (from earlier runs, or written for a request that describes no program) keep working unchanged.

The planner plans with these limits in view. When `limits` is set, its input carries `approvalLimits` (task and file counts, `allowedPaths`, `allowDelete` and the always-human paths), and it is asked to keep its writes within them unless the requirements need a file outside them. When a submitted plan would still go to a person, the planner is told once per run which writes cause it and may drop optional ones; a plan submitted again with the same writes is accepted and waits for a person at approval as before. Later plan generations of the run (a revision, a resumed plan stage) are not told again (`plan-repairs/scope-advice.json` records that the advice was given). The advice leaves out writes the planner cannot drop: a file the request names by path or file name, and the delete of a .NET template placeholder (`UnitTest1.cs`, `Class1.cs`). When only such writes need a person, the plan is accepted at its first submission. Only the host decides the approval; the advice changes what the planner proposes, not what the host approves. The advice also tells the planner that the person's approval covers every write the plan lists, and to keep approval out of task text. The host removes the sentences that make a task wait for approval (such as "this workflow path requires human approval") from each task's description and rationale before storing the graph. The implementer is told that the approved plan authorizes every write in its task's scope, so it does not refuse an approved write to a CI workflow or a manifest.

**Approval reviewer.** `"modelReview": true` in `autoApproval` (it needs `limits`), or `--approval-review` on `baked workflow run` and `baked quick` (`approvalReview: true` on `POST /v1/workflow/runs`), sends a package that leaves the limits only by its task count, file count or paths to the built-in `approval-reviewer` profile (role `reviewer`, model class `$review`, read-only). It reads the request, the spec's scope and requirements, every task's writes and the reasons auto approval declined, and returns `ApprovalReviewSchema`: `verdict` (`approve` or `escalate`), `risk` (`low`, `medium` or `high`) and its reasons. Only `approve` at `low` risk approves; the approval is stored like any automatic one, with mode `model-review` and the verdict in its answer. Anything else, a missing profile, an invalid answer or a failed call leaves the request with a person, and the request body carries `autoApproval.review` or `autoApproval.reviewError`, which the TUI approval prompt and the desktop approval card show under the declined reasons. The reviewer never sees packages with always-human writes, deletions, a token budget above the limit, uncommitted user changes in scope or post-release criteria, and it cannot change the plan, paths, tools, network or budget. A model approval is not a human approval: renewal still compares with the last approval a person gave. Chat tool approvals are not covered ([#599](https://github.com/Gulliby-development/baked/issues/599)).

An automatic approval is stored on the same approval request with the same digest a person would sign. Its actor is `auto-approval`, and its answer contains the mode and a hash of the limits. The event log shows `Decision accepted (auto approval)`. When auto approval declines, the request stays pending for a person, and `autoApproval.declined` in its body lists why.

### Notifications when a run waits

A run that starts waiting for a person is announced once: a pending request (approval, clarification, manual evidence, recovery, checkpoint, delivery) or a run that becomes blocked, such as one whose token budget ran out and needs `workflow extend`. The process that drives the run announces it: the terminal app, `baked workflow run|resume` or `baked serve`. The database records each announced request in `attention_notices`, so a request is announced once even when several processes share the workspace; a run blocked again later is announced again. Requests already waiting when BAKED is upgraded are not announced.

Each announcement goes to three places:

- **A `RunAttention` hook** ([extensions](../extensions.md#hooks)), matched against the request kind or the blocked reason. Its stdin adds `run_attention`: `run_id`, `feature_id`, `request_id` (null for a blocked run), `kind`, `blocking` and `status`.
- **A webhook**, only when `notifications.webhook.url` is set. It receives one `POST` with a JSON body; it carries no request body, prompt or file content:

  ```json
  {"event": "run.attention", "project": "shop", "workspace": "/home/me/shop", "runId": "...",
   "featureId": "checkout", "requestId": "...", "kind": "approval", "blocking": true,
   "status": "waiting", "message": "Waiting for approval", "createdAt": "2026-10-11T08:00:00.000Z"}
  ```

  `headers` adds request headers, such as an authorization token; `blockingOnly: true` skips advisory acceptance decisions (`blocking: false`), which the run does not wait for. Only `http://` and `https://` URLs are used. A failed delivery is logged and not retried.
- **A native desktop notification** from the terminal app and from `baked workflow` run in an interactive terminal, for blocking items only: `osascript` on macOS, `notify-send` on Linux (when installed) and a PowerShell toast on Windows. `notifications.system: false` turns it off, and so does the environment variable `BAKED_NO_SYSTEM_NOTIFICATIONS=1`, which the test suite sets so a test run never reaches the developer's notification centre. `baked serve` shows none: the desktop app raises its own from `GET /v1/attention`.

```json
"notifications": {
  "system": true,
  "webhook": { "url": "https://example.com/baked", "headers": { "authorization": "Bearer ..." }, "blockingOnly": false }
}
```

The desktop app edits the same settings under Settings, All projects, Run notifications. In the terminal app, `/notifications` shows them and opens a menu, and `/notifications system on|off`, `/notifications webhook URL|off` and `/notifications blocking-only on|off` change them in the global config; an idle workflow worker restarts to apply the change, and a worker driving a run applies it after BAKED restarts. Headers stay in the config file on both.

## Gates, budgets and estimates

### Gates window

A gate is one entry of `workflows.policy.checks` in `.baked/config.json`. `/workflow gates` (or G on the runs screen) opens the window that lists, adds, edits and removes them. N adds a gate, E edits the selected one, D removes it after a confirmation, R runs it now and shows the outcome, the exit code, the duration and the last 40 lines of output, and S shows what the project already offers.

- The command is one line split into an executable and arguments without a shell; quotes group words. Timeout is in seconds. Required, scope (`feature` or `task`), the env names that may be passed through and the generated outputs (`writes`) are the existing check fields. The same validation as for a run applies, so a duplicate ID or a directory outside the workspace is refused at save time.
- Saving writes only `workflows.policy.checks` and keeps every other setting of the project config. A project without a `workflows` block gets one with the default policy and `enabled: true`.
- A run takes a copy of the policy when it starts. Changing gates affects the runs created afterwards. Changing the gates of a started run still goes through `candidate` and `revise`.
- Run now goes through the workflow worker, so the interface stays responsive; Esc stops the process tree. It uses the same safe environment and timeout as a run. It records no evidence. It is refused while a run holds the workspace, because the command could change the files that run is checking. It needs workflows to be enabled, so a disabled project starts no worker.

### Gates from chat

Every chat session (the desktop chat, `baked session`, and the coordinator in the desktop app, the terminal UI and `baked session coordinator send`) has two gate tools. `list_gates` shows the configured gates, the ones BAKED detects in the project and the workflows that cannot start until a feature gate exists; it runs nothing. `save_gates` adds, replaces (same ID) or removes gates: a detected gate by its ID alone takes its command, timeout and fixer, any other gate needs a command. Each save shows an approval prompt listing the commands and writes nothing unless you approve it. Saving writes `workflows.policy.checks` like the gates window and gives new runs of the same process (the server, the terminal UI's workflow worker) the new list; started runs keep theirs. The coordinator also sets missing gates up together with a run, on its Run workflow card ([coordinator](../coordinator.md#workflows)).

### Baseline comparison in update runs

A check passes on its exit code, so a linter that exits 0 with new infos or warnings, or a test suite that now runs fewer tests, used to pass an update run unnoticed. In a run whose workspace already held source code (facts kind `source`), the runtime runs every feature check once before the approval request, on the code the run starts from, and stores the counts its output reports in `facts/check-baseline.json`: the diagnostics of Biome, ESLint, Ruff, tsc, Clippy (`cargo clippy`/`cargo check`) and `dotnet build`, and the tests of `bun test`, Jest, Vitest, pytest, `cargo test`, `dotnet test`, Maven Surefire and `go test -v`. A test count is kept only from a passing run. When a required check later passes with more diagnostics, or fewer tests, than its baseline under the same command and tool, it counts as failed: the finding `Required check X failed` says by how much (`diagnostics rose from 0 to 2 against the code the run started from (biome)`), the check's fixer runs first when it has one, and the rest is repaired like any failed check. Fewer tests are accepted when a task of the plan deletes a test file. Output no parser recognizes, a truncated or inconclusive baseline run, a changed command, a scaffold or empty workspace, and a run resumed after a task started measure nothing and compare nothing. The baseline costs one extra run of each feature check per update run; it records no evidence and does not appear in the run report's checks.

The same baseline run records, by command, the output of each required check that already fails before any change (`failures` in `facts/check-baseline.json`). A scaffold or empty workspace runs only its required checks for this and stores no counts. The baseline runs before the approval request, so the request body carries `baselineFailures`, the IDs of those checks, and the TUI approval and the desktop run decision and Needs you detail show "Required checks that fail before any change" under the checks. A greenfield test check usually fails there because its tests do not exist yet; one whose failure the plan cannot change, such as a stale `build` script, is the one to fix before approving. When a required check in the checks stage fails with the same output as before any change (colours, durations, timestamps and the workspace path left out; a path into any of the project's worktrees, `.baked/worktrees/<run>/main` or a task's `.../T005`, and the working copy itself all count as the workspace, so a stack trace that names another worktree is still the same failure), nothing the run changed affects it: a corrective task could only spend attempts on it, so the run stops at once as `no_progress` with `baseline_failure: required check X failed before any change and fails the same way now`, naming the evidence. Fix the check or the project setup (for example a `vite build` script left in the scaffold of a Bun CLI), or revise the plan, then resume. A check that fails without output, and one whose output changed (a scaffold's tests fail one way before the tests exist and another way after), are repaired as before.

### Custom gates

A gate can be any script or container that reports its result as JSON: set its result to JSON report (`"report": "json"` on a policy check, or on `command` in a gate file under `baked/gates/`; the Result toggle in the TUI form and on the desktop Setup > Gates form). The command prints one JSON object as its last JSON line on stdout or stderr; earlier log lines and other text are ignored:

```json
{"status": "failed", "summary": "2 leaked keys", "findings": [{"severity": "high", "message": "AWS key in fixture", "path": "tests/fixtures/env.json", "line": 4}]}
```

- `status` is `passed`, `failed` or `inconclusive`; `summary` (up to 2000 characters) and `findings` (up to 100, each with `severity` `critical|high|medium|low`, `message`, optional `path` and `line`) are optional.
- The report decides the check. A `passed` report counts only with exit code 0; a pass from a command that exited nonzero, a missing report or a malformed one makes the check inconclusive (reason `report_exit_mismatch` or `no_report`), which blocks a required gate without starting a repair. A `failed` report fails the check like a nonzero exit and starts the repair.
- The report is appended to the check's output as `Gate report: STATUS. SUMMARY` with one `- [SEVERITY] PATH:LINE MESSAGE` line per finding, so the repair task and the run report see where to look.
- A container is a command like any other, for example `docker run --rm -v .:/work -w /work IMAGE audit --json`; it runs without a shell, with the gate's timeout and the env names it declares. Run now treats an `inconclusive` report, or a pass that exited nonzero, as an error.

Detection offers gates; nothing is added until the user confirms. It reads the project root only:

| Ecosystem | Found by | Suggested gates |
| --- | --- | --- |
| bun, npm, pnpm, yarn | `package.json` scripts; the runner follows the lock file | `typecheck` (also `type-check`, `check-types`), `lint`, `tests` (the npm placeholder test script is ignored), `build` (advisory, not preselected) |
| Python | `pytest.ini`, `[tool.pytest]` in `pyproject.toml`, `[tool:pytest]` in `setup.cfg`, `[pytest]` in `tox.ini`, `conftest.py`, or a declared pytest dependency | `pytest`: `python -m pytest -q` (`python3` outside Windows) |
| Python lint | `ruff.toml`, `.ruff.toml`, `[tool.ruff]`, or a declared ruff dependency | `ruff`: `ruff check .` |
| Go | `go.mod` | `go-vet`: `go vet ./...` with the fixer `go fmt ./...` (`gofmt -l` exits 0 whatever it lists, so formatting is applied by the fixer, not verified), `go-test`: `go test ./...` |
| .NET | a `.slnx`, `.sln`, `.csproj`, `.fsproj` or `.vbproj` file in the root (solutions first; with several such files the first is named on the command line, because `dotnet` refuses an ambiguous folder) | `dotnet-build`: `dotnet build`, `dotnet-format`: `dotnet format --verify-no-changes` with the fixer `dotnet format`, `dotnet-test`: `dotnet test` |
| Rust | `Cargo.toml` | `cargo-fmt`: `cargo fmt --check` with the fixer `cargo fmt`, `cargo-clippy`: `cargo clippy --all-targets -- -D warnings`, `cargo-test`: `cargo test` |
| Java (Maven) | `pom.xml` | `maven-verify`: `mvn -B -q verify` |

Workspace facts list `go.mod`, `Cargo.toml`, `pom.xml`, `global.json` and any `.csproj`, `.fsproj`, `.vbproj`, `.sln` or `.slnx` file among the manifests, and the project line of the context names a .NET project.

**Language review.** When the policy names no `reviewProfiles.language` and the workspace root holds a Go, .NET, Rust or Java manifest, the run starts with the `language-reviewer` profile as its language review dimension. It looks for platform and idiom pitfalls a general reviewer misses: platform newlines in output the spec fixes byte for byte (`Environment.NewLine` is CRLF on Windows), hard-coded separators in tests, culture-dependent formatting, ignored errors, unreleased resources and code the language's formatter or linter rejects. This review runs only when the change touches a file of those languages (`.go`, `.cs`, `.fs`, `.vb`, project and solution files, `.rs`, `.java`, `.kt`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle`); a change to documentation or scripts alone skips it and acceptance does not require it. A policy that sets another profile keeps it, and that profile always runs. The language dimension, whichever profile runs it, sees only the request and the patches of the changed files (no spec, plan, task graph, check output or other reviews), about a third of the context the correctness review gets. It reports no criterion coverage, since correctness and convergence own that, and its verdict follows from its findings alone.

**Review rounds after a correction.** A repair or convergence correction keeps the round's reviews, with the source manifest and the snapshot they reviewed, as the run's `priorReviews`. The next review round treats each dimension in one of two ways:
- **Kept.** A dimension with no inconclusive criterion is kept, and runs no agent, in two cases. Its previous review passed with no finding and no changed file is in its scope: the language dimension's scope is its language files, the security dimension's scope is the security-sensitive paths, and every other dimension's scope is any changed file. Or its previous review only repeated notes: it raised findings, none of them started a correction, and each is a note that repeats a note of an earlier round (the run report's **Repeats** column), so the dimension already ran again after a correction and found nothing new; it is kept whatever changed, and its notes stay in the report. The converge stage still checks the whole change. The run records `reviews/carried-KEY-SNAPSHOT.json` with the files changed since.
- **Rerun.** A dimension that runs again gets `previousRound` in its context: its findings of the previous round, the files changed since, and a patch of those changes against what it reviewed (up to 24,000 characters). It checks those findings first and sets `repeatOf` on a finding that is the same defect.

**Portable tests.** Checks run only on the host's operating system, so the profiles guard the tests a run writes against the usual cross-platform failures: the spec author adds a criterion that the product's tests pass on Windows, macOS and Linux only when the request names CI or other operating systems (CI, GitHub Actions, Windows, macOS, Linux, cross-platform) or the project already runs CI (`.github/workflows/*.yml`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `.circleci/config.yml`, `.travis.yml`); the host passes it as `extra.crossPlatform`, and otherwise the spec adds no CI, platform matrix or release automation the request does not ask for. A request that names other operating systems but turns CI down ("No CI workflow is wanted", "without GitHub Actions") gets a note to write only what this host can check instead. An automated criterion that still claims behavior on several operating systems, browsers or real devices does not send the spec back to its author: the host keeps the claim as a `post-release` criterion, adds an automated criterion for what this host proves (platform-neutral path, line-ending and process APIs; the tests pass here) to each requirement the claim leaves without a criterion this run can check, and records both in `spec-repairs/host-bound.json`; the implementer compares resolved paths (a macOS temp directory under `/var` is `/private/var`), builds paths with the path module, does not depend on one line ending and gives spawned processes generous timeouts; the correctness reviewer reports a test that would fail on another operating system as a correctness finding.

**Layout criterion.** The sdd workflow does not render pages, so for a product with a graphical or web user interface the spec author adds a criterion that its pages fit a 1280 px wide viewport without horizontal scrolling, or names the region whose scrolling the request makes deliberate. The criterion gives the implementer and the reviewers a stated layout target; checking it in a browser is the v2 `ai-acceptance` gate.

**Documented examples.** Before the review, the host runs the command examples of the Markdown files and READMEs the run changed and hands the correctness reviewer the result as `extra.documentedExamples`, so the reviewer spends no model steps running them. An example is a fenced block whose `$ ` lines are commands followed by their output, or a shell block of one command followed (after at most two lines of prose) by a plain block of its output. The host runs a document's examples in order, in a copy of the workspace with its installed dependencies linked, so commands that write data leave the workspace as it was; each runs like a repro (one argv without a shell, a program the run's checks start, at most 30 seconds, the run's sandbox), and at most 8 run per review. Each example has the status `match`, `mismatch` (with `firstDifference`: the first documented line that differs and the line printed in its place) or `not_run` with the reason (a command that needs a shell, a program no check starts, the limit, a workspace over 64 MiB, `placeholder:`, or `needs build:`). A command with a placeholder argument (an all-caps word such as `FILE` or `--out=PATH`, `<file>`, `[options]`) is a usage line, so the host does not run it and does not compare it with the block after it. A command with an argument under a build output directory (`bin/`, `obj/`, `target/`, `dist/`, `build/`, `out/`) that does not exist, such as `dotnet src/App/bin/Release/net10.0/app.dll` after a documented `dotnet build`, is `not_run` with `needs build:`: the host copies the source files and does not build, and the reviewer reports no finding for it. A mismatch is a correctness finding whose repro is the command; the reviewer runs a `not_run` example other than a placeholder or needs-build one, or a help-text example in source code, with `run_repro` when it can. The results are kept as the `diagnostic` artifact `reviews/examples-SNAPSHOT.json`, so a resumed review does not run them again. A review attempt has 16 model steps (at most the profile's and the policy's `maxAgentSteps`), and an attempt that ends unsubmitted gets one retry with 24. The examples are written from a real run in the first place: a task that writes a README, Markdown or reStructuredText file gets `run_probe` even when it is planned, and the implementer runs each documented command on the program in the workspace and copies what it prints instead of inventing output. An example whose output the request or the spec gives verbatim (a worked example, an output block) is copied as given, even when it uses files the workspace does not have, and the implementer names the copied examples in its summary.

The same detection fills the checks written when E enables workflows on the runs screen; the build gate is not part of that set. Gates that are already configured (same ID or same command) are not offered again. Existing CI scripts are not read. On Windows, give the command name (`npm`, `pnpm`, `yarn`), not the shim file: Bun launches `npm` without a shell, but a name ending in `.cmd` fails with `EINVAL`. Only `npm` was tried on this host (npm 11.16); `pnpm` and `yarn` were not installed here.

### Token accounting and reservations

An agent attempt records its spend as each model step finishes, not only when it returns. An attempt that fails, is cancelled or stops on a cap is charged the tokens of its finished steps, writes `attempts/ID/usage.json` with stop reason `error` or `aborted` where it threw, and releases its reservation; `baked workflow usage` therefore includes failed attempts. Only an attempt interrupted by a crashed process, whose executor left no record, keeps its reservation as unknown usage. An attempt whose model steps all reported zero input and zero output tokens is not counted as free either: Codex reports a response's usage only once its tool call is answered, so an attempt that ends at its only tool call (the submit) never hears its spend. Such an attempt that returns a result is charged an estimate from the sizes of what it sent and received, at about 4 bytes a token: the prompt once per model step as input, and its text and tool call arguments (the submitted result among them) as output. The estimate is its `usedTokens`, counts toward the run's tokens, budget and `estimatedCostUsd` (priced as uncached input and output) and releases the reservation; `usage.json` records it as `estimatedUsage`, the `attempt.finished` event has `usageComplete: false` with `usageEstimated: true`, and the Markdown of `baked workflow usage` counts these attempts under "Estimated usage". One that fails or is interrupted without a result is charged its recorded steps as above. A model attempt's `usage.json` also records the reasoning effort it sent to the provider (`effort`, the `effort` or `reasoningEffort` of its provider options; absent when none was sent), and its `attempt.finished` event carries its `spend`: input tokens (cache reads included), output, cache reads, cache writes, the effort and the estimated cost at the model's list price (null when the model has no price). Each priced attempt adds its cost to the run's `estimatedCostUsd`, so the run snapshot (`GET /v1/workflow/runs/RUN_ID`, the JSON of `baked workflow status`), the desktop run list and run screen and the run report show a cost, and a provider whose tokens are mostly cache traffic (Claude Code) can be compared with one whose are not. `baked workflow usage` returns the effort of every attempt, and its Markdown groups the **By model** table by model and effort. The Codex app-server provider also waits briefly for a usage report that arrives after the turn completed, and a report that arrives between two steps of a thread is counted by the next step.

Before each step the attempt reserves its spend so far plus an estimate of that step: the input tokens the provider reported for the previous step, adjusted by the bytes added or compacted since at three bytes per token, and an output of twice the largest output seen (at least 4096 tokens, at most the profile's output cap). Before any usage is known it counts the messages at three bytes per token plus 8192 tokens for the system prompt and tool definitions. A step is refused (`Next model step exceeds remaining token budget`, with the used, held and requested tokens) only when the spend plus this estimate would pass the run limit. The attempt cap is `maxAttemptTokens` or, when less, what the run limit still leaves after the other attempts, so an attempt that starts near the limit switches to its submit-only final step in time instead of failing mid-loop. Token caps come from history and defaults, but one step costs very different amounts on different providers, so the cap also has a step floor: once steps have run, the cap is at least 10 steps (or the attempt's step limit, when lower) at the attempt's average step cost so far, up to what the run limit still leaves. The cap counts each step's input less its cache reads, plus its output (`cappedTokens` in `usage.json`): every step replays the cached prefix of the earlier ones, which costs a fraction of new input, and counting it in full ended 37 of 85 codex task attempts at the cap in one bench round. A provider that reports no cache split is counted whole. What the run limit still leaves counts every token, cache reads included, so an attempt also switches to its final step before it would pass that. The attempt's `usage.json` records the cap after the floor, the tokens it counted against it and all its tokens (`totalTokens`).

A task attempt that reaches its step or token cap, submits an incomplete result and has edited files continues once: the task becomes ready again with both caps raised by half (`taskContinuations` in the run state records it), and the next attempt gets the files as the earlier attempt left them. In a run with several writers the task's worktree is discarded, but its edits are kept (`taskCarry` in the run state): the continuation's new worktree gets each edited file back, journaled as that attempt's own edit, unless the base changed the file meanwhile, and the prompt carries the same `earlierEdits` patch as in a single-writer run. A second incomplete attempt of the same task, an incomplete attempt that edited nothing, or one that did not reach a cap blocks the run as before. The run budget still bounds every attempt.

A step that stops at the profile's output cap (finish reason `length`) usually carried a tool call that was cut off and did not run. The next step gets a notice once, naming the cap and asking for smaller edits; like the finalize notice, it stays at the position where it first appeared so the replayed prefix is unchanged. The implementer's output cap is 16384 tokens.

### Progress watcher

Every agent attempt that submits a result is watched for a stuck loop before each model step. The rules, checked in this order over the attempt's own steps:

- **Repeated reads**: the same `read`, `navigate`, `bake_find` or `bake_impact` call, with the same input, three times since the last edit.
- **Same failure**: the last three `request_check`, `run_probe` or `run_repro` results are the same tool with identical output.
- **No edits**: ten steps with tool calls and no edit, for an implementer whose task writes files.

The first signal adds one steering message that names the pattern and asks the agent to apply the change, change approach, or submit what blocks it as unresolved. The attempt is stopped only when the same pattern goes on after that message: the same read or the same check result again, or three more steps without an edit. An edit clears the signal, and an attempt is steered at most once. The stop switches the attempt to its submit-only final step (stop reason `watcher` in `attempts/ID/usage.json`), so the run gets a result with the blocker listed instead of spending the step or token cap; an attempt the watcher stopped does not get the continuation with raised caps. Both the steering message and the stop are recorded as an `attempt.advisory` event, shown in the activity feed of the TUI run view and the desktop run screen and in the `--events` stream of `baked workflow run` and `resume`.

The watcher only sees one attempt from inside its model loop. A provider call that hangs, or a host process that stops, is not detected here ([#604](https://github.com/Gulliby-development/baked/issues/604)).

### Run cost

A run's estimated cost in USD is `estimatedCostUsd` in its status (`baked workflow status RUN_ID`, `GET /v1/workflow/runs/RUN_ID`) and in `budget.updated` events. Each model attempt adds its cost when it finishes, priced from its `attempts/ATTEMPT/usage.json` with the model's price table: uncached input, cache reads, cache writes and output each at their own price, so a cache-heavy run (most of a claude-code run's input is cache traffic) costs far less than its token count at the input price. Host attempts, attempts without per-step usage and models without a price add nothing; the cost stays null until a priced attempt finishes. Runs recorded before the run kept its cost get it summed from their attempts' usage. The TUI shows it under the Tokens bar of a run and on the run list, the desktop app in the run header, run list and project home. The token limits still count every token alike; a run that should stop on dollars sets a cost cap.

### Cost cap

`maxCostUsd` caps a run's estimated cost in USD. It is opt-in: the default is `null`, the built-in policy and every budget preset keep only token, call and time limits, and a cap works beside them, never instead of them. A run takes the first cap that is set:

1. the one asked for at start: `baked workflow run --max-cost-usd N`, `maxCostUsd` in `POST /v1/workflow/runs`, or the Cost cap field of the TUI new-run form and the desktop start form;
2. `maxCostUsd` in the policy (`workflows.policy` in the config, or a `--policy` file);
3. the Cost cap setting, `runBudget.maxCostUsd` in the global or project config (Settings, Timeouts and limits in the desktop app; `/timeouts`, Workflow Cost Cap in the TUI). It is a key of its own because a project's `workflows` replaces the global one and must carry a whole policy.

The run freezes the cap in its policy at start, so a later change of the setting does not touch running runs.

- At start, and on every reroute, each model the run can call (the run model, every stage and profile route and their fallback models) must have a price in `src/core/llm/pricing.ts`, the one price table every provider shares. A model without one is refused with `maxCostUsd needs a price for every model the run can call; no price is known for MODEL`, so no model can spend outside the cap. Family guesses and Copilot request prices count as priced; they are approximate, like the cost itself.
- Before each model call, and before each step widens an attempt's reservation, the cost spent (`estimatedCostUsd`), the cost every other open attempt reserves and the call's own tokens must fit under the cap. Reserved tokens are priced at the run's cost per token so far, which carries its cache share; before anything is priced, the model's input price stands in. Parallel attempts therefore reserve against what is left, and the last wave of a run does not start tasks the cap cannot pay for. A call that does not fit stops the run with `budget_exhausted` (`The next model call would pass the run's cost cap`), like the token limit.
- `baked workflow doctor` and `baked workflow estimate` take `--max-cost-usd N` too (`maxCostUsd` in `GET /v1/workflow/doctor` and `/estimate`). With a cap and a priced estimate, the estimate carries `cost: { maxCostUsd, fits }` and prints `Cost cap $N: fits | may be passed | will very likely be passed`; the doctor adds a `budget.cost` warning when the estimate's cost may pass the cap. The desktop start form shows the same under its Cost cap field.
- Status carries the cap as `maxCostUsd` (left out when the run has none). The TUI shows `about $X of the $Y cap` under the Tokens bar and names the cap when it stopped the run; the desktop run screen shows a Cost cap meter and `$X of $Y` in the header.
- Raising the limits of a capped run (B in the TUI, Extend in the desktop app, `workflow extend` with no values) doubles the cap when the spent and reserved cost reaches 80% of it, or when no token, call or time limit is 80% used, so the cap is what stopped the run. `--cost-usd N` (`costUsd` in `POST /v1/workflow/runs/RUN_ID/extend`) sets a cap of its own; it can only go up, and a run started without a cap cannot get one by extending.

### Raising a budget limit

A run blocked with `budget_exhausted` shows B (raise limits) next to fork and cancel. The confirmation names the new values: every limit that is used up, or at least 80% used, doubles, and the tokens double when nothing else explains the stop; calls stop at 1000, active time at 24 hours and tokens at 50 million. Y applies it and the run continues from the stage that stopped.

```sh
baked workflow extend RUN_ID --expected-revision N [--tokens N] [--calls N] [--time-ms N] [--cost-usd N]
baked workflow resume RUN_ID --expected-revision NEW_N
# or both in one command, with the exit codes of resume:
baked workflow extend RUN_ID --expected-revision N --tokens N --resume [--events]
```

Limits can only go up, and `--tokens`, `--calls` and `--time-ms` are absolute values: a lower value is refused with the limit's current value and the one asked for (`Limits can only be raised: tokens 3,493,710 now, you asked 3,000,000`). The change is stored as the immutable artifact `policy-revisions/COMMAND_ID.json` (previous and new limits, both policy hashes, usage, the stage) and the run moves to `paused`. Scope, tools, checks, the stage, the evidence and the approval digest are untouched, so no new approval of the plan is needed and nothing is re-run. The user's command is the approval of the new limits. When `autoApproval.limits.maxTotalTokens` covered the old token limit, it is raised with it, so a later scope approval is not sent to a person only because of the larger budget; a bound set below the old limit is kept. For the same reason `autoApproval.renewal` accepts the extended limits: they are the policy the operator set (see [Auto approval](#auto-approval)).

An implementer attempt that uses its token cap without submitting a result after changing files continues once, also when its last step went past the cap before a final submit could be forced, like an attempt that submitted at the cap: its task runs again on those edits with both caps raised by half, and the other tasks of its batch are integrated. Any other agent attempt that uses its own token cap (the task's sized cap or `maxAttemptTokens`) without submitting a result, including that continuation, blocks the run with `attempt_cap`, not `budget_exhausted`: the run budget is not used up, so there is nothing to extend, and `workflow extend` refuses such a run with that explanation. Resume it (R in the terminal UI, Resume in the desktop app, `baked workflow resume`): the task goes back to pending and continues on the edits already in its workspace. The tasks that finished next to it in its batch stay implemented, so the resume does not run them again.

### Soft token checkpoints

The budget preset `checkpoints` removes the hard token cap (the limit becomes 1,000,000,000) and sets `checkpointTokens`, by default half the configured token limit (400k with the default policy). Calls and time are doubled like the extended preset. A run never reserves tokens past the next multiple of the interval: when the next model step could pass it, the step does not start, the run moves to `waiting` with reason `checkpoint` and a durable request of kind `checkpoint` records the usage. The same guard applies to every step of one agent loop, so a runaway loop stops at the checkpoint and not after it.

C (or Enter) continues up to the next checkpoint, one interval beyond the projected spend; X stops the run in `paused`, and resuming asks again instead of spending. From the CLI:

```sh
baked workflow continue RUN_ID --request REQUEST_ID --expected-revision N
baked workflow resume RUN_ID --expected-revision NEW_N
```

Set `workflows.policy.checkpointTokens` (at least 10000, or `null`) to choose the interval of the preset. A call interrupted by a crash, whose usage is unknown, keeps its reservation and counts toward the next checkpoint.

### Estimates

All numbers are estimates and are labeled as such. The new-run form shows a range before the start, and the run screen shows a re-estimate, the burn rate and a forecast.

- The range is built from the runs already in this project: per stage the middle half of the samples (the full spread with two or three samples, minus 30% to plus 40% around a single one), a typical number of tasks and the cost of one task. Without history it uses generic ranges and says so.
- The form compares the range with the chosen preset: it fits, the high end exceeds the budget, or even the low end does. The checkpoint preset has no cap, so it only reports the interval.
- After the plan exists, the remaining cost is the open tasks times the typical task cost plus the later stages, less what the running stage already spent. The burn rate is tokens per active minute, and the forecast names the stage where the budget runs out at the typical cost and at the high end.
- The range shown at creation is kept as `estimates/start.json`, with the approximate cost and the workflow ID. A completed run shows it next to the actual usage.

`baked workflow estimate [WORKFLOW]` prints the estimate before a run, stage by stage and model by model, with the options of `workflow run` that change it (`--model`, `--route`, `--policy`, `--worktree`, `--writers`, `--candidates`, `--json`):

- Only the definition's stages count. History is this project's runs plus those of the stores in `sizing.historyStores`, and the basis line says how many came from other projects. A stage uses earlier runs of the same workflow when they reached it, then runs of other workflows, then a generic range by stage type (tasks stages: task cost times task count; approval, check and learn stages without history: zero). Once the history holds at least 3 runs whose tokens went mostly to the model most planned stages run on, only those runs count, since providers spend very differently on the same work; with fewer, every run counts and a note says the history mixes models.
- Each stage carries the models routing gives it: the stage route, else its profile's model; tasks stages use `implementer`, review stages their review profiles, and their tokens are split evenly.
- The cost in USD prices 60% uncached input, 30% cache reads and 10% output at the prices in `src/core/llm/pricing.ts`. The estimate leaves cache writes out, so Anthropic costs read low. Family guesses and Copilot request prices are marked approximate; a model without a price is left out and the cost is marked partial. The estimate is advice only; a run's [cost cap](#cost-cap) is enforced on its measured cost.

### Doctor

`baked doctor` (short for `baked workflow doctor [WORKFLOW]`, same options as `estimate`) checks a run before it starts and exits 1 when something must be fixed:

- Start refusals: workflows disabled, then everything `workflow run` would refuse (policy, definition, routing, gates and their confirmation, auto approval confirmation, profiles, skills, worktree prerequisites, writers). The doctor calls the same validation as the start.
- Credentials: every model the run can call (stage routes, stage profiles, review and skeptic profiles, and every profile that may implement a task) needs a known provider with a key. These are the same checks a start makes: a primary model without credentials fails; an unknown provider, an unanswered check, a fallback model or an unbound profile warns.
- Commands: every check command and AI walk-through start command resolves from its working directory. Missing required ones fail, optional ones warn. Nothing is executed.
- Sandbox: the run's OS sandbox mode against this machine's backend; `required` without a backend fails, `auto` without one warns.
- Warnings that do not block: review on the implementer's model, an MCP grant of a profile that no enabled server provides, uncommitted changes, stale run worktrees, no Git repository for an inline run, a run that exited without releasing the workspace, and an estimate above `maxTotalTokens`.
- A live run holding the workspace, or one that stopped with a command of unknown outcome, fails.

`--json` prints the report with every check's `id`, `status`, `title`, `detail` and `fix`, and the estimate.

### Context compaction

Every model step resends the whole conversation, so a stage that reads many files pays for each old file again on every later step. The step budget of an agent attempt (`maxAttemptTokens`, see [step-budget](../../src/core/workflows/step-budget.ts)) replaces older large results of `read`, `navigate`, `bake_find` and `bake_impact` with short stubs that keep every evidence ID; the last three tool results stay verbatim, and edits and check results are never compacted. Evidence is written by the tools into the run store, so nothing is lost; the model reads a file again if it needs the content.

An agent profile can change this for its own attempts with an optional `compaction` object (#334). `keepRecent` (1 to 20) sets how many tool results stay verbatim. `startAtTokens` (a token count) or `startAtShare` (a share of the attempt's token cap, above 0 and at most 1), never both, holds compaction off until the attempt has spent that much; from then on it stays on, so the cached prefix keeps matching. A profile without the object compacts from the first step and keeps three results, as above, and no built-in profile sets it. For example, a project copy of `baked/agents/implementer.json` with `"compaction": { "keepRecent": 2 }` compacts earlier on small tasks, and a reviewer with `"compaction": { "startAtShare": 0.6 }` keeps full context until 60% of its cap. This applies to agents run through BAKED's own model loop; the Claude Code and Codex CLI transports keep their own context.

The evidence handed to later agents is shaped the same way. Each implemented task stores a unified diff of its changes in its `diff` evidence (`patch`, from the content kept before each edit, cut at 48,000 characters), so reviewers and the convergence auditor see the change without reading whole files. Earlier `read` evidence reaches them as its tool, the paths it named and its size, not its content; implementers get no reads at all. An implementer of a planned task gets no check logs either (`command` evidence); a corrective task still gets the logs of the checks it fixes.

An implementer's prompt is trimmed to what writing its task needs, since every step of the attempt resends it: no research (the spec and plan carry what it found), the other tasks of the graph only by ID, title, dependencies and written paths (its own task arrives whole in its input), and only its own profile in the execution contract. The files the task modifies come preloaded in its input (`taskFiles`), as the read tool shows them: whole with line numbers up to 24 KB each and 64 KB in total, outlines above that ([read-outline](../../src/core/workflows/read-outline.ts)). Under an outline come the spans of the declarations whose names appear in the task's title or description (identifiers of four or more characters), as a range read shows them, up to 16 KB per file within the same total; a named class larger than that stays outlined. The implementer edits them on its first step instead of spending a step reading them. Files the task creates, missing files and binary files are not preloaded. A corrective task may write every file of the tasks it corrects, so the files its findings point at come first: the finding's `file`, the files a failing check's output names, and written paths named in the claim or the proposed fix, with the finding's `symbol` added to the names whose spans are preloaded. Its input lists them as `correctionFocus`. The correction's first attempt may write only those files and their planned tests (`correctionFocus.scope`: `writable`, with the rest of its scope as `later`); when the fix needs a file in `later`, the attempt reports it as unresolved, and a first attempt that does not finish is retried once with the full scope, keeping its edits. A correction whose findings name no file, or name all of its files, starts with the full scope. A failed linter, formatter or type checker (a static check, not a test check) names the files it rejects, including the failing task's own: its correction starts on those files only, without their planned tests, its proposed fix says to change only what the diagnostics require, with no behavior changes and no new tests, and `correctionFocus.diagnostics` tells the implementer not to probe the task's criteria (cfgtrace 424e275b spent 1.56M tokens and created two test files for three ruff rules). When a finding carries a review repro, its correction's task description starts with that repro: the implementer runs it with `run_probe` before editing, sees the output the review saw, and runs it again after the fix. In a run with several writers, where planned tasks get no preloaded files, a corrective task gets these files preloaded from its own worktree.

The stages that judge a plan or code against the spec (analyze, the reviewers, the skeptic and convergence) get a digest of a large spec ([spec-digest](../../src/core/workflows/spec-digest.ts)). Above 24,000 bytes of spec JSON, each criterion's given, when and then is cut to its first line (at most 160 characters) and marked `full: false` when something was cut, such as an examples table; the rest of the spec is kept. The digest's note tells the agent to call `read_criterion` with up to 12 criterion IDs, which returns those criteria as `spec.json` holds them (unknown IDs come back in `unknown` with the list of known ones). `read_criterion` is a host tool, so it works with every provider; a profile gets the digest only when its `allowedTools` include it, which the built-in spec-reviewer, reviewer, security-reviewer, skeptic and spec-auditor do. The spec author, the planner, the implementers and the diff-only language reviewer always get the whole spec, and so does every stage of a spec under the threshold. A policy with `specDigest: "off"` turns the digest off. A 43-criterion spec of 53.6 KB, each criterion with the request's examples as a table, was resent whole on every step of these stages, and planning came to $5.88 of a $9.97 run.

The implementer's input also lists the existing tests that exercise the files the task changes (`affectedTests`), nearest first and at most 24 ([affected-tests](../../src/core/workflows/affected-tests.ts)). The list comes from the relative imports of the workspace's JavaScript, TypeScript and Python files, followed back from each written path for up to three hops, plus the naming conventions that pair a source with its test (`store.ts` with `store.test.ts`, `store.py` with `test_store.py`) and every `_test.go` file of a changed Go package. Dependency and build folders are skipped, and a workspace of more than 6000 source files gets no list. When a policy check at the project root runs a test runner that takes files (`bun test`, `vitest`, `jest`, `node --test`, `pytest`, `python -m pytest`, `go test`), the implementer can also run `request_check <check>-affected`: the same runner with the check's flags on the listed tests only (packages for Go). Before the task's first attempt the host records the list and runs that check once as a baseline; the record (`affectedTests` in the run state: the paths, the check id, the baseline status and its evidence) is kept for the task and the corrective tasks that repair it, and a restart or replan clears it. When the baseline passed, the check is required after the task, next to the task's own checks, unless they already run the whole suite it narrows: a test the task broke fails the task even when that test is a file the task may not write, and the finding (`Task T001 broke existing tests: check test-affected passed before the task and fails after it`) starts a corrective task that fixes the change rather than stopping the run as out of scope. When the baseline failed or was inconclusive, the check stays optional and the implementer is told those tests failed before the task. A test file the task deleted is left out of the gate.

A workflow agent's `read` of a whole file larger than 20 KB (24 KB for a file its task writes, whose exact text the edit needs) returns the file's outline instead: its classes, functions, methods, types and top-level variables with their line spans, from tree-sitter ([read-outline](../../src/core/workflows/read-outline.ts)). The agent then reads the spans it needs with `ranges` or a symbol with `target`. A file with no outline (an unsupported language or a parse failure) is read whole, and reads with ranges or a target are unchanged. A compacted `read` stub asks for `fresh: true`, because the read tool answers a repeated whole-file read with "already in your context". Reads of line ranges or symbols are never compacted and always run fresh: they are small and chosen for an edit, and an agent that lost them, or was refused a fourth range of the same file, read the same spans again instead of editing. An implementer that must edit and has only read for four steps in a row is told once to apply its edits. A retry of a task whose earlier attempt left edits in place gets those edits as a patch (`earlierEdits.patch`) and reads only the spans it still has to change.

The prompt of an agent attempt puts the run's documents (request, research, spec, plan and task graph) on one line before the attempt's own input (the snapshot hashes, the task and its evidence). Attempts of a run then share a byte-identical prefix, which providers serve from their prompt cache. On the Claude API an attempt marks its system prompt and, with the request-level automatic breakpoint, its newest message, so each step reads the earlier steps from the cache, and a breakpoint after the run's documents lets the next attempt read them too; on Claude Code those documents go into the cached system prompt ([providers](../providers.md#prompt-cache)). Attempt usage records cache reads and writes per step.

### Plan-time sizing

A policy with `sizing` prices the plan before it is approved ([sizing](../../src/core/workflows/sizing.ts)):

```json
"sizing": { "maxAttemptTokens": 600000, "maxRunTokens": 4000000, "extendToTokens": 8000000, "historyStores": ["../other-checkout"] }
```

- **Price.** A task costs, for each file it writes, the per-file rate of that file's kind and of its write action (`create` or `modify`). The kinds are docs (`*.md`, `*.mdx`, `*.markdown`, `*.rst`, `*.adoc` anywhere, and any other non-source file under `doc/` or `docs/`), test files (under `test/`, `tests/`, `__tests__/`, `spec/`, or `*.test.*`/`*.spec.*`), manifests (project manifests and solution files by name: `package.json`, `tsconfig*.json`, `go.mod`, `Cargo.toml`, `pom.xml`, Gradle build files, `pyproject.toml`, `requirements*.txt`, `*.csproj`, `*.sln`, `*.slnx` and similar) and code. A rate is the middle half of `tokens / files` over finished tasks of history that wrote only one kind, where a task's tokens include the corrective tasks of the same run that wrote the same files, because getting the task done took both. History is this store (this project's runs) plus `historyStores` (a `.sqlite` path or a project directory). With at least two of this project's tasks of the kind that only created (or only modified) their files, those tasks alone set the rate (`basis: "project"`). Otherwise every task of the kind counts, from any store and with either action, and the upper bound is kept at least at the default's (`basis: "history"`), since rates carried over from another project were off in both directions; with six or more such samples their own upper bound is used, so measured history can lower the default's. Rates are also kept per model: each sample names the model that spent most of its task's tokens, and once the model the tasks will run on (the routed model of their profile) ran at least two tasks of a kind, only those tasks price that kind; with fewer, every model's tasks count. The report names the model (`model`, and per rate the model that set it or `null`), since providers spend differently on the same task. A kind without history uses the defaults: code 30k–100k per created and 40k–130k per modified file, tests 60k–350k and 150k–350k, docs 40k–250k and 60k–250k, manifests 5k–40k either way. File size is not used: it said little about the size of a change. The run price is what the run spent before approval, plus the tasks' price, plus the review and convergence ranges once more for a correction round. The tasks' price is the sum of their midpoints plus the square root of the summed squares of their half-ranges: one task is priced at its upper estimate, many independent tasks well below the sum of their upper estimates, which overstated round 01 runs 1.3-2.8 times. The report keeps the sums of the lower, middle and upper estimates in `taskTokens`. The report is stored as `sizing/plan-N.json` (`schemaVersion: 3`, rates per kind and action).
- **Planner guidance.** The planner gets `extra.sizing`: the per-file prices of code, test and documentation files, the number of code files one attempt covers, and the instruction to put tests in tasks of their own and to give independent tasks disjoint writes and no dependencies (they run in parallel with `--worktree --writers N`).
- **Test task order.** When the plan is accepted, a task that writes only test files gets a dependency on every code task that shares one of its criteria, unless one already reaches the other. A test task then runs after the code it tests instead of beside it.
- **Test split.** When the planner submits, a task that writes only test files, more than one of them, and whose estimate is above `maxAttemptTokens` is split by the runtime into one task per test file, before analysis sees the plan. The first file keeps the task's ID and the others get the next free IDs; every part keeps the task's criteria, checks and dependencies, its description names the files of the other parts, and a task that depended on it depends on every part. The split is recorded as `sizing/split-N.json`.
- **Split.** A task that writes several files and whose estimate is above `maxAttemptTokens`, or a run price above `maxRunTokens`, sends the plan back to the planner once with a split note. Under `revision: "patch"` the split is a [revision by patch](#decisions-and-revisions): the planner gets the split note as a finding of kind `sizing` and splits the oversized tasks with edit operations on its last plan instead of writing a new one, and a patch that does not apply falls back to a new plan. A run price still above `maxRunTokens` after that continues within the ceiling under `clarification: "assume"`, recorded in `assumptions/sizing.json`; otherwise it waits for a clarification that suggests an initiative of smaller features; answering it lets the run go on within the ceiling, back at the approval step: the answer keeps the analysis verdict, because the question is about the plan size and not about the spec or the plan.
- **Steps and checks.** A task that writes only tests gets `sizing.testTaskSteps` steps (32 by default) per attempt instead of the profile's and the policy's `maxAgentSteps`; corrections use their base task's cap. With sizing on, a planned task that writes source code (`.js`, `.ts`, `.jsx`, `.tsx` and their module variants) must name the policy's task-scope typecheck check (the check `typecheck`, or one running `typecheck` or `tsc`) in its `checkIds`; otherwise the plan goes back to the planner at submission, so type errors show in the task that made them.
- **Caps and budget.** Each sized task's attempt cap is its upper estimate, at least the policy `maxAttemptTokens` (250,000 by default) and at most `sizing.maxAttemptTokens` (600,000 by default); a corrective task uses the cap of the task it corrects. A run price above `maxTotalTokens` raises the run budget to the price, at most `maxRunTokens`, with a `policy-revisions/sizing-N.json` record (`approvedBy: "sizing"`, not an operator decision). This happens before the approval request, so the approval and the auto-approval token bound see the sized budget, and also before a plan is sent back with a split note, so the re-plan does not run out of the base budget. Without `maxRunTokens` the budget is never raised automatically. The raised budget is the price plus a reserve for repair and convergence tasks, which the price does not include (`repairReserve` in `sizing/plan-N.json`); the reserve counts toward the budget, not toward the split decision. The reserve is a share of the priced work (planned tasks and verification). With at least three finished runs in this project's store and the `historyStores`, the share is the median of their loop costs: for each run, the tokens of corrective tasks and of every planned task, review or converge stage that ran again, divided by the tokens of their first pass; it stays between 30% and 300%. With fewer runs it is a flat 30%. `reserve` in `sizing/plan-N.json` gives the share, its basis (`history` or `default`) and the number of runs, and the budget reason names it.
- **Active time.** The active-time cap (`maxActiveMs`) grows together with the budget, under the same rule: only with `maxRunTokens`. Sizing estimates the active time the run needs as the tokens it expects to spend (the price plus the reserve, at most the sized budget) divided by the run's token rate: the median tokens per active minute of at least three earlier runs in this store and the `historyStores` (runs that are not created or running, with at least five active minutes and 100,000 tokens), or 60,000 tokens a minute until there are enough. When the estimate plus a quarter is above `maxActiveMs`, the cap grows to it, in whole minutes and at most 24 hours, in the same `policy-revisions/sizing-N.json` record (`previous` and `next` name each limit that grew), and a run being driven gets the new deadline at once. `activeTime` in `sizing/plan-N.json` holds the rate, its basis and number of runs, the estimate and the cap before and after; the approval request carries it as `activeTime`, and the approval in the terminal and in the desktop app shows "Estimated active time at the observed rate: N min against maxActiveMs M min" with the raised cap. Without `maxRunTokens` the cap is not raised, and the approval says when the estimate is above it.
- **Planning cost.** The plan approval request carries `planCost` ([plan-cost](../../src/core/workflows/plan-cost.ts)): what the run spent so far by model, with the stages each model ran, and the planned tasks priced from the latest `sizing/plan-N.json` (its `taskTokens` low and high at the sized model's price, with the estimate's mix of input, cache reads and output). The approval in the terminal and in the desktop app shows "Planning so far about $X (model $Y, ...); the planned tasks about $A–$B on M". An attempt on a model without a known price is left out and marks the sum partial; the tasks are left out when sizing named no model or its model has no price.
- **Plan above the ceiling.** When the plan and its repair reserve need more than the budget can reach at the ceiling, `sizing/plan-N.json` has `overCeiling`: `needTokens`, `ceilingTokens`, `expectedTasks` (the tasks, in plan order, whose midpoint estimates fit what the ceiling leaves after the run's spending and verification), `totalTasks`, `extendToTokens` (how far the run may grow past the ceiling, or null) and `warning`, one line that is also among the reasons: "Plan and reserve need X tokens, ceiling is Y; the run is expected to stop at about N of M tasks", with "unless it grows on progress, up to Z" when it may grow. The approval request body carries the same line as `budgetWarning`, and the TUI approval, the desktop run decision and the desktop Needs you detail show it above the assumptions, so the person approving knows the plan is not expected to finish within the ceiling.
- **Growth while tasks finish.** A run whose policy has `maxRunTokens` does not stop on its token budget while it is making progress: when a model call would pass `maxTotalTokens`, at least one task is implemented or verified and the budget is below the ceiling, the budget grows to cover the call, by at least half again, never above `maxRunTokens`. Each growth is a `policy-revisions/auto-N.json` record (`kind: "auto-growth"`, `approvedBy: "sizing"`, the previous and next budget, the projected tokens and the finished tasks), so it is never mistaken for an operator decision. Before the first task exists the budget starts at least at the high end of the start estimate (`estimates/start.json`), up to the ceiling (`kind: "planning-floor"`), so planning and specifying do not stop below the doctor's own estimate. The same check runs before an attempt starts: when the budget left does not cover the attempt's cap, the budget grows first, and when it still does not (the run is at its ceiling), the run stops with `budget_exhausted` before the attempt makes its first model call, instead of spending part of the attempt and failing on the run cap mid-loop. Without `maxRunTokens` an attempt starts with whatever is left and its cap shrinks to it, so it finalizes in time. Under `clarification: "assume"` a run may also grow past the ceiling, up to `sizing.extendToTokens`, or 1.5 times `maxRunTokens` when the policy does not set it: at the ceiling, a call or attempt the budget does not cover extends it by the call's need and at least a quarter of `maxRunTokens` (about one review round), provided a task finished or a finding was resolved since the previous extension (or since the run started). Each extension is a `policy-revisions/auto-N.json` record with `kind: "auto-extend"`, the hard ceiling and the progress counts it saw; a run with no progress, or one at `extendToTokens`, stops with `budget_exhausted` as before. With a dollar cap (`maxCostUsd`) the cap governs instead of the token hard limit: the run extends past `extendToTokens`, under the same progress rule, as far as the cap still pays for at the run's measured price per token (its spent dollars over its spent tokens), and the extension record's hard ceiling says how far that is. An attempt the cap cannot pay for stops the run with `budget_exhausted` and `reason: "cost"` ("The next attempt would pass the run's cost cap"), which the run screens show as a cost cap stop. Raw tokens price a codex run, whose tokens are mostly cache reads, at about a quarter of a claude-code run, so a token limit cannot stand in for the cap: a codex run stopped at its 12M token hard limit with $1.45 of its $12 cap left and its last corrective task unstarted. A call that grows the budget to the ceiling from below and still needs more extends past it in the same call, under the same rules, so the run does not stop a few thousand tokens short of the ceiling with the extension unused. A run stopped at the ceiling is still extended with `workflow extend`; without `maxRunTokens` nothing grows on its own. When the plan's price and reserve are above a budget already at the ceiling, `sizing/plan-N.json` says the budget stays at the ceiling rather than that it grows.

## Workflow definitions (v2)

Definitions of schema version 2 describe stages, transitions, contracts and gates as data ([design](v2-design.md)). `baked workflow run --workflow ID` starts a run from `sdd`, a preset or `baked/workflows/ID.json`; the new-run form lists the same IDs. A run validates the definition against the gate library when it starts and freezes the definition and the gates it binds.

- `baked workflow definitions` lists `sdd`, the nine presets (`quick`, `quick-fix`, `standard`, `full`, `spike`, `review-only`, `fix-ci`, `harden`, `tdd`) and every `baked/workflows/*.json`, with the stages, the line (each stage's type, the contracts it consumes and produces, its gates with what each does, its mode and the transition it guards, and the repair loops; the desktop draws it as the run conveyor), whether the workflow changes files and its validation problems.
- `baked workflow validate ID` or `--file FILE` checks a definition against the gate library and exits 1 with the problems. A v1 file is checked by the v1 rules and through the migration to v2.
- `baked workflow define ID --from PRESET` copies a preset or another definition to `baked/workflows/ID.json` as a custom workflow. The copy never carries auto approval; the presets use the project's own checks in their check stages and after each task.
- `baked workflow remove ID` (`/workflow remove ID` in the terminal UI, Delete on the desktop Workflows screen) deletes the project workflow `baked/workflows/ID.json`. Built-in workflows cannot be deleted; a project file with a built-in ID shadows that workflow, and deleting it brings the built-in one back. Runs that started keep the definition they froze.
- A run of a v2 definition walks its graph: each stage reports an outcome (`passed`, `failed` for a check stage whose required gate failed or a wait stage that timed out, `changes_requested` for review and reflection), and the transition that answers it is taken after its gates pass. `transition.taken` and `gate.finished` events record the walk. A loop edge runs at most `maxIterations` times (1 to 50; the editors recommend 5 or fewer) and the run at most `limits.maxStageVisits` stage visits; either bound stops the run as `no_progress`.
- Quick is for a small, located change ([design](quick.md)). `baked quick TEXT` (also `baked workflow quick TEXT`, or `--prompt-file FILE`) starts it with a feature ID derived from the text (`-2`, `-3`, ... when a run already uses it; `--feature ID` overrides). One `quick-planner` agent finds the files and plans; when the request names files, its budget is sized by them like research (4 + 2 per path + 2 steps to submit, up to its 12). Then a person approves the plan, the tasks run, the policy's feature checks run and one correctness review follows, with one repair round for review findings. The run writes nothing to `specs/` (the definition sets `"publish": false`); the spec, plan and task graph are run artifacts. It refuses to start without a feature check in the policy. `--budget quick|standard|extended|checkpoints` (also on `baked workflow run`) scales the policy like the budget presets of the new-run form; every surface applies a preset through one core function, `presetPolicy`, so each preset works whether or not the config sets `workflows.policy`. `workflows.quickWorkflow` points `baked quick` at another definition, for example a copy with auto approval. The workflow `quick` is not the budget preset `quick` of the new-run form.
- A definition's optional `publish` field (default true) decides whether the run writes its spec, plan and task graph to `specs/<feature>/`. A run that publishes refuses to start (`INPUT_CHANGED`, reason `feature_id_taken`) when `specs/<feature>/` already holds one of those files that no finished run published as it is now (a folder committed earlier, a published file a person edited) or that an open run owns; it names the files, and the fix is another feature ID, moving the folder, or finishing or cancelling the open run. Before this check the same conflict surfaced only at publication, after research, specify and plan.
- Quick fix plans from the request alone (the host states it as one requirement), asks for approval and runs the tasks and checks. Spike researches and writes a report (`report.json`, also in `completion.json`); it changes no file and asks for no approval. Review only freezes `git diff HEAD` (or the last commit when the tree is clean) when the run starts and runs the correctness and, for security-sensitive paths, the security reviewer on it; its findings are the result and are not repaired.
- A wait stage (`type: "wait"`) runs no model: it runs its command gates every `intervalSeconds` (5 to 3600) until every required one passes, then reports `passed`, or until `timeoutMinutes` (1 to 1440) pass, then reports `failed`. Use it to wait on the outside world, such as a deployed preview that answers or a pull request whose CI is green (`gh pr checks NUMBER`). The polls record nothing; the run that decides the stage records each of its gates once (`gate.finished`, check evidence). Its gates must write nothing, are frozen and confirmed with the run like any other gate, but are not run checks: the planner does not attach them to tasks and acceptance does not require them. A timeout starts no corrective work; without a `failed` transition the run blocks with `verification_failed`. The deadline is saved with the run's position, so a paused or recovered run resumes the same wait with the same deadline, and a pause or cancel stops it at once. Time asleep between polls does not count against `maxActiveMs`. A process that drives a run adds its active time to the run every second, so a process that dies (a killed terminal, a lost machine) loses at most the last second of it, and the cap, the report and the usage views count the time before the crash. The run keeps its leases while it waits, so in inline mode other inline runs wait too and an edit of a run file in the working copy during the wait blocks the run (`input_changed`); a worktree run avoids both. `wait.progress` events say which gates it still waits for and until when; the TUI run view and the desktop activity feed show them.
- An advisory gate is recorded and never blocks. A command gate with `retries` records every attempt; a pass after a failure is flagged flaky. A human gate on a transition waits for evidence: answer it with `baked workflow evidence RUN_ID --request ID --file FILE --accept --expected-revision N`.
- Auto approval belongs to the definition: an approval stage with `decision: "auto"` and the definition's `autoApproval` limits. Such a run starts only when the user confirms the limits; the refusal names them and the hash to pass (`--confirm-auto-approval HASH`). Inside the limits the host records the approval with the actor `auto-approval` and the digest a person would sign; anything outside them, or an always-human path, waits for a person. A stage with `decision: "human"` never approves on its own, and the project policy's `autoApproval` does not apply to v2 runs. Its approval request carries the reason in `autoApproval.declined`, with the steps to run an auto-approving copy ([quick](quick.md#7-auto-approval-for-quick)); the TUI and desktop approval views show the reasons under "Why this waits for you", and so do the reasons an auto-approval check declined for. The run overview shows the limits for the life of the run.
- `baked workflow gates` lists the gate library: the built-in review gates, the policy checks, the user's `~/.baked/gates/*.json` and the project's `baked/gates/*.json`, in that order of precedence, with what each gate shadows. A file that does not parse is listed as a problem and never used. Reading the library runs nothing.
- A project gate (`baked/gates/*.json`) runs only after the user confirms it: a run that binds an unconfirmed project gate does not start and names the command `baked workflow gates confirm ID...` (or `--all`). The confirmation stores the gate's hash in `.baked/gate-confirmations.json`, so editing the file asks again; the confirmation message says when the gate replaces a built-in, policy or user gate of the same ID. `baked workflow gates` marks confirmed project gates.
- Workflow agents cannot edit `baked/workflows/`, `baked/gates/`, `baked/agents/`, `baked/skills/` or `baked/constitution.md`; these paths decide what a run may do.
- A started run keeps the definition it was frozen with; editing `baked/workflows/ID.json` or a bound gate file stops it with `input_changed` at the next boundary. To move the run to the edited definition, revise it (V2-11):

  ```sh
  baked workflow candidate RUN_ID --workflow baked/workflows/ID.json [--confirm-auto-approval HASH]
  baked workflow revise RUN_ID --candidate CANDIDATE_HASH --expected-revision N
  baked workflow resume RUN_ID --expected-revision NEW_N
  ```

  The candidate is checked like a run start (schema, validator with the approval invariant, gate library, first-use confirmation of project gates, the profiles frozen in the run) and against the run's history. It is refused with every reason when the workflow ID or its inputs change, the current stage or a completed stage is missing or changes its type or contract, the run's stage visits already exceed the new `maxStageVisits`, or a stage the run can still reach consumes a contract that neither the run holds nor every path to that stage produces. New or changed auto-approval limits need `--confirm-auto-approval`, as at start; unchanged limits were confirmed at start. The execution mode cannot change. `revise` supersedes pending requests, stores the new definition, freezes its gates again, records `definition-revisions/COMMAND_ID.json` (the previous definition and both hashes, `approvedBy: "user"`) and clears the approval. A run that already has a spec, plan and task package restarts at the analysis stage, or the first approval, so the plan is approved again; a run without a package continues at its current stage under the new graph. A run of a schema 1 workflow keeps its definition; fork it or start a new run.

### Workflow editor

`/workflow edit ID` opens the editor window for a definition; E on the workflow field of the new-run form opens it for the chosen workflow, and Esc returns to the form. It edits definition files only and never a started run: a started run keeps the frozen copy it began with, and the window says so.

- Three panes: the stages (type glyph, `(writes)` for the stage that changes files), the gate lists of the selected stage (its own gates for a check or review stage, then its outgoing transitions with outcome, target, loop bound and gate count) and the ordered gates of the selected list with their effective mode (`*` marks a mode set by this workflow). Tab and Shift+Tab switch panes, ↑/↓ select. Below 90 columns the panes become one list with a pane switcher that also shows the problem count.
- A opens the gate picker for the selected list: a search over ID, type and description, and one line per gate with type, default mode, scope, timeout and source (`project, unconfirmed` for a project gate nobody confirmed yet). Gates that cannot be bound there are listed as disabled with the reason: an AI review gate on a transition, a task gate after a stage that is not `tasks`, a non-command gate in a check stage, a non-review gate in a review stage, a task gate in a stage, a gate already in the list, or a thirteenth gate on a transition.
- G sets up a new gate for the selected list from a sentence: Tab picks the kind (run a command, AI check of the running app, AI review of the change, ask a person), the input takes the check in plain words and Enter drafts it, with the configured model for a command or AI check and without a model for the other two ([gates from a sentence](#gates-from-a-sentence)). The draft is shown as text with what it may do and why it cannot be saved, if so; Enter writes `baked/gates/ID.json` (and its test script), confirms it and binds it to the list, and Esc goes back to change the sentence. The gate file is written at once; the binding is part of the working copy until Ctrl+S. A read-only workflow is duplicated with C first.
- In the gates pane J and K move the selected gate down and up, M toggles required and advisory for this workflow only (the override is stored only when it differs from the gate's default; an AI walk-through stays advisory) and D removes the binding. In the transitions pane D removes the selected transition.
- N adds a transition from the selected stage: target stage or `done`, an outcome the stage type can report and an optional loop bound (1 to 50, 5 or fewer recommended); it carries the contract the stage produces. E edits the stage options: the profile of an agent or reflection stage (only profiles that return the stage's contract), the decision (`human` or `auto`) and `covers` of an approval stage, the interval and timeout of a wait stage, and the bound of each loop leaving the stage. I puts a new station on the selected forward transition (or on the one `passed` transition leaving the selected stage): a check (no gate yet), a review (no gate yet), an approval by a person that covers every stage that writes files, or a wait stage (30 s interval, 30 min timeout, no gate yet); the transition then leads to the new station, which passes on to where it led. A check, review or wait station without a gate is a problem until A binds one. W inserts a wait stage the same way. D on a stage in the stages pane removes it: the transitions into it lead to where its `passed` transition led, and its other transitions go.
- The strip below the panes shows the problems of the working copy after every change, from the schema and from the validator a run start uses, each attached to its stage or transition, and the spend estimate of the whole definition. The estimate prices the earlier runs that started from the same workflow ID (model stages by stage ID, tasks as task price times task count, check and approval stages at zero); without such runs it says "none yet", and while workflows are off it says "not available", because the history comes from the workflow worker.
- Ctrl+S with problems refuses and lists them by stage and transition. Without problems it shows the diff against the saved file and the effective gates; Enter writes `baked/workflows/ID.json` through a temp file and a rename. Ctrl+S on an unchanged definition writes nothing.
- `sdd`, the presets and schema 1 files open read only. C duplicates one as `ID-custom` (then `ID-custom-2` and so on), with preset `custom`, version 1.0.0, human approvals and no auto approval, like `baked workflow define`.
- Switching an approval stage to `auto` adds the default limits of the design (3 tasks, 5 files, `src/**`, `tests/**` and `docs/**`, no deletions, no new dependencies, 200,000 tokens); switching the last one back to `human` removes them. When a save writes auto approval limits that the file does not already hold, the review names the limits and the save waits until the first 12 characters of the limits hash (`--confirm-auto-approval` takes the whole hash) are typed. A run of the definition still asks for its own confirmation when it starts.
- Esc with unsaved changes asks before discarding them.

The desktop app has the same editor under Setup > Workflows ([desktop app](../desktop/app.md)); it goes through `POST /v1/workflow/editor*` ([API](../desktop/api.md#workflow-editor)), which runs these rules in the project's backend.

### Workflows from a project's agents

BAKED is customized through workflows. A project may already hold custom agents made for other tools; BAKED reads them only to turn them into a workflow, and shows nothing about agents in a project without them.

| Tool | Files |
| --- | --- |
| Claude Code | `.claude/agents/*.md` |
| GitHub Copilot | `.github/agents/*.agent.md`, `.github/chatmodes/*.chatmode.md` |
| OpenCode | `.opencode/agent/*.md`, `.opencode/agents/*.md` |
| Roo Code | the `customModes` of `.roomodes` (JSON or YAML) |

Only the project's own folders are read, never the home folder. A Markdown agent's YAML frontmatter gives its name, description, tools and model; the body is its prompt. A file over 64 KB or one that does not parse is reported and skipped.

Each agent gets a suggested stage from the words of its name and description and from its tools: review, research, specify, plan or implement, with implement for an agent that can edit and research for a read-only one. An agent that hands work to other agents (Copilot `handoffs`, an OpenCode `primary` agent, a Roo orchestrator) is not used: the workflow itself does that now.

Converting writes, with nothing written when a check fails:

- for a research, specify, plan or implement agent, a profile `baked/agents/ID.json`: the built-in profile of that stage (`researcher`, `spec-author`, `planner`, `implementer`) with the agent's prompt added after BAKED's instructions as project guidance, so the stage still returns its contract. The research, specify or plan stage of the new workflow names it; for an implement agent the tasks stage names it in `profileId`, and the tasks the plan gives the default `implementer` run on it instead (a task naming another implementation profile keeps it). One agent per stage;
- for a review agent, an AI review gate `baked/gates/ID.json` (dimension `custom`, the built-in correctness reviewer with the agent's prompt as its focus, blocking on critical and high findings), confirmed at once, since the person converting chose it, and added to every review stage after `correctness-review`;
- the workflow `baked/workflows/ID.json`, a custom copy of `standard` or another definition with a tasks stage, with human approvals and no auto approval, like `baked workflow define`. Problems of the base itself (a check stage without the project's checks) do not stop the conversion: the result lists them for the editor.

A prompt longer than fits the 16,000-character field is cut, and a model an agent asks for is noted: workflow models come from [model routing](#model-routing). After a conversion the agent files can be removed (a Roo mode is removed by editing `.roomodes`); the workflow keeps working without them.

- TUI: the landing page shows a card for the agents, and `/agents` appears in the palette, both only when the project has some. `/agents` lists them (Enter on one edits it in `$EDITOR` or removes its file) and converts them.
- Desktop: the Agents section ([desktop app](../desktop/app.md)).
- CLI: `baked workflow agents` lists them as JSON, `baked workflow agents convert ID [--from PRESET] [--stages NAME=STAGE,...] [--remove]` converts them (`skip` leaves an agent out) and `baked workflow agents remove NAME` deletes one file.
- API: `/v1/agents*` ([API](../desktop/api.md#project-agents)).

### Gates from a sentence

`baked workflow gate new "TEXT"` drafts a gate from a plain-language check with the configured model (`--model` picks another, `--kind command|ai-acceptance|human|ai-review` forces the kind, `--id` sets the ID, `--from-criteria` makes an AI check that walks the run's manual acceptance criteria). `human` (a person approves, the sentence is the prompt) and `ai-review` (the sentence is the reviewer's instructions; critical and high findings block) are built without a model. An exact check (an exit code, an exact output) becomes a required `command` gate, often with a small Bun test script under `tests/gates/` that the gate runs with `bun`; a check that needs judgement becomes an advisory `ai-acceptance` gate with the `terminal` driver, its steps and expectations, the program to start and the one-shot `commands`. A check that names the spec's acceptance criteria ("walk the feature's acceptance criteria in the CLI"), or `--from-criteria`, drafts a walk-through with `"fromCriteria": "manual"` ([below](#ai-acceptance-gates)), whose own expectations may be empty. The model fills only that content (`src/core/workflows/v2/gate-draft.ts`): the host sets timeouts, retries, evidence and grants (a walk-through gets `spawnApp`, the ports the model names, no outbound hosts and no write paths), never drafts the browser driver, and refuses shells (`sh`, `bash`, `cmd`, `powershell`, ...) as executables. The draft is validated like a gate file and printed with what it may do; nothing is written until a person saves it with `--save`, or with `baked workflow gate save --file DRAFT.json` after reading the `--json` output. Saving never overwrites a gate file or a script and confirms the gate, since the person just read it. `gate list` and `gate show ID` describe the library in words. The API has the same steps (`POST /v1/workflow/gates/draft`, `POST /v1/workflow/gates`, `GET /v1/workflow/gates/ID`, capability `gate-drafts`). `gate places ID [--workflow W]` lists where the gate can go in a workflow (default: the default workflow) in words, with the reason a place is refused, by the editor's own rules (`src/core/workflows/v2/gate-placement.ts`); `gate bind ID --at PLACE` adds it there and saves the workflow. `sdd` and the presets are read only, so binding copies them as `ID-custom` first (start runs with `--workflow ID-custom`); a copy needs at least one policy check in its check stage, so while the check stage is empty `gate places` says so and refuses every place but that stage (a command gate bound there becomes its first check). `/workflow edit` binds gates by hand as before, and G there drafts, saves and binds a gate in one step.

`baked workflow status --json` lists each walk-through of the run under `acceptance`: its phase, verdict, the generated test and the promotion state, with the recorded steps (`stepId`, `action`, `observation`, `expectationIds`).

### AI acceptance gates

An `ai-acceptance` gate ([design, section 9](v2-design.md#9-the-ai-acceptance-gate), [example](examples/ai-acceptance-gate.json)) is bound on a transition and is always advisory. When the transition is taken, after its required gates, the host runs it on the current snapshot:

1. **Walk.** The `acceptance-walker` profile gets only the host tools `app_start`, `app_stop`, `record_step` and the tools of the gate's driver: `terminal_send` and `terminal_read` for `terminal` (plus `command_run` when the gate declares `commands`), or `browser_open`, `browser_snapshot`, `browser_click`, `browser_type` and `browser_key` for `browser` (see [Browser driver](#browser-driver)); no shell, file or web tool. `app_start` runs the declared `start` command as one argv without a shell, in a process group the run owns, with the safe environment plus `start.envNames` (and `PORT`/`BAKED_ACCEPTANCE_PORTS` when ports are granted), and waits for `readyWhen.logIncludes` (or a loopback `readyWhen.url`). The application talks through pipes, not a pseudo-terminal. `command_run {index}` runs one of the gate's declared `commands` the same way (one argv without a shell, in `start.cwd` with the same environment and grant, its own process group), closes its input, waits for it to exit for at most `timeoutMs` or 60 seconds, and returns its output and exit; it needs `spawnApp`, and the next `record_step` stores that command's output and exit instead of the application's terminal. "Run these five commands and check what they print" is one gate with five `commands`, not five gates. `record_step` stores the action, the observation, the expectations it concerns (`E1`, `E2`, ... in scenario order) and the last 40 terminal lines as the artifact `acceptance/<gate>/<attempt>/steps/S<n>.json`. For the browser driver the step stores the page snapshot instead of the terminal lines, the page URL, the requests the proxy refused since the previous step and the last 40 lines of the application's output. The model returns a verdict per expectation with the step IDs that show it; the host accepts only steps this attempt stored. The application's process group is stopped when the walk ends or `timeoutMs` passes.
2. **Draft.** The `acceptance-writer` profile can read the workspace and write exactly one file through `write_test`, at `promote.testPath`. It returns the assertion (`A1`, ...) that checks each expectation. A failing assertion prints `ASSERTION FAILED: A<n>` and exits non-zero. A file named like a Bun test (`*.test.ts`) runs as `bun test PATH`, any other file as `bun PATH`. Tests that refer to `.baked`, `.git`, `baked/workflows|gates|agents` or start a shell are refused before they run.
3. **Verify.** The host runs the test `promote.stableRuns` times without a model. After a passed walk every run must pass; after a failed walk every run must fail on an assertion mapped to a failed expectation. A wrong or flaky test goes back to the writer at most twice; then the gate ends `unstable`. The test file is removed from the workspace (or restored) afterwards and kept as an artifact.
4. **Accept.** A stable test becomes an `approval` request whose body has an `acceptance` section: the scenario, the verdicts with their steps, the mapping, the test text and hash. It does not stop the run, and it can be decided while the run waits, is paused or after it completed: `baked workflow approve RUN_ID --request ID --digest SHA256 --expected-revision N` or `reject ... --reason TEXT`; in the TUI the decision tab shows the test (A accepts, X rejects).
5. **Promote.** Accepting writes the test at its path and `baked/gates/<promote.commandGateId>.json`: a required command gate with `provenance` (source gate, test path and SHA-256, `approvedBy: "human"`, approval time). The gate's current hash is recorded in `.baked/gate-confirmations.json`, so the person's acceptance is also its first-use confirmation. Bind it in a check stage or on a transition like any command gate. Promotion is refused while a run executes in the workspace, when the test path changed since the walk, or when another gate with that ID exists.

A command gate with `provenance` runs only while its test file has the pinned hash; otherwise it fails without running, with the reason `test modified since approval`.

What the gate records: `acceptance.phase` events (`walking`, `walked`, `drafting`, `verifying`, `awaiting_approval`, `promoted`, `discarded`, `inconclusive`, `unstable`, `skipped`), `gate.finished` with mode `advisory` and the walk verdict (`passed`, `failed`, `inconclusive`, `skipped`), and the lifecycle in the run state under `acceptance`. A gate with `"fromCriteria": "manual"` in its scenario also walks the run's manual acceptance criteria: each spec criterion with method `manual` becomes one more expectation (`AC-ID: given ..., when ..., then ...`) after the declared ones, at most 30 in all, so the verdicts, steps and the promoted test cover what the spec asks a person to observe. The criteria still wait for a person's evidence as before; the walk-through stays advisory and only shows what it saw. Bound on a transition after implementation in a workflow with a specify stage (for example in a copy of `sdd` made with C in `/workflow edit`), it walks a CLI project's behavior for every spec. A run without a spec walks only the declared expectations, and with none declared the gate is `skipped`. A run that reaches the gate again on the same snapshot reuses the result; a new snapshot walks again and supersedes an undecided test.

Capabilities are denied unless the gate grants them, and the granted ones are listed in the plan approval as `acceptanceCapabilities`; the frozen gate is part of the approval digest. Enforcement:

| Capability | Enforced by |
| --- | --- |
| `spawnApp` | Without it the walk does not run (`inconclusive`) and `app_start` refuses. Only the declared command can start |
| `writePaths` | Source manifests before and after the walk and each test run; a change outside the granted directories is a violation (`inconclusive` for the walk, a rewrite for a test). Git-ignored files are not in the manifest and are not checked. The granted directories are left out of the run's snapshots |
| `listenPorts` | The listening TCP sockets of the application, its descendants (by parent PID, and on Linux and macOS its process group) and, on Linux and macOS, processes carrying its scope marker are compared with the grant every 200 ms; a port outside the list or a listener beyond loopback stops the application. Linux reads `/proc/net/tcp`, `/proc/net/tcp6` and `/proc/<pid>/fd`; macOS runs `ps` and `lsof -iTCP -sTCP:LISTEN`; Windows runs PowerShell (`Win32_Process` and `Get-NetTCPConnection`), so a read there takes longer and the next starts when it ends. The generated test's runs are checked the same way. When the socket table cannot be read (for example `lsof` is missing), the walk or test run records the violation `listenPorts could not be enforced` and the gate ends inconclusive instead of passing unchecked |
| `outboundHosts` | Browser driver only: every request of the browser goes through the filtering proxy (below), which allows exact host names from the list and loopback on the `listenPorts`, and answers anything else with 403. Refusals are recorded and do not end the walk. The application process itself is not filtered and can still open outbound connections the host does not see; the terminal driver does not filter anything |

In a run with the OS sandbox on ([Sandbox](#sandbox)), the application, its declared commands and the promoted test run with only the granted `writePaths` writable (the workspace is read-only), so the write grant is enforced instead of only checked. While the gate grants `listenPorts` or `outboundHosts` the application shares the host network: the host browser and the filter proxy must reach it and its listeners are read from the host. Only with neither grant does it get no network beyond loopback (unless the policy's `network` is `allow`). Without the sandbox, run the gate in a container or a network namespace when that matters.

#### Browser driver

A gate with `"driver": "browser"` walks the scenario in a headless Chromium driven through Playwright.

- **Dependency.** BAKED does not depend on Playwright and never installs it or downloads a browser. It loads `playwright` or `playwright-core` with a dynamic import, resolved from the workspace first and then from BAKED's own installation. The browser is `BAKED_BROWSER_EXECUTABLE` when set, otherwise the Chromium Playwright reports (it honours `PLAYWRIGHT_BROWSERS_PATH`). When either is missing the gate ends `inconclusive` before any model call, with a reason that starts with `missing dependency:` (install with `bun add -d playwright` and `bunx playwright install chromium`).
- **Grants.** `spawnApp` starts the application as for the terminal driver; without it the browser can still open `outboundHosts`. A gate with neither does not run (`inconclusive`).
- **Tools.** `browser_open` takes an absolute `http`/`https` URL or a path such as `/login`, resolved against `readyWhen.url`, else `http://127.0.0.1:<first listen port>/`, else `https://<first outbound host>/`; other schemes are refused. `browser_click`, `browser_type` (fills an input; `submit` presses Enter) and `browser_key` take a Playwright selector (`text=Save`, `role=button[name="Save"]`, `#id`). Every browser tool returns the URL, the title, the accessibility snapshot of the page (its visible text on Playwright versions without `ariaSnapshot`), at most 12,000 characters, and the requests refused since the previous tool result. An action times out after 30 seconds or the gate's `timeoutMs`, whichever is shorter.
- **Filtering proxy.** A forward proxy on `127.0.0.1` with an ephemeral port, started with the browser and stopped with the walk. It serves plain HTTP requests (one request per connection, absolute `http://` URL, no chunked request bodies) and `CONNECT` tunnels. A host is allowed when it equals an entry of `outboundHosts` (case and a trailing dot ignored, no wildcards) on any port, or when it is loopback (`localhost`, `127.0.0.0/8`, `::1`) on a port in `listenPorts`. Chromium is launched with `--proxy-bypass-list=<-loopback>`, so loopback requests are filtered too, and with WebRTC limited to proxied UDP and QUIC disabled. The walk artifact `walk.json` has `network.allowed` (host and port pairs) and `network.refused` (method, host, port, time and reason of every refusal).
- **Draft and verification.** The writer gets the steps with their snapshots and URLs and the launch options to use. During verification the host starts a new filtering proxy for each test run and passes its URL as `BAKED_ACCEPTANCE_PROXY` (and removes `NO_PROXY`/`no_proxy` from the test's environment); refusals during a run are listed in the run's `refused`. The test runs like any generated test (`bun test PATH` for `*.test.ts`, otherwise `bun PATH`), not through the Playwright test runner, and imports Playwright from the project. As a promoted command gate it runs without a proxy and without `BAKED_ACCEPTANCE_PROXY`, so `outboundHosts` is not enforced there.

### Sandbox

The run policy's optional `sandbox` field (`auto` or `required`) runs the run's check, fixer, repro, probe and AI acceptance processes in an OS sandbox ([OS sandbox](../sandbox.md)). `baked workflow run --sandbox off|auto|required`, the `sandbox` field of `POST /v1/workflow/runs` and the desktop New run screen set it for one run; otherwise the start writes the stricter of the policy's value and the configured `sandbox` setting (raised by the project config). Off leaves the field out, so the policy hash of an unsandboxed run is unchanged; the mode is frozen with the policy and named in the approval digest, and auto approval treats a weaker sandbox like a wider capability (`sandbox weakened from X to Y`).

Processes write only the run root (the project or the run's worktree), temp and package caches; `.git/hooks`, `.git/config`, `.baked` and `baked/` stay read-only. The network follows the policy's `network`: only `allow` grants it. With `required` and no backend the run does not start; a check refused later (for example after the backend broke) is inconclusive with reason `sandbox_unavailable`. Each check artifact stores the `sandbox` that applied: `backend`, `mode`, `network`, and the `reason` when `auto` ran without a backend. In a worktree run the Git common directory is not writable, so checks that write Git state fail there.

## Worktree execution

A run can execute in its own Git worktree instead of the working copy. Request it with `baked workflow run ... --worktree`, or in a schema 2 definition with `"execution": "worktree"`; the flag overrides the definition, which overrides the policy field `executionMode` (`inline` or `worktree`, default `inline`). The mode is part of the run policy and therefore of the approval digest. An inline run's policy has no `executionMode` field, so its hash and behavior are what they were before execution modes existed.

- Git is required. A workspace that is not the top level of a Git repository with at least one commit is refused when the run starts (`details.reason` `git_required`); it does not fall back to inline execution, because inline execution would write the working copy the user asked to keep untouched. A definition that reviews the working copy's diff (Review only) runs inline only.
- When the run first executes, the runtime records the current HEAD as the baseline and creates the branch `baked/wf/RUN_ID` from it with the worktree `.baked/worktrees/RUN_ID/main` (artifact `worktree/created.json`, `state.worktree`). Hooks do not run during creation. The project's top-level `node_modules` is linked into the worktree (a junction on Windows) so checks can run there. From then on research, spec publication, task edits, snapshots, checks, review and final acceptance all use the worktree; the working copy, its index and HEAD are never changed by the scheduler.
- Uncommitted user changes do not enter the worktree. When approved tasks write a file that has uncommitted changes in the working copy, the approval request lists it under `worktree.userChangesInScope`, auto approval declines, and approving needs the explicit choice to leave those changes out: `baked workflow approve RUN_ID --request ID --digest SHA256 --expected-revision N --exclude-user-changes` (the TUI prompt names the files and `A` makes that choice). To keep the changes instead, reject, commit them and start a new run. The excluded paths are recorded in `state.worktree.excludedUserChanges`.
- The run holds its own execution lease `execution:RUN_ID` (migration 011) and the mutation lease of its worktree (`worktree:.baked/worktrees/RUN_ID/main`, migration 005), not the project's `execution` and `mutation` leases: the user can keep editing the working copy, and ordinary BAKED edits, git menu actions and gate runs there are allowed during the run. Other worktree runs can execute at the same time (see [parallel runs](#parallel-runs)). A dead owner's leases are taken over or released by the same rules as the v1 leases.
- File effects record their root: an intent with `root` names the worktree path relative to the project; a record without `root` means the project root. Reconcile, recovery, undo and the plan consistency check resolve every effect in its own root and never against another one; an effect whose root no longer exists stays `unknown` and goes to recovery.
- On acceptance, after the acceptance checks pass, the accepted content (the files the run journaled in its worktree and the declared task writes that differ from the approval baseline, without `.baked/`, `.git/`, symbolic links and secret-looking files) is committed on the run branch with the baseline HEAD as parent. The commit is built in a temporary index, so commit hooks do not run; its author is the repository's `user.name`/`user.email` (or `BAKED workflow <workflow@baked.invalid>` when none is set) and its dates are the run's creation time, so the same accepted content always gives the same commit and a crash before the completion is saved rebuilds it. The branch is never moved when someone else moved it (`branch_moved`). `completion.json` and `state.worktree.commit` name the commit.
- The intelligence index is the project's own, used read-only by the worktree's agents; it can be stale for files the run changed. A `navigate`, `bake_find` or `bake_impact` answer that cites a file the run has edited in its worktree ends with a note naming those files and telling the agent to read them before relying on their lines or symbols. A per-worktree index is an open decision ([design](parallel-worktrees.md#open-decisions)).
- `baked workflow deliver` works for a worktree run: see [Delivery](#delivery). The scheduler never applies the result to the working copy.
- On Windows an executable that ends in `.cmd` or `.bat` (`mvn.cmd`, `gradle.bat`, npm shims) in a check, a gate fixer or `run_command` runs as `cmd.exe /d /s /c` with every word double-quoted, because Bun and Node refuse to spawn batch files directly (`spawn mvn.cmd EINVAL`). An argument containing a double quote, a percent sign, a line break or a trailing backslash is refused with an error instead of being escaped, so an argument cannot become a second command; `&`, `|`, `<`, `>` and `^` stay literal inside the quotes.
- Checks run with `MSBUILDDISABLENODEREUSE=1`, `DOTNET_CLI_USE_MSBUILD_SERVER=0` and `UseSharedCompilation=false` unless the environment sets them, so a `dotnet` check leaves no MSBuild node or compiler server running in a task worktree; such a process keeps the directory locked on Windows. Language servers are never rooted in a task worktree: a root below `.baked/worktrees` maps to the workspace it belongs to (a server whose working directory is a worktree keeps it locked on Windows), and removing a task worktree (or a run's worktrees) first stops every server rooted at or below the path, bounded to 5 seconds. Removal then retries a lock error (`EBUSY`, `EPERM`, `ENOTEMPTY`, `EACCES`) eight times with a growing delay, for at most 20 seconds. A directory that stays locked is renamed into `.baked/trash/` (deleted by the next removal), so its path is free for the next task worktree and the run goes on. Only when the rename fails too, the directory is left on disk, recorded as the artifact `worktree/leftover-TASK.json`, and removed with the run's worktrees at delivery or discard. `baked lsp status` and the `/lsp` view show each server's real working directory (`cwd`).
- The worktree is removed only for a terminal run: automatically after its delivery completes (the run branch stays as the record of the accepted commit), or by `baked workflow discard-worktree RUN_ID --expected-revision N`, which removes the worktree and deletes the run branch of a completed, failed or cancelled run (artifact `worktree/discarded.json`). The TUI offers it as D on the run screen and the desktop as Discard worktree; `workflow status` reports `worktree: {path, branch, present}` so a front end knows whether there is anything to discard. A run that is still active must be cancelled first; a delivery step of unknown outcome must be settled first.

### Several writers

A worktree run can implement independent tasks at the same time: `baked workflow run ... --worktree --writers N`, or the policy field `maxConcurrentWriters` (1..4, default 1). A value above 1 needs worktree execution; an inline run with more than one writer, or with `allowOverlappingWrites`, is refused at start. Both fields are part of the run policy, so the approval digest covers them. A policy with one writer is exactly the policy of a phase 1 worktree run (the field was already stored as 1), and `allowOverlappingWrites` is stored only when it is `true`, so stored runs keep their policy hash. With one writer the run behaves as described above.

- **Batches.** The tasks stage takes the ready tasks in graph order and forms a batch of up to N tasks that are pairwise disjoint by their written paths and by the directories their creates would bring into existence; an overlapping task moves to a later batch. Each batch is recorded as an artifact `tasks/batches/ID.json` (`tasks`, `deferredByOverlap`, `deferredByBudget`, `base`). A task without writes, and a task implemented before an interruption whose task checks did not finish, are handled one at a time in the run worktree as with one writer.
- **Budget.** The agent attempts of the whole batch are reserved before any task starts. When the remaining tokens, calls or the next soft checkpoint do not cover every task, the batch shrinks to the tasks that fit; its first task is always tried, so a run without budget for even one stops on its budget as with one writer.
- **Task worktrees.** The run worktree's current content (tracked and untracked files that are not ignored, without `.baked/` and `node_modules`) is captured as a commit that no ref points to, and each task of the batch gets the worktree `.baked/worktrees/RUN_ID/TASK_ID`, detached at that commit, with the project's `node_modules` linked as for the run worktree. The task's agent reads, edits and runs its task checks there; its file effects and check commands record that worktree as their root. At most two task checks run at the same time across the batch.
- **Concurrency.** The tasks of a batch run as concurrent asynchronous workers inside the scheduler's own thread, not in separate worker threads: every workflow tool already receives absolute paths under the task's root (`ExecutionRequest.root`), and SQLite writes stay in one connection and one thread.
- **Leases.** The run keeps its `execution` lease and the run worktree's lease. Each task worktree has its own lease `worktree:.baked/worktrees/RUN_ID/TASK_ID` with its own fencing epoch. Losing it (another owner took it over, or the task's worker failed without a result) moves only that task to `interrupted`; the other tasks of the batch finish and are integrated. When the worker failed but the lease is still the run's and the worktree has no effect of unknown outcome, the task is restarted once per run in the same drive: it runs again in a fresh worktree from the run worktree's current content, with the files the failed worker had changed applied as earlier edits (as for a continuation at the cap), and `tasks/restarts/TASK_ID.json` records the cause, the carried paths, the tokens the replaced attempt spent (`interruptedTokens`) and the part of them the restart reuses (`carriedTokens`: all of them when it carries files, else 0). Every `task.state_changed` event to `interrupted` names its `cause` (`restart`, `continue_at_cap`, `widened_correction`, `waits_for_artifact`, `spec_conflict`, `worker_lost`, `lease_lost`) and, for a restart or a lost worker, the reason as `detail`; the TUI run log and the desktop run screen show it. When the worker was lost to an error thrown by BAKED's own code rather than a workflow fault, the event also carries the error's `stack`, so its caller is known. Content hashes (`canonical` JSON) leave out an object key whose value is `undefined`, as `JSON.stringify` does; a value JSON cannot hold (NaN, Infinity, a class instance) still throws, naming its key path such as `$.task.tokens[1]`. A task whose session lost a tool it needs gets the same restart, in one-writer runs as well: an implementation that ends `blocked` or `failed` with no change runs again once in a fresh session when its summary or unresolved items say a tool (`edit_file`, `write_file`, `apply_patch`, `read`, `glob`, `grep`) is unavailable or "No such tool", or, as a host fact that needs no wording, when its attempt made no tool call and ended `no_submission`. Under `clarification: assume` any other implementation that ends `blocked`, `failed` or with unresolved items gets that one restart too (with or without changes; the changed files carry over), because a plain resume cleared every such stop of benchmark round 6. The restart prompt carries the earlier worker's summary and unresolved items as `previousAttempt`, and `tasks/restarts/TASK_ID.json` records them. A task has one restart per run; if it ends blocked again the run stops `blocked` as before. The one exception is an edit that did not apply: an implementation that ends `implemented` with an unresolved item naming a file of its own write list and saying the edit did not apply ("did not apply", "failed to apply", "old_string not found") gets one more attempt of its own, with or without `clarification: assume` and also after the task's restart, starting from the edits that did apply (`an edit of its own file did not apply: PATH` in `tasks/restarts/TASK_ID.json`, counted in `taskEditRetries` of the run state). A second such ending stops the run as before. Before any restart, an implementation that ends `blocked` with no change and whose summary or unresolved items name a file (its path, or a module path's dotted form such as `cfgtrace.__main__`) that an unfinished task writes waits for that task instead, in one-writer and parallel runs alike: the task is left ready again, `waitingFor` in the run state lists the tasks it waits for, `tasks/waits/TASK_ID.json` records them, and it runs once they are implemented. A task that is blocked, failed or cancelled, or one that already waits for the blocked task, is not waited for; when nothing else can run, every wait ends and the task runs again, so a task blocked a second time stops the run as before. Otherwise, or when the restarted worker is lost too, later batches that do not need the task still run, and then the run stops `blocked` with reason `owner_lost`. `resume` implements the interrupted task again in a fresh worktree. Under `clarification: assume` the service resumes such a run itself, after a wait of 30, 60 and 120 seconds (three resumes at most, counted in `ownerLostResumes` of the run state); each resume records `owner-lost/resume-N.json`. Without `assume`, or after the third, the run waits for a person. Migration 006 adds the `interrupted` task status.
- **Text instead of a submission.** An agent whose step ends without a tool call is not reformatted from its prose. The executor first continues the same conversation: the history is replayed, a user message asks for `submit_result` (an unfinished task as `blocked`, with what is unresolved), and only the submit tools are active with the tool choice forced; one more step corrects a submission the validators reject. If that also ends on text, the one format correction runs with `formatHints` (the task id and evidence handles of an implementation, the feature id of a plan, the hash and ids of a review) and fails as `OUTPUT_INVALID` with reason `prose_end`. The text is stored as `attempts/ATTEMPT_ID/prose-end.json`. For an implementer, the scheduler then builds the result from host facts: with a change in the task's worktree, no effect of unknown outcome and every task check passing (the declared fixer runs first), it records an `implemented` result itself (`tasks/TASK_ID/host-result.json`) and review judges it; otherwise the same ending is a `blocked` result whose unresolved items are the failing check output, and it takes the task's one restart in a fresh session. A stage agent (a planner, spec author or reviewer) that ends this way and changed nothing is restarted once in a fresh session; its context gets `extra.previousAttempt` with the start of its prose ending, so the planner of a `quick` run that read the request as work to do itself is told to submit a plan instead.
- **Host-known fields of a submission.** Before `submit_result` validates a result, the host sets its `schemaVersion` to the one the result schema requires. An analysis is bound to the manifest the host gave it: the host sets its `inputHash` and ignores the model's copy, so a mistyped hash is not a rejection. For a plan it also sets the task graph's `schemaVersion`, sets `revision` to 1 when it is missing or invalid, and replaces a `specHash` or `planHash` that is not a 64-character hex hash with a placeholder; the scheduler binds both hashes to the accepted spec and plan when it stores the task graph. A wrong schema version is no longer a rejection the agent has to fix.
- **Integration.** After the batch, its results are integrated into the run worktree one at a time in graph order. A changed file is written there as a journaled file effect (`tool: integrate`, with the pre-image kept for undo) while the run worktree still holds the content the task started from. A change outside the task's `writes` rejects that task's result: nothing of it is integrated, the task is `blocked` and the run stops with `input_changed` after the other results of the batch are integrated; the stop detail names each such file with its short hashes before and after the attempt. Only a change the attempt's own journaled edits made counts: a file outside the task's `writes` that changed in its worktree with no journaled edit of the attempt (a host process such as a whole-crate formatter pass rewrote another task's file) is put back to its content from before the attempt, recorded in `tasks/TASK_ID/reverted-outside-STEP.json` with its hashes, and the task is integrated as usual. A serial task in a worktree run gets the same; in an inline run the change may be the user's own edit, so it is kept and still stops the run. The task is then implemented on a new snapshot (`tasks/TASK_ID/diff.json` names its worktree and the integrated hashes) and settled with the task check results from its worktree. Feature checks, review and convergence run at their usual stages on the run worktree. The task worktree is removed after integration unless an effect in it is still unsettled.
- **Conflicts.** A file that the run worktree changed after the task started (another task of the batch was integrated first) is a conflict. An integrator task resolves it: an implementer call in the run worktree whose write scope is only the conflicting files, with the base, integrated and task versions of each file, both unified diffs against the base, the spec and the definitions of the tasks that write those files. It must not change other files. Its record is `tasks/TASK_ID/integration.json`; the task checks run again on the integrated result, and the run continues through checks, review and convergence with their usual bounded correction.
- **Overlapping writes.** Independent tasks that write the same path are refused at plan validation unless the policy sets `allowOverlappingWrites: true`. Then such tasks may share a batch, and the later one in graph order is integrated through the integrator.
- The scheduler never writes the user's working copy; the accepted result is committed on the run branch as with one writer.

### Best-of-N candidates

A worktree run can implement each planned task several times and keep one result: the `best-of-n` workflow (`standard` in a worktree with three candidates), `baked workflow run ... --worktree --candidates N`, `candidates` on a definition's tasks stage, or the policy field `candidates` (1..8; default 1). The run flag wins over the tasks stage, which wins over the policy. `maxCandidates` (default 4) caps it; a run that asks for more, or for more than one candidate without worktree execution, is refused at start. The resolved count is frozen in the run policy, so the approval digest covers it, and a policy with one candidate leaves the field out and keeps its hash.

- **Which tasks.** A planned task that writes files runs as candidates. A repair or convergence task, a task restarted after a lost worker or a cap, and a task that already has a selection run once.
- **Candidates.** The candidates of a task form a batch of their own: their attempts are reserved together (a run without budget for all of them runs fewer), each gets the worktree `.baked/worktrees/RUN_ID/TASK-cN` from the same base, and each runs the implementer and the task's checks there, as a task of a batch with [several writers](#several-writers) does.
- **Selection.** Candidates that did not finish or failed a required task check drop out. The others vote: candidates whose changed files are the same once whitespace is normalized count as one change, and the largest group wins. A tie first gets a distinguishing test: the `distinguisher` profile (model `$review`) reads the task's criteria and the finalists' patches and writes one command (a program the run's checks start, without a shell) with the line the spec requires it to print. The host runs it in each finalist's worktree as it runs an implementer's `run_probe` (30 s, no file changes) and keeps the finalists whose output shows that line; when only one does, it wins (`distinguishing-test`), and when it passes on every finalist or on none, it decides nothing. The test and each finalist's run are recorded as `distinction` in the selection. What is left of the tie goes to the critic's score when a critic runs (see [critic](#critic)), else to the smallest change (added plus removed lines). With `critic: select` and a [calibrated](#critic-calibration) critic, the best-scored passing candidate wins instead of the vote. When no candidate passes, the one with the fewest failing checks is integrated and goes on to repair; when none finished, the first candidate's ending is handled as a single task's.
- **Candidate models.** The policy field `candidateModels` (1 to 8 models) runs candidate k on `candidateModels[(k - 1) mod n]` instead of the task stage's route, so a task's candidates come from different models or providers; each of them must be reachable at start. Each candidate's model is recorded in `tasks/TASK/candidates/N.json`, and the estimate gives each model its share of the tasks stage.
- **Integration.** Only the selected candidate is integrated into the run worktree, as a batch task is. Every candidate is kept as `tasks/TASK/candidates/N.json` (its result, failed checks, changed files, patch, score and whether it was selected) and the choice as `tasks/TASK/selection.json` (`winner`, `method`: `only`, `vote`, `distinguishing-test`, `critic`, `smallest`, `fewest-failures` or `none`, `reason`, `passing`, `clusters`, `finalists`, `oracle` and `selectedPassed`). The candidate worktrees are removed.
- **Report and cost.** The [run report](#run-report) has a Best-of-N section with each candidate and the reason for each choice, and the oracle rate (tasks where some candidate passed its checks) beside the selected rate (tasks where the selected one did). `workflow estimate` and `workflow doctor` take `--candidates`, and the estimate prices the tasks stage for every candidate unless its price comes from earlier runs of the same workflow.

### Parallel runs

Several runs of one workspace execute at the same time when each runs in its own worktree. An inline run takes the workspace-wide `execution` lease, so two inline runs still take turns; a worktree run takes `execution:RUN_ID`. `workflows.maxParallelRuns` (1..8, default 2) caps the runs executing at once, inline and worktree together: a drive over the cap is refused with `WORKSPACE_BUSY` and a message naming the runs that execute. Set it to `1` for one executing run per workspace.

- One process drives each run in its own lane (its own leases and scheduler), so `baked serve`, the TUI and separate `baked workflow run` processes can all drive runs side by side.
- Each run has its own worktree, branch `baked/wf/RUN_ID` and delivery. Runs started from the same HEAD do not see each other's edits; deliver one and start the next from the new HEAD when they build on each other.
- A process creates and removes worktrees (`git worktree add`, `remove`, `prune`) one at a time per repository: Git does not guard `.git/worktrees` against concurrent commands, and an `add` that reads an entry another `add` is still creating fails with `failed to read .git/worktrees/main/commondir`.
- An initiative whose feature workflow runs in worktrees runs its independent features side by side, and starts a dependent feature from its upstream features' results (see [initiatives](#initiatives)).
- `baked workflow doctor` reports worktree runs that execute as `ok` (the working copy is free) and only the inline run's lease as busy.

## Pause, crash and recovery

A workspace has one writing run in its working copy (which may run several task writers in its own worktrees, see [several writers](#several-writers)), and worktree runs beside it up to `workflows.maxParallelRuns` (see [parallel runs](#parallel-runs)). Ordinary BAKED mutations use the same mutex; read-only tools stay available. An external editor is not governed by the lease, so content hashes are compared before and after checks and before acceptance. The Git baseline records HEAD, tracked files and the initial user changes; filesystem-only workspaces are supported too.

The TUI runs the workflow and SQLite transactions in a separate worker. The panel receives a consistent snapshot through asynchronous RPC; the SQLite busy timeout does not block the main interface thread. The execution time limit comes from the run's stored policy, including its revisions. A local RPC timeout does not stop observing an ongoing write.

After the worker exit is confirmed, the application creates a new session for reading state and recovery. It stores a receipt with the exact owner ID and the host PID. A live host PID alone does not mean that the exited worker keeps running. The receipt does not release the lease and does not allow repeating an unknown command: child process checks and recovery effects stay in place.

If the run's owner process has exited, `pause` and `cancel` release that run's leases when the owner is proven gone and the run has no command effect of unknown outcome whose process may still run. These are the same conditions under which `resume` would take the lease over. The release is recorded as the artifact `released-leases/ID.json`; afterwards, ordinary BAKED edits in the workspace are allowed again. A live owner or such a command keeps the lease.

Ctrl+C stores a pause and stops only the processes of that run. A second Ctrl+C forcibly ends the CLI; the next start requires recovery of unfinished effects. A lost heartbeat does not allow taking the lease from a live PID, except from an owner that stopped renewing because its run made no progress (see [stalls](#stalls-deadlines-and-automatic-resume)). With an unknown command outcome, repetition is forbidden:

```sh
baked workflow recover RUN_ID --request ID --effect EFFECT_ID --resolution record-applied --file observed-result.txt --expected-revision N
```

Resolutions: `record-applied`, `record-not-applied`, `retry`, `cancel`. `record-applied` and `record-not-applied` settle the one effect and the run goes on; `cancel` **cancels the whole run** (the headless command prints a warning, and the terminal and desktop label it "Cancel the whole run"). When the stop is an edit whose outcome nobody observed, choose `record-not-applied` after checking that the change is not in the file. The edit journal settles most of these without a person: a publish that fails after the effect was prepared re-reads the file and records `failed` when it still has the old content (the other outcomes stay `unknown` for `reconcile`), and at acceptance an unknown file effect of a task attempt is recorded as `failed` and listed in the `superseded-effects/ID.json` artifact when the task is implemented or verified and a completed attempt of it started at or after the effect's attempt; the checks and reviews ran on that result. An effect nothing supersedes (a command, a delivery step, an edit of another stage) makes acceptance open the recovery request itself: the run waits (`interrupted_effect`) with the request and a note naming `record-not-applied`, instead of blocking with `no_progress` and no request. For a command, the end of its process must be confirmed first. `retry` allows the next attempt, not an immediate replay of the previous shell command. With PID reuse the decision is conservative: a live PID blocks takeover. Do not delete the lease or the database to bypass recovery.

Before recovery or a lease takeover, the runtime checks the recorded command process and its descendants: on Windows, live processes whose parent is the recorded PID and that started after the command; on POSIX, the command's process group, and on Linux and macOS also any process that inherited the command's `BAKED_PROCESS_SCOPE` marker (Linux reads `/proc/<pid>/environ`, macOS runs `ps -E`), which finds descendants that left the group with `setsid`. Cancel and timeout signal the same set. A process table that cannot be read counts as running. On Windows, a descendant whose intermediate parent also exited cannot be linked to the command; confirm such cases by hand. Recovery `cancel` requires confirmation that all processes of the run and their descendants stopped. A known live command PID blocks this decision. The runtime stores an immutable `abandoned-effects` artifact, keeps the effect's original unknown status in history and releases only the previous leases of that run. Cancelling does not claim that the command did not change files.

Workspace and evidence files are written to a unique temp file and renamed into place. A failed write, including ENOSPC part-way through, removes the partial temp file, leaves the target unchanged and keeps the effect unknown until reconcile compares hashes. Interrupted task checks repeat before dependent tasks open. After a successful check, the runtime stores a gate bound to the generation, the snapshot and the task definition. Nested corrective tasks restore the whole chain of predecessors only after the required checks pass. The final `verified` is set during final acceptance.

### Files changed outside the run

Before each step of an approved run the runtime compares the workspace with the files it expects. A file that differs and that the run's own edit journal does not explain stops the run as `blocked` with reason `input_changed`; the stop detail names the files (the first 10, then a count). Three ways out:

- Keep the changes: `baked workflow resume RUN_ID --expected-revision N --accept-workspace` (A "accept changes" in the terminal run panel, after a Y/N confirmation listing the files; **Accept changes** in the desktop run controls; `acceptWorkspace: true` on `POST /v1/workflow/runs/RUN_ID/resume`). The run takes the current content of those files as its baseline, records an `operator/accepted-workspace-ID.json` artifact (kind `recovery`) with each path and its hash before and after, and continues from where it stopped. Accepting is refused with `STALE_DECISION` when no file differs any more (a plain resume is enough then) or when one of the files changed again since it was listed.
- Restore the files and resume as usual.
- Fork the run, or cancel it.

Accepting covers the workspace only. A changed instruction file, gate or skill the run froze still needs a revised plan (see [decisions and revisions](#decisions-and-revisions)).

### Stalls, deadlines and automatic resume

A run can stay alive and renew its lease while one call inside it never returns (benchmark round 8: an `edit_file` whose formatter child kept its output pipe open froze runs for 20 to 60 minutes after the file was written). Three bounds keep that from holding a run:

- **Tool deadlines.** Every tool call of an agent attempt runs under a deadline: file tools (`read`, `edit_file`, `multi_edit`, `undo_edit`, `ast_edit`, `structural_edit`, `delete_file`, `list_dir`, `grep`, `glob`, `navigate`) 2 minutes, every other tool (commands, git, analysis, MCP) 30 minutes on top of the limits those tools carry. A call that does not return is abandoned. If it was an edit and the file differs from its pre-image, the edit is recorded as applied from the file hash (the decision an operator makes with `record-applied`) and the model is told to re-read the file; if the file is unchanged the effect is recorded as failed and the model gets the deadline as the tool error. After `maxToolTimeouts` (3) deadlines in one attempt the attempt is stopped as stalled. The post-edit formatter (`auto-format.ts`, `project.ts formatFile`) kills the whole process tree on its own timeout (`taskkill /T /F` on Windows, the process group elsewhere) and reads its output pipes against the timer, so a surviving child no longer holds the edit. Checks, fixers and on-demand gates, and the Git calls of a run and of delivery, stop reading a command's output 2 seconds after the command exited: a process it started that inherited the output pipes (on Windows a timeout kill does not reach it once its parent is gone) would otherwise keep the run waiting for as long as it runs. A check then keeps the output read so far, ends with the note `a process it started kept its output open`, and the processes it left behind are stopped where the platform can find them (the process group, and on Linux and macOS the scope marker).
- **Journaled tool calls.** `tool.started` and `tool.finished` events (attempt, tool, status `ok`, `error` or `deadline`, duration, `resultBytes`, the size of the JSON result handed back to the model, and for a failed call `error`, its message cut to 1000 characters) are part of the run's event log, so a stall can be attributed to the call it is in and a stage's cost to the calls that fed its context. Host tools are journaled the same way as registry tools: a reviewer's `run_repro`, a repair's `run_probe` and the acceptance walk-through's commands, each under the 30-minute command deadline. The terminal view and the desktop timeline show only calls that hit their deadline and repair probes (`Probe ran`).
- **Step watchdog.** An attempt that journals no model step and no tool call for `stepStallMs` (20 minutes by default; the longest healthy silent step measured was a 569 second review) is aborted through its signal. The file edits it left unsettled are decided from their hashes, the attempt ends with a `step_stalled` fault and the run blocks with reason `step_stalled`. The service then resumes the run itself, at most `autoResumes` (3) times, counted in `stallResumes` of the run state; each resume records `stalled/resume-N.json`. After the last one the run stays blocked for a person.

The lease follows progress. While a run's owner shows progress (an event, a model step, a tool call in flight) its heartbeat renews the lease. When the run is silent for 1.5 times `stepStallMs` the owner stops renewing and marks its identity as stalled; once the lease has been expired for 30 seconds another process (`baked workflow resume`, a second TUI, the desktop app) may take it over even though the owner's PID is alive. The new owner's epoch fences the old one: its next lease assertion fails and it stops writing. A command effect whose process may still run still blocks a takeover, and a live owner that keeps making progress is never taken over.

`workflow status` (headless JSON, TUI overview, desktop run header) shows `stalled` for a running run that has journaled no event for longer than `stepStallMs`.

A provider outage gets the same treatment. When a model call keeps failing through its in-call retries and the route's fallback models (the provider is down or at capacity, or the connection keeps dropping) and the attempt changed no files, the run blocks with reason `provider_unavailable`. The service then resumes it by itself after a wait of `providerWaitMs` (1 minute by default), then three times as long each time (1, 3 and 9 minutes), at most `providerResumes` (3) times per outage, counted in `providerResumes` of the run state. Once a model attempt has completed after the last resume, the provider came back, so the next outage starts again from the first, shortest wait with all its resumes. Each wait records `provider/resume-N.json` (`attempt`, `of`, `waitMs`, `retryAt`, `completedAttempts`) before it starts, and while it runs the snapshot carries `autoRetry`: `{at, attempt, of}`; `workflow status` prints it, the TUI shows "Retrying by itself at ..." and the desktop run header "retrying by itself at ...". A person may resume, pause or cancel the run during the wait; the automatic resume then does nothing. An account problem (`provider_account`: a missing key, a sign-in, a spent quota) is not retried. After the last automatic resume the run stays blocked for a person, who can retry or move it to another model.

Configuration (milliseconds, all optional):

```json
{ "workflows": { "stall": { "toolTimeoutMs": 120000, "commandToolMs": 1800000, "stepStallMs": 1200000, "maxToolTimeouts": 3, "autoResumes": 3, "providerResumes": 3, "providerWaitMs": 60000 } } }
```

`autoResumes: 0` turns the automatic resume after a stall off, `providerResumes: 0` the one after a provider outage. Set `stepStallMs` above the longest model call of the models you route to.

### Stopped convergence

Convergence repairs the findings of its final review for at most `maxConvergenceRounds` rounds (and `maxCorrectiveTasks` corrective tasks). When it cannot start another round, the run no longer ends as `blocked` with `no_progress`: it moves to `waiting` (reason `no_progress`) with a durable request of kind `convergence`. The request body (`topic: "convergence"`) holds the `reason`, a one-line `summary`, `checksPassing` (every required check passes on the current snapshot), the `criteria` (total, passing, and the failing ones with their verdict), the open `findings` (ID, severity, kind, criteria, file, symbol, claim, impact, suggested fix) and the `contradictions` the findings ledger found. The reasons are:

- `rounds`: the convergence rounds of the policy are used;
- `tasks`: the corrective tasks of the policy are used;
- `repeat`: the last repair left the same findings against the same criteria;
- `contradiction`: a new finding repeats one that a correction of the run already addressed. The convergence agent is given those earlier findings (`earlierFindings`, with their file, symbol, criteria and claim) and sets `repeatOf` on every finding: the id of the earlier finding when it is the same defect, even if the file, symbol or wording changed or the earlier fix was partial, and `null` for a different defect, even in the same file or function. `repeatOf` is the key of the findings ledger. A finding without the field (a reviewer that did not say) falls back to the location: the same file, a symbol sharing a word with the earlier one (or none on both, with the same kind) and a shared criterion. The second occurrence of a defect is a residual: another repair would likely undo the first one or chase the same edge case again, so a decision is requested. This stop can come before the round limit; it is listed with the finding it repeats and how the repeat was recognized (`repeatOf` or `location`). A finding that carries a reproduction the host ran, with a command that differs from the earlier finding's reproduction (another command or input, such as `tag --help` after `add --help` was repaired), is a new case of the defect, not a repeat: it is repaired in the next round, even when it names the earlier finding. The corrective task of a review or convergence finding is also told to look for the same defect in sibling code paths (other commands, options, branches or callers with the same pattern) and fix every case it finds, so one repair covers them. With the policy field `classSweep: true` (absent means off, so stored policies keep their hash; set it in `workflows.policy` of `.baked/config.json` or a policy file) a review or convergence finding about input robustness (deep nesting, huge numbers, long input, invalid encoding or empty input, recognised from its claim, impact and reproduction) gets a class sweep instead ([class-sweep](../../src/core/verification/class-sweep.ts)): the robustness findings of one pass become one corrective task per profile, which may write every planned source file of its profile in the same top-level directory as a reported file (at most 12, tests excluded), starts focused on those files, and is told to run the whole battery of input shapes against every public function of each one with `run_probe`, fix each failing case and add a regression test per entry point it fixes. A class a reviewer would otherwise find one site per round (cfgtrace: the CLI, the library API, the TOML parser, the JSON parser) is repaired in one round. The same field sweeps test style: a review or convergence finding on a test file whose claim or impact is about how the tests are written (inputs built by loops or generators instead of static fixtures, hard-coded values, cases the criteria name left out, an output not checked exactly) becomes one corrective task per profile that may write every planned test file of its profile in the same directory with the same extension, starts focused on them, and is told to fix the same defect in each and make every case the criteria name appear with its exact output and exit code (aclvet: the loop-built fixtures of `check_test.go` and then of `diff_test.go`).

The person decides, on every surface:

| Decision | TUI key | CLI | API | Effect |
| --- | --- | --- | --- | --- |
| Accept | `A` | `baked workflow accept RUN_ID --request ID --expected-revision N` | `POST .../accept` | The findings become known limitations: they are closed, the criteria they name may fail at acceptance, and the run goes on as if convergence had passed. The run report lists them under "Known limitations" and `completion.json` carries them (`limitations`), so the delivery pull request shows them. |
| One more round | `C` | `baked workflow continue RUN_ID --request ID --expected-revision N --resume` | `POST .../continue` | The limit that stopped the run is raised just enough for these findings and they are repaired now. The findings a person decided to repair are not asked about again. |
| Stop | `X` | `baked workflow reject RUN_ID --request ID --reason TEXT --expected-revision N` | `POST .../reject` | The run is `paused`; resuming reviews again and asks again if the findings remain. |

`accept` continues the run after the decision like `approve`, `answer` and `evidence`; pass `--no-resume` to only record it. `continue` on a stopped convergence resumes the same way (`--no-resume` only records it); `continue` on a token checkpoint resumes only with `--resume`. In the desktop app the run's decision card has "Accept as known limitations", "One more round" and "Stop here".

With `clarification: "assume"` the host applies a decision policy to a stopped convergence and shows it in the request body (`hostRule`: `decision` `accept`, `extend` or `ask`, the three `rules`, and `why` for this stop; the terminal and desktop decision views print it):

1. **Accept** when every required check passes, at most 2 distinct findings remain (findings that repeat one cause through `repeatOf` count once; the share of failing criteria is not the measure, because one defect in a shared function fails 2 or 3 criteria at once), none is critical, and none is high with a reproduction the host ran (a high finding that rests on a static trace is accepted). The request is recorded and accepted at once (decided by `auto-approval`), the findings are listed as known limitations decided by the assume rule, and the run goes on.
2. **Extend** on a `contradiction` stop, once per run (`autoExtensions` in the run state): the stop is recorded as an automatic "one more round", the limits that stopped it are raised just enough and the findings are repaired now, because a repeat is often an incomplete earlier fix. If the next stop is for the same or another reason, rule 1 decides.
3. **Ask** otherwise, with `why` naming what stopped the host (a failing check, the number of distinct findings, a critical or reproduced high finding).

A run with no required check still waits for a person.

## TUI

`/workflow` without arguments opens the panel with the project's run list. Runs waiting for a user decision come first, then active runs, then finished ones. ↑/↓ select a run, Enter opens it, N opens the new-run form, I opens the [initiatives](#initiatives-in-the-tui), G the gates window, R the [routing screen](#routing-screen), U the [usage screen](#usage-screen), W the [workflows screen](#workflows-screen) and Esc closes the panel. `/workflow new TEXT` opens the form with the description filled in; `/workflow quick TEXT` does the same with the quick workflow selected. `/workflow edit ID` opens the [workflow editor](#workflow-editor). `/workflow routing` opens the [routing screen](#routing-screen), `/workflow usage` the [usage screen](#usage-screen) and `/workflow definitions` the [workflows screen](#workflows-screen). `/workflow report RUN_ID` prints the [run report](#run-report) in the chat. `/workflow help` prints the full command list; the other CLI commands (`run`, `status`, `approve`, `recover` and so on) are still accepted, and their result is printed in the chat as a short text.

If a configuration turned workflows off (`workflows.enabled: false`), the panel shows what will be written, and E turns them back on: an existing project block only gets `enabled: true`; when the global config turned them off, a `workflows` block with the default policy and checks found in the `package.json` scripts (`typecheck`, `lint`, `test`) for the project's runner is added to `.baked/config.json`. While the project is off, the panel starts no worker and creates no database.

The new-run form contains the description, an optional GitHub issue ([starting from a GitHub issue](#starting-from-a-github-issue); with one, the description is optional and adds instructions, and an untouched feature ID is named after the issue), the feature ID (derived from the description; Cyrillic text is transliterated), the workflow (`sdd`, the nine presets and `baked/workflows/*.json`, with the stages of the chosen one and "no file will change" for a workflow that only reads), the budget `quick`/`standard`/`extended`/`checkpoints` (×0.5/×1/×2 of the configured policy's token, call and time limits, or of the built-in default policy when the config sets none; `checkpoints` has no token cap and asks every N tokens), an optional cost cap in US dollars (empty keeps the policy's or the setting's cap, shown as the placeholder; see [cost cap](#cost-cap)), an estimate of the spend labeled as an estimate, the execution mode, the writer count, what blocking questions do (Questions: `ask` waits for your answers, `assume` lets the agents settle them with recorded assumptions; ←/→ or Space, starting at the policy's `clarification`), what the [test-integrity guard](#test-integrity) does (Tests: `block` or `warn`, starting at the policy's `testIntegrity`), the current chat tab's model and the configured checks. Ctrl+S starts from any field.

Mode (←/→ or Space) switches between `inline` (the run edits the working copy) and `worktree` ([worktree execution](#worktree-execution)); it starts at the chosen workflow's own `execution`, otherwise the policy's `executionMode`, and switching the workflow resets it. Writers (←/→, 1..4) is available only in worktree mode and is skipped by Tab otherwise; it starts at the policy's `maxConcurrentWriters`. The form sends exactly what `baked workflow run --worktree --writers N` sends: worktree mode sends the mode and the writer count, inline mode sends only the mode, so the policy's writer count applies and the core refuses a policy with more than one writer for an inline run. A definition that refuses worktree execution (review only, whose input is the working copy's diff) shows the core's refusal on the Mode line and below the form, and the run does not start until Mode is back to inline. Other refusals (no Git repository, a policy problem) come from the core when the run starts and are shown under the form. The run executes in the worker in the background; the panel switches to it immediately.

The worker reports new events of its runs to the panel immediately; the panel reads changes from other processes and active time by polling every 150 ms, and a poll without changes does not re-read the view.

The status JSON of a run (`baked workflow status`, `start` and `resume` output, `GET /v1/workflow/runs/RUN_ID`) has `limitations: {count, ids}`, the findings the run is accepted with; a completed run with `count` above 0 keeps exit code 0, and the terminal run screen and the desktop run header show the count. The run screen shows what is happening and what can be done, the stage line (a glyph per stage, ×N for a stage on its Nth round, and the current stage in brackets with the contract it is making, such as `[▶ Plan → plan]`; the desktop shows the same line as a conveyor), under it the gates of the current stage (or, once the run has ended, of the last stage that has gates) from the run's own definition, one per line with a result glyph, whether it blocks or only advises, its last result in this run (from `gate.finished`, or the check of the same ID for an `sdd` check stage; `not run yet` before that, `after N attempts` and `flaky` when they apply), and on a second line what it does and where it stands (at this stage, or before the line moves on or goes back), budget consumption (tokens used, held by attempts with unknown usage and in flight), a summary of tasks/criteria/checks/findings, the last model, the last recorded error and the event feed. When a budget blocks the run, the panel names the limit and the remaining amount. The action line contains only the keys valid in the current state: R start/resume/retry, A accept the files changed outside a run blocked with `input_changed` ([files changed outside the run](#files-changed-outside-the-run)), P pause (also for a run marked running without a live executor), C cancel with confirmation, B raise the limits of a run blocked on its budget, M switch a stopped run (created, paused, blocked or waiting) to the chat tab's model when it differs from the run model (pick it with Ctrl+L first; after a Y/N confirmation the run is [rerouted](#switching-a-run-to-another-model) and a blocked or paused run resumes), F fork for blocked and finished runs (when the workflow has stages after the implementation, ←→ picks where the fork starts, from the beginning or one of `forkStages`, and Y forks; the panel then opens the new run), D discard the worktree of a finished run while it is still on disk (after a Y/N confirmation naming the worktree and branch; the same as `workflow discard-worktree`). U undoes the run's uncommitted task edits (the same as `workflow undo` without `--path`) after a Y/N confirmation; it is offered while the run is neither created nor running. The panel then shows the `workspace-rollback` report: each restored file (restored, removed when the run created it, recreated when the run deleted it) and each file left in place with the reason, or a note that there was nothing to undo. Esc hides the report. Tab/Shift+Tab switch between overview, decision, tasks, changes, spec, plan, checks, criteria and findings. Changes lists the files the run changed according to the effect journal: created/modified/deleted, the number of edits, an unfinished status and a mark when a file was changed outside the run afterwards. ↑/↓ and Enter show the diff of the selected file against Git HEAD; the diff is available only for files in this run's journal. If the file had uncommitted changes in the baseline, the diff includes them and the panel warns about it. Without Git only the facts of the changes are shown: the journal stores hashes, and the pre-images it keeps are used only by undo. Checks shows the latest result of each check: duration, exit code, number of runs, stale evidence and the last 40 output lines of a failing check, as well as configured checks that have not run yet. When a new request appears, the panel opens decision by itself. Approval shows the criteria, the assumptions the agents made instead of asking, the files in scope, the checks and deferred criteria: A accepts the digest, X requires a rejection reason. Clarification shows the current question in full with its answer field right below it, then the references and a compact list of all questions with blocking ones marked; ↑/↓ switch questions without losing answers, Enter saves and moves on, Ctrl+S sends, and sending with an unanswered blocking question asks for a second confirmation. Questions come from research unknowns, spec open questions or analysis findings; each answer is keyed by its question ID and text. For manual evidence, Ctrl+T toggles the verdict. Recovery chooses the outcome with the keys 1..4 and requires a description of the observation. A stopped convergence shows its findings, the failing criteria and any contradiction: A accepts the findings as known limitations, C repairs once more, X stops the run. Esc returns to the list. Shift+PageUp/PageDown scrolls the content.

The status JSON also has `reviewNotes: {count, ids}`, the run's review notes (the run screen shows `Review notes N`, the desktop header `N review notes`).

While the panel is closed, a line for the selected run is shown above the footer: stage and tokens, a pending decision or the outcome. The indicator polls only an already open worker and disappears after the outcome has been seen in the panel.

A new `/workflow run` uses the current chat tab's model selected through Ctrl+L, even if the worker was opened before the model was selected. An explicit `--model provider/model` sets the model for that run only and takes precedence over the chat selection. The CLI without `--model` uses the configured defaultModel. The models of existing runs are frozen in their routing record; switching the model in the chat does not change them on resume, but M in the run screen moves a stopped run to it.

Closing the panel keeps the run in the current application process. Pause the run before closing its chat tab. Shutdown stops the workflow before shared resources are released. Session restore restores the run ID and observation; the model is not started automatically.

### Initiatives in the TUI

I on the run list opens the project's [initiatives](#initiatives). Each row shows the initiative ID, its status, accepted mandatory features of all mandatory features, open decisions and blockers, and shared tokens used of the limit; initiatives that need a person (a decision, a blocker or a pause) come first, finished ones last. ↑/↓ and Enter open one, N opens the start form, and Esc returns to the run list.

The start form takes the large request, the initiative ID (filled from the request until you edit it; lower case letters, digits and `-`), the default workflow for features that name none (←/→ over the project's workflows), the shared budget as `TOKENS CALLS TIME` such as `8M 400 4h` (empty derives it from the policy and the split), and tiered approval (off, or specs up to 5 tasks and 10 files approved for you). Feature runs use the chat tab's model. Ctrl+S, or Enter on Start, starts it like `baked workflow initiative start` without `--plan`: the decomposer proposes the split in the background and the screen opens the new initiative.

The detail shows the title, the current plan revision and whether it is approved, the feature workflow, the shared budget (tokens, calls and active time used of the limits), the next action in words, a pending split approval with its plan revision and digest prefix, the initiative's blockers, and the features in dependency order with their state, workflow, run status, run ID and upstream features. The selected feature also shows its contract, its workflow, size and starting budget share, and either its pending decision or its blockers. Enter opens the selected feature's run in the run screen, O opens the decompose run, and Esc on that run returns to the initiative. T [estimates the split](#initiatives): a line under the budget gives its level, tasks, tokens and the figure to plan for, and the selected feature its own token range.

The keys follow the commands the core accepts in the current state: A approves the pending split (after a Y/N confirmation; it is bound to the revision and digest on screen, so a changed split is refused with the core's message), P pauses an active or decomposing initiative, R resumes a paused one, C continues (`drive`) an active or decomposing initiative that this process is not already driving, N rejects the pending split with a reason you type, X re-plans the selected feature (after a Y/N confirmation; it supersedes the feature's current run, and is not offered while that run executes), B raises the shared budget (type `TOKENS [CALLS [TIME]]`, such as `8M 400 4h`; `-` keeps a limit, and limits only go up), and M [switches the initiative](#initiatives) to the chat tab's model when it differs from the initiative's model and no feature run is executing (pick it with Ctrl+L first; after a Y/N confirmation the stopped runs move to it and the initiative continues, as `reroute --resume`). The detail line shows the initiative's model next to its feature workflow, and "up to N features at once" when its features run in worktrees side by side. Approve, resume, continue and the model switch drive the initiative in the workflow worker in the background, like the CLI commands; the screen refreshes every second, shows "⟳ live" while the worker drives it, and shows the last drive error. Decisions of feature runs are made in the run screen.

While the split waits for approval, or the initiative is paused after its split was approved, the selected feature can be edited: W sets its workflow (type the workflow ID), Z its size (`small`, `medium` or `large`), E renames it (the current title is filled in), S splits it into parts typed as `id: title` separated by `;` (each part keeps the feature's scope, paths and contract, as `split` does with a parts file without them), G merges it with the features whose IDs you type (the merged feature keeps the selected ID), and D removes it after a Y/N confirmation. Each edit is a new plan revision with a new approval request; the core's refusal (fewer than 3 features, an unknown ID, a cycle) is shown as typed. Text prompts submit with Enter and cancel with Esc.

## Run report

```sh
baked workflow report RUN_ID                 # prints Markdown
baked workflow report RUN_ID --output FILE   # writes FILE (relative to the workspace), prints {runId, path, bytes}
baked workflow report RUN_ID --json          # {runId, markdown}
```

One Markdown file for a run, at any status, read from the run's database without changing it:

- the title, run and feature IDs, workflow, status with its reason, and verification state;
- a summary: for a run that did not complete, a first line with its status, reason, stage and how many tasks are done, saying the request is not done; the spec's outcome labelled `Goal:` (left out for the host-made spec of a workflow without a spec stage, whose outcome only restates the request); a report stage's summary and recommendation when the workflow has one; and the request (cut at 2,000 characters);
- changes: every file the run changed, from the effect journal and the task diffs (published spec files are marked `spec`; a file edited outside the run since is marked `changed since`);
- tasks with title, status and origin (`repair, fresh context` for a [fresh-context restart](#fresh-context-restart)), and how many are done of those the run still owes: a task a plan revision cancelled after approval is listed but not counted, and a task a revision dropped before anything ran has no row; checks with their latest result, validity, runs and time; the [code quality](code-quality.md) deltas, what the duplication ratchet found, the anti-slop rule matches, the new dependencies with their registry verdicts, the Semgrep matches, the criteria marked for property tests and the mutation score with the surviving mutants; acceptance criteria with verdicts and the final review verdict;
- which models (and their vendors) reviewed the change and which implemented it (the models the task attempts ran on, so a `--route implement=MODEL` route or a fallback is named, with the implementer profile's own model as `configured` when it differs); the [critic](#critic)'s score of each task attempt with its weakest rubric item; the [best-of-N](#best-of-n-candidates) candidates of each task with the reason for the choice and the oracle and selected rates; findings with status, severity, kind, file and claim; known limitations (findings accepted instead of repaired: at a [stopped convergence](#stopped-convergence), as notes on a low partial finding behind verified behavior, or by the repro gate on a convergence claim it did not reproduce, with who accepted them); decisions (every request with its kind, decision and who made it) and the spec's assumptions;
- review notes: review and convergence findings that started no correction, with why and the earlier note each repeats;
- usage: tokens against the budget, agent calls, active time, the estimated cost when known, and tokens per stage (in the order stages first ran) and per model;
- artifacts: the latest revision of each artifact with its ID, read with `baked workflow artifacts RUN_ID --file ID`. Attempt outputs, internal state and baselines are counted, not listed.

The report is the pull request body of a [delivery](#delivery). In the TUI, `/workflow report RUN_ID` shows it in the chat (`--output FILE` writes it). The desktop app shows it in the run's Report tab with Copy and Save buttons, and `GET /v1/workflow/runs/RUN_ID/report` returns it.

## Comparing two runs

```sh
baked workflow run sdd --feature totals-a --prompt-file request.md --worktree --route implement=MODEL_A
baked workflow run sdd --feature totals-b --prompt-file request.md --worktree --route implement=MODEL_B
baked workflow compare RUN_A RUN_B                 # prints Markdown
baked workflow compare RUN_A RUN_B --output ab.md  # writes ab.md in the project
baked workflow compare RUN_A RUN_B --json          # the comparison and its markdown
```

An A/B of routing maps runs one request twice with different `--route` maps (or `--model`), each in its own worktree so the two runs do not touch the same files, then puts the two runs side by side. `compare` reads both runs from the database without changing them, at any status:

- the routing targets whose model differs between the runs (from each run's latest `routing.json`), or a note that both used the same models;
- status with its reason, tokens, estimated cost, active time and agent calls, each with B minus A; repair rounds and review rounds, the latest result of each check (passed and failed counts), review findings by severity with how many stayed open, and accepted limitations;
- tokens per stage on both sides, in the order the stages first ran.

A note says when the two runs are different features or ran different workflows. In the TUI, `/workflow compare RUN_A RUN_B` shows the Markdown in the chat. In the desktop run list, tick two runs and press Compare: the same tables, with the better side of each row marked and Copy as Markdown. The local API answers `GET /v1/workflow/compare?a=RUN_A&b=RUN_B` (capability `run-compare`).

## Usage reports

```sh
baked usage --days 30 --group-by stage,model --format md          # prints Markdown
baked usage --days 30 --group-by stage,model --output usage.md    # writes usage.md in the project
baked workflow usage RUN_ID --format md [--output FILE]           # one run
```

Token use and estimated cost can be shared as one Markdown document. The project document has the window (days and UTC dates), the grouping, the model and stage filters, a totals table (runs, attempts, tokens, input with cache reads, output, cache reads, cache writes, estimated cost and unpriced tokens) and one row per group with the same figures, followed by a note on how cost is estimated. A run's document has its totals and the same figures by stage, by task generation (**By task generation**: a row for each task's first implementation and one for each rerun after a repair invalidated it, so a rerun's cost reads on its own) and by model; `--top` does not shorten it. When agents called code intelligence tools, it also has a **Code intelligence** line with the calls per tool and the backend that answered them, with the language server for `lsp` (for example `navigate lsp (rust-analyzer) 12, navigate tree-sitter 3, bake_find repo-map 4`), so a run shows whether rust-analyzer, csharp-ls or jdtls answered or a fallback did. The same line is in the [run report](#run-report)'s usage section, each attempt's `attempts/ATTEMPT/usage.json` has the counts as `toolBackends` (`{tool, backend, server, calls}`), and `GET /v1/workflow/runs/RUN_ID/usage` returns the run's totals as `toolBackends`. A **By tool** table lists the tools the model called, with the calls and the tokens of the steps that made them; a step's tokens are split evenly between its calls, so `--stage review` shows how much of a review went to `run_repro`, `read` or `grep`; the run report has the same figures as a **Tool calls** line. Each step in `usage.json` names its calls as `tools`, and the usage answer has `tools` (`{tool, calls, tokens}`) for the run and for each attempt; attempts recorded before tool names were have none. Only model IDs, stage IDs, the run ID and figures go in: no paths, prompts or account names. `--output` paths are relative to the project, and `--output` implies `--format md`.

In the TUI, E on the [usage screen](#usage-screen) writes the shown period as `baked-usage-30d-YYYY-MM-DD.md` in the project, grouped as on the screen; `/workflow usage RUN_ID --format md` shows a run's document in the chat (`--output FILE` writes it). The desktop Usage screen has Copy as Markdown and Export as .md for the chosen range, run and filters; the local API answers `GET /v1/usage?format=md` and `GET /v1/workflow/runs/RUN_ID/usage?format=md` with `{markdown}` ([API](../desktop/api.md)).

## Record and replay of model calls

A run can record its model calls so a fix to BAKED can be checked against the same situation without spending model tokens. Both options are off by default and only apply to the native executor.

```sh
baked workflow run --record-model-calls "Add a health endpoint"
baked workflow recording RUN_ID --output recordings/health.json
baked workflow run --replay recordings/health.json "Add a health endpoint"
```

`--record-model-calls` stores each model call of the run as the artifact `recordings/PROFILE/TASK/ATTEMPT_ID/N.json` (`TASK` is `run` outside a task). A call holds a fingerprint of the request (a hash of each prompt message, the offered tool names and the tool choice) and the provider's response. UUIDs, ISO times and `durationMs` values are replaced by placeholders before hashing, so they do not change a fingerprint. `baked workflow recording RUN_ID` prints the run's calls as one recording (`schemaVersion: 1`), or writes it to `--output FILE`.

`--replay FILE` starts a run that answers each model call from the recording instead of the provider. Calls are matched by profile and task, by the attempt's order for that key, and by the call's number within the attempt. The run starts only when the file exists and is a valid recording. When a request's fingerprint differs from the recorded one, or the recording has no call at that point, the run blocks with reason `replay_diverged`, and the message names the key, attempt and call and the first prompt message that differs. A replayed run records the calls it served, so `workflow recording` of the replay can be compared with the original. Streaming calls are not replayed.

## Import, export and retention

```sh
baked workflow import --source spec-kit --path reviewed-checkout/specs/feature --feature imported
baked workflow import --source ecc --path reviewed-checkout/agents --feature imported
baked workflow export RUN_ID --destination exports/run-001
baked workflow export-progress RUN_ID
baked workflow gc --before 2026-09-01 --dry-run
baked workflow worktrees --clean --dry-run
baked workflow redact RUN_ID --file ARTIFACT_ID --reason "Remove sensitive content"
```

For import, enable `importsEnabled` separately and point to a local source directory. The adapter does not download a repository, does not run scripts/hooks and does not activate imported agents. `.baked/workflow-imports/HASH` stores the candidate, hashes, the source commit when present, the license and an unsupported report. Spec Kit Markdown stays a draft; schema-compatible spec.json/tasks.json are validated with their IDs kept. An ECC prompt candidate requires native role/tool/output mapping and enabling through a reviewed profile. `markdown-edit` uses the same inert directory reader.

To accept a schema-compatible imported package, pass its spec/plan/tasks to `candidate`; the import itself does not change accepted data. Profiles are loaded from the built-in definitions, `~/.baked/agents/*.json`, then `baked/agents/*.json`. The source and hash are visible in `workflow profiles`. A project workflow is stored in `baked/workflows/ID.json`; the mandatory SDD stages cannot be removed or reordered. Skills live in `baked/skills/ID/SKILL.md` and are frozen by hash.

For a review by another model, route it with `modelRouting` (see [Model routing](#model-routing)) rather than copying a profile. A copied profile in `baked/agents/ID.json` can still name a specific `provider/model`, but a project file then carries one person's model choice. Reviewer context separation is mandatory regardless of the model choice; a separate profile name alone does not mean a different model. The model ID of every attempt is stored in the journal.

A CLI-backed provider (Claude Code, Codex) can pass the signed-in account to the model through the CLI's own context. The host reads that account's e-mail address from `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) and `~/.codex/auth.json` (or `$CODEX_HOME/auth.json`), and refuses an edit or a submitted result that contains the address or its local part (five characters or longer, as a whole word), telling the agent to take the owner from the project manifest or write `<project name> contributors`. An identity the workspace already names in `package.json`, `pyproject.toml`, `Cargo.toml`, `composer.json`, `LICENSE*` or `AUTHORS` is the project's own and is allowed.

### Worktree disk usage

A worktree run keeps `.baked/worktrees/RUN_ID/main` (and a directory per task with several writers) until delivery or `discard-worktree` removes it, so benchmark rounds and failed runs leave worktrees behind. `baked workflow worktrees` lists each run's directory, largest first, with its size, the size of each worktree in it, the run's status and feature, and whether a cleanup removes it. `baked workflow worktrees --clean --dry-run` shows what a cleanup removes and how many bytes it frees; `--clean` removes the worktrees of completed, failed and cancelled runs and of directories whose run the project no longer has, and empties `.baked/trash` (locked worktree directories moved aside). Running, waiting, paused and blocked runs, and runs with an unsettled delivery step, are kept. Unlike `discard-worktree`, the cleanup keeps the run branch `baked/wf/RUN_ID`, which carries the accepted commit, and records `worktree/cleaned.json` in the run. In the TUI it is the typed command `/workflow worktrees [--clean]`; the desktop run list has **Worktrees…** under the same capability, and the local API answers `GET /v1/workflow/worktrees` and `POST /v1/workflow/worktrees/clean` ([API](../desktop/api.md)).

Export creates a new directory inside the workspace. The host API allows a separate outside-path approval callback; the CLI does not provide one automatically. Raw provider messages and command output are not part of the portable report; known credentials are masked. Redaction removes the selected artifact content, keeps the original hash and a tombstone and invalidates evidence. It does not promise to remove every possible copy of a string from other artifacts.

In the desktop app, a run's screen has Export (into `.baked/exports/RUN_ID-STAMP`) and Redact…, and the run list has Import… and Clean up old runs…, which previews the runs it would remove before removing them. The local API has the same as `POST /v1/workflow/runs/RUN_ID/export` and `/redact`, `POST /v1/workflow/import` and `POST /v1/workflow/gc` ([desktop API](../desktop/api.md)).

GC removes only terminal runs older than 30 days and the given cutoff when no child run needs them and they hold no lease. Active/waiting/blocked data and the shared `specs/` are kept. For a backup, stop the writers and save `.baked/workflows.sqlite` together with `.baked/workflow-runs/`. Copying a live SQLite database also needs the WAL/SHM files or an SQLite backup; an arbitrary copy of one file during writes is not a consistent backup.

## Model routing

Profiles name a model class: built-in ones use `$active` (the run model: the tab model or `--model`), `$fast` (the quick planner), `$coding` and `$review`. The `modelRouting` section of the global or project configuration turns classes, roles, profiles and workflow stages into concrete models:

```jsonc
"modelRouting": {
  "classes": { "fast": "anthropic/claude-haiku-5-5", "review": "openai/gpt-5.1" },
  "roles": { "researcher": "$fast", "reporter": "$fast" },
  "profiles": { "security-reviewer": "anthropic/claude-opus-5-5" },
  "workflows": { "sdd": { "stages": { "research": "$fast" } } }
}
```

A value is a `provider/model` ID or `$class`. A class names a model, not another class. A project layer is merged over the global one section by section, and stage routes workflow by workflow.

The model of an agent is chosen in this order, the first match winning:

1. `--route STAGE=MODEL,...` on `workflow run`;
2. `modelRouting.workflows.<workflow>.stages.<stage>`;
3. `modelRouting.profiles.<profile>`;
4. `modelRouting.roles.<role>`;
5. the profile's class through `modelRouting.classes`; `$coding` and `$review` then fall back to the `/router` Code (`taskRouter.ember`) and Review (`taskRouter.verify`) slots, and every built-in class to the run model.

`modelRouting.specifyOnSonnet: true` (off by default, #1173) adds one route after step 2: when the run model is a Claude Code Opus model (`claude-code/opus`, `claude-code/claude-opus-5-5`, ...), the `specify` stage runs on `claude-code/sonnet` (source `modelRouting.specifyOnSonnet`) and every other stage keeps Opus. A `--route specify=...` or a configured `specify` stage route still wins, `--model-strict` ignores it, and runs on other models or providers are not affected. It exists so the bench loop can measure Sonnet specs on Opus runs; whether it becomes the default is decided after those measurements. Set it on the routing screens, with `baked workflow routing specify-sonnet on|off|unset` or with `PATCH /v1/workflow/routing`.

A stage route applies to every agent of that stage, including its tasks, review dimensions and skeptics; gates on transitions use their profile's model. A route naming a stage the workflow does not have, or an unknown class, is refused when the run starts.

A run freezes its routing at start in the `routing.json` artifact (each profile's and each routed stage's model with the source of the choice); resume, revise and fork use it, whatever the configuration says later, until a [reroute](#switching-a-run-to-another-model) writes a new revision. `baked workflow route [WORKFLOW] [--model ID] [--route ...] [--json]` prints the same table without starting a run, and `workflow profiles [--model ID]` shows each profile's resolved model and `modelSource`.

`--model` (and the chat tab's model in the terminal UI and desktop app) is the run model. An explicit `--model` serves the `$active` class even when `modelRouting.classes.active` names another model; that class keeps its effort and fallback models, the routing record keeps `explicitModel: true`, and a reroute of the run keeps it. Without `--model` the run model is `defaultModel` and a configured `classes.active` applies as written. Only the `$active` class follows `--model`, so a configured `modelRouting` class, role, profile or stage route, or a legacy `taskRouter` slot, still wins. When one wins, the start records a warning in `routing.json` and prints it as `warning: ...` on stderr of `workflow run` and `quick`: "Model X applies to the active class only; implementer uses Y (modelRouting.classes.coding)". `--model-strict` (API: `modelStrict: true`; `doctor` and `estimate` take it too) ignores every configured route for this run, so the run model serves every class, role and stage; only `--route` still overrides it. The record keeps `strict: true`, and a reroute of the run stays strict. `baked workflow status RUN_ID` returns `routing: {runModel, strict, warnings, effective: [{target, model, source}]}` (the effective model of each role and stage, from the routing record); the run view of `baked serve` carries the same `routing` object, and the terminal run overview and the desktop run's Model panel show the models by role, the warnings and whether the run is strict. The terminal New run form has a Routes field (‹ configured › or ‹ run model only ›, toggled with ←/→) and the desktop New run form a "Run model overrides configured routes" checkbox under Oven settings; both start the run with `modelStrict`.

### Effort and fallback models

Any route, and any class, can be an object instead of a model ID:

```jsonc
"modelRouting": {
  "classes": { "deep": { "model": "anthropic/claude-opus-5-5", "effort": "high", "fallback": ["openai/gpt-5.1"] } },
  "roles": { "researcher": { "model": "$deep", "effort": "low" } },
  "independentReview": "warn"
}
```

- `effort` is `default`, `low`, `medium`, `high`, `xhigh` or `max`. It replaces `performance.effort` and `performance.openaiReasoningEffort` for that agent's calls only; an OpenAI level the model does not support is lowered to the nearest one it does. `default` sends no effort setting, so the provider's default applies. Models configured with a fixed effort in a compatible provider's own settings keep it.
- An agent profile may set its own `effort` with the same values (#334). It applies when no route of the agent sets one: a role, profile, class or stage route with `effort` wins, and a stage route without it keeps the profile's. No built-in profile sets it, so it is opt-in through a profile in `baked/agents/` or `~/.baked/agents/`. `workflow profiles` and `workflow route` show it as the profile's route effort.
- `fallback` lists up to three model IDs (not classes) tried in order. A route without its own `fallback` takes the model's chain from `modelFallback` ([providers](../providers.md#model-fallback)), frozen into the run's `routing.json` at start. A class reference brings the class's effort and fallback models; the object route's own fields override them.

The primary model gets two retries on a transient provider error (timeouts, 408, 429, 5xx, 529, network errors); each fallback model gets one. A rate limit (a 429, or Codex's "429 Too Many Requests" after its own quick retries) waits about 5, 15 and 45 seconds, three retries on any model, or longer when the provider's `retry-after` asks for it, instead of retrying within seconds. A failed attempt records why in its `attempt.finished` event (`error`: `code` and the first 500 characters of the message). A provider that answers "Selected model is at capacity" or "try a different model" is treated the same way, but waits longer (about 5, 15, 45 and 90 seconds, four retries, on the primary model too) and hands the step to the next model of the route at once when there is one, instead of blocking the run as `provider_unavailable`. When a route has another model and the provider asks for a `retry-after` over 30 seconds, the step moves on instead of waiting, and a fallback model whose provider asks for such a wait is not waited for. A step also moves to the next model when its prompt does not fit the model's context window, or when the provider refuses the request for its size (the Codex app-server's `input_too_large`, a context-length error or HTTP 413). Without another model, a size refusal is not a provider outage: the step is tried once more in a fresh session, which does not carry the history that overflowed, and if that fails too, or the attempt had changed files, the run blocks with `budget_exhausted` and a message naming the limit, instead of restarting the task as a lost worker on the same history. A step never moves to another model after its attempt changed files, after a cancel, or on a non-transient error (401, 403, a refused request, invalid output). The Claude Code message that another Claude Code process is refreshing the OAuth token is transient too, but it passes in about a minute: it is retried up to three times, each after 30 to 60 seconds. When every model fails, the step fails with `provider_unavailable`, naming the primary's failure and the last model's. A refusal of the account is not retried and not handed to a fallback model on the same provider, which shares the account; the step goes to the next model of the chain on another provider instead, unless the attempt changed files. Without such a model, spent credits or quota (HTTP 402, or a 429 whose body says the quota or credits are used up, as OpenAI reports it) and a rejected API key (401, or a 403 about the key) block the run at once with `provider_account` and a message that says to add credits or fix the key, then resume. In a run with several writers this stops the batch instead of being reported as a lost task worker, and a lost worker's message now always names a cause.

`routing.json` records each entry's `effort` and `fallback`, and `workflow route` prints them in the EFFORT and FALLBACK columns. `workflow usage RUN_ID` reports each attempt's `model` and a `models` summary (attempts, tokens and steps per model, most tokens first; host attempts such as checks are grouped as `(host)`). Each attempt of a task step also has its `taskId` and `taskGeneration` (0 for the task's first implementation, one more for each repair that invalidated it; null for other steps), and `tasks` sums them per task and generation (`taskId`, `generation`, `attempts`, `tokens`, `costUsd`).

### Preflight and independent review

Before a run is created, every model it can call is checked the way `baked doctor` checks it, and the start reports the same lines. A model that a bound profile or a stage route uses as its primary, and whose known provider has no credentials, refuses the start with `CAPABILITY_DENIED`. Fallback models, profiles the workflow does not bind, unknown providers and a check that does not answer within 5 seconds only add a warning.

`independentReview` controls whether a reviewer may run on a model the implementation also uses, fallback models included: `warn` records a warning, `require` refuses the start, `off` skips the check, and `provider` asks for a reviewer of another vendor (Codex reviews Claude Code output and the other way round). Without the field, `provider` applies when the configuration names models of two known vendors (the run model, classes, roles, profiles, stage routes and the legacy router slots), else `warn` once `modelRouting` is configured. Review, converge and reflection stages and review gates count as the review side; task stages as the implementation side.

With `provider`, vendors are compared rather than models: `claude-code/*`, `anthropic/*` and Copilot or GitHub Models Claude models are `anthropic`, `codex/*`, `openai/*` and GPT models are `openai`. Every review-side route that shares a vendor with the implementation (its fallback models included) moves to the first model of another vendor, in this order: the `$review` class, any other model the configuration names, then the first model of each signed-in single-vendor provider (Claude Code, Codex, Anthropic, OpenAI). A moved route keeps its effort, drops its fallback models and has the source `independentReview: provider`; each move is listed in the run's warnings as `Cross-provider review: ...`. When no model of another vendor exists, the review stays where it is and the start records a warning instead of refusing. A reroute names its models itself, so under `provider` it only warns about a shared vendor. The [run report](#run-report) says which models (and vendors) reviewed the change and which implemented it.

Every review finding carries a `confidence` from 0 to 1 that it is real and caused by the change; reviewers leave out problems the change did not introduce, nits and style, and what the project's formatter or linter reports. A finding below `reviewMinConfidence` (0.8 by default) is a note: it stays in the review artifact and starts no correction, whatever its kind or severity. One exception is the convergence walker's `missing` or `correctness` finding on behavior the request or spec names (basis not `inferred`): a walker that reports one below the threshold without a repro is asked once to try it with `run_repro`, and when the host runs the attached repro and it prints `actual`, the finding starts a correction whatever its confidence, so a request clause the spec dropped is repaired instead of kept as a note. A finding without a confidence counts as 1. Set the threshold in `modelRouting.reviewMinConfidence` (global or project layer) or directly as `workflows.policy.reviewMinConfidence`; a start copies the routing value into the run's policy, so it is frozen with the approval digest, and a policy without it keeps its hash.

### Critic

The critic (`critic` profile, role `reviewer`, model `$review`) scores every task attempt that reaches its checks: it reads the task, the patch of the attempt and the checks that failed, and returns a `score` from 0 to 1 (its estimate that the attempt is correct and will be kept) with five rubric items, each scored with a one-sentence note: `intent`, `instructions`, `scope`, `testIntegrity` and `completeness`. The critique is stored as the artifact `tasks/TASK/critique.json` (one revision per attempt, with the attempt number, the diff it scored and the model) and listed in the run report under "Critic" with the weakest item. It is advice: it changes no status and starts no correction. A critic that fails is recorded with its error and the run goes on; only a spent budget or a checkpoint stops the run as for any agent call. An attempt already scored is not scored again on resume. The critic keeps its own profile route even when the task stage has a stage route, and `independentReview: provider` moves it to another vendor with the reviewers.

`critic` is `off` (never score), `advise` (always score, decide nothing), `select` or `earlyStop`. `select` and `earlyStop` score like `advise` and also let a [calibrated](#critic-calibration) critic decide: `select` picks the best-scored passing candidate of a [best-of-N](#best-of-n-candidates) task instead of the vote, and `earlyStop` ends a convergence loop as described below. Until the critic is calibrated both act like `advise`. Without a setting the critic runs only when its model is of another vendor than the implementation's, so a setup with one provider spends nothing on it. Set it in `modelRouting.critic` (global or project layer, on the routing screen, with `baked workflow routing critic off|advise|select|earlyStop|unset`, `PATCH /v1/workflow/routing` or the desktop's Model routing page) or directly as `workflows.policy.critic`; a start copies the routing value into the run's policy.

#### Critic outcome log

Every critic score is also kept in the project's `.baked/workflows.sqlite` (table `critic_outcomes`, one row per scored attempt), with the outcomes that later show whether the critic was right. The data stays local, like telemetry, and is what [calibration](#critic-calibration) learns from.

- `task_result` is `passed` when the attempt's task checks passed, or `repaired` when they failed and a repair task followed.
- `acceptance` is `accepted` when the run completed, or `rejected` when it failed or was cancelled.
- `delivery` applies to a run with a [delivery](#delivery). It is `merged` once the base branch contains the delivered commit, `reverted` once a commit on that branch reverts it, and otherwise `open`. It is read from the local Git repository, so fetch first to see merges made on the server.
- `survival` is the share of the non-blank lines the attempt added that the project's files still hold. It is updated until 30 days after the run completed and is then final.

The delivery and survival labels are refreshed before a run starts, at most once a day per process. `baked workflow outcomes [RUN_ID] [--refresh] [--json]` (or `/workflow outcomes` in the terminal UI) shows the log:
- a summary (attempts whose checks passed or were repaired, with the mean score of each; accepted and rejected runs; merged and reverted deliveries; mean final survival);
- one line per scored attempt.

`--refresh` updates the labels from Git first, and `--json` gives the rows for the bench loop to aggregate across projects. The run report's Critic section adds an Outcome column with the labels of each attempt.

#### Critic calibration

A critic's score only decides something once it has shown, on this project's own history, that it separates attempts that held up from those that did not. An attempt is labelled:
- **held up** when its task checks passed and nothing later undid it;
- **did not hold up** when a repair followed, its run failed or was cancelled, its delivery was reverted, or less than half of its added lines survived to the final survival label.

The critic is calibrated when the log has at least 20 labelled attempts, at least 5 of each label, and the scores rank them with an AUC (the chance that an attempt that held up scores above one that did not) of at least 0.65. The threshold is the score with the best Youden index (true positive rate minus false positive rate). `baked workflow outcomes` prints the calibration line, `--json` and `GET /v1/workflow/critic` return it as `calibration` (`{samples, good, bad, auc, threshold, calibrated, reason}`), and the desktop shows it under Critic on the Model routing page.

A run computes its calibration once, from earlier runs only, and freezes it as the artifact `critic/calibration.json`, so a resumed run decides the same way. The same artifact holds up to two recent attempts of each label with their score and weakest rubric item; the critic receives them as `earlierAttempts` to judge what this project keeps.

With `critic: earlyStop`, a convergence round whose findings would start another repair accepts them instead when:
- the critic is calibrated;
- every required check passes;
- no finding is critical, a security finding, or high with a reproduction the host ran;
- the latest attempt of every scored task scores at or above the threshold.

The findings become known limitations decided by `critic` ("critic early stop" in the run report), the reasons are stored as `critic/early-stop-N.json`, and the run goes on to acceptance. Otherwise the round continues as without the critic.

Warnings are stored in `routing.json` under `warnings` and printed by `workflow route` as `warning:` lines.

### Switching a run to another model

When a provider becomes unusable in the middle of a run (credits or quota spent, a revoked key, a retired model), move the run to another model instead of starting over:

```sh
baked workflow reroute RUN_ID --expected-revision N --model ID [--route STAGE=MODEL,...]
# or switch and continue in one command, with the exit codes of resume:
baked workflow reroute RUN_ID --expected-revision N --model ID --resume [--events]
```

The run must not be executing: `created`, `paused`, `blocked` or `waiting` (pause a running run first; a finished run is forked instead). Completed stages, tasks, approvals and evidence stay; only the next agent calls use the new models. The routes are resolved again through the current `modelRouting` and `modelFallback` with the new run model, so every profile and stage that followed the old run model (directly or through a built-in class without a configured model) follows the new one. A class configured to name a model keeps it; change the configuration first, or route its stages with `--route`. Stage routes given with `--route` at start are kept, except that one naming the old run model moves to the new one; `--route` here replaces them stage by stage. `--model` may be left out to change only stage routes.

The new record goes through the same checks as a start: a bound model without credentials refuses the switch with `CAPABILITY_DENIED`, and `independentReview: "require"` refuses a switch that puts a reviewer on an implementation model. It is written as a new revision of `routing.json` (warnings included), and a `run.rerouted` event names the old and new run model and every changed route (`stage ID` or `profile ID`, with its model and fallback chain before and after). The run keeps its status; `resume` (or `--resume`) continues it from where it stopped. A `provider_account` stop names this command in its message.

## Delivery

A completed run whose verification is `current` can be delivered through Git: one commit of the run's files on a new branch, a push of that branch and a pull request. Every step needs a person's approval of the exact plan; delivery never runs inside auto approval.

```sh
baked workflow deliver RUN_ID [--remote origin] [--branch NAME] [--draft] [--no-pr] [--with-specs|--no-specs]
baked workflow approve RUN_ID --request ID --digest SHA256 --expected-revision N
baked workflow deliver RUN_ID --execute --expected-revision N [--request ID]
```

`deliver` prepares a plan and changes nothing in Git. It is stored as the immutable artifact `delivery/PLAN_ID/plan.json` with the reviewable diff in `delivery/PLAN_ID/diff.patch`, and a pending request of kind `delivery` carries the plan's digest. The plan names the operations (`commit`, `push`, `pull_request`), the remote and its URL, the branch (default `baked/FEATURE-` followed by the first 8 characters of the run ID), the base commit and branch (the current HEAD), the commit author, every file with its action, content hash and mode, the excluded files with a reason, the user's other uncommitted changes, the commit message, the pull request title, body, base and draft flag, and the check, criterion and review results. The command prints the `approve` command for that digest. A new `deliver` supersedes an older pending plan. Approving or rejecting a delivery request does not change the run's status; the run stays `completed`.

Which files are delivered: the files of the run's effect journal (task edits and published spec artifacts) and the files that changed between the approval baseline snapshot and the final snapshot inside the tasks' declared writes. Other files in the workspace are never committed; they are listed under `userChanges` and left as they are. Excluded and reported: anything under `.baked/` or `.git/`, symbolic links, files ignored by Git, files with no net change from HEAD, and files that look like secrets (`.env*`, `.envrc`, `.netrc`, `.npmrc`, `.pypirc`, `.pgpass`, `.git-credentials`, `credentials.json`, SSH keys, `*.pem`, `*.key`, `*.crt`, `*.cer`, `*.der`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.kdbx`, `*.asc`, `*.gpg`, `*.ovpn`, or content with a private key header).

The run's own `specs/FEATURE/` documents (spec, plan and task graph) are committed only when the base commit already tracks a `specs/` directory, so a pull request to a repository that does not keep specs carries just the code; they are listed as excluded with reason `specs` and stay in the run's artifacts, and the pull request body still carries the summary and criteria. `--with-specs` delivers them anyway, `--no-specs` leaves them out of a repository that keeps specs.

Preparation refuses, with `details.reason` in the error:

| Reason | Cause |
| --- | --- |
| `git_required` | The workspace is not a Git repository, or not its top level. Delivery needs Git; a filesystem-only project keeps its changes in place |
| `run_not_completed`, `verification_not_current` | Only a completed and currently verified result is delivered |
| `dirty_files` | A delivered file differs from the run's verified snapshot |
| `base_mismatch` | A delivered file had uncommitted user changes before the run, or a commit since the run started changed it; the run's changes cannot be separated, so commit or revert those changes by hand |
| `missing_remote`, `remote_unreachable`, `missing_auth` | The remote is not configured, cannot be read, or credentials (Git or the pull request token) are missing |
| `branch_exists` | The branch exists locally or on the remote; delivery never overwrites a branch |
| `detached_head`, `no_commits`, `missing_identity` | No base branch, no base commit, or no `user.name`/`user.email` |
| `nothing_to_deliver` | Every changed file was excluded |
| `worktree_missing`, `branch_moved` | A worktree run's worktree was removed, or its run branch no longer points at the accepted commit |
| `invalid_follow_up`, `not_delivered` | `--follow-up` names the run itself, or a run with no pushed delivery |
| `answer_without_follow_up`, `no_pull_request`, `thread_not_open` | `--answer-threads` without `--follow-up`, a followed delivery that opened no pull request, or a thread that is not an unresolved review thread of that pull request |
| `review_replies_failed` | GitHub refused a reply or a resolution of an approved thread; the commit is pushed, and the next execute answers the threads not yet answered |
| `branch_missing`, `fetch_required`, `branch_checked_out` | The followed branch is gone from the remote, its tip is not in the local repository (`git fetch` it), or it is checked out in the working copy or a worktree |

A HEAD that moved since the run's baseline is accepted when the new commits do not touch the delivered files; the plan records `headMoved`.

A run executed in a worktree is delivered from its run branch: the files are read in its worktree, which must still exist and hold the branch at the accepted commit (`worktree_missing`, `branch_moved` otherwise), and the plan records them under `worktree` (path, branch, commit). The delivery commit is still built on the working copy's current HEAD in a temporary index, so the user's checkout is not touched; the user's own uncommitted changes are listed under `userChanges`. After the delivery completes the worktree is removed; the branch `baked/wf/RUN_ID` stays.

`deliver --execute` performs the latest approved plan (or `--request ID`). It refuses a plan approved by anyone but a person, a plan whose artifact no longer matches its digest, a changed remote URL, HEAD moved since the plan (`head_moved`) and files changed since the plan (`dirty_files`). The commit is built in a temporary index from the approved content; the user's checkout, index, HEAD and files are not touched, and the new branch is created only if it does not exist. The author and committer date is the plan's time, so the same plan always produces the same commit ID. Commit hooks do not run because no checkout is used; the push runs the local `pre-push` hook and the remote's hooks. The push names the branch without `+`, so Git only creates or fast-forwards it. Delivery never force-pushes, merges, resets, rebases or deletes anything.

Every operation is a `delivery` effect in the run's journal with its plan ID, branch and commit. A failure Git or the host reports for certain (non-fast-forward, hook rejection, authentication, unreachable remote, HTTP 401/403) marks the effect `failed` and stops with that reason; the next `--execute` retries only the failed step. When the outcome is not known (a crash, a dropped connection, a lost API response), the runtime checks before doing anything again: the local branch for the commit, `git ls-remote` for the push, the pull request by head branch for the pull request. A found result is recorded as `reconciled`; a confirmed absence as `failed`, which allows a retry. If the check itself cannot be answered, the effect stays `unknown` and a `recovery` request is created, as for v1 commands; it is answered with `recover` (`record-applied`, `record-not-applied`, `retry`, or `cancel`, which abandons the delivery). A later `--execute` that can check the remote settles the effect itself and supersedes the request. When everything is done, `delivery/PLAN_ID/result.json` links the commit ID, the branch, the remote and the pull request URL to the run, its revision at planning, the accepted snapshot and the approval root. Executing a delivered plan again returns that result and creates nothing.

The pull request body is the [run report](#run-report) followed by a `Delivery` section: the delivered files, the files left out with their reason, and the run, snapshot and base commit. A report longer than 60,000 characters is shortened (long tables keep their first rows, then the text is cut with a note) so GitHub accepts it; the Delivery section is always kept whole. The body is part of the plan, so its digest covers the exact text.

Pull requests use the GitHub REST API. The token is read from the environment variable named in the configuration (default `GITHUB_TOKEN`) and sent only to the configured API URL; github.com remotes map to `https://api.github.com`, other API URLs (GitHub Enterprise) serve remotes on their own host. Other hosts are delivered with `--no-pr` (commit and push only).

```json
{ "workflows": { "delivery": { "tokenEnv": "GITHUB_TOKEN", "apiUrl": "https://api.github.com" } } }
```

### Follow-up commits to a delivered pull request

A later run can add its commit to the branch and pull request of a run that was already delivered, for example a `fix-ci` run for a check that failed on that pull request, or a run that answers its review:

```sh
baked workflow deliver RUN_ID --follow-up DELIVERED_RUN_ID
```

The plan takes the branch and remote of the followed run's latest pushed delivery and builds the commit on that branch's remote tip (`base.commit`) instead of HEAD; `base.branch` stays the pull request's base. Its operations are `commit` and `push`: no pull request is opened, and `followUp` names the followed run and its pull request, which shows the new commit. The usual checks apply against that tip instead of HEAD, so a file whose content when the run started differs from the branch is refused as `base_mismatch`. A run that works on the followed run's result from the working copy (its files are still there, uncommitted) therefore delivers just its own change. The local copy of the branch, if there is one, must point at the remote tip and not be checked out in the working copy or a worktree (`branch_moved`, `branch_checked_out`): execution fast-forwards it with the commit and never changes a checkout. The push is a fast-forward as always; when someone pushed to the branch after the plan, the push is refused as `non_fast_forward`, and the next plan needs that commit fetched. `--branch`, `--draft` and `--no-pr` plan a new branch and are refused with `--follow-up`. The TUI and desktop approval views show which branch and pull request the commit goes to.

### Following a delivered pull request's checks

```sh
baked workflow follow RUN_ID [--interval 60] [--timeout 60] [--once] [--fix] [--reviews]
```

`follow` reads the checks GitHub reports on the commit the run's latest delivery pushed: check runs (a completed run passes with `success`, `neutral` or `skipped`) and commit statuses. It is host code, with no model call and no tokens. It reads every `--interval` seconds (5 to 3600, default 60) and ends at the first failed check, when every check passed, or after `--timeout` minutes (1 to 1440, default 60), with `outcome` `failed`, `passed` or `timeout`; no check reported yet counts as still running. `--once` reads once. It needs a GitHub remote and the delivery token (`workflows.delivery.tokenEnv`); a run without a pushed delivery is refused as `not_delivered`.

With a failed check the answer has `fix`: a `fix-ci` run for the failed checks, with the feature `FEATURE-ci` (`-2`, `-3` when taken) and a request that names the pull request, the commit and each failed check with GitHub's summary and link. `--fix` starts that run as `baked workflow run --workflow fix-ci` would; it reproduces the failure with the project's checks, plans, asks for approval and fixes. Its answer names the next step, `baked workflow deliver FIX_RUN_ID --follow-up RUN_ID`, which puts the fix on the same pull request ([follow-up commits](#follow-up-commits-to-a-delivered-pull-request)). Follow the fix run the same way until the checks pass. Every commit and push still waits for a person's approval of its plan.

The TUI run view offers K (PR checks) on a completed run: it reads the checks once and, when one failed, asks whether to start the fix run (Y). The desktop run screen shows a Pull request panel on a completed, delivered run with the checks, Check again, and Fix failed checks, which starts the fix run and opens it. `GET /v1/workflow/runs/RUN_ID/checks` is the same read over the [local API](../desktop/api.md).

### Repairing from review comments

```sh
baked workflow follow RUN_ID --once --reviews [--fix]
baked workflow deliver FIX_RUN_ID --follow-up RUN_ID --answer-threads THREAD_ID,THREAD_ID [--resolve]
```

Review comments are read only with `--reviews`. Once no check failed (a failed check is fixed first, as above), `follow` also reads the pull request's review threads and the latest review of each reviewer over GitHub's GraphQL API, again host code with no model call. The answer's `reviews` has `state` `changes` or `clear`, the unresolved `threads` (`id`, `path`, `line`, `outdated` and the comments with author, body and link) and `changesRequested`, the reviews whose latest state requests changes. Resolved threads are left out; comments from review bots count like any other thread. With changes asked for, `repair` is a `quick-fix` run with the feature `FEATURE-review` (`-2` and onward when taken) and a request that quotes each thread and review as data, with `threads`, the IDs its delivery answers. `--fix` starts that run, and the answer's `next` is the follow-up delivery that answers those threads.

`--answer-threads` adds the operation `review_replies` to a follow-up plan, after `commit` and `push`. When the plan is made, each thread must be an unresolved review thread of the followed run's pull request (`thread_not_open` otherwise). The plan lists the threads and the reply, `Addressed in {commit}.`, where `{commit}` is the pushed commit. `--resolve` also resolves them. The person who approves the plan's digest therefore approves the replies too, and nothing is posted before that approval. Each reply carries the plan's marker (`<!-- baked-delivery:PLAN_ID -->`), so a retry after a lost response finds the reply already there and does not post it again. The token needs permission to write pull request comments.

The TUI run view offers V (PR reviews) on a completed run: it reads the checks and reviews once and asks whether to start the repair run (Y), naming the delivery flags. The desktop Pull request panel has Read review comments, which lists the unresolved threads, and Fix review comments, which starts the repair run and shows the delivery command. The approval view of a follow-up plan lists the threads it answers. `GET /v1/workflow/runs/RUN_ID/checks?reviews=true` is the same read over the API, and `POST .../deliver` takes `answerThreads` and `resolve`.

## Initiatives

An initiative is one big idea split into 3 to 12 features, each with a boundary, a contract it provides to other features, the features it depends on, the workflow its runs use and its size. The split is approved once, as a whole; then the initiative runs one ordinary workflow run per feature in dependency order, in the same workspace: one at a time inline, and independent features side by side when every feature's workflow runs in worktrees. It is stored next to the runs in `.baked/workflows.sqlite` (migration 004): the initiative, its immutable plan revisions, the split approval requests, the links from features to run IDs, an append-only event log and idempotent commands.

```sh
baked workflow initiative start ID (--prompt TEXT | --prompt-file FILE) [--plan FILE] [--workflow sdd] [--worktree]
baked workflow initiative show ID
baked workflow initiative rename|remove|merge|split ID ... --expected-revision N
baked workflow initiative set-workflow ID --feature F --workflow W --expected-revision N
baked workflow initiative set-size ID --feature F --size small|medium|large --expected-revision N
baked workflow initiative approve ID --request ID --digest SHA256 --expected-revision N
baked workflow initiative drive ID
baked workflow initiative pause|resume ID --expected-revision N
baked workflow initiative replan ID --feature F --expected-revision N
baked workflow initiative extend ID --expected-revision N [--tokens N] [--calls N] [--time-ms N]
baked workflow initiative reroute ID --model ID --expected-revision N [--resume]
```

Initiative IDs and feature IDs are lower case slugs. A feature's runs use the workflow feature ID `INITIATIVE_FEATURE`, so its accepted spec is `specs/INITIATIVE_FEATURE/spec.json`. A run owns its feature ID: a spec whose `featureId` names another feature is stored with the run's ID instead of failing the specify stage.

**Split.** Without `--plan`, `start` runs the built-in `initiative-decompose` workflow: one agent stage with the `decomposer` profile, which reads the code and returns an `initiativePlan` (title, goals, completion criteria, and features with `id`, `title`, `boundary.scope`, `boundary.paths`, `contract`, `dependsOn`, `mandatory`, and optionally `workflow` and `size`). It changes no file. Duplicate IDs, unknown or repeated dependencies and cycles go back to the decomposer for correction. A split of more than 12 features is not corrected: the initiative becomes `refused` with the message to split the request into stages and start one initiative per stage. With `--plan FILE` the split is given by the user and validated the same way, including the bound.

**Feature workflows and sizes.** Each feature runs the workflow that fits it ([workflows.ts](../../src/core/workflows/initiatives/workflows.ts)). The decomposer gets the project's workflows that can run a feature as `extra.featureWorkflows` (each `id`, `description` and whether it writes a spec) and picks one per feature, with a size: `small`, `medium` or `large`. A feature can run under a workflow that starts without problems and writes files; with tiered approval only schema 1 workflows qualify. A feature other features depend on needs a workflow that writes a spec (such as `sdd`), because its accepted spec is the contract they pin; a feature nothing depends on may run under one without a spec (such as `quick`), and is accepted when its run completes with current verification. A feature without a workflow, from a user's or the coordinator's split, gets the one [`proposeWorkflow`](../../src/core/workflows/preset-router.ts) proposes for its title, scope and contract among the workflows that fit it, except that a change [`assessRequest`](../../src/core/workflows/preset-router.ts) rates as high risk keeps the initiative's default workflow (`--workflow`); a feature without a size gets the size the assessment gives. A decomposer's workflow that cannot run its feature is replaced the same way; a user's is refused with the reason. `set-workflow` and `set-size` change one feature before approval or while paused, each as a new plan revision; changing the workflow supersedes the feature's run on approval, changing the size does not. Plans stored before features had a workflow run every feature under the initiative's workflow.

**Approval of the split** is mandatory. Each plan revision has a digest over the initiative ID, the revision number, the plan (with each feature's workflow and size), the shared budget and the settings fixed at start (default workflow, base policy hash, tiered approval, model). The pending `split_approval` request names that digest, and `approve` must repeat it. Before approval, `rename` (title only), `remove` (dependents lose the edge), `merge --features A,B` (one feature with the union of boundaries, contracts and external dependencies) and `split --feature F --parts FILE` (dependents depend on every part) each produce a new revision, a new digest and a new request; the older request is superseded. An edit that leaves fewer than 3 features, an unknown ID or a cycle is refused.

**Execution.** `drive` (also run by `start`, `approve` and `resume`) advances the initiative until a person is needed, it is blocked or paused, or it completes. When any feature's workflow runs inline, one feature run is open at a time: the runtime guards each run's source snapshot, so a second open run would block the first. `--worktree` (and every initiative the coordinator starts from a split) runs feature runs in worktrees, so independent features run side by side. A feature starts when every feature it depends on is accepted: its run completed with current verification and its spec is the newest approved spec of that feature. The new run is started with those upstream contract hashes pinned as its spec dependencies (the spec author's own dependencies are replaced), so its readiness uses the existing `contractHash` check. Decisions inside a feature run use the run commands (`baked workflow approve RUN_ID ...`); `show` lists them under `pendingDecisions` with the run and request IDs. Under `baked serve` (the desktop app), a feature run resumed after such a decision continues its active initiative once it stops, so the next features start without a separate `drive`.

**Features in worktrees.** When the feature workflow runs in worktrees (a v2 definition with `execution: worktree`, or a base policy with `executionMode: "worktree"`), `show` reports `parallelRuns`, the workspace's [`workflows.maxParallelRuns`](#parallel-runs) (1 inline). Each drive round starts ready features, in dependency order, while fewer than `parallelRuns` feature runs can execute, then drives those runs at the same time until each stops; a feature that waits for a decision or is blocked stops the drive only when no other feature can move. A feature's worktree starts from HEAD merged with the accepted result of each feature it depends on (the commit on that run's `baked/wf/RUN_ID` branch), so its agents see the code they build on; a feature without dependencies starts from HEAD. The merge is made with `git merge-tree` and `git commit-tree` without touching the working copy, with a fixed author and date, so the same results give the same base commit. When two upstream results conflict, the start is refused with the conflicting files and the feature stays `ready`: re-plan one of the upstream features so their files do not overlap. A rebased run starts from the new upstream results. Each feature's delivery carries its upstream commits; deliver the upstream features first. Features started in the same round take equal shares of the remaining budget, as below.

**Tiered approval** (`--tiered-approval [--max-tasks 5] [--max-files 10]`, off by default) gives each feature run auto approval whose allowed paths are the feature's approved `boundary.paths`, without deletes or new dependencies, using the same auto approval check and the actor `auto-approval` as v2 definitions. A plan that writes outside the boundary, or a feature without boundary paths (or with more than 20), goes to a person. It requires a schema 1 feature workflow such as `sdd`; a v2 definition takes auto approval only from the definition, so the combination is refused at start. A v2 feature workflow with its own auto approval is started with `--confirm-auto-approval HASH`, which is passed to every feature run.

**Contract changes.** When an upstream feature is accepted again with a different contract hash (after `replan` or a split re-plan), each dependent whose run is pinned to the old hash becomes `stale`. The next drive cancels its open run if any, marks that run's evidence `input_changed`, and starts a rebased run that keeps the dependent's spec, pins the new upstream hashes and starts again at the plan stage, so the plan is made, analyzed and approved against the new contract. A rebased run never gets auto approval: a person always re-approves it. A dependent that already finished keeps its result on record and is shown `waiting` while the upstream runs again.

**Progress.** `show` returns the status, the next action and its reason, the plan revision and approval digest, and per feature: its state (`proposed`, `waiting`, `ready`, `in_progress`, `needs_decision`, `paused`, `blocked`, `failed`, `stale`, `accepted`), its blockers in words (for example `waits for core's contract (core is waiting for a decision)`), its pinned upstream hashes, its accepted contract hash, its pending decisions and its usage over all its runs. The initiative completes only when every mandatory feature is accepted; `initiative.completed` records each feature's run and contract hash.

**Shared budget.** Set it with `--budget-tokens N --budget-calls N --budget-time-ms N`; otherwise it is the base policy's per-run limits for every medium feature (half for a small one, double for a large one), plus one more. Each feature run starts with a share of what remains weighted by its size (small 1, medium 2, large 4), rounded down: remaining = limit - (usage of finished runs + the limits of open runs, decompose and superseded runs included), times the feature's weight, divided by the weights of the features of the approved plan without a run. `show` gives each such feature's `share`. A rebased run takes one more share of the same split. Agent calls per run are capped at 1000. When a share would fall below 1000 tokens, 1 call or 1 second, the initiative is blocked with the budget named; `extend` raises the shared limits (only upward). A feature run that exhausts its own share blocks like any run and is extended with `baked workflow extend RUN_ID`.

**Estimate.** `estimate ID` (TUI T, desktop Estimate, `GET /v1/initiatives/ID/estimate`) forecasts the split, approved or not, without changing anything ([estimate.ts](../../src/core/workflows/initiatives/estimate.ts)). For each feature it gives a token range and a planned task count. Once this project has finished feature runs of earlier initiatives of the same size, it measures the feature from them (from those of the same workflow when there are two). Otherwise it prices a run of the feature's workflow as `baked workflow estimate` does ([Estimates](#estimates)): runs of that workflow, then any run, then generic ranges. It then scales the tasks by size (small half, large double); the stages around the tasks stay the same. The total adds the features and is planned with a 25% margin on the high end, compared with the shared budget (`fits`: `yes`, `maybe` or `no`). The level runs from 1 to 5 by the expected task count, on the bench difficulty ladder's typical counts: about 6, 10, 15, 22 and 30 tasks. `basis` names the weakest source among the features. Every figure comes from this project's runs, so the estimate holds for any provider. It is an estimate, never a limit.

**Pause, resume and re-planning.** `pause` stops the initiative and pauses a running feature run; `resume` continues it. While paused, the split can be edited again: approving the new revision keeps every feature whose boundary, contract, dependencies and mandatory flag are unchanged (a rename keeps its run), and supersedes and cancels the runs of removed or changed features, which then run again under the new revision. `replan --feature F` supersedes one feature's current run so the next drive starts it again; other features' results stay. Superseded runs and their artifacts remain linked to the initiative and are not collected by `gc`.

**Switching the model.** `reroute --model ID` moves the whole initiative to another model, for example when its provider runs out of credits: feature runs it starts from now on use the new model, and its open runs that are not executing (the decompose run and each feature's current run) are [rerouted](#switching-a-run-to-another-model) with the same checks and a `run.rerouted` event each. Every run is checked before any is changed, so a model that cannot be called, or an `independentReview: "require"` conflict in any run, changes nothing. Runs that already use the model are left as they are, runs started before routing was recorded are skipped, and finished and superseded runs keep their models; a rebased run inherits its run's latest routing. A run that is executing refuses the switch: pause the initiative first. The `initiative.rerouted` event records the old and new model and what happened to each run (`rerouted`, `unchanged` or `skipped`), and `show` reports the model as `model` (null for the configured default). The approved split stays approved; a split still waiting for approval is proposed again as a new revision, because its digest covers the model. `--resume` also resumes the rerouted runs that are blocked and a paused initiative, then drives it, with the exit codes of `drive`. The TUI offers the same with M, the local API with `POST /v1/initiatives/ID/reroute` and the desktop in the initiative view.

Exit codes of `start`, `approve`, `drive`, `resume` and `reroute --resume`: 0 completed or still progressing, 1 refused or error, 3 waiting for a decision, 4 blocked, 5 revision conflict, 130 paused. The workflow panel and the desktop app start initiatives, edit, approve and reject the split, pause, resume, re-plan features, extend the budget and switch the model; see [Initiatives in the TUI](#initiatives-in-the-tui) and the [desktop app guide](../desktop/app.md).

## Local API (`baked serve`)

`baked serve` exposes the workflow commands to a desktop app or another local client over HTTP. It is a thin front end over the same code path as `baked workflow` (`src/core/api/server.ts` builds the CLI's `WorkflowArgs` and calls `executeWorkflowCommand`), so validation, the `workflows.enabled` setting, approval digests, expected revisions and command idempotency are identical. The chat endpoints (`/v1/sessions`, `/v1/models`) run conversations with the terminal UI's agent and store them with its sessions; they are specified in `docs/desktop/api.md`.

The desktop app's contract over this API, including the chat sessions and project setup endpoints, is [`docs/desktop/api.md`](../desktop/api.md).

```sh
baked serve [--port N] [--token-file FILE] [--allow-origin ORIGIN]... [--cwd DIR]
```

- The server binds `127.0.0.1` only. `--port 0` (the default) picks a free port. When it is ready it prints one JSON line on stdout: `{"url":"http://127.0.0.1:PORT","port":PORT,"tokenFile":"..."}`.
- Each start generates a random 32-byte bearer token (base64url) and writes it to `.baked/serve-PORT.token` in the workspace, or to `--token-file`, with mode 0600 (on Windows the file inherits the directory's ACL). Every request, `/v1/health` included, needs `Authorization: Bearer TOKEN`; the token is compared in constant time.
- The `Host` header must be `127.0.0.1:PORT` or `localhost:PORT`, otherwise the answer is 421 (DNS-rebinding protection). A request with an `Origin` header is refused with 403 unless that exact origin was given with `--allow-origin` (repeatable; `*` and paths are refused). Allowed origins get `Access-Control-Allow-Origin` with that origin and preflight answers; there is no wildcard.
- POST bodies are JSON (`Content-Type: application/json`), at most 1 MiB (413 above), validated with zod; unknown fields are refused.
- SIGINT or SIGTERM stops accepting, closes event streams, aborts active drives through their abort signals like the CLI's Ctrl+C, waits for them and removes the token file. A second signal exits at once with 130.

| `GET /v1/projects` | `projects list --json` | every folder BAKED was opened in (`~/.baked/known-projects.json`), pinned first: `path`, `name`, `projectId` (null without `baked/project.json`), `pinned`, `exists`, `current` and `overview` (`sessions`, `lastSessionAt`, `activeRuns`, `attention`). Each folder is served by its own `baked serve`. |
| `GET /v1/projects/current` | `project show` | the workspace's project: roots, working set, instruction files, latest sessions and runs; 404 without `baked/project.json` |
| `POST /v1/projects/current/working-set` | `project add`, `project remove` | `add`, `remove` (path or glob lists, removals first); returns the project; an entry outside the project roots is 400 |
| `POST /v1/projects/pin`, `/unpin`, `/forget`; `GET\|PUT /v1/projects/current/instructions`; `GET\|PATCH /v1/config`; `GET /v1/providers`, `PUT\|DELETE /v1/providers/ID/key` | `projects pin`, `projects unpin`, `projects forget` for the first three | project setup and settings; see `docs/desktop/api.md` |

Every mutation requires a client-chosen `commandId` (letters, digits, `_` and `-`): a retry with the same ID and body returns the stored result, the same ID with a different body is a conflict. Errors are `{"error":{"code","message"}}` with the workflow fault code: `NOT_FOUND` and `ARTIFACT_MISSING` 404; `INVALID_DEFINITION`, `INVALID_REFERENCE`, `CYCLE_DETECTED` and request validation (`INVALID_REQUEST`) 400; `CAPABILITY_DENIED` 403; `REVISION_CONFLICT`, `COMMAND_CONFLICT`, `STALE_DECISION`, `WORKSPACE_BUSY`, `INPUT_CHANGED` and `RUN_TERMINAL` 409; anything else 500. Messages pass through the export redaction (`redactSecrets`).

`POST /v1/workflow/runs` (202) and `.../resume` (200) answer with the snapshot as soon as the run is driving; the drive continues in the server process, as it would in the foreground CLI, until the run waits for a person, stops, or the server shuts down. Like the CLI, `approve`, `answer` and `reject` only record the decision; the client then calls `resume`. A decision that arrives while a drive of that run is winding down after it stopped waits for that drive to return first. The runtime commits a run's `waiting` status, its new requests and the state they refer to (including the approval digest's inputs) in one transaction, so a decision from any process sees a consistent run; the wait only lets this server's own drive release its leases.

The event endpoint polls the durable event log by sequence every 250 ms and sends each event as `id: SEQ` and `data: EVENT_JSON`, with a `: keep-alive` comment every 15 s. A reconnecting client sends `Last-Event-ID`, which takes precedence over `?after=`, and receives only later events. The stream stays open (also for waiting and terminal runs, which can still receive acceptance and delivery events) until the client disconnects or the server stops. Browsers' `EventSource` cannot send an `Authorization` header; read the stream with `fetch` instead.

`GET /v1/attention` lists everything waiting for a person across all runs and chat sessions of the workspace, oldest first. Each item is `{source, runId, featureId, sessionId, title, status, requestId, kind, blocking, createdAt}`; run items have `source: "run"` and null `sessionId` and `title`:

- Every pending request of a run that is not `cancelled` or `failed`: `kind` is the request kind (`approval`, `clarification`, `manual_evidence`, `recovery`, `checkpoint`, `delivery`). An advisory acceptance-test request (an `approval` request carrying an acceptance walk-through) has `blocking: false`, because the run does not wait for it; every other request has `blocking: true`. `createdAt` is the time of the request's `request.created` event.
- Every run with status `blocked`: `requestId` is `null`, `kind` is the run's reason (for example `input_changed` or `verification_failed`), `blocking` is `true` and `createdAt` is the run's last status change.
- Every pending request of an initiative: `source` is `initiative`, `initiativeId` and `title` name it, `runId`, `featureId` and `sessionId` are `null`.
- Every pending prompt of a chat session loaded by this server: `source` is `chat`, `sessionId` and `title` name the session, `runId` and `featureId` are `null`, `status` is `waiting`, `requestId` is the prompt id and `kind` the prompt kind (`outside-cwd`, `destructive`, `web-search`, `fetch-page`, `question`).

With `Accept: application/json` the answer is `{"items":[...]}`. Otherwise it is an SSE stream that polls the store every 250 ms and sends the whole list as `event: attention` with `data: {"items":[...]}` once on connect and again whenever the list changes, with the same `: keep-alive` heartbeats; there is no event ID to resume from, since every frame is complete. The list is derived from the store, so runs driven by the CLI or the TUI appear as well, and no new durable event type exists for it.

Limitations: event payloads and artifact contents are returned as `baked workflow status`, `--events` and `artifacts` return them, without the export redaction. `import` and `export` are not exposed yet; use the CLI. A run driven by another process (the CLI or the TUI) can be watched through the event endpoint; the workspace leases decide which process may drive a run, as between two CLI processes.

## Exit codes

| Code | run/resume |
| --- | --- |
| 0 | completed |
| 1 | validation/failed |
| 2 | active deadline exhausted |
| 3 | waiting, decision stored |
| 4 | blocked, including the token/call/round budget |
| 5 | revision/digest/input/lease conflict |
| 130 | pause/cancel |

Management commands return 0 when the change is stored. `status`, `list`, `artifacts` and `export` are available with the feature flag off and do not call a model. `--events` prints JSONL with the stored sequence numbers and a final snapshot; `--after N` sets the replay point for run/resume. The process does not continue working after the CLI exits.
