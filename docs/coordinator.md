# Project coordinator

The project coordinator is one long-lived chat per project. You come back to it for the whole project instead of starting a new session each time: it answers from the project's state and from a project brief it keeps up to date, and it says which focused work should go to a separate session or workflow run.

## What exists now

- **One per project.** The coordinator is a chat session with `kind: "coordinator"`, saved in `.baked/sessions/ID/` like other sessions. `POST /v1/coordinator` creates it the first time; later calls return the same session. Ordinary session lists (`GET /v1/sessions`, `baked session list`, the terminal session picker) leave it out.
- **Read-only.** It always runs in architect mode: it can read files, search and use code intelligence, but it does not edit files or run commands. It can list and read [artifacts](artifacts.md); saving and deploying them need a chat outside architect or plan mode.
- **Project brief.** A short structured note with four sections: decisions, conventions, launched work (kind, id, why, status and an optional task) and open questions. It is stored in `brief.json` next to the session, put into the system prompt of every coordinator turn, and capped at 8000 characters. The coordinator edits it with its `coordinator_brief` tool; you can edit it through `PUT /v1/coordinator/brief`, which refuses an edit made against an older revision so neither side overwrites the other unseen.
- **Project state.** The `project_state` tool answers from the same services as `baked serve`, as short summaries rather than event logs: `overview` (what waits for a person, active runs, open initiatives, sessions with a turn running), `runs`, `run` (stages, tasks, pending requests, changed files), `initiatives`, `initiative` (features, blockers, pending decisions), `sessions`, `session` (its last messages) and `attention`. Ordinary sessions do not get this tool.
- **Launching work.** `launch_session` starts a background chat session with a brief. It runs on its own in the server, shows in the session list, and its prompts reach the attention list like any session's. A session in `architect` mode starts at once. `default` or `auto` mode can edit files, so the coordinator first asks you with an approval prompt in its own chat. `start_run` and `start_initiative` use the same start paths as `POST /v1/workflow/runs` and `POST /v1/initiatives`, so a run stops at its own approval request with its estimate, and an initiative waits for your approval of its split. The coordinator has no tool that answers approvals.
- **Threads.** A session the coordinator launches records the coordinator as its `parentId`. It is one of the coordinator's threads: the desktop app lists it under Coordinator in the sidebar instead of under Chat, its header leads back to the coordinator, and the terminal session picker marks it `↳ coordinator:`. In the coordinator's conversation the `launch_session` call is drawn as a live thread card that follows the session's own event stream: its state, the tool it is in, its plan with step marks, its latest answer and tokens, and Open. The terminal UI's launched list adds the tool a working session is in.
- **Talking to a launched session.** `message_session` sends a session the coordinator launched a follow-up, a correction or an answer. The session sees it as a user message that starts with "Message from the project coordinator:" (the desktop app shows it as a bubble marked From the coordinator); it is steered into a running turn or starts the next one. A session the coordinator did not launch is refused.
- **Threads talk back.** A thread gets a `send_message` tool and a note naming its coordinator and its sibling threads. `to: "coordinator"` writes to the coordinator, a sibling's session id writes to that thread; anything else is refused, and a turn sends at most 5 messages. The message arrives as a user message that starts with `Message from session "TITLE" (ID):`, steered into a running turn or starting the next one, so a coordinator turn starts when a thread reports. The recipient is told such messages come from a session, not the person, and cannot approve anything; the desktop app marks them From "TITLE" and the terminal UI labels them `from`. Ordinary chats get no such tool.
- **Splitting a request.** For a large request the coordinator calls `propose_split` with flows. Each flow has an id, a title, a boundary (scope and the paths it writes), a contract and `dependsOn`, the shape of an initiative's features, and is checked the same way (slug ids, known dependencies, no cycles, at most 12). The chat shows the split as one card (prompt kind `split`) and the coordinator's turn waits for your answer.
  - When no flow depends on another, each flow becomes its own workflow run in its own worktree and branch, and they execute in parallel up to [`workflows.maxParallelRuns`](workflows/runtime.md#parallel-runs). Such flows must name boundary paths, and two flows whose paths may overlap are refused: merge them or make one depend on the other.
  - When any flow depends on another, the whole split becomes one initiative of 3 to 12 features, started with the split as its plan. Your approval of the card also approves the initiative's split, so you are asked once. The initiative runs the features in dependency order.
  - The card carries a digest of the split; approving it with `POST /v1/sessions/ID/prompts/PROMPT_ID` takes `{approve: true, digest}`, and a digest that does not match is refused (`STALE_PROMPT`). Rejecting it (`{approve: false}`) launches nothing; tell the coordinator what to change and it proposes a new card.
  - **Tasks.** Every flow belongs to a task, shown on the card next to the flow. A flow can name the GitHub issue it does (`issue`: an issue URL, `owner/name#N` or `#N`), which must be open. When it names none, approving the split creates an issue in the origin repository. The new issue holds the flow's scope, boundary paths, contract and the split's completion criteria, and becomes a sub-issue of the split's `parentIssue` when one is given. Approving the card covers these issues; there is no second prompt. Creating issues needs a token in [`workflows.delivery.tokenEnv`](workflows/runtime.md#delivery) (`GITHUB_TOKEN` by default) and an origin remote on the configured GitHub host. Without them the card shows `local task`, nothing is sent to GitHub, and the brief records the flow as `local:SPLIT/FLOW`. A linked public issue is read without a token.
  - In runs mode each flow's run starts from its issue, as [`baked workflow run --issue`](workflows/runtime.md#starting-from-a-github-issue) does: the run is named `issue-N-TITLE`, the flow's scope and contract are added to the issue's text, and the delivery pull request says `Closes #N`. In initiative mode each feature keeps its flow's issue beside the approved split (the plan and its digest stay as the coordinator proposed them): the feature's runs start from it, so their delivery pull request says `Closes #N`, and the initiative's feature list shows the issue.
  - When you name issues yourself ("run #120 and #121 in parallel"), the coordinator proposes a split whose flows name them; one issue goes straight to `start_run`, which also takes `issue`.
  - The brief records the decision with the first 12 characters of the digest, and one `launched` entry per run or initiative, which the coordinator then follows like any launch. The launch limits below count every flow of a split in runs mode, and a split that would pass them is refused before the card is shown.
- **Following it.** Every launch is added to the brief's launched work with its id, why and task (the issue `owner/name#N` with its URL and state, or a local task). The server checks launched items every two seconds and updates their status in the brief. Each launch records the item's title (a session's title, a run's or initiative's request, a flow's title), and an item is listed once: when the model records an item a launch tool already recorded, the existing entry keeps its status and only gains a missing title or task. When an item finishes, fails, is cancelled or waits for a person, a note such as `Run "Add usage export" (owner/name#12): waiting: approval` is added to the coordinator's chat as a `notice` event. The note's message carries a `launch` object (kind, id, feature, title, status, why, task and `event`: `status` or `task-closed`), which the desktop app and the terminal UI draw as a launch card instead of the text. When a launched session's turn ends with a new answer, the note also carries that answer as `result` (up to 2000 characters), even when the session was already `done` at the previous check; the entry's `answers` counts the answers reported so far. The model does not see these notes as messages; it reads the updated status in the brief on its next turn. An initiative started from a split gets one launched entry for the initiative and one per feature with an issue (`feature` names it); a feature entry's status follows the feature, and an accepted feature reads `completed`. Once a run or feature whose task is an open issue has completed, the server also reads the issue: when its pull request has merged and GitHub closed it, the note "Task owner/name#N closed: the pull request of Run "TITLE" merged" is added and the task is marked closed.
- **Stopping and closing.** The coordinator's `stop_launched` tool interrupts a launched session's running turn, cancels a run (through the same path as `POST /v1/workflow/runs/ID/cancel`; a cancelled run cannot resume) or pauses an initiative and its running feature runs (an initiative has no cancel; stopping a feature pauses its whole initiative). Before it cancels a run or pauses an initiative it asks you with an approval prompt in its chat. `close_launched` marks an entry closed once the item is finished, stopped or paused; an active item must be stopped first. Closing an initiative closes its feature entries too. A closed entry stays in the brief (shown as `[closed]`), but the server no longer follows it, adds no notes for it, and it does not count toward the limits below. A closed session is archived: ordinary session lists (`GET /v1/sessions`, `baked session list`, the terminal session picker) leave it out, and it still opens from the coordinator by its id. Reopening an entry (`POST /v1/coordinator/launched/close` with `reopen: true`, or Reopen in the desktop app) clears the mark and brings the session back to the lists. You can stop and close items yourself from the desktop app and the terminal UI ([below](#terminal-ui)) without asking the coordinator.
- **What's happening.** One action asks the coordinator for a digest: it starts a short turn, shown in the conversation as "What's happening?", in which the coordinator checks `project_state` and its launched work and answers in four fixed sections: **Running**, **Waits for you**, **Finished since the last summary** (since its previous summary in the conversation) and **Open questions** (from the brief), with "Nothing." under an empty one. It launches nothing in that turn. Asked while a turn runs, the summary is queued as a turn of its own. It is `POST /v1/coordinator/summary`, **What's happening** in the desktop coordinator's header, and `/coordinator summary` or `Ctrl+S` in the terminal UI.
- **Limits.** A launch is refused while `coordinator.maxActive` launched items (3 by default) are still active, or once everything launched has used `coordinator.maxTokens` tokens (20,000,000 by default) ([configuration](configuration.md#common-settings)).
- **Self-compaction.** After a turn that leaves the context fuller than `compaction.triggerThreshold` (0.7 by default, the same setting as the terminal chat), the coordinator compacts its older messages on its own. The brief is not part of the conversation, so compaction and server restarts keep it whole.

## Reaching it

| Surface | How |
| --- | --- |
| Local API | `GET/POST /v1/coordinator`, `GET/PUT /v1/coordinator/brief`, `GET /v1/coordinator/launched`, `POST /v1/coordinator/summary`, `POST /v1/coordinator/launched/stop` and `/close`, then the usual `/v1/sessions/ID/...` endpoints ([contract](desktop/api.md#project-coordinator)) |
| Headless CLI | `baked session coordinator [--json]` prints the session id and the brief |
| Desktop app | the Coordinator section of each project with What's happening in its header (Stop, Pause and Close on launch cards and in the launched list, Reopen under its closed items), and Hand to coordinator in the chat menu ([desktop app](desktop/app.md#screens)) |
| Terminal UI | `/coordinator` and `/coordinator summary` ([below](#terminal-ui)) |

## Terminal UI

`/coordinator` (in the command palette) opens the coordinator over the current tab. The terminal UI hosts it in its own process, so it needs no `baked serve`; it is the same session, brief and launch tools as the server's coordinator.

- **Conversation.** The view shows what the coordinator launched (its title, or kind and short id, then status, tokens, task and why; a wait is yellow and a failure red), then the tail of the conversation and the text the running turn streams. A launch note reads as a marked line (`◆`, or `✓` for a closed task) with its why under it. Type a message and press `Enter` to send it; a message sent while a turn runs is queued.
- **Prompts.** A split card lists its flows with their tasks, paths and dependencies. `Ctrl+Y` approves it, `Ctrl+N` rejects it, and `Ctrl+E` rejects it and starts a "Change the split: " message. Approval prompts (`launch_session` in an editing mode) take `Ctrl+Y` to allow and `Ctrl+N` to deny. A question takes an option's number or text and `Enter`.
- **Stopping and closing.** The launched list shows open items; closed ones are counted under it. `Tab` (`Shift+Tab` back) selects an item, marked `›`. `Ctrl+X` stops the selected item while it is active: a session's turn stops at once, and a run or initiative asks for a second `Ctrl+X` before it is cancelled or paused. `Ctrl+R` closes a finished, stopped or paused item. The footer shows which of the two the selected item takes.
- **What's happening.** `Ctrl+S`, while no turn runs and no prompt waits, asks for the [digest](#what-exists-now). `/coordinator summary` opens the view and asks for it at once.
- **Launching.** Runs start through the terminal UI's workflow worker, as `/workflow run` does, with the model of the current tab and owner `Coordinator`; the run shows in `/workflow` like any other. Project state is read from `.baked/workflows.sqlite` without writing to it.
- **Leaving.** `Esc` stops a running turn; when nothing runs it closes the view. The coordinator keeps following launched work while the terminal UI runs and stops when it exits.

The terminal UI and a running `baked serve` can host the coordinator of the same project at once. Both follow the same brief, which refuses an edit made against an older revision, but each answers only the prompts of its own turns.
