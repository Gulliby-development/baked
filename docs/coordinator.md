# Project coordinator

The project coordinator is one long-lived chat per project. You come back to it for the whole project instead of starting a new session each time: it answers from the project's state and from a project brief it keeps up to date, and it says which focused work should go to a separate session or workflow run.

## What exists now

- **One per project.** The coordinator is a chat session with `kind: "coordinator"`, saved in `.baked/sessions/ID/` like other sessions. `POST /v1/coordinator` creates it the first time; later calls return the same session. Ordinary session lists (`GET /v1/sessions`, `baked session list`, the terminal session picker) leave it out.
- **Reads everything, changes nothing.** It always runs in architect mode, so it reads the whole project but does not edit files or run commands: files, memory and skills; the code graph (`bake_find`, `bake_grep`, `bake_analyze`, `bake_impact`); git through the read actions of the `git` tool (status, diff, log, show, blame, branch list, stash list and show, with no flag that writes a file or runs a program such as `--output` or `--ext-diff`); [artifacts](artifacts.md) through `artifact` list and read; and runs, initiatives, sessions, what waits for a person and token usage through `project_state`. Committing, saving or deploying an artifact and any other change are refused in this mode; such work goes to what the coordinator launches, which asks you first. Every architect and plan mode chat gets the same read actions.
- **Largest context window.** When its model offers several windows (Claude Code `opus` or `sonnet`), the coordinator always runs with the largest one (1M). It has no context size setting: the terminal, the desktop app and the API offer none for it, and `PATCH /v1/sessions/ID` refuses another size ([context size per chat](providers.md#context-size-per-chat)).
- **Project brief.** A short structured note with four sections: decisions, conventions, launched work (kind, id, why, status and an optional task) and open questions. It is stored in `brief.json` next to the session, put into the system prompt of every coordinator turn, and capped at 8000 characters. The coordinator edits it with its `coordinator_brief` tool; you can edit it through `PUT /v1/coordinator/brief`, which refuses an edit made against an older revision so neither side overwrites the other unseen.
- **Project state.** The `project_state` tool answers from the same services as `baked serve`, as short summaries rather than event logs: `overview` (what waits for a person, active runs, open initiatives, sessions with a turn running), `runs`, `run` (stages, tasks, pending requests, changed files), `initiatives`, `initiative` (features, blockers, pending decisions), `sessions`, `session` (its last messages, then under Waiting for an answer each prompt it waits on: a question with its options, a plan to review or a permission), `attention` and `usage` (tokens and estimated cost of workflow runs by model and stage over the last `days` days, 7 by default, the same figures as `GET /v1/usage`). Ordinary sessions do not get this tool.
- **Launching work.** `launch_session` starts a background chat session with a brief. It runs on its own in the server, shows in the session list, and its prompts reach the attention list like any session's. A session in `architect` mode starts at once. `default` or `auto` mode can edit files, so the coordinator first asks you with an approval prompt in its own chat. `start_run` and `start_initiative` use the same start paths as `POST /v1/workflow/runs` and `POST /v1/initiatives`, so a run stops at its own approval request with its estimate, and an initiative waits for your approval of its split. `start_run` asks you first, on a workflow card ([below](#workflows)). The coordinator's model answers a run's approval only through `control_run` after your yes ([below](#workflows)); the [approval rules](#approval-rules) you turn on answer some routine approvals on their own.
- **Own worktrees for editing sessions.** A `default`- or `auto`-mode session that `launch_session` starts works in its own Git worktree, `.baked/session-worktrees/ID` (the first block of the session id), on the branch `baked/session/ID` checked out from HEAD. Two such sessions, or a session and you, therefore never overwrite each other's files. The tool's result names the path and branch, and the launched list and launch cards show the branch in the terminal UI and the desktop app. The model can pass `worktree: false` to have a session edit the shared project folder. When the project folder is not the root of a Git repository with at least one commit, the session works in the shared folder and the tool's result says why. An `architect` session only reads and keeps the project folder. The worktree and its branch stay after the session ends: commit, merge or remove them with Git (`git worktree remove`).
- **Threads.** A session the coordinator launches records the coordinator as its `parentId`. It is one of the coordinator's threads: the desktop app lists it under Coordinator in the sidebar instead of under Chat, its header leads back to the coordinator, and the terminal session picker marks it `↳ coordinator:`. In the coordinator's conversation the `launch_session` call is drawn as a live thread card that follows the session's own event stream: its state, the tool it is in, its plan with step marks, its latest answer and tokens, and Open. The terminal UI's launched list adds the tool a working session is in.
- **Talking to a launched session.** `message_session` sends a session the coordinator launched a follow-up, a correction or an answer. The session sees it as a user message that starts with "Message from the project coordinator:" (the desktop app shows it as a bubble marked From the coordinator); it is steered into a running turn or starts the next one. A session the coordinator did not launch is refused.
- **Answering a session's question.** A question a session asks in the middle of a turn is a prompt, not a message, so its history alone does not show it. The launch note of a session that waits for you carries what it asks (`asks`: the question and its options, or the plan or permission it waits on), the coordinator's wake-up includes it as "It asks: ...", and `project_state` `session` lists it. The coordinator quotes the question to you; when you answer in the coordinator's chat, its `answer_session` tool passes your answer on (an option's label is sent as that option's value). It asks you with an approval prompt first unless the coordinator has `permissions: "full"`. Only questions are answered this way: a permission or a plan review of a session stays in that session, and a session the coordinator did not launch is refused.
- **Workflows.** See [Workflows](#workflows): the coordinator lists the project's workflows, suggests one for complex work, runs it after your yes, follows it stage by stage and takes control back when it finishes.
- **Threads talk back.** A thread gets a `send_message` tool and a note naming its coordinator and its sibling threads. `to: "coordinator"` writes to the coordinator, a sibling's session id writes to that thread; anything else is refused, and a turn sends at most 5 messages. The message arrives as a user message that starts with `Message from session "TITLE" (ID):`, steered into a running turn or starting the next one, so a coordinator turn starts when a thread reports. The recipient is told such messages come from a session, not the person, and cannot approve anything; the desktop app marks them From "TITLE" and the terminal UI labels them `from`. Ordinary chats get no such tool.
- **Splitting a request.** For one big idea the coordinator makes an [initiative](workflows/runtime.md#initiatives): it calls `propose_split` with flows when it can see the features, or `start_initiative` when BAKED's decomposer should find them. Each flow has an id, a title, a boundary (scope and the paths it writes), a contract and `dependsOn`, the shape of an initiative's features, and optionally the `workflow` it runs and its `size`; it is checked the same way (slug ids, known dependencies, no cycles, at most 12). The chat shows the split as one card (prompt kind `split`, each flow with its workflow) and the coordinator's turn waits for your answer. A message that starts with "Plan this as an initiative:" comes from the desktop Initiatives screen, and the coordinator plans that idea as an initiative.
  - Three to twelve flows become one initiative, started with the split as its plan. Your approval of the card also approves the initiative's split, so you are asked once. The initiative runs the features in dependency order; its feature runs execute in worktrees, so independent features run side by side up to [`workflows.maxParallelRuns`](workflows/runtime.md#parallel-runs). Each feature runs the flow's workflow, or the one that fits it when the flow names none ([feature workflows](workflows/runtime.md#initiatives)).
  - Two flows that do not depend on each other become two workflow runs, each in its own worktree and branch, running in parallel. They must name boundary paths, and two flows whose paths may overlap are refused: merge them or make one depend on the other. Two flows where one depends on the other are refused: merge them into one run or add flows.
  - The card carries a digest of the split; approving it with `POST /v1/sessions/ID/prompts/PROMPT_ID` takes `{approve: true, digest}`, and a digest that does not match is refused (`STALE_PROMPT`). Rejecting it (`{approve: false}`) launches nothing; tell the coordinator what to change and it proposes a new card.
  - **Tasks.** Every flow belongs to a task, shown on the card next to the flow. A flow can name the GitHub issue it does (`issue`: an issue URL, `owner/name#N` or `#N`), which must be open. When it names none, approving the split creates an issue in the origin repository. The new issue holds the flow's scope, boundary paths, contract and the split's completion criteria, and becomes a sub-issue of the split's `parentIssue` when one is given. Approving the card covers these issues; there is no second prompt. Creating issues needs a token in [`workflows.delivery.tokenEnv`](workflows/runtime.md#delivery) (`GITHUB_TOKEN` by default) and an origin remote on the configured GitHub host. Without them the card shows `local task`, nothing is sent to GitHub, and the brief records the flow as `local:SPLIT/FLOW`. A linked public issue is read without a token.
  - In runs mode each flow's run starts from its issue, as [`baked workflow run --issue`](workflows/runtime.md#starting-from-a-github-issue) does: the run is named `issue-N-TITLE`, the flow's scope and contract are added to the issue's text, and the delivery pull request says `Closes #N`. In initiative mode each feature keeps its flow's issue beside the approved split: the feature's runs start from it, so their delivery pull request says `Closes #N`, and the initiative's feature list shows the issue.
  - When you name issues yourself ("run #120 and #121 in parallel"), the coordinator proposes a split whose flows name them; one issue goes straight to `start_run`, which also takes `issue`.
  - The brief records the decision with the first 12 characters of the digest, and one `launched` entry per run or initiative, which the coordinator then follows like any launch. The launch limits below count every flow of a split in runs mode, and a split that would pass them is refused before the card is shown.
- **Parallel chats.** You can always work without a workflow, through several chats at once. `propose_chats` takes a title, a why and 2 to 12 chats, each with an id, a title, a brief (its first message), a mode (`architect` only reads; `default` and `auto` edit files) and optionally the paths it writes. The chat shows them as one card (prompt kind `split` with `mode: "chats"`; each flow's `task` reads `chat, reads only` or `chat, edits files`), answered like a split card with `{approve: true, digest}`. Approving it starts every chat as a launched session, so it also covers the approval an editing session would otherwise ask for: an editing chat works in its own worktree and branch like any editing session the coordinator launches. Two editing chats whose paths may overlap are refused before the card is shown; merge them or narrow their paths. The chats are followed like any launched session and count toward the limits below one by one. Rejecting the card starts nothing and records an open question in the brief.
- **Following it.** Every launch is added to the brief's launched work with its id, why, task (the issue `owner/name#N` with its URL and state, or a local task) and, for a run, its workflow. The server checks launched items every two seconds and updates their status in the brief. Each launch records the item's title (a session's title, a run's or initiative's request, a flow's title), and an item is listed once: when the model records an item a launch tool already recorded, the existing entry keeps its status and only gains a missing title or task. When an item finishes, fails, is cancelled or waits for a person, a note such as `Run "Add usage export" (owner/name#12): waiting: approval` is added to the coordinator's chat as a `notice` event. The note's message carries a `launch` object (kind, id, feature, title, status, why, task and `event`: `status` or `task-closed`), which the desktop app and the terminal UI draw as a launch card instead of the text. When a launched session's turn ends with a new answer, the note also carries that answer as `result` (up to 2000 characters), and a session that waits for you carries what it asks as `asks`, even when the session was already `done` at the previous check; the entry's `answers` counts the answers reported so far. The same news wakes the coordinator ([taking control back](#taking-control-back)), and a session's answer is part of the wake-up. An initiative started from a split gets one launched entry for the initiative and one per feature with an issue (`feature` names it); a feature entry's status follows the feature, and an accepted feature reads `completed`. Once a run or feature whose task is an open issue has completed, the server also reads the issue: when its pull request has merged and GitHub closed it, the note "Task owner/name#N closed: the pull request of Run "TITLE" merged" is added and the task is marked closed.
- **Stopping and closing.** The coordinator's `stop_launched` tool interrupts a launched session's running turn, cancels a run (through the same path as `POST /v1/workflow/runs/ID/cancel`; a cancelled run cannot resume) or pauses an initiative and its running feature runs (an initiative has no cancel; stopping a feature pauses its whole initiative). Before it cancels a run or pauses an initiative it asks you with an approval prompt in its chat. `close_launched` marks an entry closed once the item is finished, stopped or paused; an active item must be stopped first. Closing an initiative closes its feature entries too. A closed entry stays in the brief (shown as `[closed]`), but the server no longer follows it, adds no notes for it, and it does not count toward the limits below. A closed session is archived: ordinary session lists (`GET /v1/sessions`, `baked session list`, the terminal session picker) leave it out, and it still opens from the coordinator by its id. Reopening an entry (`POST /v1/coordinator/launched/close` with `reopen: true`, or Reopen in the desktop app) clears the mark and brings the session back to the lists. You can stop and close items yourself from the desktop app, the terminal UI ([below](#terminal-ui)) and `baked session coordinator stop` and `close` without asking the coordinator.
- **Schedules.** A schedule is a prompt that starts a coordinator turn on its own, such as a nightly CI check or a morning summary. There are none until you add one: in the desktop app's Coordinator section, with `baked session coordinator schedule add`, through `POST /v1/coordinator/schedules`, or by asking the coordinator, whose `coordinator_schedule` tool asks you to confirm each new schedule with an approval prompt. Its time (`when`) is `every 30m`, `every 6h` or `every 1d` (any number of minutes, hours or days), a five-field cron expression in local time such as `0 9 * * 1-5`, or `@hourly`, `@daily`, `@weekly`, `@monthly`; a schedule fires at most every 5 minutes, and a project has at most 20. Schedules are stored in `schedules.json` next to the brief and fire only while a host of the coordinator runs: `baked serve` (the desktop app) or the terminal UI once `/coordinator` was opened. The host checks every 30 seconds; a schedule whose time passed while nothing ran fires once when a host starts, then goes on from that moment. When it fires, the coordinator gets a turn whose message shows in the chat as "Scheduled: NAME"; the model reads the schedule's prompt with a note that no person sent it. A turn that is already running keeps going and the scheduled one waits behind it. Pausing a schedule keeps it without firing; resuming goes on from now without catching up. When `baked serve` and the terminal UI host the same coordinator, a lock file lets only one of them claim each firing. Every coordinator turn lists the schedules in its system prompt.
- **What's happening.** One action asks the coordinator for a digest: it starts a short turn, shown in the conversation as "What's happening?", in which the coordinator checks `project_state` and its launched work and answers in four fixed sections: **Running**, **Waits for you**, **Finished since the last summary** (since its previous summary in the conversation) and **Open questions** (from the brief), with "Nothing." under an empty one. It launches nothing in that turn. Asked while a turn runs, the summary is queued as a turn of its own. It is `POST /v1/coordinator/summary`, **What's happening** in the desktop coordinator's header, and `/coordinator summary` or `Ctrl+S` in the terminal UI.
- **Approval rules.** Off by default; see [below](#approval-rules).
- **Limits.** A launch, or every chat of a parallel chats card, is refused while `coordinator.maxActive` launched items (3 by default) are still active, or once everything launched has used `coordinator.maxTokens` tokens (20,000,000 by default) ([configuration](configuration.md#common-settings)).
- **Self-compaction.** After a turn that leaves the context fuller than `compaction.triggerThreshold` (0.7 by default, the same setting as the terminal chat), the coordinator compacts its older messages on its own. The brief is not part of the conversation, so compaction and server restarts keep it whole.

## Workflows

Workflows are how a project customizes work, so the coordinator knows them and prefers them to a background session for work that changes code.

- **Knowing them.** `list_workflows` lists every workflow the project can run: the built-in ones and the project's `baked/workflows/*.json`, each with its description, its stages in order, whether it writes files and the problems that keep it from starting. Given the request, it first gives BAKED's assessment of it, such as `Assessment: ci-fix request, size medium, risk medium (signals: tests, failing).`: its kind, its size (small for a docs or small change, large for a large change or a request that lists four parts or more, otherwise medium), its risk (low when it only reads or reviews, high when it names data, schemas, security, secrets, payments, releases, deploys or deletion, otherwise medium) and, when the request lists two parts or more, that they may run side by side. Then it names the workflow BAKED proposes for it and why, with the same rules as [`--auto-preset`](workflows/runtime.md) (a failing check gets `fix-ci`, research gets `spike`, a small change `quick`, otherwise the project default).
- **Suggesting one.** When you describe work in the coordinator's chat that is more than a quick answer (it changes several files, needs research and a plan, fixes a failing check), the coordinator evaluates it first: it calls `list_workflows` with the request, corrects the assessment from what it knows of the code, says in one line what the task is (for example "a medium, low-risk UI change") and which workflow fits and why, and calls `start_run`. Without a named workflow it uses the proposed one; a workflow that does not exist or cannot start is refused with the list of those that can.
- **Run workflow?** `start_run` shows a card (prompt kind `workflow`) with the workflow, its stages, whether it changes files, the request, the issue it starts from, why the coordinator wants it and why this workflow. Nothing starts until you approve it: **Run workflow** starts the run, **Not now** starts nothing and the coordinator carries on in the chat. The card carries a digest of the workflow, request and issue; approving takes `{approve: true, digest}`. The run's own approvals (its plan, its estimate) still come to you.
- **Following it live.** The run shows in Launched work with its workflow, a progress bar, its stages (done, running, waiting, failed or ahead) and its tasks. Changes reach the desktop panel and the terminal view as `launched` events of the coordinator session, so they show as they happen.
- **Controlling it.** When a run waits for an approval, the coordinator asks you whether to approve it. Only after you say yes in the chat does it call `control_run`, which shows one more approval prompt in its chat and then approves the request (the run goes on in the background), rejects it with a reason, or cancels the run. It works only on runs the coordinator launched; questions, reviews and deliveries are answered in the run itself.

### Working without a workflow

Workflows are the default for work that changes code, but you can always say no. When you decline the workflow card or ask for chats, the coordinator assesses whether the task splits into parts that can run side by side (parts that write different files, or only read). If it does, it says in a line how it would split it and proposes [parallel chats](#what-exists-now), for example five chats for five independent screens; you approve them on one card and they all start. If it does not, it launches one session with the whole brief. It follows the chats like runs: it relays what each one finished or asks, and when all are done it tells you the combined result and what is left, such as merging their branches.

### Work style

The work style says how the coordinator proposes work, so it does not ask you every time. Set it in the desktop app under Settings > Coordinator, with `/coordinator style` in the terminal UI, as `coordinator.workStyle` in the global or project config, or through `PATCH /v1/settings`. It applies from the next coordinator turn.

| Style | What the coordinator does |
| --- | --- |
| Workflows only (`workflows-only`) | Always proposes a workflow run. `propose_chats` is refused; when you decline a workflow card it asks what to change in the run. |
| Mostly workflows (`prefer-workflows`) | Goes straight to the workflow card and offers chats only when you ask for them. |
| Not set (`ask`, the default) | Offers a workflow and, when you decline it, parallel chats, as described above. |
| Mostly chats (`prefer-chats`) | Skips the workflow card: parallel chats when the task splits, otherwise one chat. A workflow only when you ask for one. |
| Chats only (`chats-only`) | Always works through chats. `start_run`, `start_initiative` and `propose_split` are refused. |

The style changes only how work is proposed: the cards that start work, and the approvals of what runs, still come to you.

### Taking control back

When something the coordinator launched finishes, fails, is cancelled or waits for a person, the coordinator gets a turn of its own with the news. The chat shows the notices, not that message. The coordinator tells you in a line or two what happened (it reads the run with `project_state` when it needs the result) and continues: it starts the next step of the work, proposes what is left, or says the work is done. A request the run waits for stays your decision. The wake-up waits behind a running turn and is dropped when that turn is stopped. Set `coordinator.wake` to `false` ([configuration](configuration.md#common-settings)) to keep the notices without the turns.

## Approval rules

Approval rules let the coordinator answer the routine approvals of what it launched, so a thread or a run does not stop for something you always allow. They are off by default, and only you change them: the coordinator's model can neither read nor edit them. The server (or the terminal UI that hosts the coordinator) applies them in code at each two-second check, before it reports a wait, so a matching approval never reads as waiting for you.

| Rule | Answers | Settings |
| --- | --- | --- |
| `web-search` | a launched session's web search | none |
| `fetch-page` | fetching an `https` page from one of the hosts or their subdomains (no port, no user info) | `hosts` |
| `plan-review` | executing a plan made in plan mode with at most `maxSteps` steps | `maxSteps` (1 to 50) |
| `run-approval` | a launched run's plan approval when its token budget is at most `maxTokens` and, with `paths`, every file it writes matches one of the globs | `maxTokens`, `paths?` |

Some approvals always wait for you, whatever the rules say:

- destructive commands, paths outside the project, questions and split cards;
- plans that mention secrets, credentials, API keys, `.env`, deploying, publishing, releases, production or force pushes;
- run plans that delete a file, write a file that always needs a person in [auto-approval](workflows/runtime.md) (secrets and keys, `.env`, CI and hook configuration, `.baked/` and `specs/`, manifests and lockfiles, `AGENTS.md`), write files with your uncommitted changes, defer post-release criteria, or approve tests written first;
- the approvals of initiatives and their features, and of work the coordinator did not launch.

Each answer is logged (the latest 100) with the rule as it read, and noted twice: in the coordinator's chat as a launch card with `event: "auto-answered"` (the desktop app draws a shield card "approved by rule", the terminal UI a `✓ Approved … by your rule: …` line), and, for a session, in that session's own transcript ("The project coordinator approved … by the rule: …"). A run approved by a rule continues as after your own approve. A run approval that fails (for example because the plan changed) is not tried again; it waits for you.

The rules live in `.baked/sessions/ID/approval-rules.json` next to the brief and are saved by revision, like the brief.

| Surface | How |
| --- | --- |
| Desktop app | Approval rules in the coordinator's right panel: a switch, the rules as cards with Remove, Add a rule (Web searches, Pages, Small plans, Run plans), what always waits for you, and the latest answers |
| Terminal UI | `/coordinator rules` shows them; `/coordinator rules on`, `off`, `add web-search`, `add pages HOST...`, `add plans N`, `add runs TOKENS [GLOB...]` (`2M`, `500k`) and `remove ID` change them. The coordinator view's heading says how many rules are on |
| Headless CLI | `baked session coordinator rules` with the same words |
| Local API | `GET /v1/coordinator/approval-rules`, `PUT` with `{enabled, rules, expectedRevision}` ([contract](desktop/api.md#project-coordinator)) |

## Terminal UI

`/coordinator` (first in the command palette) opens the coordinator over the current tab. A project you switch to with `/projects` or `/project waiting` opens on its coordinator unless you picked a session to resume, and `baked --coordinator` opens it at start. The terminal UI hosts it in its own process, so it needs no `baked serve`; it is the same session, brief and launch tools as the server's coordinator.

- **Conversation.** The view lists the schedules (name, time and when each fires next, or paused), shows what the coordinator launched (its title, or kind and short id, its workflow, then status, tokens, task and why; a wait is yellow and a failure red; under a run its stages: `✓` done, `▸` running, `◆` waiting, `✗` failed, `·` ahead, with its tasks), then the tail of the conversation and the text the running turn streams. A launch note reads as a marked line (`◆`, or `✓` for a closed task or an approval answered by a rule) with its why, or the rule, under it, and for a session that waits for you, what it asks on a `?` line. Type a message and press `Enter` to send it; a message sent while a turn runs is queued.
- **Prompts.** A split card lists its flows with their tasks, paths and dependencies; a parallel chats card reads `(parallel chats)` and lists each chat with what it may do. `Ctrl+Y` approves it, `Ctrl+N` rejects it, and `Ctrl+E` rejects it and starts a "Change the split: " message. A workflow card shows the workflow, its stages, the request and why; `Ctrl+Y` runs it and `Ctrl+N` declines. Approval prompts (`launch_session` in an editing mode) take `Ctrl+Y` to allow and `Ctrl+N` to deny. A question takes an option's number or text and `Enter`.
- **Stopping and closing.** The launched list shows open items; closed ones are counted under it. `Tab` (`Shift+Tab` back) selects an item, marked `›`. `Ctrl+X` stops the selected item while it is active: a session's turn stops at once, and a run or initiative asks for a second `Ctrl+X` before it is cancelled or paused. `Ctrl+R` closes a finished, stopped or paused item. The footer shows which of the two the selected item takes.
- **What's happening.** `Ctrl+S`, while no turn runs and no prompt waits, asks for the [digest](#what-exists-now). `/coordinator summary` opens the view and asks for it at once.
- **Launching.** Runs start through the terminal UI's workflow worker, as `/workflow run` does, with the model of the current tab and owner `Coordinator`; the run shows in `/workflow` like any other. Project state is read from `.baked/workflows.sqlite` without writing to it.
- **Leaving.** `Esc` stops a running turn; when nothing runs it closes the view. The coordinator keeps following launched work and firing its schedules while the terminal UI runs, and stops when it exits.

The terminal UI and a running `baked serve` can host the coordinator of the same project at once. Both follow the same brief, which refuses an edit made against an older revision, but each answers only the prompts of its own turns.

## Headless CLI

`baked session coordinator send TEXT` runs one coordinator turn in the CLI process and prints the reply as it streams; tool calls, prompts and launch notes go to stderr. It opens the project's coordinator the first time, with `--model MODEL` or `defaultModel`. The turn's prompts never leave it hanging:

- `--yes` approves every approval, split card and [workflow card](#workflows) (a split or workflow card with its digest).
- Otherwise an interactive terminal asks for each one (`y` allows; a question takes an option's number or text). A workflow card reads `Run the workflow NAME (STAGES): WHY` with the request under it.
- Without a terminal an approval is denied and a question is skipped, or takes its first option when it cannot be skipped.

The CLI hosts the coordinator the way the terminal UI does, so the sessions and runs it launches run in this process. `send` therefore keeps following them after the reply and prints each launch note until none is active, then lists them. While it follows, each time a launched run moves it prints the run's stage track to stderr, as `Run "TITLE": ✓ reproduce  ▸ tasks  · check  (tasks 1/2)` (`✓` completed, `▸` running, `◆` waiting, `✗` failed, `–` skipped, `·` not started). `Ctrl+C` stops the running turn. With `--no-follow` it returns after the reply: a run it started resumes later with `baked workflow resume`, and a launched session's turn stops when the process exits. `--json` prints `{sessionId, reply, launched, error?}` at the end instead. A failed turn exits 1.

`baked session coordinator launched [--json]` lists what the coordinator launched with a run's workflow and its stage track on the line under it, its live status, the tool a session is in and its tokens (`●` active, `○` not), and counts closed items. It starts nothing; `--json` prints `{sessionId, launched}` as `GET /v1/coordinator/launched` does.
