# Bench loop

The objective of the loop is to make BAKED a better harness. The apps, updates and published repositories are the test bench, not the product: when budget, time or attention is short, the loop spends it on analysis and BAKED fixes rather than on getting more apps through, chases quality first and reports cost as a measurement, never hand-fixes an app or works around a BAKED defect to make a run pass (a stuck run is recorded as blocked and becomes a finding), and judges a round by BAKED-side metrics (interventions per run, stop reasons, tokens per verified app, runs completed without intervention, and whether last round's fixes worked) before app counts.

The bench loop tunes BAKED by building small, useful apps with it, round after round, on a real machine with real providers. Its operating spec is an `AGENTS.md` for an orchestrator agent and its roles, in [`bench/loop/`](../bench/loop/AGENTS.md); any agent harness that reads `AGENTS.md` and can run sub-agents can drive it.

## One round

1. **Prepare.** Pin the BAKED runner checkout to `main`, refresh the spec from it, check with `baked lsp status --json` / `baked lsp check` that a language server works for every language the round uses and install missing ones with `baked lsp install <language>` (recorded in `round.json` `lsp`), run `baked doctor`, check every configured provider.
2. **Ideate and review.** An ideator proposes 5 new apps and, for 3 public repositories of `Gulliby-development` picked at random (seeded with the round number; private repositories are never touched), one small feature each after reading the repository (a CI pipeline counts when the repository has none; small hygiene extras such as a missing license, logo, topics or description may ride along). A reviewer keeps 2 new apps, checks each update (useful, small, testable, precise, no duplicate, no breaking change) and writes the exact brief BAKED gets.
3. **Build.** An implementer (up to `round.maxConcurrentRuns` runs at once, 3 from round 7) runs each of the 2 new apps, the 3 updates (a fresh clone of the repository, its baseline tests recorded first, tracked as the separate group `update`) and 3 fixed control apps (url-shortener, md-site, expenses-py) through `baked workflow run` with fixed settings (`--worktree --writers 3`, sizing, `clarification: assume`) and records tokens, steps, time, interventions and corrections.
4. **Verify.** A verifier clones each app, follows only its README, runs its tests and a smoke test, and screenshots UI apps. For an update it runs the repository's whole test suite, the new README example and one error case, and checks that the diff holds only what the brief names.
5. **Analyze and scout.** An analyst turns each run into findings with a point fix and a broader option; a scout reads harness news once per round and keeps a map of task types to workflows. Each finding has a kind (`invariant`: BAKED is wrong whatever the model answered; `recovery`: an ordinary model mistake BAKED did not detect or recover from; `model-behavior`: a habit of one model or provider) and the models it was seen on, plus a fault origin (`host`, `model` or `environment`) and an escaped layer: the cheapest check that should have caught it first (`unit`, `scenario`, `gate-matrix`, `replay`, `shadow`, `fault-matrix`, `mini-suite`, `smoke` or `round`). The retro ranks layers by escapes, and the fix for an escaped finding adds a check at that layer. A `model-behavior` finding is re-run on another vendor's model (`baked workflow fork --from-stage STAGE`, `reroute`, `resume`, so only the failed stage runs again) before it gets an issue; one that does not reproduce, or is seen only once, is watched in the ledger instead of filed. The analyst also gives every `decision.would_stop` record of a stop reason in shadow or advisory mode a verdict (`justified`, `false` or `unknown`) in a would-stops ledger; a reason with records in two rounds in a row and no false verdict gets an issue to promote it to `enforce` in a pull request of its own (see [Stop reasons and shadow mode](workflows/runtime.md#stop-reasons-and-shadow-mode)).
6. **Backlog and fix.** Findings become issues on the project board, together with the sibling places an adversarial sweep review of the fix pull requests merged since the previous round names (run locally through the Claude Code or Codex CLI of the other model family than the fixer's, see CONTRIBUTING.md); a fixer implements up to 6 per round through ordinary pull requests. The backlog role also ranks scout ideas and puts the top one into the fix set as the round's broad feature; only things the owner alone can do or decide are labelled `needs-gulliby`.
7. **Publish.** Apps that pass verification become public MIT repositories in `Gulliby-development` with a README, a one-shot SVG logo and CI on three operating systems. This happens right after an app passes verification, not at round end: the repository is created private, pushed, checked by CI on all three operating systems and only then made public. The default is `publish.mode: "auto"`; `"approve-per-round"` is an optional mode the owner may switch on to approve each round's batch first. gulliby gave standing authorization on 2026-10-11 to create public repositories in Gulliby-development for verified apps without asking; with publish.mode auto no approval is requested. An agent harness with its own permission layer may still block `gh repo create ... --public` or `gh repo edit --visibility public`: then the loop reports it once, does not work around it, and the owner adds an allow rule for the loop's session (the loop never changes permission settings itself). The published repositories are listed with their links in the round report and the round message. An update is not a new repository: the publisher opens a pull request in the existing repository (neutral commit author, no BAKED `specs/` or `.baked/` in the diff), waits for its CI on all three operating systems, merges it with a merge commit and then applies any topics and description the brief lists; if CI is red for logic reasons the PR is closed and recorded as a finding. Updates apply from round 3.
8. **Report.** One round report and one row per run in a metrics ledger. The anonymised usage trace of each app (`bun scripts/bench-trace.ts export`) goes to `tests/fixtures/bench-traces/RNN/` through a pull request, so every later change to a host decision (the forecast, sizing, cost caps or the first-response deadline) replays on the round before it merges (see CONTRIBUTING.md and the [replay-corpus skill](../.agents/skills/replay-corpus/SKILL.md), #1649, #1715). Every run and initiative records its model calls (`--record-model-calls`), and the recording of each run that stopped goes to `tests/fixtures/bench-recordings/RNN/<app>/` in the same pull request, so a later change can be replayed against the model answers that led to the stop. The report's Finding chains table comes from `bun scripts/bench-trace.ts chains` over the round's traces: chain length, battery results and the correctives' cost per chain (#1981).
9. **Retro.** Every third round (`retro.everyRounds`) a retro role measures the loop itself (tokens and hours per confirmed BAKED problem, share of findings that were noise, time to a merged fix, whether fixes moved their metric, how many of the advisory [adversarial sweep review](../CONTRIBUTING.md)'s findings on fix PRs were real and how many missed siblings it named), reads what others publish about evaluating coding agents, judges its earlier changes and reverts those that did not work, and makes at most two new ones. It changes role wording, templates, ledger fields and triage criteria itself through a PR to `bench/loop/` merged after green CI, tries a new loop step for one round as a trial, and only proposes changes to `config.json`, the control apps, the objective and the "never" rules to the owner. Changes are recorded in `ledger/loop-changes.jsonl`.

## Stacks, lanes and difficulty

- **Languages.** The loop built Python and TypeScript (Bun) projects until round 6. From round 7 every round has at least two of Go, .NET, Rust and Java (Maven + JUnit) across its new apps, updates and controls. Workspaces come from `tools/scaffold.py` (`bun`, `webunit`, `python`) and `tools/scaffold_lang.py` (`go`, `dotnet`, `rust`, `java`); brownfield clones from `tools/scaffold_update.py` and `tools/scaffold_update_lang.py`.
- **Checks.** Go: `go vet ./...` (fixer `go fmt ./...`), `go test ./...`. .NET: `dotnet build`, `dotnet format --verify-no-changes`, `dotnet test`. Rust: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`. Java: `mvn -B -q verify`.
- **Toolchains.** Prepare checks `go`, `dotnet`, `cargo` (with `rustfmt` and `clippy`) and `java` with `mvn`; a missing one removes its language from the round and is reported. Shells that the harness starts may lack them on `PATH`, so the launch script and the scaffold scripts add their directories explicitly.
- **Language servers.** BAKED's code intelligence uses a standalone language server per language when one is found (`PATH`, BAKED's `lsp-servers` folder, Mason's `bin`) and falls back to ts-morph, tree-sitter and regex otherwise. Prepare runs `baked lsp status --json` for the languages of the round (`uncovered` lists those without a working server), installs a missing one with `baked lsp install <language>` (non-interactive, exit 1 on failure or a missing toolchain) and confirms with `baked lsp check`; the result goes to `round.json` `lsp`. The loop never installs a server by hand or with a system-wide package manager. When an install fails, it is reported once and the round runs without that server, and the analyst compares behavior with and without it. The commands are described in [headless mode](headless.md#language-servers).

  | Language | Server | Install |
  | --- | --- | --- |
  | Python | `pyright-langserver` | `baked lsp install python` |
  | TypeScript | `typescript-language-server` | `baked lsp install typescript` |
  | Go | `gopls` | `baked lsp install go` |
  | .NET | `csharp-ls` | `baked lsp install csharp` |
  | Rust | `rust-analyzer` | `baked lsp install rust` |
  | Java | `jdtls` | `baked lsp install java` |

  Installing a server needs its toolchain (`go`, `cargo`, `npm`, `pip3`) on `PATH`; the launch script adds the toolchain directories.
- **Lanes.** `round.maxConcurrentRuns` in `config.json` is 3 from round 7 (it was 2). If builds or tests time out because the PC is saturated, the next round goes back to 2.
- **Difficulty.** Quality first (owner's decision of 2026-10-14): the loop runs level 3 until a level-3 round has no errors (every new app of the level built, verified and published, and no new P0 or P1 finding), then level 4, then level 5; a round with errors repeats its level. The caps are in dollars ($12 per run and $40 per round at levels 1-3, $22 and $60 at levels 4 and 5); tokens are reported, not capped. The levels run from 1 (a single-purpose tool, about 6 planned tasks) to 5 (a small service, about 30 tasks, always built as a BAKED initiative with one run per feature); the loop never goes above level 5. The ladder with sizes and expected token costs is in `bench/loop/roles/ideator.md`.
- **Publishing.** CI templates in `bench/loop/templates/ci/`: `bun`, `vite`, `python`, `go`, `dotnet`, `rust`, `java`, all on `ubuntu-latest`, `windows-latest` and `macos-latest`.

- **AI app track.** From round 67 every round also builds one AI-related app (`round.aiApps`, default 1): a skill or agent pack with its validator, a small agent harness, an MCP server, an eval or prompt tool, a context packer, a doc or diagram generator, picked from the archetype catalogue in `bench/loop/roles/ideator.md` and rotated so the last 4 AI apps never share an archetype. Its tests, CI and README examples run offline with no API key: the app either calls no model or calls one only through a provider interface whose default is a deterministic fake. It has its own level (from 4), its own cap `budgets.aiAppUsd` ($22 at level 4, $32 at level 5) on top of `roundRunUsd`, its own metrics group `ai`, and is published like the other new apps.
- **Model noise.** When no other experiment is planned, one new app per round runs its review stages on another vendor's model (`review.rotateReviewer`), so a single reviewer's habits do not pass for BAKED behavior. Cross-model re-runs are capped by `confirm.maxTokensPerRound` (3M) and count toward the round budget.
- **Cloud smoke runs.** A scheduled cloud session outside the loop runs short `quick` smoke rounds on `main` with a cheaper model after fixes merge and files only `invariant` and `recovery` findings, as issues labelled `bench-loop` and `smoke`; the backlog role ranks them with its own. Each smoke round also runs one [mini-suite](#nightly-mini-suite) task per language with k = 2 and posts the pass^k table to #861.

Control apps keep the same prompts, workflow and reference model every round and are never published, so their numbers show whether BAKED improved. The runner stays on one commit for the whole round; fixes merged during a round are measured in the next one.

## Hot modules

A few harness modules account for most chains of a fix followed by a new stop (#1637 → #1643, #1602 → #1627). They are listed once, in [`.github/hot-modules.json`](../.github/hot-modules.json): cost forecast and pricing, sizing and estimates, budgets and cap growth, auto-approval, provider timers and stall limits, and scheduler retry. Each module names its files; its tests are the test files that import one of them, so the list of tests never goes stale. The same list serves three things:

- **Error budget** (AGENTS.md). At most one behavior change per hot module per bench round: the runner stays on one commit for a round, so two changes to one module in a round cannot be told apart in the next. After a round with two or more stops caused by fresh fixes, the next round accepts only reverts and regression fixes in those modules. The backlog role applies both when it picks the fix set; the fix lines apply them to their own pull requests.
- **Pull request check.** The `Hot modules` workflow names the modules a pull request touches in its step summary, labels it `hot-module` and runs those modules' tests and the forecast replay (`tests/forecast-replay-corpus*.test.ts`, `tests/forecast-trace-replay.test.ts`) as a job of their own, so a red result names the module.
- **Weekly mutation run** (#1723). Every Monday the workflow runs BAKED's own built-in mutation engine (the one the mutation gate uses on apps) over each module's files, with the module's tests killing the mutants, and uploads the report. Survivors in a module that a bug fix touched in the last 14 days are filed as one open issue per module (`Surviving mutants in hot module ID`), or added to it as a comment. Each mutant's time limit comes from one green run of the module's tests before the first mutant, since a killed mutant stops early under `--bail`; a timed-out mutant counts as detected, so a limit taken from killed runs would score survivors as kills. One module by hand: `bun scripts/hot-modules.ts mutate --module cost-forecast`. A survivor is answered by a test that kills it, in a test file that imports the module's file (only those run against its mutants); an equivalent one, such as a parameter default no caller leaves out, is removed from the code rather than explained, so the next weekly run does not file it again.

**Escape rate.** `bun scripts/hot-modules.ts escape --issues ISSUES.json --rounds rounds.json [--from N] [--to N]` computes, per module, the share of bug-fix merges (`bugfix/` branches on `main`) followed within two rounds by a new bench-loop issue that names a file of the module in its `## Where` section (or its body, when it has none). A fix merged while round r ran is measured in round r+1, so its window ends with round r+2; a fix whose window has not ended counts as pending. Issues come from `gh api 'repos/Gulliby-development/baked/issues?labels=bench-loop&state=all&per_page=100&page=N'`, rounds from the bench stats `rounds.json`, whose report names give each round's end. `--by-file` treats every source file a fix touched as a module of its own, to find files for the list: two escapes in a month put a file on it. The rate is coarse: a large fix that touches a module in passing counts as a fix of it.

## Nightly mini-suite

A level-5 round builds one app in one language, so it catches a language-bound regression only in the round that happens to use that language. `bench/suite/` holds small tasks in every supported language: TypeScript on Bun, JavaScript on npm, Python with pytest, Go, Rust, Java with Maven, Kotlin with Gradle, C# on .NET, PHP, Lua and C with make. Some tasks rebuild past stops (`origin` in `task.json`). Each task has a brief (`prompt.md`), a seed repository, a hidden acceptance check (`check.sh` with its tests in `hidden/`) and a reference solution.

```sh
bun run bench:suite --per-language --k 2        # one task per language, rotating by day
bun run bench:suite --k 3                       # every task three times
bun run bench:suite --self-check                # no model: check fails on the seed, passes on the solution
```

The runner copies the seed into a fresh git repository and writes the task's checks and allowed paths into `.baked/config.json`. It runs `baked workflow quick --budget quick --model <model> --model-strict --worktree` and approves a plan that stays inside the allowed paths. After a completed run it runs the hidden check in the run's worktree. Any other stop counts as an intervention and ends the trial. The default model is `claude-code/haiku`, and a task whose toolchain is missing is reported as skipped. The table lists pass^k (the chance that k trials all pass), passes, interventions per run, tokens and cost per task. Results go to `bench-suite-results/<date>/`.

A capability task whose pass^k falls from 1 is filed as a bench-loop issue with its run ids. A task that keeps pass^k = 1 for five nights graduates to `bench/suite/regression.json`, and regression tasks must stay at 100%. The task format, the self-check and the graduation rules are in the [bench-suite skill](../.agents/skills/bench-suite/SKILL.md).

Start the loop session with the loop root as its working folder. On first start the loop copies the settings template to `<loop root>/.claude/settings.local.json` if missing (and re-checks each round, never overwriting an existing file); Claude Code reads that file from the session's project folder, so otherwise the allow rules do not apply and `gh repo create` / `gh repo edit --visibility public` may be blocked. The `.claude` folder is not part of the repository.

Round data (state, ledgers, round folders, app repositories) lives on the machine that runs the loop, never in this repository, except the anonymised usage traces in [`tests/fixtures/bench-traces/`](../tests/fixtures/bench-traces/accepted.json): token counts, prices, policy revisions, task and stage transitions and timestamps, without prompts, model output or file contents; prose is replaced by stand-ins. A trace keeps no file manifest either: a snapshot's `manifest_json` and a run state's `expectedFiles` and prior reviews' `files` are exported empty (the manifest hash stays), since no replay reads them and a committed dependency tree made them most of a trace (#2338). `export` refuses a trace above 10 MiB gzipped and names its largest tables; `--max-mib N` sets another bound.
