A resume after an `invalid_output` stop is refused as a repeat only when the diagnostic and every run input are unchanged (`invalidOutputRepeat` in `src/core/workflows/invalid-output-repeat.ts`, which `noteInvalidOutput` and the run views' `stopRecovery` both read, so a view never offers a retry the guard refuses, #2201). The prompt is one input; the others are the revisions `invalidOutputInputs` returns (today the `routing.json` revision a reroute writes, and the `host-release` links of the correction chain once there is one, #2540). A new way to change a run's input after an invalid output without touching the prompt (a policy revision, a profile edit) adds its revision there and its case to `tests/workflow-scenario-reroute-repeat-guard.test.ts`, which fails when `reroute --resume` is refused or a plain resume with nothing changed passes (#2191). A repeat key is built from host-observed facts, never from a model's wording: when the attempts carried writes the tool policy refused, the key is their sorted (refusal, path) pairs (`invalidOutputKey`, `WRITE_REFUSALS` in `src/core/workflows/write-refusals.ts`), and the diagnostic's hash only when there were none (#2520). A resume step that changes an input of the key after the key was computed records the key again with that input, and a note the host rewrites in the prompt (the row repair, `repairedRunText`) is matched in its rewritten form too (#2696). The running build (`buildId` in `src/core/build-info.ts`, version and commit) is an input of every repeat key that can refuse a resume, so a host check fixed between two resumes is tried once on the new build (#2587); a new resume guard, or a would-stop promoted to `enforce` that compares an attempt with one from before a resume, includes it, and reads the build only from `runningBuild`, never from `package.json` or `git` itself.
