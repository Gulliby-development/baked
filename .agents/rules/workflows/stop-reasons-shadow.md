Any new or changed logic that can stop a run, park it or decline an approval registers its reason in `src/core/workflows/stop-reasons.ts` and ships in `shadow` mode, recording `decision.would_stop` events instead of stopping. A stopping fault is made with `stopFault`; `tests/stop-reasons.test.ts` fails on one made another way. Promoting a reason to `enforce` is a pull request of its own that cites two bench rounds with no false would-stop. Hard limits the person set (money, tokens, time, storage) are registered as enforce-only. A reason that compares a measured quantity with the plan's estimate waits for the first measurement (as `initiative-dollar-share` waits for `measuredFeatures` above 0, #1714), and its replay case in `tests/forecast-replay-corpus.test.ts` shows the round whose false would-stops it removes. A rule that can decline a start keeps its shadow data in the corpus with the final spend of the run (`shareWouldStop` on each replayed start of `replayInitiativeStarts`, next to `finalUsd`; a would-stop for dollars the initiative never ran short of is false, and an accepted one is listed in `tests/fixtures/bench-traces/accepted.json` with that spend in its reason), and its promotion to `enforce` cites two rounds with none false; a dollar rule that prices with a measured rate waits, as the forecast's ratio does, for `MIN_CALIBRATION_FEATURES` measured features before the cap bounds it (`initiative-dollar-share` counts the remaining dollars to the tolerance ceiling until then, #2099). See [Stop reasons and shadow mode](../../../docs/workflows/runtime.md#stop-reasons-and-shadow-mode). A corrective chain's failing required checks are compared, not only counted: each failing corrective records `repeats/tasks/<task>.json` (kind `repeated-failure`, kept in traces, replayed by `replayRepeatedFailures` with the `newRepeatStops` counter) and the `repeated_failure` reason records a would-stop when its hash equals the previous corrective's (`src/core/workflows/repeated-failure.ts`, #1996). A new check runner whose failing output carries a value that changes between runs of the same failure (a timestamp, a duration, a temporary path, an address) adds its normalization to `normalizeVolatile` (`src/core/verification/volatile.ts`), the one table that `normalizeCheckOutput`, the check baseline's `shapedFailureSignature` (`output-counts.ts`) and the check finding's `failureSignature` (`convergence.ts`) all read, never to one of them (#2295), and its pair of outputs to `tests/repeated-failure.test.ts`, which fails when two runs of one toolchain's failing check hash, or get a baseline signature or finding text, differently and when a runner of `TEST_RUNNERS` (`src/core/verification/output-counts.ts`) has no pair (the pair's name starts with the runner); a value is normalized by its shape (a number with a unit word, a compound `1m 3s`, `mm:ss.fff`, a rate `N runs/s`, a seed, an address with or without `0x`), not by one runner's spelling, and a whole number with a unit only after a word that introduces a time (`in`, `after`, `Time:`, `Duration:`), so positions and asserted values still differ (#2281); a new path that opens a task-level correction for check failures goes through `repair(..., "task")` or calls `recordRepeatedFailures` itself, with a case in `tests/workflow-scenario-repeated-failure.test.ts`.
