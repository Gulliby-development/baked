A host tool that writes a file on an agent's behalf (`apply_fix`, `restore_file`, `place_rows`) writes it through the attempt's tool guard (`guard.execute("edit_file", { path }, ...)`; a session tool through the executor's `hostEdit`, which also marks the attempt as edited), so the edit is journaled with its pre-image, stays inside the task's write scope and counts as an edit for the progress watcher (`EDIT_TOOLS` in `src/core/workflows/progress-watch.ts`). Whether a task's session changed a file is decided only from the journal and `taskEditsInPlace` in `src/core/workflows/rollback.ts` (the task's uncommitted writes still in place, against the hash before its first edit), on every task path (single-writer, batch worker, lost worker), never from the root as the attempt found it and never per tool; a new write tool needs no entry there, and a new task path calls it. `tests/workflow-scenario-row-file-write.test.ts` (R84) fails when a batch retry's inherited `place_rows` write is refused as "changed none of its files" (#2585). A new watcher hint about the files themselves comes from state the executor keeps as it edits (the `broken` map of unparsable files) and is passed to `steeringNotice`, never re-read inside the synchronous step controller (#1835).
