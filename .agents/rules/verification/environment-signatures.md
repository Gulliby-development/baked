A check failure that comes from the machine, not the code (a JDK that cannot open its loopback pipe), is recognised only through `ENVIRONMENT_SIGNATURES` (`src/core/verification/environment-faults.ts`), which the check runner (`environment_broken`, inconclusive, no correction) and the doctor's probe both read: a new gate toolchain gets a row there (its signatures, or `none(reason)`; the record's type requires it) and a row in the "environment signature" cell of `tests/gate-matrix.test.ts` when it has one (#2273). A `none` row names the bench round and date through which nothing was observed (`NONE_OBSERVED`; the cell fails on one without), and a signature added from a bench round keeps that round's outputs as fixtures (`tests/fixtures/swiftpm-crash-outputs.ts`) with a failure of the code that must not match. A required check that fails on its exit code with no failure line of any toolchain (`silentFailure`) is re-run once before a correction opens only through `silentRerun` in `scheduler.ts` under the `silent_check_failure` stop reason (shadow, `decision.would_rerun`); a new place that opens a correction from a failed required check calls it, and a new failure line a toolchain prints belongs in `output-counts.ts` or `FAILURE_WORD`, not in a per-site exception (#2418). A check with a `fix` command or one `runsFormatter` reads as a formatter is never re-run that way: its diff or file list is a finding its fixer answers (#2829), so a new formatter gate needs no output shape there.
