A check timeout is never a dead end: a required check that timed out after passing earlier in the run, or whose formatter does not finish on one written file run alone (`fileScopedFormat` in `src/core/workflows/format-written.ts`, bisected by `hangingFile` in `src/core/verification/check-runner.ts`), is failed with the reason `timeout_slow` and a note naming the file; its fixer is not run (the same tool hangs again), and an inconclusive check that timed out twice on one snapshot blocks with that said and the `revise` remedy (`inconclusiveFault` in `scheduler.ts`), never an automatic skip. A new formatter gate gets a file-scoped form (a `FILE_FORMATTERS` row, or a case in `fileScopedFormat`) and its stack's row in `FORMAT_FILE` for the gate-matrix cell "formatter timeout is a finding"; a new place that runs a check's fixer skips `timeout_slow` results; a new check reason that blocks gets its case in `tests/workflow-scenario-formatter-timeout.test.ts` (#2240). A tool that runs a formatter tells a timeout apart from a failure: it says so in its result and records it (`recordFormatTimeout` in `src/core/tools/auto-format.ts`), which `hangingFile` reads before a bisect (#2242). A task-end formatter check outside `FILE_FORMATTERS` (`rustFormatWrittenChecks`, #2248) gets its own case in `fileScopedFormat`, so its timeout names the file too. Only a person skips a required check: the `accept-limitation` remedy of a check that timed out twice on one snapshot records it as a `check_not_run` limitation the report lists; a new place that gates on a required check honours `acceptedCheckTimeouts` (`acceptedTimeout` in `scheduler.ts`, `assertAcceptance` in `verification/acceptance.ts`) (#2358). A new host run of a project command that can time out without a check result names the command and file and records it through `recordCommandTimeout` (`src/core/verification/command-timeouts.ts`), never a bare "ran too long" (#2358).
