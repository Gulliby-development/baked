An id format a result schema checks with a pattern (requirement, criterion and task ids) comes only from `HOST_ID_FORMATS` in `src/core/workflows/host-ids.ts`: the schemas in `schemas.ts`, the instructions that state the formats (`SPEC_ID_RULE` and the planner's task-id sentence in `builtin.ts`) and the normaliser `fillHostConstants` runs before validation all read it. A new id kind gets its row there, its spelling, and a case in `tests/workflow-spec-ids.test.ts`; never write the pattern into a schema or an instruction by hand (#1871). A result field the host fills or rebinds after submission (a schema version, a plan hash, an analysis `inputHash`, an implementation result's `taskId`) is listed in `HOST_FIELDS` in `src/core/workflows/host-constants.ts`, which both fills it and makes it optional in the `submit_result` schema the model sees (`advertisedSchema`); it is never left required in what the model is shown, and `tests/workflow-host-constants.test.ts` fails when a filled field is missing from the list (#1929). A field the host knows is never an acceptance test: a task result is bound to the step's task once, by `taskImplementation` in `scheduler.ts` on every task path (planned, corrective, batch worker, best-of-N candidate, integrator), and no site compares the model's `taskId` with the task's to reject it (#2828). A result schema field that carries a literal value of a row, case or program output (a derivation's `recomputed`, a repro's `expected` and `actual`) allows the empty string with `Value`; `Text` is for prose (#1947).
