The number of runs a workspace executes at once comes from `parallelRunCap` (`src/core/workflows/schemas.ts`), and an initiative's slot count from `InitiativeService.parallelRuns`, which applies the plan's width (`planWidth` in `src/core/workflows/initiatives/critical-path.ts`) under `parallelRunsFromPlan`; never read `workflows.maxParallelRuns` or `DEFAULT_MAX_PARALLEL_RUNS` anywhere else (the scheduler's field is set from `parallelRunCap` before each drive), or the lease cap and the slot count disagree and a third feature is refused with `WORKSPACE_BUSY` (#1822). A command that applies a change and then drives the run (the headless CLI's `driveAfter` for `extend`, `revise`, `reroute`, the decision commands and a `resume` with a remedy or accepted workspace, the TUI worker's `action`) answers the cap's refusal (`WORKSPACE_BUSY` with `details.reason: "parallel_cap"`) through `queuedResume` (`src/core/workflows/queued-resume.ts`): the change took effect and the run waits for a slot, exit 0, never the bare refusal. A new command of that kind does the same and adds its case to `tests/workflow-recovery-ergonomics.test.ts` (#2415). The local API's `launch` (`src/core/api/server.ts`) answers the same refusal through `queuedResume` too, and keeps the answer on `GET /v1/workflow/runs/RUN_ID` as `queued` while the run waits; never log it as a `drive-error` the client cannot see (#2421).
