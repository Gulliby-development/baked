Which features a prescribed row needs through the command it runs is decided only by `rowNeedsFeatures` in `src/core/workflows/initiatives/plan.ts`: the row's first quoted word (`rowTokens`, the program's own name skipped) joined with the features whose boundary holds that command's source (a code path whose stem, with case and separators removed, is the command, `<command>command` or `<command>cmd`, or a `main` file in a directory of that name) or whose scope names "the <command> command" (#3010). `rowOwnerProblems` reports such a row as `later-command` when only features after the row file's owner write the command, and `sequenceSharedPaths` (given the request) makes a sharer whose rows run a later sharer's command wait for it unless that sharer's rows need the first one too. `rowOwnerProblems` reads the plan after `hostSequenced` (documentation and shared-path order), so a dependency the host adds counts as one the decomposer wrote. A new source of evidence that a row needs a feature (a flag's handler, a module a row imports) joins `rowNeedsFeatures`, never a second matcher in a caller, with a case per row notation in `tests/workflow-scenario-row-command-owner.test.ts`.
