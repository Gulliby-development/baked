A layout a host tool gives the lines it writes into a project file (`place_rows`' indentation, #2618) comes first from the request's own text where it shows one (`SuppliedRows.indent`), then the file, then a per-language record (`ROW_INDENT` in `src/core/tools/place-rows.ts`, registered in `tests/language-parity.test.ts` with a golden per fixture), never from a fixed constant alone; a constant is the fallback only for a language whose row is `none(reason)`. Such a tool states its default in its description and the brief's note, shows the written line in its result, and accepts a correction of that layout in one call (`reindent`), so a wrong guess never costs a session. Which file line holds a prescribed row is decided only by `heldLines` in the same file, which gives a row the request prescribes more than once the next equal line after its earlier copies, never the first equal line, so a duplicate row is held only as often as the file holds it. The same holds for what ends a written line: a separator the request's own row already ends with (`,` or `;`) is layout, kept by default and replaced by the caller's `separator` or `lastSeparator`, never doubled (`SEPARATOR_DEFAULT`; a C statement row once came out as `...;,`). A host tool that takes or names a prescribed row by number uses the request block's numbers, the ones the feature prompt states under `FEATURE_ROWS_HEADING`, never a row's place in the run's own rows: `placeRowNumbers` in `src/core/tools/place-rows.ts` maps a feature run's rows back, and the input, description, brief note, result and refusals all go through it. A new message or input that names a row number does too, and `tests/workflow-scenario-place-rows-numbers.test.ts` fails when a feature run's tool numbers its rows 1 to n.

A session tool that changes a prescribed-row file writes through `WorkflowToolPolicy.guarded` (`place_rows` does, as an `edit_file` of the path through `hostEdit`), and the guard (`rowEditBreaks`, #2558) judges each call alone, so a row changes place only in one call that leaves every prescribed row in the file (#2955): `place_rows` with `move: true` (`moved` in `src/core/tools/place-rows.ts`, which takes the held lines out and places the rows again through the same insertion, never a second row reader) or a single `multi_edit`. A new move or reorder route, or a new rule about where a row may stand, states how the guard sees it in `MOVE_NOTE` (the tool's description and the brief's note) and in `rowEditBreakText`'s move advice (given when the task asks for a move, `asksForMove`), and adds its case to `tests/workflow-scenario-place-rows-move.test.ts`, whose R102 tailcut scenario fails when a held row in the wrong order or list cannot be moved.
