# Developing BAKED

BAKED runs on Bun. Install dependencies with `bun install`, then start the terminal UI with `bun run dev`.

## Architecture

- `src/boot.tsx` routes startup to the terminal UI or headless CLI.
- `src/components/`, `src/hooks/`, and `src/stores/` implement the OpenTUI/React interface.
- `src/core/agents/bake.ts` assembles the agent, prompts, tools, approvals, and execution modes.
- `src/core/tools/` provides file operations, shell execution, Git, and code analysis.
- `src/core/context/` and `src/core/intelligence/` maintain context, repository graphs, and standalone language servers.
- `src/core/llm/providers/` contains Claude, OpenAI API, Codex, GitHub Copilot, and GitHub Models connections. `tests/provider-fault-matrix.test.ts` runs each adapter against a misbehaving transport (`tests/helpers/faulty-provider.ts`: a fake `fetch` speaking the provider's wire protocol, or a fake CLI runner) for every fault profile: a first byte as slow as the slowest healthy one in the replay corpus (at least the 502 s of bench round 50), every recorded call shape (provider, stage, effort) at its p99 first byte, a hang, a 429 with the longest recorded rate-limit `retry-after` (and every recorded wait over an hour, as a usage limit), a 5xx overload, a stream cut mid-answer, a malformed tool call and an empty answer, plus `SQLITE_BUSY` on store reads. Each row asserts the class the runtime gives the failure. The profile's numbers come from `corpusCallProfile` over `tests/fixtures/bench-traces/` (#1729); `bun scripts/bench-trace.ts latencies <trace>...` prints them. A new adapter is added to `FAULT_PROVIDERS` in the same pull request.
- `src/headless/` provides command-line automation and interactive console chat.
- `src/core/api/` serves the workflow commands as a local HTTP API with an event stream (`baked serve`); it reuses the `baked workflow` command path. See the [runtime guide](docs/workflows/runtime.md#local-api-baked-serve); the desktop contract is [docs/desktop/api.md](docs/desktop/api.md).
- `src/core/sessions/` and `src/core/memory/` manage persisted sessions and memory.
- `src/core/projects/` resolves the project manifest (`baked/project.json`), its trusted roots and working set; `ProjectService` is the contract for the CLI and the local API ([projects](docs/projects.md)).
- `src/core/workflows/` owns durable workflow commands, scheduling, approvals, budgets, leases and recovery. `src/core/specs/`, `src/core/agents/profiles/` and `src/core/verification/` implement artifact validation, agent capabilities and acceptance.

Keep agent logic independent of the UI. Preserve approval callbacks, secret handling, file access checks, and coordination between tabs when changing tools. Use strict TypeScript and the existing Biome configuration.

## Workflow development

- [SDD workflows](docs/workflows/README.md): architecture, the v2 definition format and the runtime guide. Workflows are on by default; `workflows.enabled: false` turns them off.
- Run `bun test tests/workflow-runtime.test.ts tests/workflow-adapters.test.ts` for deterministic workflow integration, native SDK tool execution and terminal UI coverage. Fixtures do not require provider credentials.
- Quality gates have a matrix in `tests/gate-matrix.test.ts`: one fixture per stack (Bun, npm, Python, Go, Rust, Maven, .NET) against each gate decision (gate detection, the test check the mutation gate needs, per-task or integration checks, dependency detection, property tests, mutation tool detection), once in a plain checkout and once in the run and task worktrees the scheduler creates, with the working copy's `node_modules` linked and read through the scheduler's tool shell and property-library probe. A new gate, or a change to how a gate reads a toolchain or a project layout, adds its cells; a fix for a gate bug adds the failing cell first, and an open bug stays listed in `KNOWN` with its issue until the fix removes it. `BAKED_GATE_MATRIX_TOOLCHAINS=1` also runs every stack's detected gates on a minimal project with the real tools (CI job `gate-matrix`); locally a missing toolchain skips its row.
- Host decisions are replayed on recorded bench rounds (#1649, #1715). `tests/fixtures/bench-traces/RNN/<app>.sqlite.gz` holds the anonymised usage trace of each bench-round app: its workflow database with token counts, prices, policy revisions, task and stage transitions and timestamps, and without prompts, model output or file contents. Prose (specs, plans, reports, titles) is replaced by stand-ins such as `problem-3`, one per distinct text, so the run state in the kept `state` artifact still reopens with the same features and shares. `tests/forecast-replay-corpus.test.ts`, part of `bun run test` and so of the required `check` job, rewinds each run to every attempt it started and runs the current `assertForecastFits` there. It also checks each recorded attempt's reservation against the current per-call cost cap (`costCapDecision`, #1740), and each recorded model call against the current first-response deadline (`providerFirstByteMs`), from the timing every call now keeps in `attempts/*/usage.json` (`calls`; older traces fall back to the length of a one-step buffered CLI attempt). It also replays every initiative share-gate decision (`shareShortfall`) from the inputs the `feature.share_gate` event records at each feature start and park. It also rewinds each initiative to every feature start it made and asks the same gate again with the view the current code computes there (its estimate, prices and dollar forecast), with the initiative's history stores replaced by their corpus traces as they were at that moment and its planned features routed as the runner routed them (`replayInitiativeStarts`); at the first start it also compares each feature's estimated range with what the feature used (#1806). It also prices each recorded plan approval again at the moment it was asked, with an earlier round's traces as its history, and compares the price with what the tasks then cost (`replayPlanPrices`). It also decides every plan auto-approval of R52 and later again on the run state the scheduler held when it asked (`replayPlanApprovals`). It also decides again, from each recorded `sizing/plan-N.json`, whether each planned test task splits (`exceedsTestCapacity`, #1789), from the task's recorded cases and price, the observed case capacity and the attempt cap. It also decides again what the run did with each attempt a provider refused under its usage policy (`policyRefusalDecision`, #1895), from the refusals recorded before it for the same task or stage on the same model. It also decides every finding-chain decision again from its recorded inputs (`replayFindingChains`, #1959): whether a corrective rewrote the symbol of a `repeatOf` chain (`chains/tasks/`), and whether a battery run before a review reopened the correction (`chains/battery/`). A trace keeps each finding's body without its prose (#1981: `repeatOf`, file, symbol and repro, with stand-ins for text), so `replayChainEscalation` decides from the findings themselves where a chain-rewrite policy would have rewritten and what its battery would hold, for runs recorded with the policy off; `chainCosts` reads each recorded chain's length, battery results and corrective cost, and `bun scripts/bench-trace.ts chains <trace> ...` prints both for the round report. It also compares each failing corrective's required checks with the corrective's before it again (`replayRepeatedFailures`, #1996), from the `repeats/tasks/` records, whose normalized outputs a trace keeps as stand-ins, or for a run recorded before them from its stood-in check findings (R64 cfgquill lint repeats at T006). It also decides each spec conflict's decision for the request again (`replayRequestConflicts`, #2016) from the `conflicts/request/` records: the checked sides (kinds, refs and whether each quote was found, never the quotes), the tests the run did not write, the cited criteria and the re-audit's verdicts. It also walks the recovery ladder again over every recorded stalled attempt (`replayStallLadder`, #1877): the rung the current `nextRung` takes after a call that got no first response, against the rung the run's `attempt.recovery` events recorded. A forecast stop, cap growth, cost-cap refusal, first-response stop, test split, recovery rung, policy stop, chain decision, repeated-failure would-stop, conflict decision, share-gate park or approval decision the recorded run did not make fails the suite. A change that means to decide differently there lists the run in `tests/fixtures/bench-traces/accepted.json` (`"RNN/app.sqlite.gz#RUN_ID": {"newStops": n, "newGrowth": n, "newFirstByteStops": n, "newCostStops": n, "newTestSplits": n, "newRecoveries": n, "newPolicyStops": n, "newChainDecisions": n, "newRepeatStops": n, "newConflictDecisions": n, "reason": "..."}`, or `#INITIATIVE_ID` with `"newShareStops": n` or `"newStartStops": n`, and `"newApprovalDeclines": n` or `"newAutoApprovals": n` for a plan approval), so the decision shows in the diff. Every new host decision adds its replay hook in the same pull request; the [replay-corpus skill](.agents/skills/replay-corpus/SKILL.md) says how. `bun scripts/bench-trace.ts export <workspace> <out>` writes a trace; `bun scripts/bench-trace.ts replay <trace> ...` prints each run's differing decisions and how far its forecast was off at 25%, 50% and 75% of its final cost.
- Change run state through `NativeWorkflowService`; keep React and UI stores out of the runtime. Durable events and SQLite are authoritative. Never use a model's claim as command evidence or bypass a stale approval.
- A `baked workflow` option is added once, to its command's list in `commandFlags` (and to `booleanFlags` when it takes no value) in `src/headless/workflow-parse.ts`; the parser's set of known options is derived from those lists. `tests/workflow-argv-spawn.test.ts` starts the real CLI with every option of the commands that start or change runs, so add a command there when it gains options.

## Verification

```sh
bun run typecheck
bun run lint
bun test tests/<feature>.test.ts
bun run test
bun run build
```

`bun run typecheck` runs `bun check` (Bun 1.4.3 or newer, the version CI uses). On an older Bun, `bun run typecheck:tsc` runs the same check with `tsc` from `package.json`.

Run the full test suite for shared behavior changes. Use `bun run test` rather than a bare `bun test` for the whole suite: the script passes `--timeout 30000`, which workflow tests need on slower machines, and Bun applies a timeout set in a preload only to the first test file.

CI runs `bun run test` on Linux for every pull request (`CI / check`). The `OS tests` workflow runs it on Windows and macOS (runners there cost 2x and 10x Linux minutes) in the merge queue for changes to platform-sensitive code, nightly against `main`, and on manual dispatch. On a pull request its `test (windows-latest)` and `test (macos-latest)` checks pass at once, unless the pull request changes the workflow, `scripts/test-shard.ts` or `scripts/flaky-ledger.ts`; the queue runs them on the change merged with the current `main`. Windows runs in three shards side by side (`bun scripts/test-shard.ts <index> <count>` runs one shard locally), and each `test (...)` check reports whether all shards of its platform passed. Windows shards allow 90 s per test instead of 30 s (a test that passes its own limit keeps it, so a test passes one only above 30 s; `tests/os-tests-workflow.test.ts` refuses an explicit 30 s, #1910): Windows runners start processes and write files several times slower, and slow down further for a minute at a time (#1177). Windows shards put the system temp directory, where every test keeps its scratch repositories and databases, in `RUNNER_TEMP` on the work disk D: instead of C: (#1910). That directory grants the runner user its own ACE, as its profile's temp directory does: the user is an administrator whose files there are owned by the Administrators group, which the OS sandbox makes deny-only. Every test run in CI ends with a slow-test report (`bun scripts/slow-tests.ts <junit.xml> <limit ms> [--fail]`): each test above half of its limit (the run's `--timeout`, or the number its `test(name, fn, ms)` call passes) is a warning annotation on its line, and above 80 percent an error. The nightly `OS tests` run against `main` fails on such an error; in the merge queue and on pull requests it is only an annotation, so a test that grows into its limit shows up before it times out on a busy runner and ejects a pull request (#1589, #1656). A failed `OS tests` shard reruns each failed test alone three times on the same commit and OS (`bun scripts/flaky-ledger.ts <junit.xml> <timeout ms> <ledger.json>`, up to five tests). Each failure gets an annotation on its line: `likely flaky (n/3 isolated reruns passed)` when any rerun passes, `real` when none does. The shard writes the results as the `flaky-ledger-<os>-<shard>` job artifact. The shard still fails: a likely flaky test is fixed, never skipped, and its cause is recorded on the Bug issue for it (#1724). Every day the `Flaky test ledger` workflow (`bun scripts/flaky-issues.ts [--days 14] [--threshold 2] [--dry-run]`) downloads the ledgers of the last 14 days of `OS tests` runs and counts each test's likely flaky failures, keyed by its file and describe path. A test with two or more gets a Bug issue labelled `flaky-test` with `Priority: P1`, its runs, operating systems and rerun results, and a `<!-- flaky-ledger: KEY -->` marker. Later failures are added to that issue as comments, and a closed issue is reopened when the test flakes in a run that started after it was closed. Run it with `--dry-run` from the Actions tab to see what it would file. A test cleanup that removes a directory after stopping a service or process uses `removeTempDir` from `tests/helpers/temp-dir.ts`, which retries while Windows still holds a handle inside it (`EBUSY`). The test setup opens workflow databases without a disk flush per commit (`BAKED_WORKFLOW_DB_SYNC=normal`); with it, a throttled runner disk made every workflow event take seconds. In CI the test setup sets `BAKED_TRACE_RUN_BLOCKS=1`, which prints why a workflow run blocked, a check slower than 3 s, an agent-call error, and the latest events of a run still active when its service closes. Its `scope` job holds the path list: process, shell, path, file system and key store code (`src/core/platform`, `workflows`, `verification`, `tools`, `sessions`, `git` and similar), `src/headless`, the test setup, dependencies and the workflow file. Add a directory there when it gains platform-specific behavior. A test of a feature one platform lacks uses `test.skipIf` with a comment naming the platform; a test that fails on one platform is fixed, not skipped. `tests/sandbox-integration.test.ts` runs real commands in the [OS sandbox](docs/sandbox.md) and skips where no backend works; CI installs bubblewrap and sets `BAKED_REQUIRE_SANDBOX` (`bwrap` on Linux, `seatbelt` on macOS) so a missing backend fails there instead of skipping. Build after changes to startup, dependencies, or bundling. The generated application starts with `bun run dist/index.js`.

Checkouts use LF line endings on every platform (`.gitattributes`). A Windows checkout made before that file existed still has CRLF files, which `bun run lint` reports as format errors. Convert it once with `git rm --cached -r -q . && git reset --hard` after committing or stashing your work.

The `Security` workflow (`.github/workflows/security.yml`, #1844) runs three keyless scanners on every pull request and in the merge queue. Its checks report only, so a finding does not block the merge yet. After two weeks without false positives they become required checks of the merge-queue ruleset.
- `zizmor` audits the workflows, `dependabot.yml` and any `action.yml` for template injection, unpinned actions, broad permissions, persisted credentials and cache poisoning. It runs offline, with accepted findings in `.github/zizmor.yml`.
- `gitleaks` scans the commits the pull request adds (`base..head`) for secrets, with test-fixture allowlists in `.gitleaks.toml`.
- `osv-scanner` checks `bun.lock` and `apps/desktop/bun.lock` against the OSV database, with accepted advisories (each with a reason and a review date) in `.github/security/osv-scanner.toml`. It reads Bun's text lockfile (329 packages in the root one), and an OSV API error fails the job (exit 127) instead of passing it.

The tools are pinned: zizmor by version and wheel hash in `.github/security/zizmor-requirements.txt`, and gitleaks and osv-scanner by module version, which `go install` checks against the Go checksum database. To run them locally:
- `pip install zizmor==1.30.1`, then `zizmor --offline --config .github/zizmor.yml .`
- `gitleaks git --config .gitleaks.toml --log-opts=origin/main..HEAD .`
- `osv-scanner scan source --config .github/security/osv-scanner.toml --lockfile bun.lock`

Every suppression carries its reason and the issue or pull request that accepted it.

## Distributables

| Script | Output | Builds on |
| --- | --- | --- |
| `bun run build` | npm package (`dist/`, needs Bun at runtime) | any OS |
| `bun run bundle`, `bundle:x64` | macOS arm64 / x64 `.tar.gz` with `install.sh` | any OS |
| `bun run bundle:linux`, `bundle:linux-arm64` | Linux x64 / arm64 `.tar.gz`; `bash scripts/bundle.sh x64-baseline linux` for CPUs without AVX | any OS |
| `bun run bundle:windows`, `bundle:windows-arm64` | Windows `.zip` with `baked.exe` and `deps/` (needs `pwsh`) | any OS |
| `bun run installer:windows` | NSIS installer, x64 only (needs `makensis`) | any OS |
| `bun run selfextract:windows`, `selfextract:windows-arm64` | Installer that downloads the zip from GitHub Releases | any OS |

Every package must keep its `deps/` tree (OpenTUI native library, worker bundles, tree-sitter WASM) next to the binary or in the per-user data directory. `baked self-check` loads each of them plus SQLite without a terminal or provider key and exits non-zero on a failure. The `Builds` workflow runs it on every package that can execute on its runner: Linux on every pull request; Windows and macOS when a pull request changes packaging files, nightly, and on manual dispatch. Linux arm64 and Windows arm64 are cross-built and checked for contents only. Binaries are not code-signed or notarized.

## Merging

A pull request that closes a Bug issue also gets an advisory adversarial sweep review (#1722). `bun run review:adversarial --pr N --post` (`scripts/adversarial-review.ts`) gives a model of the other family than the fixer's (read from the commits' co-author trailers) the diff, the issue and the `## Sweep` section, with the instructions in [`.agents/skills/file-issue/adversarial-review.md`](.agents/skills/file-issue/adversarial-review.md) and the Sweep sections of the [file-issue skill](.agents/skills/file-issue/SKILL.md) as its checklist, and posts one comment, updated on each run, naming missed sibling places, languages and a scenario that should fail. Each missed place is a finding with a severity (P0 breaks a common run, P1 a real path the defect reaches, P2 an edge path or an incomplete `Languages:` line), its file and lines, the checklist item or AGENTS.md rule it falls under, and a collapsed "Prompt for AI agents" with the fix in one paragraph, so a fix line can take it as is (#1845). Each finding then goes to a fresh run of the same CLI with [instructions to disprove it](.agents/skills/file-issue/adversarial-verify.md), only that finding, its rule and the diff of its file; the verifier keeps it, downgrades it one severity or drops it, with a 1-5 confidence and a reason. Dropped findings stay in the comment in a collapsed section with that reason, and a finding whose verifier run failed is kept and marked unverified. The review's inputs (`REVIEW_INPUTS` in the script: both prompts, the file-issue skill and AGENTS.md, which the reviewer also gets) are read from the pull request's base commit, not its head, so a pull request cannot weaken its own review; one that edits them is still reviewed by the base version, and the comment lists the edited files under "Configuration changes in this PR". A re-review remembers the previous one: every finding has an ID (`A1`, `A2`, kept for the same file and claim), the comment stores its findings in a hidden block, and people answer a finding in any comment on the pull request by a line that names its ID, with 👍 or 👎 (or `+1`, `-1`) and an optional reason (`👎 A2 the Maven path already does this`). The next run gives the reviewer the earlier findings with those answers, asks it whether each is fixed, still present or dismissed, never raises a turned-down or answered finding again, and opens the comment with a "Since last review" section. The reviewer also gets the call-graph context of the changed functions, read with tree-sitter from the pull request's head (fetched into this checkout as `pull/N/head`): for each function the diff touches, its callers, the repository functions it calls, the files that import its file, and the functions most like it by name or body (MinHash similarity of at least 0.5), so the sibling sweep starts from the code that reaches the change. The call and import spellings of each language are the `CALL_SYNTAX` record in `src/core/intelligence/call-context.ts`; a checkout that cannot fetch the head reviews without the context. It runs locally through the Claude Code CLI (`claude -p` with no tools) or the Codex CLI (`codex exec` in a read-only sandbox), whichever is installed and of the other family, on the subscription that CLI is logged in with; it needs no API key and has no CI job, and `--reviewer claude|codex` picks the CLI by hand. A fixer runs it before merging when the other family's CLI is on its machine; the bench loop's backlog role runs `--since <date> --post` each round on the machine that has both CLIs, which reviews every open or merged fix pull request once per head commit, including those merged from machines without the other CLI. A failed or missing review only prints a warning. `--out DIR` also writes the prompt and the review; `--last N --out DIR` does it for the last N merged pull requests that closed a Bug issue, for comparing the findings with the bench loop's retro sibling audits.

`main` is protected by a merge queue. Add a pull request to it with `gh pr merge <number> --merge --auto` (or "Merge when ready" on GitHub); it joins the queue once its own checks pass. The queue tests each pull request merged with the current `main` and the pull requests ahead of it, runs the same `CI`, `Builds` and `OS tests` workflows on that `merge_group` event, and merges it with a merge commit when they pass, so pull requests no longer need to be brought up to date with `main` by hand. A pull request that fails in the queue is removed from it. Direct pushes to `main` are rejected.

## Releases

Versions follow semantic versioning and are tagged `vX.Y.Z`. `main` takes changes only through the merge queue, so a release is a pull request followed by a tag. From an up-to-date `main` with every change merged:

```sh
bun run release:dry     # next version and the commits since the last tag
bun run release:minor   # or release:patch / release:major
```

`scripts/release.sh` runs the checks (`bun run lint`, `bun run typecheck` and `bun run test`, the suite with its 30 s timeout), commits the version bump of `package.json` and `apps/desktop/package.json` as "Release X.Y.Z" on a `feature/release-x-y-z` branch and pushes it; with the GitHub CLI installed it also opens the pull request and adds it to the merge queue. Once that pull request is merged, pull `main` and tag the merged commit:

```sh
git switch main && git pull
bun run release:tag     # tags vX.Y.Z from package.json and pushes the tag
```

The tag starts `.github/workflows/release.yml`, which checks that the tag matches `package.json`, runs the full check suite, builds every archive through the Builds workflow and publishes a GitHub release with `SHA256SUMS.txt` and notes generated from the merged pull requests. Label a pull request `skip-changelog` to leave it out of the notes; Dependabot pull requests are grouped under "Dependencies".
